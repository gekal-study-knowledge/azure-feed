<h1>Why hybrid networks need native routing policy</h1>
<p>Hybrid networks connect remote sites across multiple routing domains to an Azure Virtual Network (VNet). As these environments grow, you need a consistent way to control which routes Azure Route Server learns and advertises at the VNet boundary. That control matters wherever Azure Route Server exchanges routes with hybrid connections:</p>
<ul>
<li><strong>ExpressRoute and Azure VPN gateways:</strong> exchanged routes between Azure VNets and your on-premises networks.</li>
<li><strong>Software-defined WAN (SD-WAN):</strong> manage routing across distributed branches and appliances.</li>
<li><strong>Network virtual appliances (NVAs):</strong> control learned and advertised routes from remote sites or other clouds.</li>
</ul>
<p>Without a native policy layer, your options for route control are limited, and they get harder to manage as the network grows.</p>
<p>This need becomes more urgent when branch-to-branch connectivity is enabled in Azure Route Server because routes can propagate across all connected networks. Production architectures, however, often require selective filtering, route summarization, segmentation, and predictable primary and backup paths.&nbsp;</p>
<h2>Operational challenges without route maps</h2>
<p>Without route maps, growing hybrid networks can become difficult to scale, secure, and operate. The main challenges include:</p>
<ul>
<li><strong>Route scale:</strong> Without inbound or outbound summarization, every specific prefix must be carried across the hybrid environment. Large deployments can approach or exceed Azure platform route limits, making routing tables harder to manage and troubleshoot. For example, if a VNet advertises more than 1,000 prefixes to an ExpressRoute circuit, the route limit is exceeded and the BGP session between the ExpressRoute gateway and the circuit is disconnected.</li>
<li><strong>Path selection:</strong> When multiple connections reach the same remote site, customers need a straightforward way to define a preferred path and a backup path.</li>
<li><strong>Network isolation:</strong> Unrestricted route propagation among SD-WAN, VPN, ExpressRoute, and NVA connections can expose segments to networks that should remain isolated.</li>
<li><strong>Operational complexity in SD-WAN:</strong> Large SD-WAN deployments may require multiple NVAs for capacity and resiliency. Each appliance exchanges routes with the VNet, increasing the number of IP routes that operators must configure, monitor, and troubleshoot.</li>
</ul>
<h2>How route maps addresses these challenges</h2>
<p>Route maps in Azure Route Server provide a native Azure policy layer for controlling the routes that enter and leave the VNet. They address the main operational challenges in the following ways:</p>
<ul>
<li><strong>Reduce route count:</strong> Summarize prefixes before they cross connection boundaries, reducing the number of propagated routes and helping limit routing-table growth.</li>
<li><strong>Control path selection:</strong> Modify AS-PATH attributes to influence primary and backup path selection across hybrid connections.</li>
<li><strong>Strengthen network isolation:</strong> Apply independent inbound and outbound policies to limit route exchange among SD-WAN, VPN, ExpressRoute, and NVA domains.</li>
<li><strong>Simplify SD-WAN interoperability:</strong> Use BGP attribute manipulation to streamline route exchange with existing SD-WAN environments.</li>
<li><strong>Enable downstream policy enforcement:</strong> Attach BGP communities that downstream devices can use to apply additional routing policies.</li>
</ul>
<h2>How route maps work</h2>
<p>Route maps in Azure Route Server provide granular control over routes received from and advertised to hybrid networks.</p>
<p>You can apply route maps to the following connection types:</p>
<ul>
<li>BGP peerings with a network virtual appliance (NVA) deployed in the virtual hub</li>
<li>ExpressRoute gateway connections</li>
<li>VPN gateway connections</li>
</ul>
<p>If the NVA is deployed in a spoke virtual network, apply the route map to the hub's virtual network connection to that spoke.</p>
<p>An inbound route map processes routes as Azure Route Server learns them, whereas an outbound route map processes routes before Azure Route Server advertises them. Each route-map rule evaluates its configured match conditions and can modify route attributes, permit the route, or deny it. The following diagram illustrates this policy flow.</p>

<h2>Core capabilities and supported connections</h2>
<p>Route maps support route summarization, route filtering, path selection, and route tagging with BGP communities. They can advertise aggregate prefixes, control which routes enter or leave an Azure Route Server deployment, modify AS-PATH to influence preference, and attach BGP communities that downstream devices can use when applying routing policy.</p>
<p>You can apply route maps to BGP peerings with NVAs, ExpressRoute gateway connections, and Azure VPN gateway connections. Policies can be associated independently in the inbound and outbound directions, allowing the same connection to use different controls for received and advertised routes.</p>

<h1>Conclusion</h1>
<p>Route maps are a significant step forward for Azure Route Server, adding a native routing policy layer that strengthens governance and control over route exchange across hybrid connectivity and Azure VNets. In this scenario, an outbound route map summarizes 100 spoke prefixes into three aggregate routes, reducing routing-table growth while preserving reachability across the complete spoke address range. The same policy model supports filtering, path selection, and BGP community tagging, helping customers control route propagation and operate growing hub-and-spoke environments more predictably.</p>
