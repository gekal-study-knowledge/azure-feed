The design has not been built, and the test in section 9 is a simulation. The value figures come from the case and from that simulation, and the cost figures are my estimates at Azure list prices. <h5><strong><span class="lia-text-color-11"> Summary</span></strong></h5>
<p><span>Most green hydrogen export plants will start life on fixed dispatch rules and spreadsheets. In the case study behind this paper, that costs a 500 MW solar, wind and electrolysis complex 8 to 10% of its ammonia output. The plant also earns a premium of EUR 200 a tonne under EU rules, but only on tonnes it can prove, and under the rules in force the proof must hold hour by hour from 2030.</span><span>&nbsp;</span></p>
<p><span>This paper describes a way to run such a plant with AI agents on Microsoft Azure. An optimiser makes the plan, and five agents do the work around it. A policy layer checks every agent action, one gateway is the only write path to the plant, and the safety system stays hardwired. Every hour of production is sealed as certification evidence as it happens.</span><span>&nbsp;</span></p>
<p><span>I have not built it. I tested the logic on a simulated plant over a year of real weather and priced it on Azure at about EUR 0.59 a tonne. The paper gives the pattern, the Azure architecture with the reason for each service, the test and the cost.</span><span>&nbsp;</span></p>

<p><span><br />Fixed rules are safe, but they cannot look ahead. They find out about a dust front when it arrives. The case puts the cost at 8 to 10% of output, and since those tonnes would come from assets that are already paid for, most of their value is margin.</span><span>&nbsp;</span></p>
<p><span>The case plant is on Morocco’s Atlantic coast. The four clocks are the same for any plant that runs electrolysers on variable renewables and sells into the EU.</span><span>&nbsp;</span></p>
<h5><strong><span class="lia-text-color-11"> Why the proof matters now</span></strong></h5>
<p><span>The premium in the case is EUR 200 a tonne, or EUR 80M a year at 400,000 tonnes. The same hourly data also feeds the Carbon Border Adjustment Mechanism, which has applied to hydrogen and ammonia imports since January 2026.</span><span>&nbsp;</span></p>
<p><span>Power is matched to production by calendar month until the end of 2029 and by the hour from 2030. The Commission also plans to postpone some of these requirements and has not said which dates will move. So, the evidence must be automatic from the first day, and the rule version has to change without a rebuild.</span><span>&nbsp;</span></p>

<li><span><span>A setpoint gateway on site is the only write path to the control system, and it checks the limits and interlocks again.</span></span><span>&nbsp;</span></li>

<p><span>The orchestrator is a fixed workflow on Microsoft Agent Framework, with a checkpoint at every step and a pause wherever a person decides. I rejected a group chat between agents, because after a fault nobody could replay it for a lender. An approval describes the plant as it was when the card was sent, and a dust front can arrive in ten minutes, so the policy check runs again after the operator approves.</span><span>&nbsp;</span></p>
<h5><span class="lia-text-color-11"><strong> The architecture on Azure</strong></span></h5>
<p><span>Figure 2 shows the full design. It reads from the bottom up.</span><span>&nbsp;</span></p>
<p><span>The control system and the safety system run the plant as they do today. Next to them, a three-node Azure Local cluster runs two things: Azure IoT Operations, which reads every tag over OPC UA and keeps working when the link drops, and the setpoint gateway, the only component allowed to write back. This layer stays on site because there is no Azure region in Morocco, and because no plant should depend on a cloud link to stay safe.</span><span>&nbsp;</span></p>
<p><span>A private ExpressRoute circuit links the site to one EU region. In the reference design that is Sweden Central, for its three availability zones and its Foundry services, with North Europe for any service it does not offer. Microsoft Fabric holds the live twin and the full history. I preferred it to assembling separate ingestion, time-series and reporting services, because one capacity with one security model is simpler to run, and OneLake keeps the history in open Delta tables that a lender can read without the platform. The optimiser is a Container Apps job, since it is a deterministic solver that starts every 15 minutes and should cost nothing in between.</span><span>&nbsp;</span></p>
<p><span>The agents run in Foundry Agent Service. They call models in the EU Data Zone through Azure API Management, which routes between a small and a reasoning model, caps the tokens of each agent and logs its cost. No language model computes a setpoint, so the small model can take about three calls in four. Each agent reaches the plant only through allow-listed MCP tools, under its own Entra Agent ID, so it can be audited and revoked alone. Table 4 gives the reason for each service.</span><span>&nbsp;</span></p>

</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>&nbsp;</p>
<p><span>Two services are in preview, Aurora in Foundry and the digital twin builder in Fabric, and each has a fallback that changes nothing else.</span><span>&nbsp;</span></p>
<h5><strong><span class="lia-text-color-11"> Proving every hour</span></strong></h5>
<p><span>The certification agent produces what the premium is paid for. Every hour it measures, calculates, records, signs and seals (Figure 3).</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<img />
<p class="lia-align-center"><strong><span class="lia-text-color-15">Figure 3. The evidence chain. It runs every hour, which gives 8,760 sealed records a year.&nbsp;</span></strong></p>
<p>&nbsp;</p>
<p><span>Four choices make the proof hold up.</span><span>&nbsp;</span></p>
<ol>
<li><span><span>Rules as code, with the version in the record. When the rules change, both versions run side by side and sealed hours stay sealed.</span></span><span>&nbsp;</span></li>
</ol>
<ol>
<li><span><span>One record per hour: the power by source, the matching in time and place, additionality, and the mass balance from hydrogen to ammonia, </span><span>tank</span><span> and ship.</span></span><span>&nbsp;</span></li>
</ol>
<ol>
<li><span><span>A seal the plant cannot rewrite. Each record is hashed, signed with a key in Key Vault Managed HSM and written to Azure Confidential Ledger, which is append-only and protected from insiders, the cloud provider included.</span></span><span>&nbsp;</span></li>
</ol>
<ol>
<li><span><span>Verifiers check each receipt against the identity of the ledger, without having to trust the plant.</span></span><span>&nbsp;</span></li>
</ol>
<p><span>I tested the third choice in my demo. I changed one number in a chain of 24-hourly records, and the chain caught it. When I also recomputed every later hash, the chain verified again, and only a copy of the last hash kept outside the plant showed the change. That is why a database table with an audit log would not do: the administrator who can change the table can change the log.</span><span>&nbsp;</span></p>
<p><span>The target is 8,760 sealed hours a year, with the evidence pack for each cargo ready when loading starts, for a scheme such as CertifHy.</span><span>&nbsp;</span></p>
<h5><span class="lia-text-color-11"><strong>&nbsp;Evaluation, security and resiliency</strong></span></h5>
<p><span>A change goes live, and an agent moves up a level, only after the same gates: zero agent actions outside the limits in a full-year replay, zero impermissible behaviours in ASSERT, 100% tool input accuracy on write tools in the Foundry evaluators, and a ledger receipt for every hour.</span><span>&nbsp;</span></p>
<p><span>Agents bring two threats that a classic plant design does not have: instructions injected through a document or a partner’s agent, and an agent acting outside its job. So, Prompt Shields screen every input, partner text is treated as data, and no agent has a tool that changes a contract term or reaches the safety system. My reading of the EU AI Act is that the agents are not high-risk, because none is a safety component, and each plant should confirm that with counsel.</span><span>&nbsp;</span></p>
<p><span>When something breaks, the plant carries on. If the link drops, the control system holds its setpoints and the edge replays every tag later. If an agent or a model fails, no policy answer means no action. If the region fails, the sealed records are already copied to a second EU region, and the agents redeploy from code.</span><span>&nbsp;</span></p>
<h5><strong><span class="lia-text-color-11"> Testing it on a twin before you build</span></strong></h5>
<p><span>Before anyone buys hardware, I would run two copies of the plant on the same weather for a full year, one on fixed rules and one with the pattern. I did this for the case plant on a simple twin, with 8,760 hours of real weather for a site on Morocco’s Atlantic coast. <h5><strong><span class="lia-text-color-11"> What it costs</span></strong></h5>
<p><span>I priced every Azure line of the design at list prices of November 2026, for the 400,000 tonnes a year of the case. It comes to about EUR 345k a year, and EUR 237k after five savings such as a reserved Fabric capacity, a small model first and test environments paused out of hours. That is EUR 0.59 a tonne, next to a premium of EUR 200 on the same tonne.</span><span>&nbsp;</span></p>
<p><span>The agents and their models are 11% of that bill. Trust, security and data are 56%. Anyone who budgets an agent system by counting tokens will miss most of the cost.</span><span>&nbsp;</span></p>
<p><span>With delivery and edge servers I estimate EUR 3.2 to 4.0M over the first three years, indicative until a partner quotes it. Proving 1% more tonnes is worth EUR 0.8M a year, 3.4 times the Azure run cost.</span><span>&nbsp;</span></p>
<h5><strong><span class="lia-text-color-11"> Where the pattern does not fit</span></strong></h5>
<p><span>I would not use this pattern where there is no reliable process model to optimise against, where telemetry is thin, or where someone wants AI inside the safety function. In the first two cases, start with data and a planning model. In the third, the answer is no.</span><span>&nbsp;</span></p>
<p><span>My own work leaves two things open. The language-model agents and their evaluation are designed and have not been run. And a sealed record is not a certified tonne until a certification body accepts the method.</span><span>&nbsp;</span></p>
<p><span>Within those limits I expect the pattern to carry to e-fuels, desalination, chemicals and mining, wherever AI sits next to process safety and a buyer or regulator wants proof.</span><span>&nbsp;</span></p>
<h5><strong><span class="lia-text-color-11"> Conclusion</span></strong></h5>
<p><span>My recommendation is to let an optimiser plan, to give the agents the work around the plan, and to design the hourly proof as carefully as the plant itself. Start with ten weeks on the plant’s own data. If the gain does not show up there, the board will know before it has spent the build budget.</span><span>&nbsp;</span></p>

### Introducing Brewlet: Manage Golden Images at Platform Speed

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/introducing-brewlet-manage-golden-images-at-platform-speed/ba-p/4576767](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/introducing-brewlet-manage-golden-images-at-platform-speed/ba-p/4576767)
- **Published**: 2026-11-26 05:14:07
- **Fetched**: 2026-11-26 22:17:52

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>In October 2026, the PHP project released security updates for critical vulnerabilities that could allow unauthenticated remote code execution. For teams running PHP in Kubernetes, applying a runtime fix can mean more than updating PHP: it can mean rebuilding application images, waiting for application pipelines and approvals, and coordinating deployments across services, even when the application code itself has not changed. That delivery gap matters.</p>
<p>AI is accelerating software development, but also vulnerability discovery and exploitation, increasing pressure on organizations to respond quickly. But asking every application team to rebuild and redeploy at once is not always practical. How can platform teams deliver a runtime update without making unrelated application releases a prerequisite?</p>
<p>Today, we’re introducing&nbsp;<a class="lia-external-url" href="https://brewlet.sh" rel="noopener" target="_blank">Brewlet</a>, an experimental open-source project that treats approved runtimes as Kubernetes infrastructure. Application teams publish their application code and launch instructions as an OCI image. Platform teams approve golden runtime images and offer them to selected Kubernetes node pools. Compatible workloads can then use an updated runtime, with a security patch, without rebuilding their application image.</p>
<h2>Golden images and independent runtime updates solve different problems</h2>
<p>A golden image can help remove unnecessary components, attack surface and the amount of software teams need to assess. But it still bundles a language interpreter, system library or certificate bundle. When these components live in the final artifact of an application image, their security patches are still tied to the application’s build and release process.</p>
<p>Brewlet explores a different boundary: separate the application workload from its execution environment so they can be managed on distinct lifecycles. Of course, not every runtime should be moved out of every application image. The right boundary depends on compatibility, operations and who should own the update. But the goal here is to make the separation available when it helps.</p>
<h2>The application runtime shifts back to infrastructure.</h2>
<p>With Brewlet, an application image contains the application and its dependencies under /app, along with an explicit launch.json describing how to start it. It does not bundle the selected runtime. A platform team approves a digest-pinned golden runtime image, including its non-root identity, and decides which node pools offer it.</p>
<p>At container creation, Brewlet composes the application with the approved runtime available on the node. Applications remain ordinary Kubernetes workloads using OCI artifacts, containerd and runc. Sharing runtime files does not mean sharing a process, heap, writable filesystem or resource limits between applications.</p>
<p>Ultimately, the platform team can curate the runtime environment for its workloads, optionally with a set of common platform-owned dependencies, while application teams keep ownership of application code and application-specific dependencies.</p>
<h2>How Brewlet fits into Kubernetes</h2>
<ol>
<li><strong>Approve a runtime.</strong> The platform team defines a RuntimeImage that points to an approved runtime image by digest and declares its non-root identity.</li>
<li><strong>Offer it on a pool.</strong> A NodeProfile determines which nodes provide the runtime and how it is provisioned.</li>
<li><strong>Package the application.</strong> Developers use their existing build tools, then package the application files and launch metadata into an OCI image with the Brewlet CLI.</li>
<li><strong>Select the runtime.</strong> The Kubernetes workload uses runtimeClassName: brewlet and selects a runtime ID for each managed container. Admission validates the selection and placement; the node provisioner installs the approved runtime, and the Brewlet shim prepares the container for runc.</li>
</ol>
<p>The following illustrative Deployment selects a platform-approved php-8.4 runtime for a separately packaged application:</p>
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
  annotations:
    brewlet.sh/restart-on-rotation: "true"
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders
      annotations:
        runtime-image.brewlet.sh/app: php-8.4
    spec:
      runtimeClassName: brewlet
      containers:
        - name: app
          image: registry.example.com/apps/orders:v1
<p>This example assumes the platform has approved and offered php-8.4, and the application has been packaged for that runtime. The restart annotation is on the Deployment metadata. For Brewlet to restart opted-in workloads during rotation, the operator’s rotation-restart feature must also be enabled.</p>
<h2>Change the runtime, not the application artifact</h2>
<p>The&nbsp;<a href="https://brewlet.sh/docs/php/" rel="noopener" target="_blank">Brewlet PHP guide</a> demonstrates moving a PHP workload from PHP 8.4.26 to 8.4.27 by changing the approved runtime image while keeping the application digest the same. This example shows that a PHP security release can be qualified and distributed as a platform runtime update rather than requiring an application rebuild for every service.</p>
<p>It is important to note that a runtime rotation is not an in-place patch to a running process. Existing containers continue using the generation they started with, while new containers use the new generation, and workloads that have opted-in to restart-on-rotation be rolled by their Kubernetes controller when the operator feature is enabled. Workload rollout strategies still apply; paused, partitioned or otherwise constrained workloads can remain on the older generation.</p>
<p>The <a href="https://brewlet.sh/docs/demo/" rel="noopener" target="_blank">Java demonstration</a> illustrates another kind of runtime change: rotating a JDK also changes the certificate roots in that JDK’s bundled trust store, while preserving the application artifact. It makes visible that a runtime can contain security-relevant material beyond the language executable.</p>
<h2>What runtime separation does, and does not, solve</h2>
<p>Brewlet can help platform teams govern and roll out common components supplied by the approved runtime image. It does not update vulnerable libraries packaged under /app, such as application-specific dependencies; those still need an application update. Nor does it eliminate shared risk: if many workloads use the same vulnerable runtime, they are still exposed until they are running a fixed generation. Brewlet changes how that runtime can be distributed and governed, not the need to qualify it, replace workloads and verify the outcome.</p>
<p>Kubernetes <a href="https://kubernetes.io/docs/concepts/storage/volumes/#image" rel="noopener" target="_blank">image volumes</a> can also separate an application from runtime files and may be the simpler choice for teams whose existing policies and tooling already cover their needs. Brewlet’s additional value is an integrated model for runtime approval, node-pool provisioning, start-time authorization, generation visibility and opt-in rotation.</p>
<h2>Try Brewlet</h2>
<p>Brewlet is an MIT-licensed open-source project. The current releases are experimental and intended for evaluation. Start with the&nbsp;<a href="https://brewlet.sh/docs/local-kubernetes/" rel="noopener" target="_blank">local Kubernetes tutorial</a>, which deploys a Python application and demonstrates a runtime rotation in kind. Explore the <a href="https://brewlet.sh/docs/demo/" rel="noopener" target="_blank">Java demonstration</a>, the <a href="https://brewlet.sh/docs/language-recipes/" rel="noopener" target="_blank">language guides</a>, and <a href="https://brewlet.sh/docs/choosing-brewlet/" rel="noopener" target="_blank">when to consider Brewlet</a> for a fuller description of the operational tradeoffs.</p>
<p>Find Brewlet on&nbsp;<a href="https://github.com/microsoft/brewlet" rel="noopener" target="_blank">GitHub</a>, and use the <a href="https://github.com/microsoft/brewlet/issues" rel="noopener" target="_blank">issue tracker</a> to report problems or share feedback. We’d like to hear how runtime updates flow through your organization today, and whether separating runtime delivery from application releases would make those updates easier to govern.</p>

### Azure Functions and AWS Lambda: One Trigger vs. Multiple Triggers—What Changes in Your Design?

- **Published**: 2026-11-26 11:28:19
- **Fetched**: 2026-11-27 13:37:28

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>When moving between Azure Functions and AWS Lambda, one difference quickly stands out:</p>
<ul>
<li>An individual&nbsp;<strong>Azure function must have exactly one trigger</strong>.</li>
<li>An&nbsp;<strong>AWS Lambda function can have multiple triggers</strong>.</li>
</ul>
<p>At first glance, Lambda appears more flexible. But what does this difference actually mean for code reuse, event handling, and application design?</p>
<p>Let’s explore it using a practical example.</p>
<h2>First, distinguish a function from a Function App</h2>
<p>In Azure, a&nbsp;<strong>function</strong>&nbsp;and a&nbsp;<strong>Function App</strong>&nbsp;are different things.</p>
<p>A function is an individual entry point with its own trigger. A Function App is the Azure resource that hosts one or more functions.</p>
<p>Therefore:</p>
<p>The one-trigger rule applies to each Azure function—not to the entire Function App.</p>
<p>A single Function App can contain HTTP-triggered, queue-triggered, and timer-triggered functions.</p>
<p>Microsoft’s&nbsp;<a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-triggers-bindings" target="_blank">triggers and bindings documentation</a>&nbsp;explicitly states that a function must have exactly one trigger.</p>
<p>A Lambda function can have multiple triggers, each invoking it independently. It can also be deployed without any configured triggers and tested directly using a test event in the AWS Lambda console.</p>
<h2>The scenario: one business operation, multiple entry points</h2>
<p>Suppose an application processes orders through three channels:</p>
<ol>
<li>An HTTP request submits an order.</li>
<li>A queue delivers an order for background processing.</li>
<li>A scheduled job starts an order-reconciliation run.</li>
</ol>
<p>These entry points may reuse some of the same business logic, even though their payloads and execution requirements differ.</p>

<p>However,&nbsp;<strong>multiple triggers do not mean one invocation combines events from multiple sources</strong>. Each source invokes the function independently.</p>
<p>The handler must understand the event it receives and apply the appropriate behavior.</p>
<p>For example:</p>
<ul>
<li>API Gateway supplies an HTTP-oriented event.</li>
<li>SQS supplies a batch-oriented message event.</li>
<li>A scheduled invocation supplies its configured payload.</li>
</ul>
<p>If those payloads differ, the handler needs routing and normalization logic. Integrations that support payload transformation can sometimes reduce that work.</p>
<p>There is also an important terminology distinction: not every Lambda integration uses the same mechanism. SQS uses a Lambda&nbsp;<strong>event source mapping</strong>, which polls the queue and invokes the function with batches.</p>

<h2>Final takeaway</h2>
<p>AWS Lambda allows several event sources to invoke one function. Azure Functions requires exactly one trigger per function, while allowing multiple functions within a Function App.</p>
<p>The most useful comparison is not:</p>
<p>“Which platform lets me attach more triggers?”</p>
<p>It is:</p>
<p>“Where should event-specific handling end, and shared business logic begin?”</p>
<p>Both platforms support reusable business logic. Their trigger models give you different ways to organize the entry points around it.</p>
