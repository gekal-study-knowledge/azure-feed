## Azure Infrastructure Blog

### Implement Virtual WAN Secure Hub with Customer-Owned Public IPs for Firewall using AVM

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/implement-virtual-wan-secure-hub-with-customer-owned-public-ips/ba-p/4575390](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/implement-virtual-wan-secure-hub-with-customer-owned-public-ips/ba-p/4575390)
- **Published**: 2026-11-21 19:27:54
- **Fetched**: 2026-11-22 21:04:04

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><span>Azure Virtual WAN provides a managed networking architecture that simplifies connectivity between virtual networks, branch locations, VPN connections, and ExpressRoute connections. At the centre of this architecture is the </span><span>Virtual Hub</span><span>, which provides managed connectivity and routing. When Azure Firewall and the associated security and routing policies are configured for the Virtual Hub through Azure Firewall Manager, it becomes a </span><span>secured virtual hub</span><span>. Azure Firewall in the secured virtual hub can then provide centralized security and traffic inspection for traffic moving through the Virtual WAN environment. The same firewall can also be configured for private and public networking traffic inspection by setting the private and public Routing Intent.</span>&nbsp;</p>
<h3><span>Public IP Addresses with Azure Firewall</span></h3>
<p><span>While we use the azure vWAN secure Hub with Azure Firewall and public routing intent, it requires Public IP addresses for public connectivity. These Public IP addresses are important for both </span><span>inbound and outbound traffic scenarios</span><span>.</span><span>&nbsp;</span></p>
<p><span>For </span><span>outbound traffic</span><span>, Azure Firewall Public IP addresses can be used as source addresses when workloads communicate with destinations on the internet. Having known Public IP addresses can be important when external systems allow traffic based on specific source IP addresses.</span>&nbsp;<br /><span>&nbsp;</span><span>For </span><span>inbound traffic</span><span>, Azure Firewall can provide controlled access to internal workloads through features such as Destination Network Address Translation (DNAT). External traffic reaches a Public IP associated with the firewall and is translated and forwarded to the appropriate internal destination according to the configured firewall rules. The same IP then can also be configured with DNS to provide an FQDN based endpoint solution to the upstream applications. In many deployments, Public IP addresses can be managed as part of the Azure Firewall deployment. </span>&nbsp;<br />&nbsp;<br /><span>However, there are also scenarios where organizations want to </span><span>create and manage their own Public IP resources</span><span> and then associate those specific Public IP addresses with Azure Firewall.</span><span>&nbsp;</span></p>
<p><span>For example, an organization might need to:</span><span>&nbsp;</span></p>
<ul>
<li><span>Maintain consistent Public IP addresses across the deployment.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Control the creation and lifecycle of the Public IP resources separately from Azure Firewall.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Use known Public IP addresses for outbound connectivity where external systems depend on source IP allowlists.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Maintain specific Public IP addresses for inbound connectivity and DNAT scenarios.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Meet existing networking, security, or compliance requirements that depend on known Public IP addresses.</span><span>&nbsp;</span></li>
</ul>
<p><span>The deployment model therefore changes from simply defining </span><span>how many Public IP addresses the firewall requires</span><span> to defining </span><span>which Public IP resources the firewall should use</span><span>.</span><span>&nbsp;<br /><br /></span></p>
<img />
<h3><span>Customer-Provided Public IP Addresses</span></h3>
<p><span>Azure Firewall in Virtual WAN secured hubs now supports the use of customer-provided public IP addresses. This capability enables organizations to bring their own public IP addresses when deploying Azure Firewall in a secured Virtual WAN hub, providing greater flexibility and control over network infrastructure.</span>&nbsp;<br /><span>With this feature, instead of relying on Azure-managed public IP addresses, you can specify your own public IP addresses that are already allocated in your Azure subscription. This is particularly valuable for organizations that require consistent IP addresses for compliance, security policies, or integration with third-party systems</span><span>.</span>&nbsp;</p>
<p><span>Inbound Traffic flow</span><span>&nbsp;</span></p>
<p><span>Internet &gt; Azure firewall Public IP &gt; DNAT Rule &gt; Vwan secure Hub &gt; Application Ingress</span><span>&nbsp;</span></p>
<p><span>Outbound Traffic flow</span>&nbsp;<br /><span>Apps &gt; Secured Virtual Hub &gt; Azure Firewall → Customer-managed Public IP → Internet</span> <br /><span>According to Microsoft documentation, customer-provided Public IP addresses must:</span><span>&nbsp;</span></p>
<ul>
<li><span>Use the </span><span>Standard SKU</span><span>.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Use </span><span>Static allocation</span><span>.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Should be deployed in the </span><span>same Azure region</span><span> as the Virtual Hub.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Not already be associated with another Azure resource.</span><span>&nbsp;</span></li>
</ul>
<p><span>A secured virtual hub can also associate multiple customer-provided Public IP addresses with Azure Firewall.</span><span>&nbsp;</span></p>
<p><span><span>The configuration can be implemented directly through the Azure portal when deploying Azure Firewall in a secured Virtual WAN hub. During the firewall configuration, existing eligible Public IP resources can be selected as customer-provided Public IP addresses instead of relying on Azure-managed Public IPs. This allows the firewall to use specific Public IP resources while their lifecycle remains independently managed.</span>&nbsp;<br /><span>Source: </span><a href="https://learn.microsoft.com/en-us/azure/firewall/secured-hub-customer-public-ip?tabs=portal" target="_blank"><span><span>Customer provided public IP address support in secured hubs | Microsoft Learn</span></span></a></span></p>
<h3><span><span><span>The Infrastructure-as-Code Challenge</span></span></span></h3>
<p><span>Although customer-provided Public IP addresses can be configured for Azure Firewall in a secured Virtual WAN hub through the Azure platform, implementing the same configuration through Infrastructure as Code introduces an additional consideration.</span><span>&nbsp;</span></p>
<p><span>The Virtual WAN environment in this implementation is deployed using Terraform and Azure Verified Modules (AVM). AVM provides reusable Terraform modules for deploying Azure resources using standardized patterns and helps keep infrastructure deployments consistent and repeatable.</span><span>&nbsp;</span></p>
<p><span>For the secured Virtual Hub Azure Firewall configuration, the available implementation exposed a parameter such as vhub_public_ip_count. This parameter is suitable when the deployment only needs to define </span><span>how many Public IP addresses should be associated with the firewall</span><span>. For example, a value of 2 represents the requirement for two Public IP addresses to be provisioned as part of the firewall configuration.</span><span>&nbsp;</span></p>
<p><span>Customer-provided Public IP addresses work differently. In this scenario, the Public IP resources already exist or are created separately, so the deployment does not simply need to know the number of Public IP addresses. It needs to know </span><span>which specific Public IP resources should be associated with Azure Firewall</span><span>. This requires passing the Azure resource IDs of those Public IP addresses into the firewall configuration.</span><span>&nbsp;</span></p>
<p><span>Therefore, a count-based parameter such as vhub_public_ip_count alone cannot represent the complete customer-provided Public IP configuration. At the time of this implementation, the available AVM-based configuration provided the option to specify the Public IP count but did not expose an input through which specific customer-provided Public IP resource IDs could be passed to the secured hub firewall.</span>&nbsp;<br />&nbsp;<br /><span>This created a gap between the capability already supported by the Azure platform and the way that capability could be represented through the existing Terraform and AVM implementation.</span></p>
<h3><span><span>Remediation: Customer-Provided Public IP Support in AVM</span></span></h3>
<p><span>The Azure platform already supported customer-provided Public IP addresses for Azure Firewall in a secured Virtual WAN hub. However, the earlier AVM implementation primarily exposed vhub_public_ip_count, which allowed the deployment to specify the number of Public IP addresses required by the firewall but did not provide a direct way to pass specific customer-owned Public IP resource IDs.</span>&nbsp;<br /><span>&nbsp;</span><span>To address this gap, support for customer-provided Public IP addresses was introduced in the Azure Verified Pattern Module for Azure Landing Zone Connectivity with Virtual WAN through a GitHub contribution.</span>&nbsp;<br /><span>&nbsp;</span><span>The enhancement added support for an ip_configurations map under the firewall configuration of each Virtual Hub. Each entry can now specify a firewall IP configuration name together with the public_ip_address_id of an existing customer-managed Public IP resource.</span>&nbsp;<br /><span>&nbsp;</span><span>The change was reviewed through the module's GitHub contribution process and has now been merged into the AVM repository. As a result, the AVM Virtual WAN module can now support both deployment models:</span><span>&nbsp;</span></p>
<p><span>Azure-managed Public IPs</span><span>&nbsp;</span></p>
<p><span>The existing vhub_public_ip_count configuration can continue to be used when Azure should manage the Public IP addresses associated with the secured hub firewall.</span><span>&nbsp;</span></p>
<p><span>Customer-provided Public IPs</span><span>&nbsp;</span></p>
<p><span>The new </span><span>firewall.ip_configurations</span><span> configuration can be used when specific existing Public IP resources need to be associated with Azure Firewall</span>&nbsp;<br />&nbsp;</p>
