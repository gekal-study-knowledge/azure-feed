## Azure Networking Blog

### What’s new in AKS networking: Connectivity, performance, and observability

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/what-s-new-in-aks-networking-connectivity-performance-and/ba-p/4571806](https://techcommunity.microsoft.com/t5/azure-networking-blog/what-s-new-in-aks-networking-connectivity-performance-and/ba-p/4571806)
- **Published**: 2026-11-11 04:06:23
- **Fetched**: 2026-11-11 10:32:21

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>As organizations scale their cloud-native applications, networking requirements continue to evolve. AI and high-performance computing workloads demand high-throughput, low-latency connectivity, applications increasingly span multiple Kubernetes clusters and enterprises need greater control over how workload traffic is routed and isolated. At the same time, platform teams need deeper network visibility that is customizable without the complexity and cost of collecting unnecessary data.<br /><br />At Microsoft, our focus is to simplify these AKS networking challenges, enabling customers to build and scale AI applications without having to manage increasingly complex networking infrastructure.<br /><br />This November, container networking in Azure is introducing four capabilities designed to help customers build, scale, and operate the next generation of applications on AKS. These advancements address three key customer scenarios:<br /><br />·&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; <strong>Connect distributed applications:</strong> Simplify connectivity and service discovery across Kubernetes clusters, making it easier to build and manage distributed applications.<br /><br />·&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; <strong>Enable AI and specialized workloads:</strong> Support high-performance networking for distributed AI training and HPC, along with flexible network configurations for data-intensive and specialized applications.<br /><br />·&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; <strong>Operate with customizable visibility and control:</strong> Gain deeper insights into application networking, troubleshoot issues faster, and manage observability costs through targeted telemetry collection.</p>
<p>Together, these capabilities expand what customers can run on AKS while reducing the complexity of the underlying networking infrastructure.</p>
<h2><strong>Connect distributed applications</strong></h2>
<h4><strong>Cross-cluster networking for Azure Kubernetes Fleet Manager | Generally Available</strong></h4>
<p>As enterprises scale their applications across multiple Kubernetes clusters, connecting services across cluster boundaries often requires additional networking infrastructure, complex configurations, and operational overhead.</p>
<p>With the general availability of cross-cluster networking for Azure Kubernetes Fleet Manager, part of Advanced Container Networking Services, customers can connect workloads across AKS clusters without deploying and managing gateways or proxies.</p>
<p>For example, an enterprise running applications across multiple AKS clusters can enable services to discover and communicate with each other as though they were running within a single cluster. Built on Cilium, this capability also extends network policy enforcement and observability across cluster boundaries.</p>
<p>The result is simpler multi-cluster application architectures, reduced operational complexity, and greater visibility into application connectivity as environments scale. <br /><br /></p>
<img />
<p><strong>Learn more about cross-cluster networking at: </strong><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/kubernetes-fleet/concepts-cross-cluster-networking" rel="noopener" target="_blank">https://learn.microsoft.com/en-us/azure/kubernetes-fleet/concepts-cross-cluster-networking</a><a href="https://learn.microsoft.com/en-us/azure/kubernetes-fleet/concepts-cross-cluster-networking" rel="noopener" target="_blank"><em> </em></a></p>
<h2><strong>Enable AI and specialized workloads</strong></h2>
<p><strong>Multi-NIC pods for AKS | Public Preview</strong></p>
<p>Traditional Kubernetes networking provides a single primary network interface for application traffic. However, enterprises running specialized workloads often need to separate different types of network traffic to meet their performance, connectivity, and isolation requirements.</p>
<p>With Multi-NIC pods support in AKS, customers can attach multiple network interfaces to Kubernetes nodes and workloads, enabling greater control over how traffic is routed.</p>
<p>For example, an enterprise running data-intensive applications can use separate network interfaces for application communication and storage traffic, helping isolate workloads and optimize network resource utilization.</p>
<p>&nbsp;</p>
<img />
<p>Multi-NIC pods give customers greater flexibility to design Kubernetes networking architectures around their application requirements, without having to manage additional networking components themselves.</p>
<p><strong>Learn more about Multi-NIC pods at:</strong> <a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/aks/multiple-network-interfaces-for-pods-overview" rel="noopener" target="_blank">https://learn.microsoft.com/en-us/azure/aks/multiple-network-interfaces-for-pods-overview</a><a href="https://learn.microsoft.com/en-us/azure/aks/multiple-network-interfaces-for-pods-overview" rel="noopener" target="_blank"><em> </em></a></p>
<p><strong>Managed support for DRANET for RDMA</strong><strong> | Generally Available</strong></p>
<p>AI training, machine learning, and high-performance computing workloads require fast, efficient communication between GPUs and compute resources. Configuring and managing the specialized networking infrastructure needed for these workloads can introduce significant operational complexity.</p>
<p>With Managed support for DRANET for RDMA NICs in AKS, we're simplifying access to high-throughput, low-latency networking through a managed experience that supports topology-aware resource allocation.</p>
<p>For example, organizations running distributed AI training workloads can more easily provision RDMA networking resources to support accelerated communication between compute nodes, without taking on the complexity of managing the underlying networking configuration.</p>
<p>This enables customers to focus on scaling their AI and HPC workloads while taking advantage of the performance capabilities of RDMA-enabled Azure infrastructure.</p>
<p><strong>Learn more about managed support for DRANET for RDMA at:</strong> <a class="lia-external-url" href="https://learn.microsoft.com/en-gb/azure/aks/managed-support-for-dranet?tabs=add-ubuntu-rdma-node-pool" rel="noopener" target="_blank">https://learn.microsoft.com/en-gb/azure/aks/managed-support-for-dranet?tabs=add-ubuntu-rdma-node-pool</a><em>&nbsp;</em></p>
<h2><strong>Operate with customizable visibility and control </strong></h2>
<p><strong>Configurable dimensions in Advanced Container Networking Services observability | Public Preview</strong></p>
<p>Performance and connectivity are only part of operating cloud-native applications at scale. Platform, security, and SRE teams also need the right level of network visibility to troubleshoot applications, investigate threats, and meet compliance requirements.</p>
<p>With configurable dimensions for container network observability in Advanced Container Networking Services, customers can now scope the traffic they care about and choose the level of detail to retain. For example, a security team investigating suspicious outbound traffic can retain the DNS query, source pod IP, and destination IP for the affected workload. A security engineer can collect detailed records for a failing namespace, while a compliance team can retain FQDN information for selected egress-facing applications.</p>
<p>Customers can now also select network observations by Cilium security identity to deeply investigate unexpected outbound activity and filter logs with external destination IPs and destination port-distribution metrics. These capabilities help platform engineers understand outbound communication patterns and give application teams more context when investigating changes in how a service communicates.</p>
<p>The result is persistent, actionable network visibility for security, troubleshooting, and compliance, with control over the scope and cost of the data collected.</p>
<p><strong><a href="https://aka.ms/acns/howtoenablecnl" rel="noopener" target="_blank"><span class="lia-text-color-21">Learn more about configuring Container Network Logs</span></a><span class="lia-text-color-21"> at:</span></strong> <a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/aks/container-network-observability-logs" rel="noopener" target="_blank">https://learn.microsoft.com/en-us/azure/aks/container-network-observability-logs</a><a href="https://learn.microsoft.com/en-us/azure/aks/container-network-observability-logs" rel="noopener" target="_blank"><em> </em></a><em> </em></p>
<p>These announcements reflect our continued investment in making Azure Kubernetes networking simpler to consume while supporting an increasingly diverse set of workloads.</p>
<p>Whether customers are connecting applications across clusters, isolating network traffic for specialized workloads, accelerating communication for AI and HPC applications, or building deeper observability, our focus remains the same: deliver the networking capabilities customers need, with less infrastructure to manage and greater flexibility to scale.</p>
<p>We're excited to bring these capabilities to our customers and look forward to connecting with the cloud-native community at KubeCon and Ignite.</p>

### Run on your schedule: App Service plan start/stop now in public preview

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/run-on-your-schedule-app-service-plan-start-stop-now-in-public/ba-p/4566184](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/run-on-your-schedule-app-service-plan-start-stop-now-in-public/ba-p/4566184)
- **Published**: 2026-11-11 03:32:36
- **Fetched**: 2026-11-11 06:30:20

<details class="entry-summary">
<summary>詳細を表示</summary>
<h2>Start and stop your apps together</h2>
<p>Managing an environment with multiple apps shouldn't mean stopping and starting each app individually. App Service plan start/stop brings that control to the plan level, letting you manage the apps and deployment slots it hosts together.</p>
<p>Today, we're announcing the public preview for this feature for <strong>Premium v4 (Pv4) and Premium memory-optimized v4 (Pmv4) plans</strong>. Stop the plan to take its workloads offline, then start it again when you're ready, without issuing separate commands for each app.</p>
<blockquote>
<p><strong>NOTE: </strong></p>
<p>Start and stop operations are asynchronous: the apps on your plan don’t all stop or become ready to serve requests immediately. After you stop a plan, app shutdown and cleanup can continue over the next few minutes. When you start it again, allow time for your applications to become ready before sending traffic.</p>
</blockquote>
<p>This is particularly useful for development, test, and demo environments that share an operating schedule. Because the operation affects the entire plan, make sure every hosted workload can tolerate the interruption. To bring workloads on a stopped plan back online, start the plan rather than an individual app.</p>
<h2>Get started with Azure CLI</h2>
<p>You can call the start and stop REST operations using <code>az rest</code>. Sign in to Azure, select the subscription containing your plan, and set its resource group and name:</p>
resourceGroup="[RESOURCE-GROUP-NAME]"
planName="[APP-SERVICE-PLAN-NAME]"

planId=$(az appservice plan show \
  --resource-group "$resourceGroup" \
  --name "$planName" \
  --query id --output tsv) || exit 1

# Stop the plan. All hosted apps and deployment slots will be unavailable.
az rest --method post --url "https://management.azure.com${planId}/stopSites?api-version=2026-07-15"
<p>When you're ready to run the workloads again, start the plan:</p>
az rest --method post --url "https://management.azure.com${planId}/startSites?api-version=2026-07-15"
<p>Plan for application startup time before sending traffic back to the environment. A successful API response isn't a substitute for checking that your applications are ready to serve requests.</p>
<h2>Get started with the Azure portal</h2>
<p>You can also use the Azure portal to start and stop your plans. On the App Service plan Overview page, select start and stop as you may have done for your individual apps. If you try to start an app when its App Service plan is stopped, you will get an error letting you know to start the App Service plan instead.</p>
<blockquote>
<p><strong>NOTE:</strong></p>
<p>This feature is rolling out in the portal over the next few weeks. If you don't see the option in the portal yet, check back in a couple days and use the Azure CLI in the meantime.</p>
</blockquote>
<img />
<h2>Billing considerations</h2>
<p>Compute billing for an eligible plan pauses when the plan is stopped, even though app shutdown and cleanup can continue over the next few minutes. Compute billing resumes when the plan is started. Charges for other resources and services can continue.</p>
<h2>Preview limitations and considerations</h2>
<ul>
<li><strong>Supported tiers:</strong> Premium v4 and Premium memory-optimized v4 only. Other App Service plan tiers aren't supported.</li>
<li><strong>Availability:</strong> [Insert confirmed preview regions, cloud availability]</li>
<li><strong>Plan-wide impact:</strong> All apps and deployment slots on the plan are affected. Don't stop a plan that also hosts workloads that must remain available.</li>
<li><strong>Restart at the plan level:</strong> Attempting to start an individual app will not restart the plan. You must restart the plan to restart the apps.</li>
<li><strong>Automatic scaling:</strong> Plans with App Service automatic scaling enabled aren't supported. This is distinct from Azure Monitor autoscale.</li>
<li><strong>Scaling in progress:</strong> Wait for an in-progress asynchronous scale operation to finish before starting or stopping the plan.</li>
<li>
<p><strong>Start/stop throttling:</strong> Plan start and stop operations are subject to a five-minute throttle. Account for this when scheduling operations or testing repeated start/stop cycles.</p>
</li>
<li><strong>Changes while stopped:</strong> Start the plan before scaling it or making other plan updates.</li>
</ul>
<h2>Try the preview</h2>
<p>Try start/stop on a development or test plan whose apps share an operating schedule. Review the apps and deployment slots it hosts, then use the plan-level commands to stop and start those workloads together instead of managing each app individually.</p>
<p>For the API details, see <a href="https://learn.microsoft.com/en-us/rest/api/appservice/app-service-plans/stop-web-apps?view=rest-appservice-2026-07-15" rel="noopener" target="_blank">Stop Web Apps</a> and <a href="https://learn.microsoft.com/en-us/rest/api/appservice/app-service-plans/start-web-apps?view=rest-appservice-2026-07-15" rel="noopener" target="_blank">Start Web Apps</a>.</p>
</details>

### .NET 11 is now generally available in Azure Functions

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/net-11-is-now-generally-available-in-azure-functions/ba-p/4571176](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/net-11-is-now-generally-available-in-azure-functions/ba-p/4571176)
- **Published**: 2026-11-11 04:58:09
- **Fetched**: 2026-11-11 06:30:20

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Today, we're announcing general availability of .NET 11 support in Azure Functions through the <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/dotnet-isolated-process-guide" rel="noopener" target="_blank">isolated worker model</a>. You can build new serverless applications with .NET 11 or update your existing isolated worker apps to target the new release.</p>
<p>This release also introduces a required project SDK for .NET 11 function apps: <a class="lia-external-url" href="https://www.nuget.org/packages/Azure.Functions.Sdk" rel="noopener" target="_blank">Azure.Functions.Sdk</a>. Updated Azure Functions tooling templates use the new SDK, giving new projects a simpler project file while preserving the isolated worker programming model.</p>
<p>.NET 11 support in Azure Functions is currently available for C# apps. F# support is temporarily unavailable.</p>
<h1>A simpler project SDK</h1>
<p><strong>Azure.Functions.Sdk</strong> brings the Functions build integration into the project's SDK declaration. Instead of using <em>Microsoft.NET.Sdk</em> as the project SDK and adding<em> Microsoft.Azure.Functions.Worker.Sdk </em>as a package reference, use <em>Azure.Functions.Sdk</em> in the opening Project element and target net11.0.</p>
<p>Keep an explicit package reference to <em>Microsoft.Azure.Functions.Worker</em>, which provides the worker runtime, along with the trigger and binding extensions your application uses. Azure.Functions.Sdk replaces the build SDK package; it does not replace the worker runtime package.</p>
<p>The new SDK supplies the underlying .NET worker SDK, defaults AzureFunctionsVersion to v4, and includes the analyzers and source generators that prepare your functions for deployment. It also integrates with Azure Functions tooling so that dotnet run starts the Functions host when Azure Functions Core Tools is installed.</p>
<p>Using a custom container? .NET 11 Functions base images are published as chiseled images. Use &nbsp;<strong>mcr.microsoft.com/azure-functions/dotnet-isolated:4-dotnet-isolated11.0-chiseled </strong>; the <em>4-dotnet-isolated11.0</em> and <em>4-dotnet-isolated11.0-appservice</em> tags aren’t published. Chiseled images don’t include a shell or SSH server. See <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/container-concepts#maintaining-custom-containers" target="_blank">Maintaining custom containers</a>.</p>
<h1>Get started with .NET 11</h1>
<ol>
<li>Install the .NET 11 SDK and update your Azure Functions development tools and templates. Use your preferred <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/functions-develop-local" rel="noopener" target="_blank">local development experience</a> to create a .NET 11 isolated worker project.</li>
</ol>
<p>With the updated Azure Functions Core Tools, run:</p>
func init --worker-runtime dotnet-isolated --target-framework net11.0
<p>For .NET 11, use&nbsp;<em>Azure.Functions.Sdk</em> version 1.0.1 or later. We also recommend&nbsp;<em>Microsoft.Azure.Functions.Worker</em> version 2.50.0 or later. The versions in the project example below reflect the current template and may differ from these minimum and recommended versions. The generated project file looks like this:</p>
&lt;Project Sdk="Azure.Functions.Sdk/1.0.1"&gt;
  &lt;PropertyGroup&gt;
    &lt;TargetFramework&gt;net11.0&lt;/TargetFramework&gt;
    &lt;ImplicitUsings&gt;enable&lt;/ImplicitUsings&gt;
    &lt;Nullable&gt;enable&lt;/Nullable&gt;
  &lt;/PropertyGroup&gt;
  &lt;ItemGroup&gt;
    &lt;PackageReference Include="Microsoft.Azure.Functions.Worker"
      Version="2.52.0" /&gt;
    &lt;PackageReference
      Include="Microsoft.Azure.Functions.Worker.OpenTelemetry"
      Version="1.2.0" /&gt;
    &lt;PackageReference Include="OpenTelemetry.Extensions.Hosting"
      Version="1.15.3" /&gt;
    &lt;PackageReference Include="Azure.Monitor.OpenTelemetry.Exporter"
      Version="1.7.0" /&gt;
    &lt;PackageReference
      Include="Microsoft.Azure.Functions.Worker.Extensions.Http.AspNetCore"
      Version="2.1.1" /&gt;
  &lt;/ItemGroup&gt;
&lt;/Project&gt;
<p>These package versions reflect the current template example, not minimum requirements for every app. The template includes OpenTelemetry and ASP.NET Core HTTP integration packages; retain or adjust your app's dependencies to match the features and telemetry configuration you use.</p>
<ol start="2">
<li>Check that the generated project uses Azure.Functions.Sdk and targets net11.0. Keep the template's Microsoft.Azure.Functions.Worker reference and add the binding extension packages your functions need.</li>
<li>Build and run locally, then deploy to a function app configured for the .NET 11 isolated worker stack. Follow the <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/dotnet-isolated-process-guide#deploy-to-azure-functions" rel="noopener" target="_blank">deployment guidance</a> and check the <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/dotnet-isolated-process-guide#supported-versions" rel="noopener" target="_blank">supported versions</a> for hosting restrictions.</li>
</ol>
<p>.NET 11 is supported only in the isolated worker model, not the in-process model. Support for the in-process model ended on November 10, 2026. If your app still uses this model, follow the migration guide to move to isolated worker before adopting .NET 11.</p>
<p>Linux Consumption does not support .NET 10 or later; if you're moving an app from Linux Consumption, review the <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/migration/migrate-plan-consumption-to-flex" rel="noopener" target="_blank">migration guidance for Flex Consumption</a> before upgrading.</p>
<h1>Update an existing isolated worker app</h1>
<p>For an app that already uses the isolated worker model, start by updating its dependencies and checking compatibility with .NET 11. Then update the project SDK and target framework, remove the Microsoft.Azure.Functions.Worker.Sdk package reference, and retain an explicit Microsoft.Azure.Functions.Worker reference.</p>
<p>You can remove OutputType and AzureFunctionsVersion because the new SDK sets them automatically. Remove FunctionsEnableWorkerIndexing if present; worker indexing is always enabled with the new SDK.</p>
<p>The build SDK migration itself doesn't require changes to Program.cs, function classes, or host.json when you're using a current worker package. Retargeting to .NET 11 is a separate framework upgrade: review dependency compatibility and test your application's triggers, bindings, and deployment before updating production. The <a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/dotnet-isolated-process-guide#migrate-to-azurefunctionssdk" rel="noopener" target="_blank">isolated worker guide</a> walks through the project SDK changes.</p>
<p>If your app still uses the in-process model, follow the&nbsp;<a class="lia-external-url" href="https://learn.microsoft.com/azure/azure-functions/migrate-dotnet-to-isolated-model" rel="noopener" target="_blank">migration guide</a> to move to isolated worker before adopting .NET 11. The isolated worker model gives you control over application startup, standard .NET dependency injection, and separation between your application's dependencies and the Functions host.</p>

<p>Thank you to everyone who has shared feedback and helped improve .NET on Azure Functions. Explore the <a class="lia-external-url" href="https://github.com/Azure/azure-functions-dotnet-worker/tree/main/samples" rel="noopener" target="_blank">Azure Functions .NET worker samples</a> as you plan your next application, and share questions or feedback in <a class="lia-external-url" href="https://github.com/Azure/azure-functions-dotnet-worker/discussions" rel="noopener" target="_blank">GitHub discussions</a>. If you encounter a problem, <a class="lia-external-url" href="https://github.com/Azure/azure-functions-dotnet-worker/issues" rel="noopener" target="_blank">open an issue</a> so we can investigate.</p>
