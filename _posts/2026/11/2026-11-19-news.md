### Inside the architecture: How connectors work with Azure Functions

- **Link**: [https://techcommunity.microsoft.com/t5/azure-architecture-blog/inside-the-architecture-how-connectors-work-with-azure-functions/ba-p/4573939](https://techcommunity.microsoft.com/t5/azure-architecture-blog/inside-the-architecture-how-connectors-work-with-azure-functions/ba-p/4573939)
- **Published**: 2026-11-19 05:43:32
- **Fetched**: 2026-11-19 17:04:34

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Say you run a shared support inbox. Each time a customer writes in, you want a function to read the email, pick out the important parts, and post a summary in your team's Teams channel. The business logic might be twenty lines. The rest is authorization, change detection, event delivery, and a second set of permissions to post in Teams, and you rebuild most of it for every service you touch.</p>
<p>Azure Connectors and the Connector SDKs take that work on. The platform manages connections and authorization. The same app can react to events in one service and call operations in another. Webhook and poll delivery give you push or pull, so you can pick what fits your app. One SDK per language covers the Connector catalog with typed operations and payloads, VS Code tooling handles setup, and SDKs are available for .NET, Python, and Node.js from day one.</p>
<p>Underneath those promises are a handful of pieces we built and a few decisions about where each one stops. The support inbox runs through all of them.</p>
<h4>Starting from what Azure already has</h4>
<p>Azure already runs more than 1,000 managed Connectors, connecting to 1,600+ services. They power Azure Logic Apps and Power Automate, and API Hub hosts their connections, OAuth consent, and runtime. Logic Apps already knows how to run Connector triggers, whether the source sends notifications, accepts a webhook subscription, or has to be polled.</p>
<p>So we didn't write a second integration for each service. We built a new front door to the existing Connector runtime, one that application code can use directly, and added the glue Azure Functions needs on top. Most of the new work falls into four areas:</p>
<ul>
<li>A control plane, the Connector Namespace, that exposes connections, access policies, and trigger configurations as Azure resources.</li>
<li>A runtime layer that proxies SDK calls into API Hub and turns trigger configurations into system-managed workflows with a delivery step at the end.</li>
<li>A Functions Connector extension, with host and worker pieces, that receives events by webhook or by polling and feeds the Functions scale controller.</li>
<li>One code generator that emits typed SDKs for .NET, Python, and Node.js from live Connector metadata, plus tooling that sets everything up.</li>
</ul>
<img />
<p>Azure Connectors and Azure Functions architecture: the Outlook mailbox, the connector platform, and the Function App, with every flow from the email arriving to the summary reaching Teams</p>

<h4>The control plane: Connector Namespace</h4>
<p>A Connector Namespace is an Azure Resource Manager resource of type <span class="lia-text-color-10">`Microsoft.Web/connectorGateways`</span>. Under it sit three child resource types: connections, connection access policies, and trigger configurations. Because they're ARM resources, you can create them with Bicep, the CLI, or the VS Code tooling, and they get the usual Azure role-based access control and lifecycle.</p>
<p>A connection is the application-facing name for a backing API Hub connection, the same kind Logic Apps uses. The consent you grant for Outlook lives there. An access policy lists the Microsoft Entra identities, such as a Function App's managed identity, that may use a connection. That split means the identity that calls the connection and the account that consented to the mailbox are separate, and you can change one without touching the other.</p>
<img />
<p>Authorize the connections: the Function App's managed identity presents a token to the access policies, and the Outlook and Teams connections hold OAuth consent for their accounts</p>

<p>&nbsp;</p>
<p>A trigger configuration describes an event source. Its properties include the connection, the connector operation (for the support inbox, <span class="lia-text-color-15">`OnNewEmailV3`</span>), the operation's parameters, optional trigger conditions and settings, and a delivery mode. For webhook delivery it carries the callback details; for Poll delivery the service fills in the polling endpoints.</p>
<p>Each namespace also gets a stable host name, and a background job repairs its DNS record if it drifts.</p>
<h4>The action path: a proxy into API Hub</h4>
<p>When your handler posts the summary to Teams, the generated SDK client sends an HTTPS request to the connection's runtime URL. On the platform side that URL maps to `<span class="lia-text-color-15">api/connectorGateways/{gateway}/connections/{connection}/runtime`</span>, followed by the operation's own path.</p>
<p>Behind that route, the runtime processor handles each request in four steps:</p>
<ol>
<li>It resolves the application-facing connection to its backing API Hub connection and environment, in the namespace's scale unit.</li>
<li>It builds the API Hub runtime URL and checks that the requested path stays inside that connection, so a caller can't reach a different connection by rewriting the path.</li>
<li>It strips identity headers supplied by the caller and attaches a platform service token, plus headers that pass the caller's managed identity through.</li>
<li>It forwards the method, path, query, and body to API Hub, which runs the connector operation against Teams.</li>
</ol>
<p>The caller authenticates with a Microsoft Entra token for the API Hub audience. In the Node.js SDK the default scope is <span class="lia-text-color-15">`https://apihub.azure.com/.default`</span>, and the token comes from any Azure Identity <span class="lia-text-color-15">`TokenCredential`</span>, typically the Function App's managed identity.</p>
<p>The SDK side is thin on purpose. Generated clients extend a shared base class that holds the runtime URL and credential. A shared HTTP pipeline built on Azure Core adds the token, a user agent, tracing, and retries. Retries apply by default only to safe methods such as <span class="lia-text-color-15">`GET`</span> and <span class="lia-text-color-15">`HEAD`</span>, because retrying a `POST` that sends a message could send it twice. Paged operations follow `nextLink` values. When a continuation link points at a different host, as some connector back ends return, the SDK reroutes its path and query through the connection's runtime URL, so paging stays behind the proxy. Failures surface as a `ConnectorError` that carries the connector name, the operation, the status code, and the response body.</p>
<h4>The trigger path: system-managed workflows</h4>
<p>When you create a trigger configuration, the trigger API validates the request, generates a Logic Apps workflow definition, creates the workflow directly in a platform-owned subscription under a generated name, and stores the workflow details alongside the trigger configuration. Updates rewrite the workflow, and deleting the trigger configuration removes the workflow, its Poll queue, and its message history.</p>
<img />The trigger configuration generates the backing trigger workflow, which uses the Outlook connection
<p>The workflow generator picks the right trigger shape for the operation's metadata: a notification subscription, a webhook subscription, or a recurring poll. It adds <span class="lia-text-color-15">`splitOn` </span>for operations that return batches, so each item becomes its own run unless the configuration opts out, and it applies any trigger conditions you set. The workflow ends with a connector delivery action.</p>
<p>We generate a workflow per trigger configuration because Logic Apps already has years of hardening around subscription renewal, polling state, and trigger history, and every connector trigger already runs on it. The workflow stays an implementation detail: customers work with the trigger configuration resource and never see or edit the workflow.</p>
<h4>Two ways to deliver an event</h4>
<p>How the platform notices a new email and how the event reaches your function are separate problems. The backing workflow handles the first. The delivery action at the end of the workflow handles the second, and it supports two transports.</p>
<h5>Webhook delivery</h5>
<p>For webhook delivery, which is the default, the delivery action makes an HTTPS call to the callback in the trigger configuration, using the workflow engine's HTTP retry policy. On the Function App side, the callback is the host's `/runtime/webhooks/connector` route, protected by a system key named `connector_extension`. A `functionName` query parameter selects the function. The host returns `202` when the invocation succeeds, `400` for a missing or invalid name, `404` for an unknown function, and `500` when the invocation fails.</p>
<h5>Poll delivery</h5>
<p>For Poll delivery, the delivery action writes the event to an Azure Storage queue owned by that trigger configuration and records it in a message history table. Storage queue messages are limited to 64 KiB, so when an event is larger the action queues a reference to the workflow run's output instead of the output itself.</p>
<p>The Poll runtime API sits in front of the queue and has four operations: <span class="lia-text-color-15">`receive`</span>, <span class="lia-text-color-15">`acknowledge`</span>, <span class="lia-text-color-15">`hasMessages`,</span> and <span class="lia-text-color-15">`approximateQueueDepth`</span>. <span class="lia-text-color-15">`receive` </span>hands out events under a temporary lease with an opaque lock token. `acknowledge` deletes an event only when the message ID and a still-valid lock token match. If the lease expires first, the event becomes visible again. The reported depth is approximate and excludes leased messages.</p>
<img />
<p>Deliver the event by Poll: the delivery action enqueues the event, and the Functions host receives and acknowledges it from the Poll queue</p>

<p>Poll delivery means the Function App never exposes an inbound endpoint, and work can build up safely when the app is busy, scaled to zero, or running on a developer's laptop.</p>
<h4>Inside Azure Functions: the connector extension</h4>
<p>The Functions side has two layers. A host extension, written as a WebJobs extension, owns transport and scaling. A worker extension for each language turns payloads into typed objects for your handler.</p>
<h5>The host extension</h5>
<p>The host extension registers a `<span class="lia-text-color-15">connectorTrigger` </span>binding. Each function picks webhook or Poll delivery, and the binding starts the matching listener.</p>
<p>The Poll listener runs a receive loop. When the queue is empty it backs off with jitter, up to a configurable maximum interval, and receive failures get their own capped backoff. It authenticates to the polling endpoint with the connection's credential, usually the Function App's managed identity. A function that takes one event at a time can run several invocations in parallel, up to <span class="lia-text-color-15">`MaxConcurrentCalls`.</span> A batched function processes one batch at a time per listener. An event is acknowledged only after its invocation succeeds; a failed invocation leaves the event unacknowledged so it comes back when the lease expires. When an event holds a link to a large output, the listener downloads it, with a 100 MiB default cap.</p>
<p>Poll delivery also plugs into Azure Functions target-based scaling. The connector trigger reports how much work is waiting by reading the queue's approximate depth through the same Poll runtime API. Azure Functions does the scaling, aiming for <span class="lia-text-color-15">`ceil(depth / target)`</span> instances. The target is the function's pending-event threshold, or the per-instance concurrency that the platform supplies when it has one. Batch size and concurrency don't change that calculation.</p>
<p>&nbsp;</p>
<p>Batching therefore happens in several places. The source trigger can return a collection, <span class="lia-text-color-15">`splitOn` </span>can split it into separate runs, and the Poll listener can deliver several events to one invocation. The batch settings have the same meaning in every language:</p>

<h5>The worker extensions</h5>
<p>Because the host extension does the transport work, each language worker only has to bind payloads. The .NET isolated worker extension deserializes the payload into the type your function declares, such as a generated <span class="lia-text-color-15">`Office365OnNewEmailTriggerPayload`</span>, or into <span class="lia-text-color-15">`ConnectorEvent[]`</span> when you also want each Poll message ID. Python functions use the <span class="lia-text-color-15">`connector_trigger` </span>decorator from the <span class="lia-text-color-15">`azure-functions`</span> library. Other workers reach the same host extension through the Functions extension bundle and the <span class="lia-text-color-15">`connectorTrigger` </span>binding type.</p>
<p>The Node.js extension shows how thin this layer is. One generic wrapper registers the trigger and flattens every payload shape (a single item, a collection in `<span class="lia-text-color-15">body.value`</span>, or an array of Poll envelopes) into one list of items, keeping the original in <span class="lia-text-color-15">`rawPayload`.</span> Each connector's helper is then a few lines that add a friendly alias and borrow the item type from the generated SDK. This is the whole OneDrive for Business file:</p>
<pre>&nbsp;</pre>
import { BlobMetadata } from "@azure/connectors/generated/OneDriveForBusinessExtensions"; import { OneDriveFileTriggerContext } from "../../types"; import { createConnectorTrigger } from "./createConnectorTrigger"; const registerFileTrigger = createConnectorTrigger&lt;BlobMetadata, OneDriveFileTriggerContext&gt;( (context) =&gt; ({ ...context, files: context.items }), ); export const onNewFiles = registerFileTrigger; export const onUpdatedFiles = registerFileTrigger;
<p><span class="lia-text-color-15">`BlobMetadata`</span>&nbsp;comes from the same generated module that the OneDrive client uses for actions, so a trigger payload and an action response share one type, defined once from the connector's metadata.</p>
<h5>Calling out from the handler</h5>
<p>After reading the email, the handler posts a summary to Teams. That call leaves the Function App through the same connector platform, going the other way.</p>
<p>The handler calls a generated Teams client with typed input. The client holds the Teams connection's runtime URL and an Azure Identity credential, gets a Microsoft Entra token, usually for the Function App's managed identity, and sends the request. The Function App never holds a Teams token or secret.</p>
<p>The connection's access policies decide whether that identity may use the Teams connection, and the connection holds the OAuth consent for the account that posts. The connector runtime resolves the connection, replaces the caller's identity headers with a platform token, and runs the operation against Teams.</p>
<img />Post the summary to Teams: the handler calls the Teams SDK client, the request goes through the connector runtime using the Function App's identity and the Teams connection's consent, and the runtime posts the message to Teams
<p>This path doesn't depend on how the email arrived, so it works the same with webhook or Poll delivery and with any connector in the catalog. Idempotency is the handler's job. The SDK won't retry a failed post, but a redelivered event runs the whole invocation again, so the handler should check before posting the same summary twice.</p>
<h4>One generator, three SDKs</h4>
<p>The SDKs are generated. A shared generator in the Logic Apps codebase, <span class="lia-text-color-15">`CodefulSdkGenerator`</span>, reads live connector Swagger definitions through Azure Resource Manager, cleans them up, and emits clients for C#, Python, and TypeScript. Each SDK repository records what produced it in a generation manifest: the generator commits, the metadata API version, and a hash of every connector's Swagger input. That makes each regeneration traceable to a specific generator revision and a specific set of connector definitions.</p>
<p>Besides action methods, the generator emits models for request and response bodies, typed trigger payloads and trigger operation constants, catalog constants that list the available connectors, and support for paging and dynamic schemas. Each language then has a small handwritten runtime (the base client, the HTTP pipeline, errors, and paging) that the generated code builds on. Naming rules are kept consistent across languages, so the same connector and operation have recognizable names whether you write C#, Python, or TypeScript.</p>
<p>For setup, the VS Code connection manager and the connection-setup skill create the namespace and connection through the ARM preview API, open the OAuth consent page and check that the connection reports `Connected`, add access policies for your developer identity or the Function App's managed identity, and write the runtime URLs into local or deployed app settings.</p>
<h4>Recap</h4>
<p>When a customer writes in, the backing workflow detects the email through API Hub's existing connector trigger. The delivery action then either calls the Function App's webhook or writes to a per-trigger Storage queue that the host extension polls and scales on. The language worker binds the payload to a type that came from the same generator as the SDK, and the handler uses a generated Teams client whose calls go through the namespace's runtime proxy into API Hub.</p>
<p>Each piece reuses what was already there: the Logic Apps workflow engine for triggers, API Hub for connections and connector runtime, the Functions extension model and scale controller for hosting, and Azure Identity for credentials. The new parts are the namespace resources that tie them together, the delivery step, the Functions extension, and the generator that keeps every language's types in step with the connectors themselves.</p>

### Designing GitHub Actions Runners on Private AKS with a Secured Azure Virtual WAN Hub

<p>Self-hosted GitHub Actions runners can execute workflows close to private deployment targets without making those targets publicly reachable. That network access also makes the runner environment part of the security boundary. A workflow can use the connectivity and credentials available to its runner, so private connectivity needs to be considered alongside outbound access, repository permissions, and workload isolation.</p>
<p>A private Azure Kubernetes Service (AKS) cluster protects access to the Kubernetes API through private networking. It does not, by itself, restrict all traffic leaving the nodes or runner pods. In this single-region design, the AKS virtual network connects to a secured Azure Virtual WAN hub. Azure Firewall applies destination-based policies to Internet-bound connections, while authorized administrators reach the private API from a management host with the required network access.</p>
<p>Actions Runner Controller (ARC) manages ephemeral runners as Kubernetes pods and adjusts runner capacity to the jobs assigned by GitHub Actions. A dedicated user node pool separates runner execution from the pool selected for the controller and listener. Runner-pod scaling and AKS node scaling remain different mechanisms, with separate capacity and operational considerations.</p>
<p>The design brings together private API access, controlled GitHub egress, runner authentication, and firewall logging. Network-isolated AKS with a managed bootstrap cache and GitHub App authentication are selected options, not universal requirements for every private runner deployment. The sections below explain those choices and link their commands and configuration settings to official Microsoft and GitHub sources.</p>
<h2>Overall connectivity</h2>
<img /><em>Figure 1. Overall connectivity for GitHub Actions runners on private AKS with a secured Azure Virtual WAN hub.</em>
<p>The four numbered paths show how the environment is managed, reaches GitHub, retrieves bootstrap artifacts, and records firewall activity:</p>
<ol>
<li>Administrators reach the management VM through Azure Bastion or approved private access, then manage AKS through its private Kubernetes API.</li>
<li>The ARC controller, listener, and runner pods initiate outbound HTTPS connections to GitHub through the secured hub and Azure Firewall. No inbound GitHub job webhook is configured.</li>
<li>AKS nodes retrieve bootstrap artifacts through the private ACR endpoint. This cache does not replace GitHub Container Registry access for runner images.</li>
<li>Azure Firewall sends diagnostic logs to Log Analytics so operators can investigate allowed and denied connections.</li>
</ol>
<p>The private API and bootstrap-cache paths do not traverse the hub firewall. Management-tool Internet access and connections to deployment targets are not shown.</p>
<h2>Architecture scope and validation</h2>
<p>The architecture and configuration examples cover:</p>
<ul>
<li>Private Kubernetes API access from an authorized management host, without a public API endpoint</li>
<li>Internet-bound spoke traffic routed through the secured hub and GitHub-specific firewall application rules</li>
<li>ARC configuration and a manually triggered workflow targeting a dedicated runner node pool</li>
<li>Firewall evidence for allowed GitHub connections and controlled denied connections</li>
<li>Ephemeral runner lifecycle and its distinction from AKS node autoscaling</li>
</ul>
<p>The baseline uses GitHub.com, Azure public cloud, Linux nodes, organization-scoped runner registration, and shell-only workflow steps. It does not configure container builds, production deployment credentials, or hostile multi-tenant isolation.</p>

<h2>Prerequisites and assumptions</h2>
<p>The configuration examples assume:</p>
<ul>
<li>An Azure subscription with the permissions required for the network, firewall, AKS cluster, managed identity, and scoped role assignments</li>
<li>Sufficient regional VM quota and an approved budget for Azure Firewall, Virtual WAN, AKS nodes, the private bootstrap registry, monitoring, and management services</li>
<li>A GitHub organization and private repository, with a plan that supports creating the additional restricted runner group used here, such as GitHub Team or GitHub Enterprise</li>
<li>Permission to configure an approved ARC authentication method; the example chooses an organization-owned GitHub App</li>
<li>An approved Linux management host with private access to the AKS spoke, Azure CLI 2.73.0 or later, Helm 3, a compatible&nbsp;kubectl,&nbsp;kubelogin, and Bash</li>
<li>Outbound access from that management host to Azure sign-in and management services and GitHub's OCI chart distribution endpoints</li>
</ul>
<p>The host can be a VM in the spoke's management subnet, accessed through Azure Bastion or an existing approved private connection. A public SSH endpoint is not part of this design. A default, unconnected Cloud Shell session does not provide private cluster access. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/private-cluster-connect" rel="noopener" target="_blank">private AKS connectivity guidance</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/azure/bastion/tutorial-create-host-portal" rel="noopener" target="_blank">Azure Bastion connectivity</a>, and&nbsp;<a href="https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access" rel="noopener" target="_blank">runner-group availability and access</a>.</p>
<p>Command blocks illustrate configuration from that Bash host. They are not intended for direct execution without environment-specific review. Private keys and tokens do not belong in repositories, terminal history, or published screenshots.</p>
<p>[!WARNING] Setting runner capacity to zero does not stop firewall, hub, registry, monitoring, or system-node charges. These services have independent pricing and capacity requirements.</p>
<h2>Step 1: Network and AKS egress model</h2>
<p>Azure CNI Overlay separates node addressing from pod addressing. Nodes receive IP addresses from their VNet subnets, while pods use a separate CIDR range. Each additional runner pod therefore does not consume another VNet subnet address. This conserves spoke address space as runner capacity grows. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-ip-address-planning#overlay-networks" rel="noopener" target="_blank">Microsoft's Overlay subnet-sizing guidance</a>.</p>
<p>The address plan separates the hub, node pools, management access, pod network, and Kubernetes services:</p>
<ul>
<li>Secured virtual hub:&nbsp;10.60.x.x/22, for Virtual WAN hub services and Azure Firewall</li>
<li>AKS spoke VNet:&nbsp;10.61.x.x/16, for nodes and private management</li>
<li>System node subnet:&nbsp;10.61.x.x/24, for AKS services and the selected ARC controller and listener placement</li>
<li>Runner node subnet:&nbsp;10.61.x.x/23, for the dedicated Linux user node pool</li>
<li>Management subnet:&nbsp;10.61.x.x/24, for the approved private administration host</li>
<li>AzureBastionSubnet, if used:&nbsp;10.61.x.x/26, separate from the management subnet</li>
<li>Overlay pod address space:&nbsp;10.62.x.x/16</li>
<li>Kubernetes service range:&nbsp;10.63.x.x/24, with a DNS service IP represented as&nbsp;10.63.x.x</li>
</ul>
<p>Size each node subnet for that pool's maximum node count, additional nodes used during surge upgrades, and any other resources consuming addresses from the subnet. Azure reserves five addresses in each subnet, leaving 251 usable addresses in a&nbsp;/24&nbsp;before resources are allocated. Sizing only for the initial nodes can leave insufficient addresses for scaling or upgrades. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-azure-cni-overlay#cluster-nodes" rel="noopener" target="_blank">Overlay node-subnet planning</a>&nbsp;and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-ip-address-planning#upgrading-and-scaling-considerations" rel="noopener" target="_blank">AKS upgrade and scaling considerations</a>.</p>
<p>Size the pod CIDR for nodes across both the system and runner pools, including temporary surge nodes. Overlay allocates a fixed&nbsp;/24&nbsp;pod block to every node; lowering&nbsp;maxPods&nbsp;does not shrink that block. The networking model supports up to 250 pods per node, but that is not a recommendation to place 250 CI runners on one node. An ARC runner-pod limit does not replace node-level address planning. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-azure-cni-overlay#pods" rel="noopener" target="_blank">Overlay pod allocation</a>.</p>
<p>Choose a supported RFC 1918 or RFC 6598 pod range that does not overlap node subnets or connected networks. An overlap with a destination network can make that destination unreachable from pods even when the firewall allows it. Keep the Kubernetes service CIDR separate from the pod, node, and connected-network ranges. The DNS service IP must be inside the service CIDR and must not use its first service address. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-azure-cni-overlay#ip-address-planning" rel="noopener" target="_blank">Overlay address-planning requirements</a>&nbsp;and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-cni-overview#aks-cni-networking-prerequisites" rel="noopener" target="_blank">AKS reserved-range restrictions</a>.</p>
<h3>Network-isolated AKS with outbound type none</h3>
<p>The example selects a private, network-isolated AKS cluster with an AKS-managed bootstrap artifact cache and&nbsp;outboundType: none. Network isolation is an additional choice beyond a private API endpoint, not a prerequisite imposed by ARC or Virtual WAN.</p>
<p>Microsoft documents that&nbsp;none&nbsp;does not create an AKS egress path or require a default route during validation, and supports bring-your-own VNets. Required egress is supplied explicitly through a firewall, proxy, gateway, or other network component. Here, that component is the secured Virtual WAN hub. The private cache supplies AKS bootstrap images; GitHub traffic still needs the firewall path described below.</p>
<p>This is a different AKS outbound model from&nbsp;userDefinedRouting, not a claim that a vWAN-propagated default satisfies UDR validation. The&nbsp;userDefinedRouting&nbsp;model has its own node-subnet route-table requirements and is not an interchangeable option in the example.</p>
<p>See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/egress-outboundtype" rel="noopener" target="_blank">AKS outbound types</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-isolated" rel="noopener" target="_blank">network-isolated AKS</a>, and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/network-isolated" rel="noopener" target="_blank">the managed-cache creation guide</a>.</p>
<p>A conventional private AKS cluster can instead use another documented outbound model and permit its required AKS dependencies through the chosen egress controls. Changing to that model requires a different configuration and endpoint review; removing the cache flags from this example is not an equivalent substitution.</p>
<h2>Step 2: Secured hub and spoke connectivity</h2>
<p>The example separates networking into&nbsp;rg-arc-network&nbsp;and the cluster and identity into&nbsp;rg-arc-aks. The resources use the same selected region.</p>
<p>The configuration consists of:</p>
<ol>
<li>A&nbsp;<strong>Standard</strong>&nbsp;Virtual WAN with a secured virtual hub and&nbsp;<strong>Azure Firewall Standard</strong>. Azure Firewall Manager exposes the secured-hub creation flow. The&nbsp;/22&nbsp;address-space choice accommodates Microsoft's documented Azure Firewall scaling requirement in&nbsp;<a href="https://learn.microsoft.com/en-us/azure/virtual-wan/hub-settings#virtual-hub-address-space" rel="noopener" target="_blank">virtual hub address-space settings</a>. VPN and ExpressRoute gateways are separate requirements when the management design uses them.</li>
<li>An associated Firewall Policy with default-deny behavior, rather than an unrestricted outbound allow.</li>
<li>A spoke named&nbsp;vnet-arc-spoke, with system subnet&nbsp;snet-aks-system, runner subnet&nbsp;snet-aks-runners, and management subnet&nbsp;snet-management. The AKS node subnets are not delegated to another service.</li>
<li>A&nbsp;<strong>Virtual WAN &gt; Virtual network connections</strong>&nbsp;connection between the hub and spoke. This is not VNet peering to a customer-managed hub VNet.</li>
<li><strong>Azure-provided DNS</strong>&nbsp;for the baseline, with the management host in the same VNet as the AKS nodes.</li>
<li>Intra-cluster connectivity consistent with&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/azure-cni-overlay" rel="noopener" target="_blank">Azure CNI Overlay requirements</a>. NSGs must account for required communication between the system and runner subnets.</li>
</ol>
<p>The official&nbsp;<a href="https://learn.microsoft.com/en-us/azure/firewall-manager/secure-cloud-network" rel="noopener" target="_blank">secured cloud network tutorial</a> documents the portal creation flow. Resource names and some blade labels can vary as the portal evolves.</p>

<h2>Step 3: GitHub egress policy and logging</h2>
<p>The associated&nbsp;<strong>Firewall Policy &gt; Rule collection groups</strong>&nbsp;contains an&nbsp;<strong>Application</strong>&nbsp;rule collection with action&nbsp;<strong>Allow</strong>, for example at priority&nbsp;200. The rules use&nbsp;<strong>HTTPS:443</strong>&nbsp;and target FQDNs.</p>
<p>Rule sources are the system and runner subnet CIDRs, represented here as&nbsp;10.61.x.x/24&nbsp;and&nbsp;10.61.x.x/23. The controller and listener need GitHub connectivity as well as the runner pods. With Azure CNI Overlay, traffic leaving the cluster is translated to node addresses, rather than using the overlay pod CIDR as the firewall source for these flows.</p>
<p>The following destinations are a subset of GitHub's documented domains, grouped by function. Essential service traffic and the chart and image pulls used here need their corresponding rules. Action, artifact, package, and release functions need the relevant destinations when those functions are used; the table is not a claim that every job needs every row.</p>

<h3>Rule evaluation and inspection depth</h3>
<p>Azure Firewall evaluates network rules before application rules. An&nbsp;<strong>Any destination / TCP 443</strong>&nbsp;network allow can therefore bypass the intended application FQDN restriction. Inherited policies also affect evaluation. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/firewall/rule-processing" rel="noopener" target="_blank">rule processing</a>.</p>
<p>Standard performs SNI-based HTTPS destination filtering. It does not decrypt HTTPS payloads. Premium TLS inspection is a separate design, including certificate trust in nodes, controller, listener, runners, and tools that make inspected connections. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/firewall/features-by-sku" rel="noopener" target="_blank">features by SKU</a>.</p>
<h3>Diagnostic configuration</h3>
<p>Diagnostic settings belong to the&nbsp;<strong>Azure Firewall resource</strong>, not only the policy. The configuration includes:</p>
<ol>
<li>Application-rule and network-rule logs sent to an approved Log Analytics workspace</li>
<li><strong>Resource specific</strong>&nbsp;destination tables for the query example below</li>
<li>DNS-proxy logs when DNS proxy is enabled</li>
<li>Appropriate retention and access controls for network and workflow-related evidence</li>
</ol>
<p>Resource logs are not retained for query until a diagnostic destination is configured. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/firewall/monitor-firewall" rel="noopener" target="_blank">Azure Firewall monitoring</a>.</p>
<h2>Step 4: Routing intent and the default path</h2>
<p>The routing configuration includes:</p>
<ol>
<li><strong>Internet Traffic</strong>&nbsp;routing intent with the hub's&nbsp;<strong>Azure Firewall</strong>&nbsp;as next hop</li>
<li>The applicable&nbsp;<strong>Internet security / default-route propagation</strong>&nbsp;setting enabled on the spoke connection</li>
<li><strong>Private Traffic</strong>&nbsp;left unconfigured in this baseline; supported inter-spoke or hybrid private inspection is a separate policy decision</li>
<li>Gateway-route propagation enabled on any relevant spoke subnet route table</li>
<li>Effective routes showing the spoke's Internet default toward the virtual hub and the hub's Internet policy selecting Azure Firewall</li>
</ol>
<p>The NIC next-hop display need not show the firewall's private IP directly. The spoke-to-hub and hub-to-firewall parts need to be considered together. An unexplained manual default route to the secured-hub firewall is not part of this example.</p>
<p>See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/virtual-wan/how-to-routing-policies" rel="noopener" target="_blank">routing intent configuration and troubleshooting</a>&nbsp;and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-routing-problem" rel="noopener" target="_blank">NIC effective routes</a>.</p>
<p>The evidence described in Step 10 includes matching firewall records. A configured policy or a successful HTTPS request alone does not prove that the request traversed the firewall.</p>
<h2>Step 5: Private AKS and the managed bootstrap cache</h2>
<p>The managed bootstrap cache is&nbsp;<strong>not mandatory for every private AKS cluster</strong>. It is the selected bootstrap option for the network-isolated&nbsp;Cache&nbsp;plus&nbsp;none&nbsp;model used here. Microsoft also documents a bring-your-own private ACR option. ARC itself requires a suitable Kubernetes cluster, not an AKS bootstrap cache. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/network-isolated" rel="noopener" target="_blank">Microsoft's network-isolated cluster options</a>&nbsp;and&nbsp;<a href="https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/get-started#prerequisites" rel="noopener" target="_blank">GitHub's ARC prerequisites</a>.</p>
<p>An existing suitable cluster does not need to be recreated for ARC. The creation example below applies only when provisioning the selected cluster model; it is not a migration procedure for an existing cluster.</p>
<p>The Bash examples adapt Microsoft's documented commands to the resource names and choices in this design. The resource groups, VNet, subnets, hub connection, and firewall configuration are assumed to exist. CIDRs and the DNS service IP remain placeholders. The combined sequence is not ready-to-run deployment instructions.</p>
<p>The following block uses&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/authenticate-azure-cli-interactively" rel="noopener" target="_blank">Azure sign-in</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/account#az-account-set" rel="noopener" target="_blank">subscription selection</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/network/vnet#az-network-vnet-show" rel="noopener" target="_blank">VNet lookup</a>, and Microsoft's&nbsp;<a href="https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access#how-to-configure-private-subnets" rel="noopener" target="_blank">private-subnet configuration example</a>. The variable names and grouping are adaptations.</p>
export SUBSCRIPTION_ID="&lt;subscription-id&gt;"
export LOCATION="&lt;azure-region&gt;"
export NETWORK_RG="rg-arc-network"
export WORKLOAD_RG="rg-arc-aks"
export VNET_NAME="vnet-arc-spoke"
export AKS_NAME="aks-arc"
export POD_CIDR="&lt;pod-cidr&gt;"
export SERVICE_CIDR="&lt;service-cidr&gt;"
export DNS_SERVICE_IP="&lt;dns-service-ip&gt;"

az login
az account set --subscription "$SUBSCRIPTION_ID"

VNET_ID=$(az network vnet show \
  --resource-group "$NETWORK_RG" --name "$VNET_NAME" \
  --query id --output tsv)

SYSTEM_SUBNET_ID="${VNET_ID}/subnets/snet-aks-system"
RUNNER_SUBNET_ID="${VNET_ID}/subnets/snet-aks-runners"

az network vnet subnet update \
  --resource-group "$NETWORK_RG" --vnet-name "$VNET_NAME" \
  --name snet-aks-system --default-outbound false

az network vnet subnet update \
  --resource-group "$NETWORK_RG" --vnet-name "$VNET_NAME" \
  --name snet-aks-runners --default-outbound false
<p>The private-subnet setting removes reliance on implicit default outbound access. It does not block explicit firewall egress and is separate from making the AKS API private. This example sets it before creating nodes. For existing VMs, Microsoft documents that a stop and deallocation is required for subnet changes to take effect on their interfaces; this is not guidance to modify AKS-managed VM instances directly. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access" rel="noopener" target="_blank">default outbound access guidance</a>.</p>
<h3>Control-plane identity</h3>
<p>The user-assigned control-plane identity has&nbsp;<strong>Network Contributor on the example VNet</strong>. The VNet scope also supports the private DNS VNet-link operation; this is not a subscription-wide grant. Role-assignment and identity-use permissions are separate deployment prerequisites.</p>
<p>The commands adapt&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/user-assigned-managed-identity" rel="noopener" target="_blank">user-assigned managed identity creation</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/concepts-network-cni-overview#aks-cni-networking-prerequisites" rel="noopener" target="_blank">AKS VNet permissions</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/role/assignment#az-role-assignment-create" rel="noopener" target="_blank">role-assignment syntax</a>, and&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/aks#az-aks-get-versions" rel="noopener" target="_blank">regional Kubernetes version lookup</a>.</p>
AKS_IDENTITY_ID=$(az identity create \
  --resource-group "$WORKLOAD_RG" --name id-aks-arc \
  --location "$LOCATION" \
  --query id --output tsv)

AKS_IDENTITY_PRINCIPAL_ID=$(az identity show \
  --ids "$AKS_IDENTITY_ID" --query principalId --output tsv)

az role assignment create \
  --assignee-object-id "$AKS_IDENTITY_PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal \
  --role "Network Contributor" --scope "$VNET_ID"

az aks get-versions --location "$LOCATION" --output table
export KUBERNETES_VERSION="&lt;supported-regional-kubernetes-version&gt;"
<p>Role assignments have propagation delays. The Kubernetes version also needs to be a currently supported regional release, not an obsolete release merely because it exceeds the network-isolated minimum. <h3>Cluster configuration example</h3>
<p>Microsoft's&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/network-isolated?pivots=aks-managed-acr#deploy-a-network-isolated-cluster-with-aks-managed-acr" rel="noopener" target="_blank">AKS-managed ACR creation example</a>&nbsp;explicitly includes&nbsp;--bootstrap-artifact-source Cache,&nbsp;--outbound-type none, and&nbsp;--enable-private-cluster. The longer command below combines that example with documented&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/private-clusters" rel="noopener" target="_blank">private DNS and public-FQDN options</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/azure-cni-overlay" rel="noopener" target="_blank">Overlay options</a>, and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/entra-id-authorization" rel="noopener" target="_blank">Microsoft Entra authorization</a>.</p>
<p>All remaining switches are described in the&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/aks#az-aks-create" rel="noopener" target="_blank">official&nbsp;az aks create&nbsp;reference</a>. The selected node name, VM size, count, disk type, and maximum pods are example choices, not a Microsoft-prescribed ARC configuration.</p>
az aks create \
  --resource-group "$WORKLOAD_RG" \
  --name "$AKS_NAME" \
  --location "$LOCATION" \
  --kubernetes-version "$KUBERNETES_VERSION" \
  --assign-identity "$AKS_IDENTITY_ID" \
  --enable-private-cluster \
  --disable-public-fqdn \
  --private-dns-zone system \
  --bootstrap-artifact-source Cache \
  --outbound-type none \
  --network-plugin azure \
  --network-plugin-mode overlay \
  --pod-cidr "$POD_CIDR" \
  --service-cidr "$SERVICE_CIDR" \
  --dns-service-ip "$DNS_SERVICE_IP" \
  --vnet-subnet-id "$SYSTEM_SUBNET_ID" \
  --vm-set-type VirtualMachineScaleSets \
  --load-balancer-sku standard \
  --nodepool-name systempool \
  --node-count 2 \
  --node-vm-size Standard_D4s_v5 \
  --node-osdisk-type Managed \
  --os-sku Ubuntu \
  --max-pods 30 \
  --node-os-upgrade-channel NodeImage \
  --enable-aad \
  --enable-azure-rbac \
  --disable-local-accounts \
  --generate-ssh-keys
<p>Omitting a bootstrap registry resource ID selects the documented AKS-managed cache path. AKS manages its bootstrap registry, cache rules, and private connectivity. The default cache supplies Microsoft bootstrap images; it does not automatically mirror the GHCR controller and runner images. Those pulls need the GitHub egress rules from Step 3.</p>
<p>The two-node system pool is an illustrative minimum, not a production availability recommendation. Capacity needs to account for AKS services, the ARC controller, and the listener. Microsoft recommends three system nodes for production. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/use-system-pools" rel="noopener" target="_blank">system-pool requirements</a>, the&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/network-isolated" rel="noopener" target="_blank">network-isolated creation guide</a>, and the&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/aks#az-aks-create" rel="noopener" target="_blank">CLI parameter reference</a>.</p>
<h3>Installer access and private DNS</h3>
<p>The authorization and connectivity requirements are separate:</p>
<ol>
<li><strong>Azure Kubernetes Service RBAC Cluster Admin</strong>, scoped to the cluster, is one broad built-in role that permits the approved installer to install ARC CRDs and cluster-scoped RBAC. It is not a requirement to give every operator permanent cluster-admin access.</li>
<li>Cluster-user credential retrieval requires the corresponding management permission, such as&nbsp;<strong>Azure Kubernetes Service Cluster User Role</strong>&nbsp;when not already covered.</li>
<li>Assignment propagation affects access availability. These installer permissions are not workflow permissions.</li>
<li>The management host needs private API resolution and network reachability independently of its credentials.</li>
</ol>
<p>The credential and connection commands adapt&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/private-cluster-connect#create-a-vm-in-the-same-virtual-network" rel="noopener" target="_blank">private-cluster connectivity checks</a>&nbsp;and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/kubelogin-authentication?pivots=azure-cli" rel="noopener" target="_blank">kubelogin's Azure CLI authentication example</a>. The DNS lookup uses the documented nslookup check.</p>
<p>The expected state is private API resolution and nodes marked&nbsp;Ready. With Azure-provided DNS, AKS's default API private-zone link to the node VNet supplies API resolution. Registry resolution is a separate check: inspect the AKS-created bootstrap registry, its private endpoint, and the relevant private DNS records and VNet links. Both registry login and data-endpoint names must resolve to the intended private endpoints. Do not assume successful API resolution also verifies registry DNS.</p>
<p>Private API or bootstrap-image failures are distinct from ARC installation failures. Relevant references are&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/private-clusters" rel="noopener" target="_blank">private-cluster DNS</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/troubleshoot/azure/azure-kubernetes/extensions/troubleshoot-network-isolated-cluster" rel="noopener" target="_blank">network-isolated troubleshooting</a>, and&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/entra-id-authorization" rel="noopener" target="_blank">Microsoft Entra authorization for AKS</a>.</p>
<h2>Step 6: Dedicated runner user pool</h2>
<p>The configuration separates runner execution from the pool selected for the controller and listener. The runner pool is a Linux&nbsp;<strong>User</strong>&nbsp;pool on its own subnet, with a taint and Cluster Autoscaler bounds. This pool separation is a design choice, not an ARC installation requirement.</p>
<p>The command combines documented&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/azure-cni-overlay#add-a-new-node-pool-to-a-dedicated-subnet" rel="noopener" target="_blank">dedicated-subnet Overlay configuration</a>,&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/operator-best-practices-advanced-scheduler" rel="noopener" target="_blank">taints and tolerations</a>, and&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/aks/nodepool#az-aks-nodepool-add" rel="noopener" target="_blank">node-pool parameters</a>. The node count, VM size, taint value, and autoscaler bounds are illustrative.</p>
<p>The Helm values in Step 8 combine a runner-pool selector with the matching toleration. A toleration alone permits placement; it does not require that placement.</p>
<p>ARC scales runner pods. Cluster Autoscaler supplies node capacity for unschedulable pods. Their limits are independent, and neither is a hard spending cap. See&nbsp;<a href="https://learn.microsoft.com/en-us/azure/aks/cluster-autoscaler-overview" rel="noopener" target="_blank">AKS Cluster Autoscaler</a>&nbsp;and&nbsp;<a href="https://learn.microsoft.com/en-us/cli/azure/aks/nodepool#az-aks-nodepool-add" rel="noopener" target="_blank">node-pool commands</a>.</p>
<h2>Step 7: GitHub authentication and repository access</h2>
<p>A GitHub App is&nbsp;<strong>recommended, not mandatory</strong>, for repository- or organization-scoped ARC registration. GitHub also documents personal access token authentication, including classic and fine-grained tokens. Enterprise-level runner registration does not support GitHub App authentication; GitHub's ARC quickstart specifies a personal access token (classic) for that scope. See&nbsp;<a href="https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/authenticate-to-the-api" rel="noopener" target="_blank">ARC authentication methods</a>&nbsp;and the&nbsp;<a href="https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/get-started#installing-actions-runner-controller" rel="noopener" target="_blank">ARC quickstart</a>.</p>
<p>This example retains the recommended organization-owned GitHub App option. Its configuration includes:</p>
<ol>
<li><strong>Organization permissions &gt; Self-hosted runners: Read and write</strong>&nbsp;and&nbsp;<strong>Repository permissions &gt; Metadata: Read-only</strong>. The documented repository&nbsp;<strong>Administration: Read and write</strong>&nbsp;permission applies to repository-scoped registration, not the organization-scoped configuration used here.</li>
<li>An App installation in the organization, with its&nbsp;<strong>App ID</strong>,&nbsp;<strong>installation ID</strong>, and private key held securely outside the repository.</li>
<li>A runner group named&nbsp;arc-private, restricted to the intended private repository. App installation scope is not a substitute for runner-group access control.</li>
<li>GitHub credentials held in a Kubernetes Secret in the runner scale-set namespace.</li>
</ol>
<p>ARC scale-set job delivery uses outbound HTTPS long polling. A public inbound job webhook is not required by this mechanism; a separate integration can have different requirements. This flow is described in&nbsp;<a href="https://docs.github.com/en/actions/concepts/runners/actions-runner-controller#about-actions-runner-controller" rel="noopener" target="_blank">GitHub's ARC architecture</a>.</p>
<p>The Secret command adapts GitHub's&nbsp;<a href="https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets#option-1-create-a-kubernetes-secret-recommended" rel="noopener" target="_blank">documented file-based private-key example</a>. The names and variable substitutions are the changes; the Secret keys follow the documented format.</p>
<p>The example reads key contents from a file instead of putting the private key in a shell argument or Helm values. The file, Kubernetes Secret, Secret-reading permissions, and key rotation remain security responsibilities. See&nbsp;<a href="https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/authenticate-to-the-api" rel="noopener" target="_blank">ARC authentication</a>&nbsp;and&nbsp;<a href="https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access" rel="noopener" target="_blank">runner-group access controls</a>.</p>
<p>If an approved personal access token is used instead, the Secret uses the documented&nbsp;github_token&nbsp;key and the permissions required for the chosen registration scope. That is an alternative authentication configuration, not an additional credential required alongside the GitHub App.</p>
<p>This credential authenticates ARC to GitHub. It does not authorize an Azure deployment. Deployment jobs need a separate, least-privilege identity relationship, such as&nbsp;<a href="https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-openid-connect" rel="noopener" target="_blank">GitHub-to-Azure OIDC</a>, rather than general access through the installer, cluster, or kubelet identity.</p>

<h2>Step 9: Workflow targeting the private runner</h2>
<p>The workflow follows the&nbsp;<a href="https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/get-started#using-runner-scale-sets" rel="noopener" target="_blank">official ARC quickstart's verification workflow</a>, with a descriptive name, the example scale-set target, and an English output message. <p>Manual dispatch requires the workflow to be available on the repository's default branch. name: Private AKS runner verification

on:
  workflow_dispatch:

permissions: {}

jobs:
  verify-runner:
    runs-on: arc-private-aks
    timeout-minutes: 5
    steps:
      - run: echo "This job uses runner scale set runners."

<p>This workflow verifies job execution only. <p>Gateway API is the long-term Kubernetes standard for ingress and L7 traffic management. Compared with the traditional Ingress resource, Gateway API separates infrastructure entry points from routing configuration, giving platform and application teams clearer ownership boundaries and a more extensible model for managing application traffic.</p>
<p>&nbsp;Customers can now discover and configure Gateway API-based ingress solutions, view Gateway and HTTPRoute resources and better understand the ingress configuration of an AKS cluster without leaving the Portal.</p>
<h2>A new Ingress profile for AKS</h2>
<p>AKS offers two options for Gateway API implementations:</p>
<ul>
<li><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/aks/app-routing-gateway-api?pivots=azure-portal" target="_blank"><strong>Application Routing with Gateway API</strong></a>, an AKS-native path for cluster-hosted routing.</li>
<li><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/overview?toc=/azure/aks/toc.json&amp;bc=/azure/aks/breadcrumb/toc.json" target="_blank"><strong>Application Gateway for Containers</strong></a>, an Azure application-layer load balancing and traffic-management solution managed through the ALB Controller.</li>
</ul>
<p>To enable either Gateway controller, you can:</p>
<ol>
<li>Navigate to an AKS cluster in the Azure portal.</li>
<li>Select <strong>Networking</strong>.</li>
<li>Select <strong>Ingress profile</strong>.</li>
<li>Select <strong>Manage </strong>under <strong>Application Routing with Gateway API </strong>or<strong> Application Gateway for Containers</strong></li>
<li>Select <strong>Enable.</strong></li>
</ol>
<img />
<p>The portal will install the Managed Gateway API add-on as a prerequisite to using either Gateway API implementation, if not already installed. Once enablement is complete, you can return to the <span style="color: rgb(30, 30, 30);"><strong>Ingress profile</strong> on any cluster to easily understand which controller(s) are currently enabled and disable if desired.</span></p>
<h2>Gateways and HTTPRoutes are now visible under Kubernetes resources</h2>
<p>The AKS Kubernetes resources experience also now surfaces <strong>Gateways</strong> and <strong>HTTPRoutes</strong>, allowing customers to inspect the Gateway API resources running on their cluster directly from the Portal.</p>
