<p><em>This is Part 1 of a two-part series. Part 1 explains how Microsoft Perception works and why it matters to teams that run Azure infrastructure. Part 2 will connect it to a real image-automation pipeline.</em></p>
<h2>1. Why security operations need a different model</h2>
<p>If you run Azure platforms, you know this pattern. A scanner flags a vulnerable package in a golden image. An alert fires on a VM built from that image. Someone checks whether the alert is real, someone else works out how exposed the workload is, and a third person decides what to patch first. Each step is reasonable on its own. Together they are slow, because every hand-off waits for a person to pick up context that the previous person already had.</p>
<p>AI assistants have helped individual analysts move faster: you ask a question, you get a summary or a query. But the hand-offs remain. Attackers, meanwhile, are increasingly using automation of their own. The gap is less about how fast one person can work and more about how quickly an organisation can move from <em>signal</em> to <em>decision</em> to <em>fix</em>.</p>
<p>Microsoft Perception is Microsoft's answer to that gap. Instead of one assistant helping one person, it coordinates several specialised agents that share context and carry work from one stage to the next, while people stay in charge of the decisions that matter.</p>
<h2>2. What is Microsoft Perception?</h2>
<p>Microsoft Learn describes Perception as a coordinated, multi-agent defense system designed to help security teams protect continuously, respond faster, and reduce risk. It was introduced earlier this year as <em>Project Perception</em> and announced as Microsoft Perception at Microsoft Ignite 2026.</p>
<p>Three things are worth knowing up front:</p>
<ul>
<li><strong>It lives in the Microsoft Defender portal.</strong> You select <em>Perception</em> in the Defender navigation pane. There is no separate console to deploy.</li>
<li><strong>It works with agents that Microsoft publishes.</strong> These are purpose-built security agents, not general chatbots.</li>
<li><strong>Humans approve the important steps.</strong> Agents surface recommendations and ask for approval when needed, and every piece of work is recorded.</li>
</ul>
<p>Availability and licensing are changing quickly, so check the Microsoft Learn documentation linked at the end for the current status before you plan a rollout.</p>
<h2>3. Why multi-agent, and not one bigger assistant?</h2>
<p>Security work naturally splits into different ways of thinking. An attacker asks, "Where can I get in?" A defender asks, "Is this real and how bad is it?" An engineer asks, "What do I fix first so this can't happen again?" Each question needs different data, different tools and different judgement.</p>
<p>Putting all of that into a single assistant makes it a generalist that does everything adequately. Splitting it across specialised agents lets each one be good at a narrow job. The hard part then becomes coordination: getting the output of one agent into the next without losing context. That coordination is what Perception adds.</p>
<p>If you've built agentic systems yourself, the shape will feel familiar: specialised workers, shared state, a defined workflow and a human-in-the-loop checkpoint. The difference is that Perception packages this for security operations, with the agents, permissions and audit trail already built in.</p>
<h2>4. The three agent teams</h2>
<p>Perception borrows from classic security exercises and groups its agents into three teams. Microsoft Learn describes them as red team agents that expose vulnerabilities before attackers can exploit them, blue team agents that detect, triage and investigate threats, and green team agents that remediate and harden posture.</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="width: 100%; border-width: 1px;"><thead><tr><th>Team</th><th>Agent</th><th>What it does</th></tr></thead><tbody><tr><td>Red</td><td>Recon Agent</td><td>Scouts your environment the way an attacker would, surfacing attack paths, choke points, valuable assets, configuration issues and excess permissions.</td></tr><tr><td>Blue</td><td>Triage Agent</td><td>Classifies alerts as true or false positives and explains its reasoning, learning from context and feedback.</td></tr><tr><td>Blue</td><td>Threat Intelligence Agent</td><td>Turns threat intelligence into structured objects such as attack techniques, indicators and CVEs.</td></tr><tr><td>Blue</td><td>Attack Investigation Agent</td><td>Reconstructs the full attack story across alerts and incidents, with verdict, timeline and affected entities.</td></tr><tr><td>Blue</td><td>Detection Authoring Agent</td><td>Finds gaps in detection coverage and creates new detection rules.</td></tr><tr><td>Green</td><td>Posture Prioritization Agent</td><td>Ranks posture issues by real-world risk, exposure, exploitability and asset criticality, and explains what to fix first and why.</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>Together these form a closed loop: red finds weaknesses, blue checks what is actually happening, and green decides what to improve. Each pass makes the next one better informed.</p>
<h2>5. Architecture: sessions, agents and playbooks</h2>
<p>Perception organises all agentic work around three concepts. Once you understand these, the rest of the product makes sense.</p>
<img />
<h3>Agents</h3>
<p>An agent is a software entity that can reason, use tools and carry out tasks. Before a Perception agent can run, it needs its own <strong>agent identity and role assignment</strong>. That is an important design choice: an agent never borrows a user's permissions, and its access can be scoped, reviewed and removed like any other identity. If your organisation scopes access with Defender for Endpoint device groups or Defender unified RBAC, the agent identity has to be granted the scopes it needs.</p>
<h3>Playbooks</h3>
<p>A playbook is a reusable, agent-driven set of actions for a specific security objective. It assigns a team of agents a set of objectives and orchestrates them through the workflow. Some points from the documentation that matter for planning:</p>
<ul>
<li>Playbooks are <strong>preset by Microsoft</strong>. In the current release you can't create custom ones.</li>
<li>One playbook can use several agents, and one agent can appear in several playbooks.</li>
<li>Some playbooks need an <strong>input</strong> before they start, such as an incident ID, a threat intelligence article or an Azure subscription.</li>
<li>A playbook is only active when <strong>all</strong> of its required agents are set up and enabled.</li>
<li>All playbooks can be run manually, and some can also be triggered by automation rules.</li>
</ul>
<p>Examples of documented playbooks include <em>Triage alert</em>, <em>Investigate attack</em>, <em>Extract threat intelligence</em> and <em>Protect against a threat</em>. The last one is a good illustration of multi-agent work, covered in the next section.</p>
<h3>Sessions</h3>
<p>A session is the record of an agent interaction. It captures activity, decisions, inputs, outputs and any approvals or human interventions. A session can involve one agent or several working together, and its status reflects the state of all tasks inside it. For auditors and change managers, this is the most reassuring part of the design: every piece of agent work leaves a reviewable trail.</p>
<h3>Four ways in</h3>
<p>Inside the Defender portal, Perception has five main areas: <strong>New Chat</strong>, <strong>Sessions</strong>, <strong>Agents</strong>, <strong>Playbooks</strong> and <strong>Insights</strong>. You can start work by describing a task in natural language in Chat (Perception picks a playbook and fills in inputs), by running a playbook directly, by running a single agent, or by letting an automation rule start a playbook.</p>
<h2>6. How the agents collaborate: "Protect against a threat"</h2>
<p>The <em>Protect against a threat</em> playbook shows the model end to end. It takes a threat intelligence source and produces attack path analysis, posture findings, prioritised remediation and new detection rules. Four agents take part, and each one's output feeds the next:</p>
<ol>
<li><strong>Threat Intelligence Agent</strong> reads the threat report and extracts the techniques, indicators and CVEs involved.</li>
<li><strong>Recon Agent</strong> uses that intelligence to look for matching attack paths and exposures in your environment.</li>
<li><strong>Posture Prioritization Agent</strong> ranks the findings by real risk, so the team sees what to fix first and why.</li>
<li><strong>Detection Authoring Agent</strong> creates detection rules for the techniques that are not yet covered.</li>
</ol>
<p>Done by hand, this is several days of work across a threat intel analyst, a security engineer and a platform team. Here it becomes a single session that an analyst starts, watches and approves. The people are still there; they just spend their time reviewing conclusions instead of gathering evidence.</p>
<h2>7. Perception and Security Copilot</h2>
<p>A common question is how Perception relates to Microsoft Security Copilot. A simple way to think about it:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="width: 100%; border-width: 1px;"><thead><tr><th>Aspect</th><th>Security Copilot</th><th>Microsoft Perception</th></tr></thead><tbody><tr><td>Main role</td><td>Helps an analyst with a task</td><td>Coordinates agents through a security workflow</td></tr><tr><td>Interaction</td><td>You ask, it answers</td><td>You start a playbook or describe a goal; agents carry it forward</td></tr><tr><td>Unit of work</td><td>A prompt or a promptbook</td><td>A session driven by a playbook</td></tr><tr><td>Human role</td><td>Directs each step</td><td>Supervises, approves and redirects</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>They are complementary rather than competing. Many teams will use an assistant for ad-hoc questions and a coordinated system for repeatable workflows.</p>
<h2>8. Security and governance: keeping humans in control</h2>
<p>Handing security work to agents raises fair questions. Perception answers them in four ways:</p>
<ul>
<li><strong>Identity per agent.</strong> Each agent runs under its own identity and role, so its access is explicit and can be reviewed.</li>
<li><strong>Role-based access for people.</strong> Perception relies on Defender unified RBAC (URBAC), which must be enabled across all Defender workloads. Security Admins set up and remove agents; Security Readers can start and work with sessions. Starting a playbook needs Run access to every agent it uses.</li>
<li><strong>Approvals and stop controls.</strong> Agents pause and ask for input when a decision needs a person. Users can approve, reject, give alternative guidance or stop a session, which ends all ongoing agent work.</li>
<li><strong>A full audit trail.</strong> Sessions record what each agent did, with what input, and who approved what.</li>
</ul>
<p>For platform teams this matters as much as accuracy. An agent that can act but can't be audited is a risk; one that acts inside a clear identity, permission and approval model is something you can put in front of a change advisory board.</p>
<h2>9. What this means for Azure platform teams</h2>
<p>Most Perception material is written for security operations centres. It is just as relevant to teams that build and run Azure infrastructure:</p>
<ul>
<li><strong>Prioritising image and VM vulnerabilities.</strong> The Posture Prioritization Agent ranks issues by exposure and asset criticality, which is exactly the question a golden-image team asks: which CVE do we rebuild for first?</li>
<li><strong>Understanding real attack paths.</strong> The Recon Agent's view of attack paths, choke points and excess permissions helps platform teams see how a misconfigured subscription or identity can be used, not just that it exists.</li>
<li><strong>Cutting alert noise.</strong> The Triage Agent's false-positive filtering means infrastructure teams get pulled into fewer incidents that turn out to be nothing.</li>
<li><strong>Closing the loop with automation.</strong> Perception decides what matters; your pipelines (Packer, Azure DevOps, Bicep) still make the change. That hand-off from prioritised finding to automated, validated fix is where platform engineering adds value.</li>
</ul>
<h2>10. Getting ready</h2>
<p>If you want to try Perception, these are the documented prerequisites and first steps:</p>
<ol>
<li>Make sure you have access to the Microsoft Defender portal.</li>
<li>Enable Defender unified RBAC across all Defender workloads.</li>
<li>Have at least one Security Admin who can set up agent identities and permissions.</li>
<li>If you scope access with device groups or RBAC scopes, plan what each agent identity needs to see.</li>
<li>Start simple: ask a question in Chat, or run a single-agent playbook such as <em>Triage alert</em>, then review the session it creates.</li>
</ol>
<h2>Conclusion and what's next</h2>
<p>Microsoft Perception moves security AI from "help me do this task" to "coordinate this workflow, and check with me before anything important happens". Its building blocks are simple: agents with their own identities, Microsoft-published playbooks that coordinate them, and sessions that record everything. The red, blue and green teams give a structure that both security and platform engineers can reason about.</p>
<p>In <strong>Part 2</strong>, I'll take this into a hands-on scenario: taking a prioritised finding about a vulnerable VM image and connecting it to an automated rebuild-and-validate pipeline, so the loop runs from exposure to fix.</p>

<p><em>This is Part 2 of a two-part series. <strong>Part 1</strong> explained how Microsoft Perception works: red, blue and green team agents, Microsoft-published playbooks, and sessions that record every step. This part puts it to work for an Azure platform team.</em></p>

<h2>1. The gap between "fix this first" and the fix</h2>
<p>Perception is very good at answering one hard question: <strong>out of hundreds of findings, which ones actually matter?</strong> The Posture Prioritization Agent ranks issues by real-world risk, exposure, exploitability and asset criticality, and explains what to fix first and why.</p>
<p>For many Azure estates, though, the fix for a vulnerable VM does not happen on the VM. If your workloads run from a golden image in Azure Compute Gallery, patching machines one by one creates drift: the next scale-out or rebuild brings the vulnerability straight back. The durable fix is to <strong>rebuild the image, validate it, publish a new version and roll it out</strong>.</p>
<p>That is exactly the pipeline we built earlier in this blog series with Packer and Azure DevOps. This article connects the two: Perception decides what matters and a person approves it; a small, auditable bridge works out which images are affected and queues the existing image pipeline to rebuild them.</p>
<h2>2. What we are building</h2>
<img />
<p>The flow has five stages:</p>
<ol>
<li><strong>Decide</strong> – run a Perception playbook, review the session and approve the CVEs to act on.</li>
<li><strong>Find</strong> – use Defender advanced hunting to list the devices exposed to those CVEs.</li>
<li><strong>Map</strong> – use Azure Resource Graph to map those VMs to the Compute Gallery image they were built from.</li>
<li><strong>Rebuild</strong> – queue the image pipeline for each affected image, with the CVE IDs recorded as the reason.</li>
<li><strong>Verify</strong> – once the new image is rolled out, confirm in Defender that the exposure is gone.</li>
</ol>
<p>Two design rules run through every stage:</p>
<ul>
<li><strong>A person approves the hand-off.</strong> Nothing is rebuilt just because an agent said so. The bridge only acts on CVE IDs a person has reviewed in a Perception session.</li>
<li><strong>Only documented interfaces.</strong> The bridge uses public APIs (Microsoft Graph advanced hunting, Azure Resource Graph and the Azure DevOps Pipelines REST API). It does not depend on any undocumented Perception internals.</li>
</ul>
<h2>3. Prerequisites</h2>
<ul>
<li><strong>Perception</strong> enabled in your tenant, with Defender unified RBAC turned on and the agents used by your chosen playbook set up. Check Microsoft Learn for current availability.</li>
<li><strong>Defender Vulnerability Management data</strong> for your VMs (for example through Defender for Servers or Defender for Endpoint), so the <code>DeviceTvmSoftwareVulnerabilities</code> table is populated.</li>
<li><strong>An image pipeline</strong> in Azure DevOps that builds, validates and publishes to Azure Compute Gallery, such as the one from Part 1 of the image automation series.</li>
<li><strong>An identity for the bridge</strong> with:
<ul>
<li>Microsoft Graph application permission <code>ThreatHunting.Read.All</code> to run advanced hunting queries.</li>
<li><strong>Reader</strong> on the subscriptions that hold your VMs, for Resource Graph.</li>
<li>Permission to queue the image pipeline in Azure DevOps.</li>
</ul>
</li>
<li>Python 3.10 or later.</li>
</ul>
<h2>4. Step 1 – Decide in Perception</h2>
<p>Start in the Microsoft Defender portal and select <strong>Perception</strong>. Two documented playbooks fit this scenario well:</p>
<ul>
<li><strong>Plan for posture remediation</strong> builds a prioritised remediation plan across clouds, devices and AI, weighing exposure, exploitability and asset context.</li>
<li><strong>Protect against a threat</strong> starts from a threat intelligence source and produces attack path analysis, posture findings, prioritised remediation and new detection rules.</li>
</ul>
<p>Run the playbook from the <strong>Playbooks</strong> page (or describe the goal in <strong>New Chat</strong>), then open the session. Review the agents' reasoning and the prioritised list. Where agents ask for input, approve, reject or redirect them as you would with a colleague.</p>
<p>The output we need is small: <strong>the CVE IDs the team agrees to fix through the image pipeline</strong>. Record them with the session link in your change ticket. This is the human checkpoint, and the session gives you the audit trail for why the rebuild happened.</p>
<blockquote>
<p><strong>Tip:</strong> Not every finding belongs in the image pipeline. Configuration issues or excess permissions surfaced by the Recon Agent are usually fixed in Bicep, policy or identity settings. Send only software vulnerabilities baked into the image down this path.</p>
</blockquote>
<h2>5. Step 2 – Find the exposed devices</h2>
<p>Advanced hunting in Defender exposes vulnerability data in the <code>DeviceTvmSoftwareVulnerabilities</code> table, including the device, software, CVE ID and severity. Try the query in the portal first (<strong>Hunting &gt; Advanced hunting</strong>):</p>
<pre class="lia-code-sample language-kusto" contenteditable="false" tabindex="0"><code>// Devices exposed to the CVEs approved in the Perception session
let approvedCves = dynamic(["CVE-YYYY-NNNNN"]);   // replace with the CVE IDs from your session
DeviceTvmSoftwareVulnerabilities
| where CveId in~ (approvedCves)
| summarize Cves = make_set(CveId),
            Software = make_set(strcat(SoftwareName, " ", SoftwareVersion)),
            Severity = max(VulnerabilitySeverityLevel)
          by DeviceId, DeviceName, OSPlatform</code></pre>
<p>You should see each exposed VM, the vulnerable software and the CVEs that affect it. If the list is empty, check that the VMs are onboarded and reporting vulnerability data.</p>
<h2>6. Step 3 – Map devices to gallery images</h2>
<p>Defender knows which machines are vulnerable; Azure knows which image each VM came from. Azure Resource Graph joins the two quickly across subscriptions. This query lists every VM built from a Compute Gallery image, with its computer name for matching:</p>
<pre class="lia-code-sample language-kusto" contenteditable="false" tabindex="0"><code>resources
| where type =~ 'microsoft.compute/virtualmachines'
| extend computerName = tolower(tostring(properties.osProfile.computerName)),
         imageId      = tolower(tostring(properties.storageProfile.imageReference.id))
| where imageId contains '/galleries/'
| project name, resourceGroup, subscriptionId, computerName, imageId</code></pre>
<p>Matching on computer name is simple and works well when VM host names are unique, which is common in platform-managed estates. If your naming is less strict, add another key such as subscription or resource group. The query covers single VMs; extend it with <code>microsoft.compute/virtualmachinescalesets</code> if you run scale sets.</p>
<h2>7. Step 4 – The remediation bridge</h2>
<p>The bridge is a short Python script that runs both queries, groups the results by image definition and, only when asked, queues the image pipeline. It defaults to a <strong>dry run</strong>, so the first thing you see is a report, not a pipeline run.</p>
<pre class="lia-code-sample language-python" contenteditable="false" tabindex="0"><code>"""exposure_to_image.py - map approved CVEs to Compute Gallery images and queue rebuilds.

Dry run by default. Pass --queue to start the image pipeline for each affected image.
"""
import argparse, os, re, requests
from collections import defaultdict
from azure.identity import DefaultAzureCredential
from azure.mgmt.resourcegraph import ResourceGraphClient
from azure.mgmt.resourcegraph.models import QueryRequest

GRAPH = "https://graph.microsoft.com/v1.0/security/runHuntingQuery"
ADO_SCOPE = "499b84ac-1321-427f-aa17-267ca6975798/.default"   # Azure DevOps resource ID
IMAGE_RE = re.compile(r"/galleries/([^/]+)/images/([^/]+)")

def hunt(cred, cves):
    cve_list = ", ".join(f'"{c}"' for c in cves)
    query = f"""DeviceTvmSoftwareVulnerabilities
| where CveId in~ ({cve_list})
| summarize Cves = make_set(CveId) by DeviceId, DeviceName"""
    token = cred.get_token("https://graph.microsoft.com/.default").token
    r = requests.post(GRAPH, json={"Query": query},
                      headers={"Authorization": "Bearer " + token}, timeout=60)
    r.raise_for_status()
    # DeviceName is an FQDN; keep the host part to match the VM computer name
    return {row["DeviceName"].split(".")[0].lower(): row["Cves"]
            for row in r.json()["results"]}

def gallery_vms(cred, subscriptions):
    query = """resources
| where type =~ 'microsoft.compute/virtualmachines'
| extend computerName = tolower(tostring(properties.osProfile.computerName)),
         imageId = tolower(tostring(properties.storageProfile.imageReference.id))
| where imageId contains '/galleries/'
| project name, computerName, imageId"""
    client = ResourceGraphClient(cred)
    return client.resources(QueryRequest(subscriptions=subscriptions, query=query)).data

def queue_rebuild(cred, image_definition, cves):
    org, project, pipeline_id = (os.environ[k] for k in ("ADO_ORG", "ADO_PROJECT", "ADO_PIPELINE_ID"))
    token = cred.get_token(ADO_SCOPE).token
    url = f"https://dev.azure.com/{org}/{project}/_apis/pipelines/{pipeline_id}/runs?api-version=7.1"
    body = {"templateParameters": {"imageDefinition": image_definition,
                                   "triggerReason": "perception-remediation",
                                   "cveIds": ",".join(sorted(cves))}}
    r = requests.post(url, json=body, headers={"Authorization": "Bearer " + token}, timeout=60)
    r.raise_for_status()
    return r.json()["_links"]["web"]["href"]

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--cve", action="append", required=True, help="CVE ID approved in the Perception session")
    p.add_argument("--subscription", action="append", required=True)
    p.add_argument("--queue", action="store_true", help="queue pipeline runs (default: dry run)")
    a = p.parse_args()

    cred = DefaultAzureCredential()
    exposed = hunt(cred, a.cve)
    impact = defaultdict(lambda: {"vms": [], "cves": set()})
    for vm in gallery_vms(cred, a.subscription):
        cves = exposed.get(vm["computerName"])
        m = IMAGE_RE.search(vm["imageId"])
        if cves and m:
            key = f"{m.group(1)}/{m.group(2)}"          # gallery/imageDefinition
            impact[key]["vms"].append(vm["name"])
            impact[key]["cves"].update(cves)

    if not impact:
        print("No gallery-based VMs are exposed to the selected CVEs.")
    for image, info in impact.items():
        print(f"{image}: {len(info['vms'])} VM(s), CVEs {sorted(info['cves'])}")
        if a.queue:
            print("  queued:", queue_rebuild(cred, image.split("/")[1], info["cves"]))

if __name__ == "__main__":
    main()</code></pre>
<p>A few points about the design:</p>
<ul>
<li><strong>One rebuild per image, not per VM.</strong> Twenty exposed VMs from the same image result in one pipeline run.</li>
<li><strong>The reason travels with the run.</strong> The CVE IDs and trigger reason are passed as pipeline parameters, so they appear in the run history.</li>
<li><strong>Standard authentication.</strong> <code>DefaultAzureCredential</code> works with a managed identity, a workload identity in a pipeline, or your own sign-in for testing. No secrets are stored in the script.</li>
</ul>
<p>Run it:</p>
<pre class="lia-code-sample language-bash" contenteditable="false" tabindex="0"><code>pip install azure-identity azure-mgmt-resourcegraph requests
export ADO_ORG=&lt;your-org&gt; ADO_PROJECT=&lt;your-project&gt; ADO_PIPELINE_ID=&lt;image-pipeline-id&gt;

# 1. Dry run: see which images are affected
python exposure_to_image.py --cve CVE-YYYY-NNNNN --subscription &lt;subscription-id&gt;

# 2. After review, queue the rebuilds
python exposure_to_image.py --cve CVE-YYYY-NNNNN --subscription &lt;subscription-id&gt; --queue</code></pre>
<h2>8. Step 5 – Make the image pipeline remediation-aware</h2>
<p>The pipeline needs three new parameters and a way to record why each image version was built. Here is the relevant part, added to the Part 1 pipeline:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>parameters:
- name: imageDefinition
  type: string
- name: triggerReason
  type: string
  default: scheduled
- name: cveIds
  type: string
  default: ''

stages:
- stage: Build          # Packer build from Part 1, unchanged
  # ...
- stage: Validate       # existing validation stage from Part 1
  # ...
- stage: Promote
  dependsOn: Validate
  jobs:
  - deployment: Promote
    environment: image-promotion          # add an approval check on this environment
    strategy:
      runOnce:
        deploy:
          steps:

<p>Two details matter here:</p>
<ul>
<li><strong>The approval check on the promotion environment</strong> means a person still signs off before a new image version is promoted, even when the run was queued by automation.</li>
<li><strong>Tagging the image version</strong> with <code>remediatedCves</code> gives you a clear link from the Perception session, to the pipeline run, to the image version that fixed it.</li>
</ul>
<p>Because the pipeline still runs your validation stage, the rebuilt image goes through the same checks as any other release.</p>
<h2>9. Step 6 – Roll out and verify</h2>
<p>Roll the new image version out using your normal process: reimage, redeploy or update the scale set model. Then confirm the exposure has gone:</p>
<pre class="lia-code-sample language-kusto" contenteditable="false" tabindex="0"><code>let approvedCves = dynamic(["CVE-YYYY-NNNNN"]);
DeviceTvmSoftwareVulnerabilities
| where CveId in~ (approvedCves)
| summarize ExposedDevices = dcount(DeviceId) by CveId</code></pre>
<p>Vulnerability data is refreshed periodically, so allow time after rollout before you expect the count to reach zero. Finally, re-run the Perception playbook. The finding should drop out of the prioritised list, and the new session records that the loop is closed.</p>

<h2>11. Limitations and what to watch</h2>
<ul>
<li><strong>Preset playbooks.</strong> Perception playbooks are set by Microsoft and you cannot create custom ones in the current release, so the hand-off to the pipeline happens after the session rather than inside it.</li>
<li><strong>The hand-off is CVE IDs.</strong> The bridge deliberately uses public Defender and Azure APIs rather than any Perception-specific interface. If Microsoft publishes documented integration points for Perception output, the manual step could become an automation rule.</li>
<li><strong>Data freshness.</strong> Vulnerability data is not real time. Expect a delay between rollout and a clean result.</li>
<li><strong>Matching.</strong> Computer-name matching assumes unique host names. Test it against your naming standard before you rely on it.</li>
<li><strong>Not every fix is an image fix.</strong> Use this path for software baked into the image; use infrastructure-as-code or policy for configuration findings.</li>
</ul>
<h2>Conclusion</h2>
<p>Perception changes where a platform team's time goes. Instead of sorting a long vulnerability list, the team reviews a prioritised, explained set of findings in a session and approves what to act on. Everything after that is engineering the team already trusts: a query to find exposure, a map from VMs to images, and the same build, validate and promote pipeline used for every other release.</p>
<p>The result is a loop that runs from <strong>exposure to fix</strong>, with a person in control at the two points that matter (what to fix, and what to promote) and a clear audit trail from the Perception session to the image version that closed the gap.</p>

<h1 id="mcetoc_1k7sgd7jv_1"><span class="lia-text-color-15">Introduction</span></h1>
<p>Azure Route Server uses Border Gateway Protocol (BGP) to exchange routes dynamically with network virtual appliances (NVAs) and with ExpressRoute and VPN gateways in a virtual network (VNet).</p>
<p>For maximum resilience, many hybrid designs combine all three connectivity options: an ExpressRoute gateway, a VPN gateway, and NVAs (typically a pair). If one path fails because of maintenance, a hardware failure, or a software bug, traffic continues over the remaining paths. However, when every path advertises the same on-premises prefixes, you need a way to decide which path Azure uses first. This article shows how Route Server route maps give you that control.</p>
<p>Route maps for Azure Route Server let you filter routes and change BGP attributes, such as the AS path, on the routes that Route Server learns (inbound) or advertises (outbound). You can apply them to BGP peerings with NVAs and to the ExpressRoute and VPN gateway connections.</p>
<p>The focus is on path selection and failover, not throughput. For simplicity, only the hub VNet is shown; the same approach applies to hub-and-spoke topologies.</p>
<p>The following diagram shows the reference configuration:</p>
<img />
<p>On-premises sites can reach the hub VNet over three independent paths:</p>
<ul>
<li>ExpressRoute: a private connection through an ExpressRoute circuit and the ExpressRoute gateway, with no traffic crossing the public internet.</li>
<li>Site-to-site VPN: IPsec tunnels over the internet between the Azure VPN gateway and the on-premises VPN device or firewall.</li>
<li>NVAs: encrypted tunnels over the internet between the NVAs and the on-premises devices, using IPsec, WireGuard, or a proprietary protocol of your choice.</li>
</ul>
<p>Route Server exchanges routes with the NVAs using BGP and integrates the routes they advertise into the VNet. Route Server also peers automatically with the ExpressRoute and VPN gateways; this peering requires no configuration. By default, however, Route Server doesn't propagate routes between the NVAs, the ExpressRoute gateway, and the VPN gateway. To let these components learn each other's routes, enable route exchange (the <strong>branch-to-branch</strong> setting) on Route Server.</p>
<p>If each path advertises different on-premises prefixes, there is nothing to choose between: each network prefix has a single path. If that path fails, its routes are withdrawn and those prefixes become unreachable from Azure.</p>
<h1 id="mcetoc_1k7sgd7jv_2"><span class="lia-text-color-15">1. Routing Preference: how Route Server chooses among paths</span></h1>
<p>When Route Server is deployed and the same on-premises prefixes are advertised over multiple paths, its <strong><a class="lia-external-url" href="https://learn.microsoft.com/azure/route-server/hub-routing-preference" rel="noopener" target="_blank">Routing Preference</a></strong>&nbsp;setting determines which path is preferred. The Azure portal offers three options: ExpressRoute, VPN, and AS Path.</p>
<img />
<p><strong>Routing Preference</strong> controls only one direction: traffic from Azure to on-premises. Traffic from on-premises to Azure follows the routing policy configured on the on-premises devices. The rest of this article covers only the Azure-to-on-premises direction.</p>
<ul>
<li>By default, <strong>Routing Preference</strong> is set to <strong><u>ExpressRoute</u></strong>: Route Server prefers routes learned from ExpressRoute regardless of AS path length, even when the VPN gateway or the NVAs advertise the same prefixes with a shorter AS path.</li>
<li>With <strong>Routing Preference</strong> set to <strong><u>VPN</u></strong>, Route Server prefers routes learned from the VPN gateway and from the NVAs over routes learned from ExpressRoute, regardless of AS path length. This option doesn't distinguish between the VPN gateway and the NVAs: if both advertise the same prefix, Route Server selects the route with the shortest AS path.</li>
<li>With <strong>Routing Preference</strong> set to <strong><u>AS Path</u></strong>, Route Server selects the route with the shortest AS path, whichever connection it comes from. This is the option used in the rest of this article, because it lets route maps control path selection through AS path prepending.</li>
</ul>

<h1><span class="lia-text-color-15">3. Create a custom routing policy in the VNet</span></h1>
<p>The goal is to create a custom routing policy in the Azure VNet that sets an order of priority in path selection:</p>
<ul>
<li>ExpressRoute is the preferred path.</li>
<li>The site-to-site VPN path is used when the ExpressRoute path is unavailable.</li>
<li>The NVA paths are used when both the ExpressRoute and VPN paths are unavailable.</li>
</ul>
<p>This order is only an example; you can apply any priority sequence that fits your architecture requirements. When you prepend, don't use ASNs reserved by Azure: the public ASNs 8074, 8075, and 12076, and the private ASNs 65515, 65517, 65518, 65519, and 65520.</p>
<p>To enforce this order, apply inbound route maps that use AS path prepending, which adds copies of an ASN to the AS path so that BGP treats the route as less preferred. Each route map lengthens the AS path of 10.20.0.0/24 as Route Server receives it from a connection, giving every path a different AS path length:</p>
<ul>
<li>ExpressRoute: no route map needed. The AS path remains {12076, 12076} (length 2).</li>
<li>Site-to-site VPN: an inbound route map on the VPN connection prepends AS 65020 twice. The AS path becomes {65020, 65020, 65020} (length 3).</li>
<li>NVAs: an inbound route map on the nva100-1 and nva100-2 connections prepends AS 100 twice. The AS path becomes {100, 100, 100, 65020} (length 4).</li>
</ul>
<img />

<ul>
<li>Path 1<strong> (primary):</strong> Preferred because it has the shortest AS path.</li>
<li>Path 2<strong> (secondary):</strong> Used only if Path 1 is unavailable.</li>
<li>Path 3 <strong>(tertiary):</strong> Used only if both Path 1 and Path 2 are unavailable.</li>
</ul>

<h1><span class="lia-text-color-15">4. Summary</span></h1>
<p>With Routing Preference set to AS Path, inbound route maps that prepend the AS path let you set a path priority for traffic from Azure to on-premises. Key points to remember:</p>
<ul>
<li>Set <strong>Routing Preference</strong> to AS Path so that AS path length decides which path Route Server prefers.</li>
<li>Verify path selection in the effective routes of Route Server, not in the learned routes of each gateway, because each gateway applies its own BGP weights.</li>
<li>Use inbound route maps to prepend the AS path and set the priority. The ExpressRoute, VPN, NVA order used here is only an example; adjust the prepend lengths to match your own priorities.</li>
<li>This custom routing policy is local to the Azure VNet: it changes only how Route Server selects routes for traffic from Azure to on-premises, and it isn't propagated to on-premises. To avoid asymmetric routing, which stateful firewalls on either side can drop, configure the on-premises devices to prefer the same path order for traffic toward Azure, for example with BGP local preference.</li>
</ul>
