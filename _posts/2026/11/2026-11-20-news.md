### Announcing public preview of Azure DDoS Protection peacetime telemetry

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/announcing-public-preview-of-azure-ddos-protection-peacetime/ba-p/4574781](https://techcommunity.microsoft.com/t5/azure-networking-blog/announcing-public-preview-of-azure-ddos-protection-peacetime/ba-p/4574781)

<p><span>We're excited to announce the public preview of peacetime telemetry for Azure DDoS Protection. The DDoS traffic metrics you rely on during an attack now show your traffic during normal operation too. You can learn what normal looks like, set alerts and test your monitoring well before you need them.</span><span>&nbsp;</span></p>
<p><strong><span><span>Why it matters</span></span><span>&nbsp;</span></strong></p>
<p><span>Azure DDoS Protection already monitors your traffic around the clock and mitigates attacks automatically, and that doesn't change. Peacetime telemetry adds visibility on top of that protection. Your teams get an everyday view of the traffic reaching your public IPs, in the same metrics they use during an attack, so they can understand that traffic and prepare their monitoring ahead of time.</span><span>&nbsp;</span></p>
<p><strong><span><span>What's</span><span> new</span></span><span>&nbsp;</span></strong></p>
<p><span>Before this preview, the DDoS traffic metrics for a protected public IP address showed data only while a mitigation was active. Now they also show the traffic reaching the IP during normal operation: the total in Inbound packets DDoS, and a breakdown in Inbound TCP packets DDoS, Inbound SYN packets DDoS, Inbound UDP packets DDoS and Inbound other packets DDoS. "Other" covers all traffic that isn't TCP or UDP. At the same time, Under DDoS attack or not stays at 0, which means DDoS Protection doesn't report an attack.</span><span>&nbsp;</span></p>
<p><span>These are the metrics you already know, and nothing is renamed. For the full list, see the </span><a href="https://learn.microsoft.com/azure/ddos-protection/monitor-ddos-protection-reference" rel="noopener" target="_blank"><span><span>monitoring data reference</span></span></a><span>.</span><span>&nbsp;</span></p>
<p><strong><span><span>What you can do with it</span></span><span>&nbsp;</span></strong></p>
<ul>
<li><span>Learn your normal. Watch TCP, SYN, UDP and other traffic for each protected public IP over days and weeks, so you know your busy periods before an attack.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Compare traffic with mitigation triggers. Chart observed packet rates next to the trigger metrics for the same IP to see how everyday traffic compares with the thresholds that start mitigation.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Alert on traffic conditions. Create Azure Monitor metric alerts with thresholds that fit each workload. These alerts sit alongside your attack alerts; they don't replace them, and they don't change how mitigation starts.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Test your monitoring with everyday traffic. Check that your charts, workbooks and alerts receive data without simulating an attack.</span><span>&nbsp;</span></li>
</ul>

<ul>
<li><span>Both tiers. It works with DDoS Network Protection and DDoS IP Protection.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>The resources you already protect. It covers the </span><a href="https://learn.microsoft.com/azure/ddos-protection/ddos-protection-reference-architectures#protected-resources" rel="noopener" target="_blank"><span><span>same resources DDoS Protection supports today</span></span></a><span>.</span><span>&nbsp;</span></li>

### Introducing Azure SRE Agent in Azure Managed Grafana: The Dashboard as Command Center

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/introducing-azure-sre-agent-in-azure-managed-grafana-the/ba-p/4575039](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/introducing-azure-sre-agent-in-azure-managed-grafana-the/ba-p/4575039)
- **Published**: 2026-11-20 15:01:47
- **Fetched**: 2026-11-21 20:52:11

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>We're introducing the <a href="https://learn.microsoft.com/azure/managed-grafana/how-to-integrate-with-sre-agent" rel="noopener" target="_blank">Azure SRE Agent integration in Azure Managed Grafana</a>, now in preview. Pair an <a href="https://learn.microsoft.com/azure/sre-agent/overview" rel="noopener" target="_blank">Azure SRE Agent</a> with your Grafana workspace, and an agent icon appears in the toolbar of your dashboards. Select it, and the agent opens in a pane beside the dashboard you're looking at. It reads that dashboard and queries the same data sources, so you can ask it to investigate without writing the queries yourself. If you've given it the permissions, it can also act on what it finds, and it asks for your approval first.</p>
<h2>One screen, four prompts</h2>
<p>To try it, I built a small web app with a bug I planted: an Orders API on Azure App Service whose in-memory order cache is never evicted. I gave it a Grafana dashboard and a steady trickle of traffic, then waited. About 15 minutes later the dashboard turned red. I opened the agent pane and typed the least careful question I could:</p>
<blockquote>
<p>Order lookups have started failing. What's going on?</p>
</blockquote>
<p>I didn't name the app, the resource group, a table or a metric. About 30 seconds later:</p>
<img />
<p>The answer starts with the conclusion: "Order lookups are failing because the order cache grows without bound. Lookups scan a larger cache each time, and past a point they time out and return 503." Then it lists the evidence, and where each piece came from:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="width: 100%; border-width: 1px;"><thead><tr><th>Source</th><th>What the agent found</th></tr></thead><tbody><tr><td>Prometheus (the app's own metrics)</td><td><code>orders_cache_entries</code> rose from 147 to 1,587, and process uptime climbed steadily, so no restart had cleared it</td></tr><tr><td>Application Insights</td><td>P95 lookup time went from 288 ms to 805 ms to about 1.2 s; HTTP 503 responses first appeared in the 05:10 UTC bin</td></tr><tr><td>Console log in Log Analytics</td><td>14 <code>OrderCacheLookupTimeout</code> errors between 05:12 and 05:20, with a sample line: <code>scanned 656 of 658 cached orders in 1500 ms</code></td></tr></tbody></table></div>
<p>It also said what it hadn't done: "I did not read the code, so this is inferred from the telemetry." It named a mitigation (restart the app, which empties the cache), named the fix (bound the cache and replace the scan with a keyed lookup), and ended with: "I have not made any changes. I can restart the <code>orders-api-2611</code> web app if you approve."</p>
<p>So I typed the second prompt:</p>
<blockquote>
<p>Yes, restart it, then confirm from the dashboard's data that it recovered.</p>
</blockquote>
<p>The agent didn't run anything yet. It showed me the exact command and waited:</p>
<img />
<p>I selected <strong>Approve action</strong>. What happened next is the part I like most. The restart command returned success, and the agent still didn't call the incident over. It went back to the data and reported: "I can't confirm recovery. The restart command returned success, but the dashboard data shows the app has not recovered." The uptime gauge was still climbing and the cache was still growing. It was right. App Service brought the new process up about two minutes after the restart call, and the agent had checked before that.</p>
<img />
<p>Third prompt: "Don't restart again. Give it a moment and check the data once more." This time uptime had fallen from 1,391 seconds to 17, the cache had dropped from 1,764 entries to 19, P95 lookup time was back to between 207 and 462 ms, and there were no 503s in the last three minutes. The agent added a warning I hadn't asked for: "This restart only buys time." At the rate the cache refills, the failures would return in 10 to 15 minutes.</p>
<p>For the fourth prompt I gave it the exact times of the restart and asked for a short incident note for the ticket. It wrote a timeline, the cause, the mitigation, three follow-ups and a list of gaps in its own analysis, while the success rate beside it was back at 100%:</p>
<img />
<p>From the first question to the incident note took about 11 minutes. I wrote four sentences, no query, and I never left the dashboard.</p>
<h2>Same dashboard, two readers</h2>
<p>A dashboard is a team's understanding of a system, written down in a form that runs. Each panel is a query someone wrote because the answer mattered, pointed at the right resource and titled with the question it answers. I argued in <a href="https://techcommunity.microsoft.com/blog/appsonazureblog/dashboards-are-for-ai-agents-too-not-just-humans/4556383" rel="noopener" target="_blank">an earlier post</a> that this makes a dashboard a map for an AI agent as much as for a person. This integration puts both readers in front of the same map at the same time.</p>
<p>Here is how the agent gets there. Each conversation in the pane starts with a short block of host context that Grafana adds for you:</p>
<blockquote>
<p><code>The user is using the SRE Agent embedded chat in Grafana.</code><br /><code>Current Grafana URL: https://&lt;grafana-endpoint&gt;/d/orders-api/orders-api?from=now-30m&amp;to=now…</code></p>
</blockquote>
<p>The URL carries the dashboard, the time range and the variable values, so "this dashboard" and "the last 30 minutes" mean the same thing to the agent as they do to you. From there the agent works through the workspace's <a href="https://learn.microsoft.com/azure/managed-grafana/grafana-mcp-server" rel="noopener" target="_blank">MCP endpoint</a>, the same MCP tools other clients use. The pane shows each call as it happens. For my first prompt there were six:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="width: 100%; border-width: 1px;"><thead><tr><th>Calls</th><th>Tool</th><th>What it did</th></tr></thead><tbody><tr><td>1</td><td><code>amgmcp_dashboard_inspect</code></td><td>Read the dashboard: its panels, their queries, data sources and descriptions</td></tr><tr><td>3</td><td><code>amgmcp_prometheus_query</code></td><td>Queried the app's own metrics: cache entries, uptime, request rate by status</td></tr><tr><td>2</td><td><code>amgmcp_query_resource_log</code></td><td>Ran KQL for the Application Insights and console-log evidence</td></tr></tbody></table></div>
<p>Between the first and second call, the agent also read a note from its own memory. It's the same agent you use in the SRE Agent portal, with the same connectors, knowledge and memory. The pane is another door into it.</p>
<p>The dashboard itself is worth a look, because it is what made the investigation short. It has 16 panels over four sources, one row each:</p>
<ul>
<li><strong>What callers see</strong> comes from Application Insights: lookups by result code, and lookup time at P50, P95 and P99.</li>
<li><strong>What the platform sees</strong> comes from Azure Monitor platform metrics: the web app's memory working set, the App Service plan's CPU and memory, and HTTP 5xx at the front end.</li>
<li><strong>What the app says about itself</strong> comes from Prometheus, scraped from the app's <code>/metrics</code> endpoint into an Azure Monitor workspace: cached orders, cache size, lookup duration and uptime.</li>
<li><strong>What the logs say</strong> comes from Log Analytics: the console log and its errors grouped by kind.</li>
</ul>
<img />
<p>In this incident, no single source told the story. The platform metrics show memory climbing but not why. Application Insights shows callers failing but not what is filling up. The cache gauge in Prometheus is the cause, and the console log confirms it. Putting those four on one page is what Grafana is for. The agent inherits that work: one <code>amgmcp_dashboard_inspect</code> call tells it which sources exist, which queries matter and what each panel means.</p>
<h2>From reading to acting</h2>
<p>Reading and acting use different identities, and that is deliberate.</p>
<p><strong>Reading goes through Grafana.</strong> The agent's queries run through the workspace's data sources, with whatever identity each data source is configured with. If a data source can't see something, the agent can't see it through Grafana either.</p>
<p><strong>Acting uses the agent's own permissions.</strong> The restart ran as the agent's managed identity. The approval card says so: "Agent permissions will be used to complete this action." The Azure activity log agrees: the <code>Microsoft.Web/sites/restart/action</code> operation at 05:25:39 UTC lists that identity as the caller.</p>
<p>For this demo I gave that identity two roles, Reader and Website Contributor, scoped to the demo's resource group and nothing else. I also turned on the agent's Azure CLI tools in the SRE Agent portal and left the write tool's permission on <strong>Ask</strong>, which is why the restart waited for me. Before I did either, I asked the agent whether it could restart a web app. It checked its own role assignments and answered that it couldn't, and that the command would fail with a 403.</p>
<p>That is the shape I want from an agent that can touch production. It works with the permissions I've granted. It shows the command before it runs. It checks the result against the data, and it doesn't treat "the command succeeded" as "the problem is fixed".</p>
<h2>The command center</h2>
<p>Think about the big screen in an operations room. It shows the state of the system to everyone at once, and showing is all it does. The investigating and the acting happen at people's desks: in query editors, in the portal, in a terminal. Each step away from the screen costs context, and the person on call pays that cost at the worst possible time.</p>
<p>With the agent in the pane, the screen is where the work happens. You see the problem, ask about it, get the drill-down without writing the queries, approve an action, and watch the panels recover, all on one page. The dashboard gives the agent its context, and the agent makes the dashboard something you can act from.</p>
<h2>Set it up</h2>
<p>You need an Azure Managed Grafana workspace in the Standard tier and an Azure SRE Agent. Then there are three steps, and you do all three yourself: enabling the integration doesn't create connectors or role assignments for you.</p>
<ol>
<li><strong>Connect the agent to Grafana.</strong> In the <a href="https://sre.azure.com" rel="noopener" target="_blank">SRE Agent portal</a>, add the Azure Managed Grafana connector for your workspace. Choose <strong>Viewer</strong> for read-only access or <strong>Editor</strong> if the agent should also create and update dashboards. An MCP connector that points at <code>https://&lt;grafana-endpoint&gt;/api/azure-mcp</code> works too.</li>
<li><strong>Enable the integration.</strong> In the Azure portal, open your Grafana workspace, go to <strong>Integrations</strong> &gt; <strong>Azure SRE Agent (Preview)</strong>, select the agent and select <strong>Save</strong>. The portal checks for the connector and shows "SRE Agent has connected to Grafana" when it finds it.</li>
<li><strong>Give people access.</strong> Each person who uses the pane needs the <strong>SRE Agent Standard User</strong> role on the agent and a Grafana role on the workspace. Assign the role to a Microsoft Entra group if you can.</li>
</ol>
<p>Then open any dashboard and select the <strong>Azure SRE Agent</strong> icon in the toolbar. The full steps, including the Azure CLI command for the role assignment and how to turn the integration off, are in <a href="https://learn.microsoft.com/azure/managed-grafana/how-to-integrate-with-sre-agent" rel="noopener" target="_blank">Integrate Azure SRE Agent (preview) with Azure Managed Grafana</a>.</p>
<h2>What to know</h2>
<ul>
<li><strong>It's in preview.</strong> Expect changes, and check the agent's work. The pane says so itself: AI-generated content might be incorrect.</li>
<li><strong>Investigation works with the Grafana connector alone. Action needs more.</strong> To let the agent change anything in Azure, grant its identity a role on the target, as narrowly as you can, and decide which tools may run without asking.</li>
<li><strong>A restart is a mitigation.</strong> In my demo the cache started refilling the moment the app came back. The agent said so twice, and it was right.</li>
<li><strong>The pane keeps your conversation while the browser tab stays open.</strong> To go back to an earlier one, use <strong>My chats</strong> in the pane.</li>
</ul>
<h2>Try it</h2>
<p>Open one of your own dashboards and start with a prompt the pane suggests:</p>
<blockquote>
<p>Summarize this dashboard and highlight anything unusual</p>
</blockquote>
<blockquote>
<p>Which panels show spikes or anomalies in the current time range?</p>
</blockquote>
<p>Then ask about something you'd normally write a query for.</p>
