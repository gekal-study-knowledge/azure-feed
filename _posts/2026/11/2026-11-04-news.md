<p><span>I've seen customers move from L1 to L2 and pay less overall, with better storage efficiency, and I've seen the opposite. I<strong>t's an equation each customer has to solve before the purchase order,</strong> especially when a VMware renewal has already made cost the headline. And because the fee is per physical core, the CPU choice is a licensing decision too: cores the workloads don't need are a monthly cost, not a one-time one.</span><span>&nbsp;</span></p>
<p><span>Two billing details catch people out. New registrations get a 60-day free trial, so the meter starts later than the deployment. And retiring an instance is a billing event too: if you stop using it without deleting its Azure resource, billing continues until it has been disconnected for more than 31 days. <strong>Delete what you decommission.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><strong><span class="lia-text-color-8">People are part of the cost&nbsp;</span></strong></p>
<p><span>Many teams rush to Azure Local because the VMware renewal date is coming, planning to migrate first and figure it out afterwards. That bill arrives later, as training under pressure, avoidable mistakes and outages. Engineers with 25 or 40 years of VMware experience are an asset, but Azure Local is a different beast, and the <strong>mindset shift is a lot like the move from on-premises to the cloud.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><span><strong>Upskill before Day 1</strong>, not after the first incident. Arc Jumpstart LocalBox is a good place to start: it deploys a complete Azure Local sandbox, nested inside a single Azure VM, so the team can practice deployment, VM provisioning, updates and break-fix without touching production (Which is also a common pattern - no Dev/test clusters planned as part of the PO)</span></p>
<h4><span><span><span class="lia-text-color-8"><strong>Mistake 1:</strong></span> <strong>Selling a hypervisor, not a hybrid platform</strong></span></span><span>&nbsp;</span></h4>
<p><span>The most common expectation I hear is some version of "a vSphere look-alike we deploy once and run however we like." Azure Local isn't that, and pretending otherwise sets the project up for disappointment.</span><span>&nbsp;</span></p>
<p><span>The way I explain it: Hyper-V on Windows Server 2025 is a set of building blocks. It's Lego, and you can design it however you want as long as you respect the foundational patterns. Azure Local runs on the same Hyper-V engine, but it was designed from day one as a complete solution and a true extension of Azure. That brings a cloud-like experience on-premises, with obligations attached.</span><span>&nbsp;</span></p>

</td><td class="lia-border-color-6" style="height: 67.2266px;">

<p><strong><span>VM management</span><span>&nbsp;</span></strong></p>

</td><td class="lia-border-color-6" style="height: 67.2266px;">

</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p><span><strong>The VM management model deserves its own decision record</strong>, because it shapes recovery and migration later. Azure Local VMs enabled by Azure Arc are created and managed through Azure:<span class="lia-text-color-11"><strong> the portal, Azure CLI or any IaC tool that can interact with ARM APIs</strong></span>. Their lifecycle operations (create, start and stop, delete, NIC and disk changes, vCPU and memory changes, extensions) belong there. Hyper-V Manager, Failover Cluster Manager, Windows Admin Center and PowerShell <span class="lia-text-color-8"><strong>are supported only for the operations on Microsoft's supported list.</strong></span> <strong><span class="lia-text-color-12">A few things aren't supported with any tool:</span></strong> changing a NIC's VLAN ID, live-migrating a VM to another cluster, storage live migration, changing the disk type, and cloning. Live migration between machines of the same instance is fine.</span><span>&nbsp;</span></p>
<p><span>Hyper-V VMs created locally run on the same hypervisor but don't show up as Azure Local VMs. You can Arc-enable their guest OS to bring Azure management services to them, but their lifecycle stays local. Neither model is wrong. Mixing them without rules is how you end up with VMs nobody can recover the same way twice.</span><span>&nbsp;</span></p>
<p><u><span>N.B : The Hyper - VM living in Azure Local today can become hydrated to Azure Local native VMs once the hydration feature is out.</span></u></p>
<h4><span class="lia-text-color-11"><strong>What to do instead&nbsp;</strong></span></h4>
<ul>
<li><span>Run a fit workshop before the hardware conversation, covering workloads, the VM management model, connectivity and the update lifecycle.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Record the VM management model for each workload class, with the reasons.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Be explicit about the 30-day sync. If a site genuinely can't connect, that's a different design conversation, and you want it now, not after delivery.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>If the customer is weighing Azure Local against Hyper-V on Windows Server 2025, score both honestly.<strong> Sometimes the Lego set is the right answer.</strong></span></li>
</ul>

<h4><strong><span><span><span class="lia-text-color-8">Mistake 3: </span>Skipping the Azure landing zone discussion</span></span><span>&nbsp;</span></strong></h4>
<p><span>This is the one I push hardest, because of Arc. Every Azure Local instance projects its resources into Azure, into an environment that's <strong><u>either </u></strong>well structured or not. If you're plugging into an existing Azure estate, <span class="lia-text-color-8"><strong>the plumbing has to be right.</strong></span></span><span class="lia-text-color-8"><strong>&nbsp;</strong></span></p>
<p><span>Azure Local has historically been driven by OEMs and partners, and many only ask the customer for a subscription ID and enough permissions to deploy. <span class="lia-text-color-8"><strong>The instances land somewhere in Azure and nobody assesses the risks</strong></span>. I've also seen a VM recovery stall because its image lived in a different resource group.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<img /><span><span>Figure 2. An Azure Local instance lands inside your Azure governance: management groups, policy, RBAC and resource group layout all apply from day one.</span></span>
<p>&nbsp;</p>
<h5><span class="lia-text-color-11"><strong>Under the hood&nbsp;</strong></span></h5>
<p><span><span class="lia-text-color-8"><strong>Placement is permanent</strong></span>.</span><span> The Azure Local FAQ is explicit: moving resources between subscriptions or resource groups isn't supported for any Azure Local resource. To change location, you redeploy the instance into the new subscription and resource group. <span class="lia-text-color-11"><strong>Decide the layout once, deliberately.</strong></span></span><span class="lia-text-color-11"><strong>&nbsp;</strong></span></p>
<p><span>Prerequisites belong in the landing zone, not the deployment call.</span><span> The subscription needs these resource providers registered:</span><span>&nbsp;</span></p>
$providers = "Microsoft.HybridCompute", "Microsoft.GuestConfiguration", "Microsoft.HybridConnectivity", "Microsoft.AzureStackHCI", "Microsoft.Kubernetes", "Microsoft.KubernetesConfiguration", "Microsoft.ExtendedLocation", "Microsoft.ResourceConnector", "Microsoft.HybridContainerService", "Microsoft.Attestation", "Microsoft.Storage", "Microsoft.Insights", "Microsoft.KeyVault" foreach ($p in $providers) { az provider register --namespace $p }

<p><span>Policy reaches the nodes.</span><span> Each machine is an Arc-enabled server, so <span class="lia-text-color-8"><strong>any policy assignment that targets Arc machines, at management group or subscription scope, applies to your cluster nodes as well</strong></span>. <span class="lia-text-color-6"><strong>Azure Local isn't a standard Arc-enabled server, though</strong></span>. Updates are a good example: <strong>Microsoft's guidance is not to update Azure Local through Azure Update Manager's Machines pane or the Arc machine's Updates pane (nor through SConfig, Windows Admin Center or manual Cluster-Aware Updating runs), because that can install unsupported out-of-band updates and add billing for periodic assessment and patching. <h4><strong><span class="lia-text-color-11">What to do instead&nbsp;</span></strong></h4>
<ul>
<li><span>Start the conversation in Azure, before the OEM deploys anything: <strong>are landing zones in place? is the Cloud Adoption Framework followed? does the Sovereign Landing Zone apply?</strong></span><strong><span>&nbsp;</span></strong></li>
</ul>
<ul>
<li><span>Settle the subscription and resource group layout knowing you can't move it later.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Separate deployment roles from operations roles, and make elevated access time-bound using <strong>PIM and a structured SG layout.</strong></span></li>
</ul>
<ul>
<li><span>Review every inherited policy assignment that targets Arc machines, and<strong> add exemptions where a policy assumes a regular server.</strong></span><strong><span>&nbsp;</span></strong></li>
</ul>
<ul>
<li><span>Decide who may deploy extensions to nodes and VMs, and <strong>audit it.</strong></span><strong><span>&nbsp;</span></strong></li>
</ul>
<ul>
<li><strong><span>Bring the landing-zone owner to the first design workshop, not the deployment call.</span><span>&nbsp;</span></strong></li>
</ul>
<h4><strong><span><span><span class="lia-text-color-8">Mistake 4:</span> DNS that can't change after deployment</span></span><span>&nbsp;</span></strong></h4>
<p><span>Most people working with Azure Local have heard this one, and it still keeps happening. <span class="lia-text-color-8"><strong>The DNS servers you give the infrastructure at deployment can't be changed afterwards.</strong></span> If they must change, <strong><u>you're looking at a rebuild.</u></strong>&nbsp;</span></p>
<p><span>Three versions of the same story. One customer was advised not to change host DNS after deployment, did it anyway, and some VMs lost external connectivity. Another retired a domain controller without realizing it was one of the cluster's infrastructure DNS servers, and DNS went unhealthy. <p><span>Preparation is well documented, and the tooling does the heavy lifting:</span><span> <a href="https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-prep-active-directory?view=azloc-2610" rel="noopener" target="_blank">Prepare Active Directory for Azure Local deployment - Azure Local | Microsoft Learn</a></span></p>
Install-Module AsHciADArtifactsPreCreationTool -Repository PSGallery -Force New-HciAdObjectsPreCreation -AzureStackLCMUserCredential (Get-Credential) -AsHciOUName "&lt;OU name or distinguished name including the domain components&gt;"
<p><span style="color: rgb(30, 30, 30);">It creates a dedicated OU that blocks inherited GPOs and holds the deployment user.<strong> Keep one instance per OU</strong>. Believe it or not, the pattern keeps repeating anyway. Six months after a clean deployment, someone links a new GPO at the domain root, the Azure Local OU inherits it, and the next call is <strong><span class="lia-text-color-8">"my resource bridge VM is offline."</span></strong></span><strong><span class="lia-text-color-8">&nbsp;</span></strong></p>
<p><span>The detail people miss: <u><strong>blocking inheritance doesn't stop a GPO whose link is set to Enforced</strong></u>. Check what actually reaches the OU, not what you think reaches it:</span><span>&nbsp;</span></p>
(Get-GPInheritance -Target "OU=AzL-Prod01,DC=contoso,DC=com").InheritedGpoLinks | Format-Table DisplayName, Enforced, Target
<p><span>Replication is the other trap. Adding a node once failed validation until OU permission changes had replicated to every domain controller. Run </span><span>repadmin /replsummary</span><span> before you blame the product. And if Active Directory itself is the blocker, deployment with local identity, without AD, has been generally available since release 2604.</span><span>&nbsp;</span></p>
<p><strong><span><span>Firewall and proxy</span></span><span>&nbsp;</span></strong></p>
<p>&nbsp;</p>
<img /><span><span>Figure 5. Arc gateway shrinks the allow-list, but some endpoints are always reached directly.</span></span>
<p><span>Static IP allow-lists quietly go stale (Most modern firewalls support dynamic lists), <strong>because the addresses behind Microsoft's endpoints change over time</strong>. The firewall requirements page links per-region endpoint lists, so build rules on FQDNs, keep them under change control, and review them with each release.</span><span>&nbsp;</span></p>
<p><span>Arc gateway changes the shape of the problem. It's generally available for new deployments, and since release 2610 it can be enabled on existing instances. Once enabled there, it can't be turned off, so rehearse it first. With the gateway, an Arc proxy on each machine sends most traffic to a single gateway FQDN, <u><strong>but some endpoints still go through your proxy or firewall directly:</strong></u></span><u><strong><span>&nbsp;</span></strong></u></p>
<ul>
<li><span>Bootstrap: aka.ms and azurestackreleases.download.prss.microsoft.com</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Arc registration: login.microsoftonline.com, the regional login endpoint, management.azure.com, gbl.his.arc.azure.com and the regional his.arc.azure.com endpoint</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>The gateway URL itself, your Key Vault and your cloud witness storage account</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>HTTP certificate revocation endpoints, because the gateway doesn't carry HTTP traffic</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>For AKS extensions, the regional &lt;region&gt;.obo.arc.azure.com endpoint on port 8084</span><span>&nbsp;</span></li>
</ul>
<p><span>The gateway doesn't work with TLS-terminating proxies, so plan for no TLS inspection on that path. Azure Arc private link scopes aren't supported by Azure Local either, and Arc endpoints must resolve to public IPs through whatever proxy you run.</span><span>&nbsp;</span></p>
<p><span>The proxy bypass list is set during Arc registration, and its format trips people up. It must include the IP address and NetBIOS name of every machine and of the cluster, plus the infrastructure IPs or the whole infrastructure subnet. Entries are comma-separated and wildcards work, <span class="lia-text-color-8"><strong>but CIDR notation and "&lt;local&gt;" don't:</strong></span></span><span class="lia-text-color-8"><strong>&nbsp;</strong></span></p>
Invoke-AzStackHciArcInitialization &lt;...&gt; -Proxy "http://proxy.contoso.com:8080" ` -ProxyBypass "localhost,127.0.0.1,*.contoso.com,node01,node02,azlclus01,10.20.10.*"
<p><span>Changing proxy settings after deployment is possible from release 2610, but it's far easier to get right the first time.</span><span>&nbsp;</span></p>
<p><span>Two smaller items cause outsized pain. The first is a reachable, verified time source: <strong>check it with </strong></span><strong><span>w32tm /query /status</span></strong><span><strong> on every machine</strong>. The second is the <span class="lia-text-color-8"><strong>OEM's in-band path from the operating system to the iDRAC or iLO</strong></span>, which the Solution Builder Extension (SBE) relies on during updates.</span><span>&nbsp;</span></p>
<p><strong><span><span>Validate in week one</span></span><span>&nbsp;</span></strong></p>
<p><span>Deployment runs its own validation, but that's the worst possible day to discover a blocked endpoint or a missing OU permission. Run the Environment Checker yourself in week one, when there's still time to fix what it finds, and again before every update:</span><span>&nbsp;</span></p>
Install-Module -Name AzStackHci.EnvironmentChecker -Repository PSGallery -Force Invoke-AzStackHciConnectivityValidation Invoke-AzStackHciHardwareValidation Invoke-AzStackHciSoftwareValidation Invoke-AzStackHciNetworkValidation Invoke-AzStackHciArcIntegrationValidation Invoke-AzStackHciExternalActiveDirectoryValidation # takes your OU, domain and naming parameters
<h4><span class="lia-text-color-8"><strong>Mistake 7: <span class="lia-text-color-21">No headroom in storage or network&nbsp;</span></strong></span></h4>
<p><span>Sizing usually happens once, right before the hardware order. <span class="lia-text-color-8"><strong>Then the migration starts and the cluster fills up with workloads nobody accounted for.</strong></span></span><span class="lia-text-color-8"><strong>&nbsp;</strong></span></p>
<p><span>Two things are usually missing. <u><strong>The first is repair:</strong></u> nodes go down for maintenance, disks fail, and Storage Spaces Direct needs free capacity to rebuild into. <u><strong>The second is growth.</strong></u> Azure Local keeps adding reasons to run more on it, from Azure Virtual Desktop and AKS to Foundry Local, and a cluster sized only for today's migration has nowhere to put them. On one cluster we reviewed, the pool was close to 80% full with every drive bay populated, so the only way to grow was a whole new node, with the budget and lead time that come with it.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<img /><span><span>Figure 6. With a three-way mirror, usable capacity is a fraction of raw. Illustrative only; size real designs with the Azure Local sizer.</span></span>
<h4><strong><span class="lia-text-color-6">Storage, under the hood&nbsp;</span></strong></h4>
<p><span>With three or more machines,<strong> the usual resiliency is a three-way mirror:</strong> three copies of every write, 33.3% storage efficiency. On top of that, Microsoft's guidance is to leave unallocated reserve in the pool equal to one capacity drive per server, up to four drives, so repairs have somewhere to go.</span><span>&nbsp;</span></p>
<p><span>Run the numbers in Figure 6 and two things stand out. The reserve is capped at four drives, so it weighs less as the cluster grows: going from four to five nodes adds 20.5 TB of usable capacity while the reserve stays at 30.7 TB. And doubling the drives per node more than doubles usable capacity. <strong>Efficiency belongs in the same equation as cost, and empty drive bays are the cheapest growth path you'll ever have.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><span>To see where a pool stands today:</span><span>&nbsp;</span></p>
Get-StoragePool -IsPrimordial $false | Select-Object FriendlyName, @{n='SizeTB'; e={[math]::Round($_.Size/1TB,1)}}, @{n='AllocatedTB'; e={[math]::Round($_.AllocatedSize/1TB,1)}}, @{n='FreeTB'; e={[math]::Round(($_.Size-$_.AllocatedSize)/1TB,1)}}
<p><u><strong><span>If the free space is smaller than one capacity drive per node (up to four), you're already eating into repair capacity.</span><span>&nbsp;</span></strong></u></p>
<h4><span class="lia-text-color-6"><strong>Network, under the hood:</strong></span></h4>
<p><span>I regularly find 25 GbE ports left idle, storage on 10 GbE while management and compute got the 25 GbE links, or a storage MTU left at the default. <strong>Network ATC makes the intent explicit, so start there:</strong></span><strong><span>&nbsp;</span></strong></p>
Get-NetIntent # which adapters carry management, compute and storage Get-NetIntentStatus # did the intent apply cleanly on every machine? Get-NetAdapterRdma # is RDMA enabled where storage expects it? Get-NetAdapterAdvancedProperty -RegistryKeyword "*JumboPacket"
<p><span><strong>Match storage bandwidth to drive density</strong>, <u><strong>put the fastest ports on storage, and keep jumbo frames consistent from adapter to switch</strong></u>. The deployment offers 1514, 4088 or 9014 bytes on the adapters, and Microsoft's guidance uses a 9216-byte MTU on the switch side for RDMA storage traffic.</span><span>&nbsp;<br /></span></p>
<p><u><strong><span><span>Network intents: design for what </span><span>you'll</span><span> enable later</span></span><span>&nbsp;</span></strong></u></p>
<p><span>Network ATC intents feel like plumbing, but they decide which features you can turn on later. In a recent case, a cluster went live with four intents: management, compute, storage, and a fourth for an isolated backup network used by a third-party backup appliance. Months later, SDN enabled by Arc stopped during enablement because it found more than three intents, and the project was blocked.</span><span>&nbsp;</span></p>
<p><span><strong>Before SDN is enabled,</strong> the way out is manageable: remove the extra intent and its virtual switch, enable SDN, then add the backup intent back. <strong>After SDN is enabled, the options narrow</strong>. Enablement can't be rolled back or disabled, and the virtual switches carry the policies the Network Controller pushes, so removing or recreating one isn't a change to make casually. Remember too that SDN resources live on a single virtual switch, and NSGs apply to Azure Local VMs on it, so a VM that only sits on a separate backup switch won't get them.&nbsp;</span></p>
<p><span><span class="lia-text-color-6"><u><strong>If SDN is anywhere on the roadmap</strong></u></span>, check the intent design against its supported networking patterns before deployment. Microsoft Learn lists these intent configurations as unsupported for SDN enabled by Arc:</span><span>&nbsp;</span></p>

<h4><strong><span><span><span class="lia-text-color-8">Mistake 9:</span> Updating without a readiness routine</span></span><span>&nbsp;</span></strong></h4>
<p><span><strong>Azure Local updates are a lifecycle, not Patch Tuesday.</strong> Each release is supported for six months, and the rule is strict: <strong>outside that window, Microsoft Support can only help you update to a supported version, even in the middle of an outage.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><span>That said, nobody has to patch every month. <span class="lia-text-color-6"><strong>You need to stay inside the six-month window</strong></span>, with a maintenance routine that fits your own change calendar. What hurts is having neither: no defined window, no readiness check, and a team constantly chasing the latest release.</span><span>&nbsp;</span></p>
<p><span>The worst case I've seen was an estate where most clusters were failing updates on mixed versions, security updates were more than a month late, and a go-live was slipping. Looking back at the update escalations I've been part of, very few came down to a single product defect. Most traced back to readiness, drift or coordination: a VLAN change that broke the resource bridge, a certificate lost during rotation, a capacity alert disabled instead of addressed, or hosts reimaged from the same OEM image ending up <span class="lia-text-color-8"><strong>on different hotfix levels.</strong></span></span><span class="lia-text-color-8"><strong>&nbsp;</strong></span></p>
<p>&nbsp;</p>
<img /><span><span>Figure 7. Stay inside the six-month window, and run the same routine before every maintenance window.</span></span>
<h4><span class="lia-text-color-6"><strong>Under the hood&nbsp;</strong></span></h4>
<p><span>A solution update isn't just an OS patch. It covers the <u>operating system</u>, the <u>core agents</u> and <u>services (including the Connected Machine agent and the Arc resource bridge)</u> and, where the OEM integrates, the <u>Solution Builder Extension with drivers and firmware</u>. <span class="lia-text-color-8"><strong>Out-of-band updates to individual components aren't supported</strong></span>. The typical cadence is a cumulative update every month and a feature update twice a year. Within a feature release train you can skip ahead to a later release, <strong>but you must install the last cumulative update before moving to the next feature update.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><span>Use the Azure Local view in Azure Update Manager to update at scale, or PowerShell on a node:</span><span>&nbsp;</span></p>
# Where are we, and what's available? Get-SolutionUpdateEnvironment Get-SolutionUpdate | Format-Table DisplayName, State # Download and run the readiness checks without installing Get-SolutionUpdate -Id &lt;update-id&gt; | Start-SolutionUpdate -PrepareOnly # Install, then follow progress Get-SolutionUpdate -Id &lt;update-id&gt; | Start-SolutionUpdate Get-SolutionUpdate -Id &lt;update-id&gt; | Format-Table DisplayName, State
<p><span>When a run stops, </span><span>Get-SolutionUpdateRun</span><span> gives you the details of where it stopped. </span><span>Start-SolutionUpdate</span><span> also has an </span><span>-IgnoreWarnings</span><span> switch. <span class="lia-text-color-8"><strong>Use it only when you understand every warning it would skip.</strong></span></span><span class="lia-text-color-8"><strong>&nbsp;</strong></span></p>
<p><span>Before the window, <strong>I also check the storage layer directly,</strong> because an update that starts on a degraded pool is an escalation waiting to happen:</span><span>&nbsp;</span></p>
Get-StorageJob | Where-Object JobState -ne 'Completed' # no repairs still running Get-VirtualDisk | Where-Object HealthStatus -ne 'Healthy' # every volume healthy Get-HealthFault # open faults on the cluster
<h4><strong><span class="lia-text-color-6">What to do instead&nbsp;</span></strong></h4>
<ul>
<li><span>Check: run the Environment Checker, the health checks and the OEM prerequisites, and clear open faults.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Fix drift first: versions, VLANs, certificates and disabled alerts.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Rehearse on the test cluster, on the same version as production.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Update production inside the window, and keep every cluster on the same version.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Validate afterwards: live migration, the resource bridge and your workloads.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Check the Azure Local Supportability repository on GitHub before and after each window, for known issues and troubleshooting guides.</span><span>&nbsp;</span></li>
</ul>

<h4><strong><span class="lia-text-color-6">Under the hood: backup and recovery&nbsp;</span></strong></h4>
<p><span><strong>Backup scope drifts</strong>. VMs moved or re-created on another cluster can silently fall out of the backup job meant to protect them, <strong>so check scope after every migration wave</strong>. Microsoft Azure Backup Server (MABS) V4 can protect Azure Local VMs and Hyper-V VMs at host or guest level, and many customers use partner products. Know your restore path before you need it: <strong>restoring an Azure Local VM to an alternate location with MABS or ASR gives you a VM that's no longer managed from Azure.</strong></span><strong><span>&nbsp;</span></strong></p>
<p><span>For disaster recovery, <span class="lia-text-color-6"><strong>Azure Site Recovery for Azure Local became generally available in October 2026.</strong></span> It replicates Windows and Linux VMs (Generation 1 and 2) to Azure, fails over there, and fails back to the same or an alternate host.</span><span>&nbsp;</span></p>
<p><span><span class="lia-text-color-8"><strong>BitLocker recovery keys often stay inside the cluster they protect</strong>.</span> If the cluster is down and the domain controllers run on it, the keys may be out of reach exactly when you need them. <strong>Export them from a local console, an RDP session or a CredSSP remote session, and store them outside the cluster, for example in Azure Key Vault</strong>:</span><span>&nbsp;</span></p>
Get-AsRecoveryKeyInfo | Format-Table ComputerName, PasswordID, RecoveryKey 
<p><u><span>Starting with release 2609, automatic backup of the keys to a backup key vault is also available.</span></u></p>
<h4><strong><span class="lia-text-color-6">What to do instead&nbsp;</span></strong></h4>
<ul>
<li><span>Treat Day 2 as part of Day 1. Turn on Insights and the health alerts, add the recommended alert rules, and route them to an action group somebody reads - I would just get notified through a teams chat or through an SMS sent to my Phone. <u>(Use the Azure Native power)</u></span></li>
</ul>
<ul>

</ul>

### Implementing Traefik as an Ingress Controller on Azure Kubernetes Service (AKS)

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/implementing-traefik-as-an-ingress-controller-on-azure/ba-p/4570088](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/implementing-traefik-as-an-ingress-controller-on-azure/ba-p/4570088)
- **Published**: 2026-11-04 15:49:05
- **Fetched**: 2026-11-05 22:36:24

<details class="entry-summary">
<summary>詳細を表示</summary>
<h2>Prerequisites</h2>
<p>Before starting the implementation, ensure you have:</p>
<ul>
<li>An existing Azure Kubernetes Service (AKS) cluster with a user node pool available for ingress workloads.</li>
<li>kubectl configured with access to the AKS cluster.</li>
<li>Helm 3 installed and access to the Traefik Helm repository.</li>
<li>Permissions to create Kubernetes resources, including Deployments, Services, Secrets, and Traefik CRDs.</li>
<li>An application already deployed in AKS and exposed through a Kubernetes Service.</li>
<li>An Azure virtual network and subnet configured for the AKS internal Load Balancer.</li>
<li>Appropriate Azure permissions to create and configure an Internal Load Balancer and Azure Private Link Service.</li>
<li>Azure Front Door Premium, if implementing the private origin integration described in this article.</li>
<li>Required TLS certificates and Kubernetes TLS secrets for HTTPS routing.</li>
</ul>
<p><strong>Note:</strong> The Azure networking and Front Door components require appropriate permissions and configuration in the target Azure environment.</p>
<h1>1. Architecture overview</h1>
<p>The solution uses the following traffic flow:</p>
<p><strong>Client → Azure Front Door Premium → Azure Private Link → AKS Internal Load Balancer → Traefik → Kubernetes Service → Application Pod</strong></p>
<p>The main components are:</p>
<ul>
<li><strong>Azure Front Door Premium:</strong> Provides the entry point for application traffic and supports private connectivity to the origin.</li>
<li><strong>Azure Private Link Service:</strong> Enables private connectivity to the AKS-hosted ingress endpoint.</li>
<li><strong>Internal Azure Load Balancer:</strong> Exposes Traefik through a private IP address within the virtual network.</li>
<li><strong>Traefik:</strong> Handles incoming HTTP/HTTPS traffic and routes requests based on hostnames and URL paths.</li>
<li><strong>Kubernetes Service:</strong> Provides internal connectivity to the application pods.</li>
</ul>
<h2>2. Deploying Traefik using Helm</h2>
<p>I used the official Traefik Helm chart to deploy Traefik into a dedicated Kubernetes namespace.</p>
<p>First, add the Traefik Helm repository:</p>
<p>helm repo add traefik<strong> https://traefik.github.io/charts </strong>helm repo update</p>
<p>Create a dedicated namespace:</p>
<p><strong>kubectl create namespace ingress-system</strong></p>
<p>For a production deployment, I used a custom values.yaml file to configure the deployment, service, node selection, and Kubernetes providers.</p>
<h3>Key Helm configuration</h3>
<p>deployment: replicas: 2 nodeSelector: kubernetes.azure.com/agentpool: application ingressClass: enabled: true isDefaultClass: true providers: kubernetesCRD: enabled: true allowCrossNamespace: true kubernetesIngress: enabled: true service: enabled: true type: LoadBalancer annotations: service.beta.kubernetes.io/azure-load-balancer-internal: "true" service.beta.kubernetes.io/azure-load-balancer-health-probe-protocol: "tcp" service.beta.kubernetes.io/azure-pls-create: "true" service.beta.kubernetes.io/azure-pls-name: "aks-ingress-private-link" spec: externalTrafficPolicy: Local</p>
<p>The internal load balancer subnet annotation should be added according to the target AKS environment.</p>
<h3>Important configuration considerations</h3>
<ul>
<li>Two replicas provide availability across application workloads.</li>
<li>The node selector ensures Traefik is scheduled on the intended user node pool.</li>
<li>Kubernetes CRD and Ingress providers allow Traefik to discover routing configurations.</li>
<li>The internal load balancer annotation ensures Traefik is exposed through a private IP.</li>
<li>The Private Link Service annotation enables private connectivity to the ingress endpoint.</li>
<li>externalTrafficPolicy: Local helps preserve the original client source IP at the Kubernetes service forwarding layer.</li>
</ul>
<h2>3. Deploy Traefik</h2>
<p>Once the Helm values file is ready, deploy Traefik:</p>
<p>helm upgrade --install traefik traefik/traefik \ --version 41.6.0 \ --namespace ingress-system \ --values values.yaml \ --wait \ --timeout 10m</p>
<p><strong>Validate the deployment:</strong></p>
<p>kubectl get pods -n ingress-system kubectl get svc -n ingress-system kubectl get deployment -n ingress-system</p>
<p>The Traefik service should receive a private IP address from the configured subnet.</p>
<h2>4. Configure application routing using IngressRoute</h2>
<p>Traefik supports Kubernetes Custom Resource Definitions (CRDs), including IngressRoute, which provides more flexible routing capabilities.</p>
<p>For this implementation, I used an IngressRoute to route requests based on the hostname and URL path.</p>
<p>Example:</p>
<p><strong>apiVersion: traefik.io/v1alpha1 kind: IngressRoute metadata: name: application-route namespace: application-namespace spec: entryPoints: - websecure routes: - match: Host(`internal.example.com`) &amp;&amp; PathPrefix(`/api`) kind: Rule middlewares: - name: api-to-v1 services: - name: application-backend port: 4545 tls: secretName: application-tls</strong></p>
<p>Update the hostname, namespace, backend service, port, and TLS secret to match the application environment.</p>
<p>The configuration ensures that HTTPS requests matching the specified hostname and /api path are forwarded to the corresponding Kubernetes Service.</p>
<h2>5. Configure Traefik Middleware for URL rewriting</h2>
<p>In this implementation, the application expected requests to reach its /v1 API endpoints, while incoming requests used the /api prefix.</p>
<p>I used Traefik's Middleware CRD with a regular expression to rewrite the request path.</p>
<p>Example:</p>
<p><strong>apiVersion: traefik.io/v1alpha1 kind: Middleware metadata: name: api-to-v1 namespace: application-namespace spec: replacePathRegex: regex: '^/api(/(.*))?$' replacement: '/${2}'</strong></p>
<p>This configuration removes the /api prefix before forwarding the request to the backend.</p>
<p>For example:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table><tbody><tr><th>Incoming request</th><th>Rewritten path</th></tr><tr><td>/api/health</td><td>/health</td></tr><tr><td>/api/orders</td><td>/orders</td></tr><tr><td>/api</td><td>/</td></tr></tbody></table></div>
<p>This allows the application to retain its existing API structure without requiring changes to the application code.</p>
<h2>6. Integrating Azure Private Link Service</h2>
<p>To enable private connectivity to the AKS ingress endpoint, I configured Azure Private Link Service on the internal load balancer.</p>
<p>The relevant Kubernetes Service annotations are:</p>
<p>service.beta.kubernetes.io/azure-load-balancer-internal: "true" service.beta.kubernetes.io/azure-pls-create: "true" service.beta.kubernetes.io/azure-pls-name: "aks-ingress-private-link"</p>
<p>The Azure Private Link Service is associated with the internal load balancer frontend.</p>
<p>This provides a private connectivity option for consumers that need to access the application without exposing the AKS ingress endpoint directly to the public internet.</p>
<p>The Private Link Service configuration and connection approval must also be validated on the Azure side.<br /><br /></p>
<h2>7. Configuring TLS Termination in Traefik</h2>
<p>TLS termination is an important part of the ingress architecture. It allows Traefik to handle HTTPS connections, manage certificates, and forward requests to backend Kubernetes services.</p>
<p>In this implementation, Azure Front Door Premium handles the client-facing TLS connection and establishes a separate HTTPS connection to the AKS origin. Traefik terminates this origin-side TLS connection using a Kubernetes TLS Secret.</p>
<h3>How TLS works in this architecture</h3>
<ol>
<li>The client sends an HTTPS request to Azure Front Door.</li>
<li>Azure Front Door terminates the client-facing TLS connection.</li>
<li>Front Door establishes a new HTTPS connection to the AKS origin through Private Link.</li>
<li>Traefik receives the HTTPS request and terminates TLS using the configured certificate.</li>
<li>Traefik applies the routing rules and forwards the request to the application Kubernetes Service.</li>
</ol>
<h3>Step 1: Create a Kubernetes TLS Secret</h3>
<p>Traefik uses a Kubernetes TLS Secret containing the certificate and private key.</p>
<p>kubectl create secret tls application-tls \ --cert=tls.crt \ --key=tls.key \ --namespace application-namespace</p>
<p>The secret contains:</p>
<ul>
<li>tls.crt: TLS certificate.</li>
<li>tls.key: Corresponding private key.</li>
</ul>
<p>Ensure the certificate is valid for the hostname configured in the IngressRoute.</p>
<h3>Step 2: Configure TLS in IngressRoute</h3>
<p>Reference the TLS Secret in the IngressRoute configuration:</p>
<p>apiVersion: traefik.io/v1alpha1 kind: IngressRoute metadata: name: application-route namespace: application-namespace spec: entryPoints: - websecure routes: - match: Host(`internal.example.com`) &amp;&amp; PathPrefix(`/api`) kind: Rule middlewares: - name: api-to-v1 services: - name: application-backend port: 4545 tls: secretName: application-tls</p>
<p>The websecure entry point handles HTTPS traffic, while secretName tells Traefik which Kubernetes TLS Secret to use for the certificate.</p>
<h3>Step 3: Validate the TLS configuration</h3>
<p>Check whether the TLS Secret exists:</p>
<p>kubectl get secret application-tls \ -n application-namespace</p>
<p>Inspect the IngressRoute:</p>
<p>kubectl describe ingressroute application-route \ -n application-namespace</p>
<p>Check Traefik logs for certificate or routing-related errors:</p>
<p>kubectl logs deployment/traefik \ -n ingress-system</p>
<h3>Important considerations</h3>
<ul>
<li>The certificate hostname must match the hostname used for the Front Door origin connection.</li>
<li>The certificate must be trusted by Azure Front Door, with a valid certificate chain.</li>
<li>The certificate and private key must be stored securely.</li>
<li>The TLS Secret must exist in the same namespace as the IngressRoute referencing it.</li>
<li>Configure certificate renewal and rotation before certificates expire.</li>
<li>For production, avoid disabling certificate subject name validation at Azure Front Door.</li>
</ul>
<p>With this configuration, Traefik handles HTTPS termination at the AKS ingress layer, while application routing remains managed through Kubernetes CRDs.</p>
<h2>8. Integrating Azure Front Door Premium</h2>
<p>Azure Front Door Premium was configured to use the private AKS ingress endpoint as an origin.</p>
<p>The important configuration areas include:</p>
<ul>
<li>Creating an origin group for the AKS-hosted application.</li>
<li>Configuring the origin hostname and host header.</li>
<li>Enabling Private Link for the origin.</li>
<li>Selecting the appropriate Private Link Service.</li>
<li>Configuring HTTPS on port 443.</li>
<li>Setting up the health probe.</li>
<li>Associating the origin group with the relevant Front Door route.</li>
<li>Configuring the required WAF and security policies.</li>
</ul>
<p>This provides a managed entry point for application traffic while keeping the AKS ingress endpoint private.</p>
<h2>9. Validation and troubleshooting</h2>
<p>After deployment, I validated the components at different layers rather than relying only on the Helm deployment status.</p>
<h3>Kubernetes validation</h3>
<p>Check Traefik pods:</p>
<p><strong>kubectl get pods -n ingress-system</strong></p>
<p>Check the Traefik service and its assigned IP:</p>
<p><strong>kubectl get svc -n ingress-system</strong></p>
<p>Check the application services:</p>
<p><strong>kubectl get svc -n application-namespace</strong></p>
<p>Check the application endpoints:</p>
<p><strong>kubectl get endpoints -n application-namespace</strong></p>
<p>Check the routing resources:</p>
<p><strong>kubectl get ingressroute -A kubectl get middleware -A</strong></p>
<h3>Key areas to validate</h3>
<ol>
<li><strong>Pod scheduling:</strong> Confirm Traefik pods are scheduled on the intended node pool.</li>
<li><strong>Image availability:</strong> Ensure AKS nodes can access the container image registries required for deployment.</li>
<li><strong>Internal Load Balancer:</strong> Verify that the service receives the expected private IP.</li>
<li><strong>Private Link Service:</strong> Confirm the service is provisioned and the required private endpoint connection is approved.</li>
<li><strong>Backend service:</strong> Verify that the Kubernetes Service name and port match the actual application configuration.</li>
<li><strong>Service endpoints:</strong> Confirm that the backend Service has healthy pod endpoints.</li>
<li><strong>Routing and middleware:</strong> Validate the hostname match, path prefix, TLS secret, and rewrite behavior.</li>
<li><strong>End-to-end connectivity:</strong> Test the complete traffic flow through Azure Front Door and the AKS ingress endpoint.</li>
</ol>
<h2>10. Key learnings</h2>
<p>A few practical takeaways from the implementation:</p>
<ul>
<li><strong>Node pool selection matters:</strong> System node pools can have scheduling restrictions or taints. Plan the Traefik placement accordingly.</li>
<li><strong>Validate backend service details:</strong> The Service name and port configured in an IngressRoute must match the actual Kubernetes Service.</li>
<li><strong>Check service endpoints:</strong> A Kubernetes Service existing does not necessarily mean that it has healthy backend endpoints.</li>
<li><strong>Understand the networking path:</strong> Validate the internal load balancer, Private Link Service, and Front Door configuration independently.</li>
<li><strong>Use middleware for routing flexibility:</strong> Traefik path rewriting can help integrate applications without changing their existing API structure.</li>
<li><strong>Validate image registry connectivity:</strong> AKS nodes need outbound access to the registries hosting the required container images.</li>
<li><strong>Test end to end:</strong> Successful Helm deployment alone does not confirm that the complete application traffic flow is working.</li>
</ul>
<h2>Conclusion</h2>
<p>Deploying Traefik on AKS provides a flexible way to manage application ingress, host-based routing, path rewriting, and TLS configuration.</p>
<p>By combining Traefik with an internal Azure Load Balancer, Azure Private Link Service, and Azure Front Door Premium, it is possible to build a private and scalable application ingress architecture on Azure.</p>
<p>The most important part of the implementation is validating each layer independently and then testing the complete traffic flow.</p>
<p>This implementation was a good hands-on exercise in bringing together Kubernetes ingress capabilities and Azure networking services to support secure application connectivity.</p>

### What if your Azure Databricks workspaces have overlapping CIDRs?

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/what-if-your-azure-databricks-workspaces-have-overlapping-cidrs/ba-p/4569360](https://techcommunity.microsoft.com/t5/azure-networking-blog/what-if-your-azure-databricks-workspaces-have-overlapping-cidrs/ba-p/4569360)

<h1>&nbsp;</h1>
<p>Consider a common enterprise networking challenge:</p>
<p>You have three Azure Databricks workspaces. Each workspace uses classic VNet-injected compute, and each compute VNet uses the same address space:</p>
<p>10.100.0.0/20</p>
<p>Your networking team immediately sees the problem:</p>
<p>If multiple networks advertise 10.100.0.0/20, which workspace should traffic for that prefix reach?</p>
<p>At first glance, this looks like an IP-renumbering problem.</p>
<p>But there is another question worth asking first:</p>
<p><strong>Do enterprise users actually need network access to the Databricks compute subnets, or do they only need private access to the Databricks workspace service?</strong></p>
<p>For standard workspace web UI and REST API access, that distinction can fundamentally change the architecture.</p>
<p>The key design principle is:</p>
<p><strong>Route to uniquely addressed private endpoints, not to the overlapping compute networks.</strong></p>
<h2>The architecture challenge</h2>
<p>RFC1918 address space may be private, but in large enterprises it is often far from unlimited.</p>
<p>Acquisitions, independently designed environments, large historical reservations, and decentralized networking can result in multiple environments using the same address ranges.</p>
<p>Imagine this deployment:</p>
<ul>
<li>Three Azure Databricks workspaces: <strong>A</strong>, <strong>B</strong>, and <strong>C</strong></li>
<li>Three isolated VNet-injected compute VNets</li>
<li>Each compute VNet uses 10.100.0.0/20</li>
<li>Enterprise users require private access to all three workspaces</li>
<li>Enterprise connectivity arrives through ExpressRoute private peering or VPN</li>
</ul>
<p>Directly exposing all three compute VNets to a shared routing domain creates an obvious ambiguity because the same prefix exists three times.</p>
<p>Fortunately, workspace service access does not require enterprise clients to route directly into those compute networks.</p>
<h2>Service access is different from compute-network access</h2>
<p>Azure Databricks distinguishes between front-end Private Link, classic compute back-end Private Link, and serverless outbound connectivity.</p>
<p>For front-end access, private endpoints can provide connectivity to the Databricks workspace web application and REST APIs without requiring enterprise clients to route into the workspace compute VNet.</p>
<p>That separation gives us the basis for this design.</p>
<p>Instead of importing the overlapping compute prefixes into the enterprise network:</p>
<ol>
<li>Create a uniquely addressed <strong>Transit VNet</strong>.</li>
<li>Place the Databricks front-end private endpoints in that Transit VNet.</li>
<li>Make the Transit VNet reachable from the enterprise connectivity hub.</li>
<li>Keep each overlapping compute VNet in its own isolated routing domain.</li>
</ol>
<p>The enterprise network then routes only to addresses that are unique.</p>
<p><strong>Important:</strong> This does not make overlapping VNets routable to one another. It avoids adding those overlapping prefixes to the common enterprise routing domain.</p>
<p>Compute still requires its own control-plane connectivity, data access, and egress design. Those paths need to be considered independently.</p>
<h2>Example topology</h2>
<p>Consider the following illustrative single-region deployment.</p>
<p><strong>Databricks compute networks</strong></p>
<ul>
<li>Workspace A VNet: 10.100.0.0/20</li>
<li>Workspace B VNet: 10.100.0.0/20</li>
<li>Workspace C VNet: 10.100.0.0/20</li>
</ul>
<p><strong>Enterprise-reachable Transit VNet</strong></p>
<ul>
<li>Transit VNet: 10.200.0.0/16</li>
<li>Private endpoint subnet: 10.200.10.0/24</li>
</ul>
<p><strong>Example private endpoint addresses</strong></p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Private endpoint</th><th>Example IP</th><th>Purpose</th></tr></thead><tbody><tr><td>PE-A</td><td>10.200.10.10</td><td>Workspace A databricks_ui_api</td></tr><tr><td>PE-B</td><td>10.200.10.11</td><td>Workspace B databricks_ui_api</td></tr><tr><td>PE-C</td><td>10.200.10.12</td><td>Workspace C databricks_ui_api</td></tr><tr><td>Browser-auth PE</td><td>10.200.10.20</td><td>Shared regional browser_authentication</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>These addresses are examples only and are not production sizing recommendations.</p>
<p>The enterprise network connects to either:</p>
<ul>
<li>a conventional connectivity hub, <strong>or</strong></li>
<li>an Azure Virtual WAN hub.</li>
</ul>
<p>The example does not require chaining both hub models together.</p>
<p>Enterprise connectivity reaches the selected hub through ExpressRoute <strong>private peering</strong> or VPN, and the Transit VNet connects using the appropriate mechanism for that topology.</p>
<h3>Architecture diagram</h3>
<img />
<p class="lia-clear-both">&nbsp;</p>
<p><em>Figure 1. Enterprise routes terminate at uniquely addressed Transit VNet private endpoints for Databricks workspace services. The overlapping compute networks remain outside the enterprise routing domain.</em></p>
<p>The important part is what is <strong>not</strong> connected.</p>
<p>The three compute VNets are not:</p>
<ul>
<li>peered to the enterprise-connected Transit VNet,</li>
<li>peered to the conventional enterprise hub,</li>
<li>attached to the Azure Virtual WAN hub, or</li>
<li>advertised into enterprise routing.</li>
</ul>
<p>Therefore, the three instances of 10.100.0.0/20 never compete in the same enterprise routing table.</p>
<p>The address-space benefit is quite specific:</p>
<p><strong>Enterprise routing consumes a unique ingress range rather than requiring three unique enterprise-visible compute ranges.</strong></p>
<p>Each Databricks workspace still consumes its own subnet address space locally.</p>
<h2>How the private service path works</h2>
<p>Suppose a user wants to open Workspace B.</p>
<p>The flow is conceptually:</p>
<p><strong>Client → enterprise connectivity → hub → Transit VNet → PE-B → Databricks workspace service</strong></p>
<p>The user accesses the normal workspace hostname.</p>
<p>DNS resolves that hostname to the appropriate private endpoint address in the Transit VNet. Enterprise routing carries the traffic to that address, and Azure Private Link provides connectivity from the endpoint to the corresponding Databricks workspace service.</p>
<p>The association remains deterministic:</p>
<ul>
<li>PE-A → Workspace A</li>
<li>PE-B → Workspace B</li>
<li>PE-C → Workspace C</li>
</ul>
<p>This is <strong>service-specific private connectivity</strong>.</p>
<p>It is not a routed entrance into Workspace A, B, or C's compute subnet.</p>
<p>Applications and users should also continue to use the <strong>standard Databricks workspace hostname</strong>, rather than configuring private endpoint IP addresses directly in browsers or API clients.</p>
<h2>Don't forget browser authentication</h2>
<p>There is another dependency that deserves special attention.</p>
<p>The databricks_ui_api endpoint provides workspace UI and REST API connectivity.</p>
<p>The browser_authentication endpoint has a different purpose: browser single sign-on callbacks.</p>
<p>It is not the authentication endpoint used for REST API requests.</p>
<p>Microsoft documents a browser-authentication endpoint per Azure region and private DNS zone that can be shared by workspaces in that region that use the same DNS configuration.</p>
<p>Microsoft also recommends using a separate production web-auth workspace that:</p>
<ul>
<li>has no compute workloads,</li>
<li>does not have a databricks_ui_api private endpoint on that host, and</li>
<li>is treated as a shared infrastructure dependency.</li>
</ul>
<p>This dependency matters operationally because removing the workspace that hosts the browser-authentication endpoint can break browser authentication for dependent workspaces.</p>
<p><strong>Design note:</strong> This example is intentionally region-local. It should not be interpreted as a single global browser-authentication endpoint design.</p>
<p>Other Databricks access scenarios may also use endpoints such as general_access or service_direct. Those scenarios should be evaluated separately against the current Azure Databricks documentation.</p>
<h2>DNS is as important as routing</h2>
<p>A route to PE-B does not help if the Workspace B hostname resolves somewhere else.</p>
<p>For hybrid clients, the DNS design should make the normal Databricks workspace hostname resolve to the private endpoint that the client can actually reach.</p>
<p>Microsoft's hybrid Private Endpoint DNS guidance recommends conditionally forwarding the relevant <strong>public service suffix</strong> to a reachable Azure DNS Private Resolver inbound endpoint.</p>
<p>For Azure Databricks, that means forwarding:</p>
<p>azuredatabricks.net</p>
<p>rather than designing the hybrid forwarding path around only:</p>
<p>privatelink.azuredatabricks.net</p>
<p>On-premises DNS should also not query Azure's 168.63.129.16 virtual IP directly.</p>
<p>The resolver VNet context should be linked to the central:</p>
<p>privatelink.azuredatabricks.net</p>
<p>private DNS zone.</p>
<p>Azure-provided DNS can then process the normal workspace hostname through the service DNS chain and private-zone lookup so that the client ultimately receives the appropriate Transit private endpoint address.</p>
<p>An outbound Private Resolver endpoint is not required solely for servicing these inbound queries.</p>
<h3>DNS architecture</h3>
<img />
<p><em>Figure 2. DNS resolution and HTTPS traffic are separate paths. DNS returns the reachable Transit private endpoint address; the private DNS zone itself is not part of the HTTPS routing path.</em></p>
<p>Private Endpoint DNS zone groups should be used to maintain the service mappings instead of manually guessing record names.</p>
<h2>A subtle DNS trap with front-end and back-end Private Link</h2>
<p>There is an important architectural trap when both front-end and back-end private endpoints exist.</p>
<p>Your enterprise clients need DNS to return the <strong>front-end Transit endpoint</strong> they can reach.</p>
<p>Compute environments using back-end connectivity may require a different DNS view that returns endpoints reachable from those networks.</p>
<p>If both endpoint types compete to update the same records in the same shared private DNS zone, name resolution may succeed while returning an endpoint that the client cannot reach.</p>
<p>That leads to a useful design principle:</p>
<p><strong>DNS visibility should follow network reachability.</strong></p>
<p>Keep the central front-end DNS view populated with the Transit endpoints.</p>
<p>Where isolated compute environments also require back-end private endpoints, design an appropriate reachable DNS view for those environments instead of peering overlapping VNets merely to solve DNS.</p>
<p>And remember: DNS is not an access-control mechanism. Hiding a DNS record does not replace network or identity controls.</p>
<h2>Private access does not automatically mean private-only</h2>
<p>This is one of the most important distinctions in the design.</p>
<p>Creating front-end private endpoints establishes a <strong>private access path</strong>.</p>
<p>It does not, by itself, guarantee that public workspace access has been disabled.</p>
<p>Microsoft distinguishes an inbound-only configuration from a complete private-isolation configuration.</p>
<p>Complete private isolation introduces additional requirements, including back-end Private Link connectivity and the corresponding workspace networking configuration.</p>
<p>Therefore:</p>
<p><strong>Do not disable public network access on workload workspaces simply because the front-end Transit private endpoints are working.</strong></p>
<p>First validate the required back-end/control-plane path, compute connectivity, data dependencies, and egress requirements against the complete-isolation guidance.</p>
<p>Otherwise, a successful browser test could hide a broken compute environment.</p>
<p>The dedicated browser-authentication workspace is also configured differently from workload workspaces. Its configuration should not be copied indiscriminately to the compute workspaces.</p>
<h2>What this pattern solves</h2>
<p>This design is useful when:</p>
<ul>
<li>multiple classic VNet-injected Databricks environments use overlapping compute address spaces,</li>
<li>those compute networks can remain isolated,</li>
<li>enterprise users need private UI access,</li>
<li>applications need private REST API access, and</li>
<li>the organization has a uniquely addressed enterprise-reachable Transit VNet.</li>
</ul>
<p>It reduces the requirement for unique <strong>enterprise-visible compute prefixes</strong>.</p>
<p>It does not reduce the local address consumption of each Databricks workspace.</p>
<h2>What this pattern does not solve</h2>
<p>This design is not a general solution for overlapping networks.</p>
<p>It does <strong>not</strong> make the overlapping compute VNets mutually routable.</p>
<p>It also does not replace the design for:</p>
<ul>
<li>storage connectivity,</li>
<li>data-service private endpoints,</li>
<li>compute-to-control-plane connectivity,</li>
<li>outbound/egress controls,</li>
<li>direct cross-workspace compute communication, or</li>
<li>serverless outbound networking.</li>
</ul>
<p>If workloads in Workspace A must communicate directly with workloads in Workspace B, and both networks use 10.100.0.0/20, you have returned to an address-ambiguity problem.</p>
<p>That requirement needs a separate connectivity and addressing strategy.</p>
<h2>Operational considerations</h2>
<p>Before adopting this architecture, review the documented Azure Databricks Private Link prerequisites.</p>
<p>These include considerations around:</p>
<ul>
<li>Premium workspaces,</li>
<li>VNet injection,</li>
<li>Secure Cluster Connectivity / No Public IP,</li>
<li>configuration permissions,</li>
<li>regional placement requirements, and</li>
<li>potential downtime when retrofitting existing workspaces.</li>
</ul>
<p>Also consider the following operational areas.</p>
<h3>Address capacity and cost</h3>
<p>Plan enough space for private endpoints, subnet reservations, future endpoints, DNS infrastructure, and applicable platform limits.</p>
<p>Private Endpoint, DNS Private Resolver, ExpressRoute/VPN, and the selected hub architecture also have associated costs.</p>
<p>Reusing compute CIDRs does not mean the connectivity layer is free.</p>
<h3>Network controls</h3>
<p>When private endpoint network policies and NSG controls are applicable, validate the current documented service flows.</p>
<p>Azure Databricks documentation currently lists inbound TCP requirements including:</p>
<ul>
<li>443</li>
<li>6666</li>
<li>3306</li>
<li>8443-8451</li>
</ul>
<p>Use appropriately scoped rules based on the current service requirements rather than assuming that allowing only TCP 443 is sufficient.</p>
<h3>Traffic inspection</h3>
<p>A centralized private endpoint does not automatically imply centralized firewall inspection.</p>
<p>Verify:</p>
<ul>
<li>effective routes,</li>
<li>the selected hub topology,</li>
<li>firewall traversal where required, and</li>
<li>the actual data path.</li>
</ul>
<h2>Validation checklist</h2>
<p>Before declaring the design operational, validate it from each relevant network.</p>
<h3>DNS</h3>
<ul>
<li>[ ] Resolve every standard Databricks workspace hostname.</li>
<li>[ ] Confirm that each hostname returns its expected Transit private endpoint IP.</li>
<li>[ ] Validate browser-authentication DNS resolution.</li>
<li>[ ] Confirm that isolated compute environments receive only endpoints they can reach.</li>
</ul>
<h3>Workspace connectivity</h3>
<ul>
<li>[ ] Open each workspace using its standard hostname.</li>
<li>[ ] Verify connectivity follows the intended private path.</li>
<li>[ ] Complete browser sign-in.</li>
<li>[ ] Test an authenticated REST API request to each workspace.</li>
</ul>
<h3>Security</h3>
<ul>
<li>[ ] Verify unauthorized network sources are denied by the intended network controls.</li>
<li>[ ] Verify unauthorized identities cannot access workspace resources.</li>
<li>[ ] If complete private isolation is required, confirm public UI/API access is unavailable from outside the approved private path.</li>
</ul>
<h3>Compute</h3>
<ul>
<li>[ ] Start representative classic compute.</li>
<li>[ ] Validate control-plane connectivity independently.</li>
<li>[ ] Validate storage and data-service access.</li>
<li>[ ] Validate required outbound/egress connectivity.</li>
</ul>
<p>These are proposed architectural validation checks, not reported results from a deployed test environment.</p>
<h2>Key takeaway</h2>
<p>Overlapping prefixes appear to be the central problem only if enterprise clients need to route directly into those prefixes.</p>
<p>For standard Azure Databricks workspace UI and REST API ingress, they do not.</p>
<p>Instead:</p>
<p><strong>Give each workspace service a unique private endpoint in an enterprise-reachable Transit VNet, route enterprise clients to those endpoints, and keep the overlapping compute networks out of the shared routing domain.</strong></p>
<p>Then make DNS return the endpoint the client can actually reach.</p>
<p>Finally, treat compute networking, back-end Private Link, data dependencies, egress, public exposure, and serverless networking as separate design decisions.</p>
<p>The goal is not to make overlapping networks routable.</p>
<p>The goal is to <strong>solve the service-access requirement without importing the overlapping routes in the first place</strong>.</p>
