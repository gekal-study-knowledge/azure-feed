<h2>Key Takeaways</h2>
<ul>
<li>Terraform drift detection is valuable but <strong>Terraform alone is not enough</strong> when enterprises also rely on design documents, migration inventories, and operational portal validations.&nbsp;</li>
<li>Azure attributes such as <strong>SKU, tags, accelerated networking, managed disk type, and zone placement</strong> can all be validated using a mix of Terraform state parsing, Azure APIs/Resource Graph, and portal verification.&nbsp;</li>
<li><strong>Azure Resource Graph</strong> is especially useful for fast, large-scale live validation because it can query resource properties across subscriptions without calling every resource provider one by one.&nbsp;</li>
<li><strong>Managed Identity</strong> is the preferred enterprise authentication model for a read-only validator because it removes credential handling and supports token-based access to downstream Azure services.</li>
<li>Manual <strong>Azure Portal verification with documented steps and screenshot placeholders</strong> makes the solution feel audit-ready, migration-ready, and operationally trustworthy.</li>
</ul>
<h2>1. Introduction</h2>
<p>Terraform drift in Azure happens when what is actually deployed no longer matches what Terraform thinks exists or what the original design intended. In practice, drift appears after portal edits, partial manual changes, external scripts, policy remediation, or emergency operational actions that never get folded back into code. HashiCorp recommends automated drift detection because unmanaged divergence can create operational inconsistency, security exposure, and compliance risk.</p>
<p>Azure environments make this especially important because infrastructure is often governed by multiple teams: architects define the target design, DevOps teams deploy through Terraform, and operations teams may validate or troubleshoot through Azure Portal. Azure Resource Graph itself exists to support large-scale governance and current-state visibility across subscriptions, which makes it a strong foundation for live verification.&nbsp;</p>
<p>That is why an enterprise-grade drift validator should not compare only <strong>Terraform vs Azure</strong>. It should compare:</p>
<ul>
<li><strong>Design intent</strong> from Excel or architecture documentation</li>
<li><strong>Terraform state</strong> as the IaC-managed representation</li>
<li><strong>Azure live configuration</strong> as the real runtime state</li>
</ul>
<h2>2. Problem Statement</h2>
<p>Many organizations still maintain infrastructure specifications in Excel, migration trackers, or design documents. Those documents often contain the details that matter most to governance and operations: VM sizes, storage SKUs, disk performance expectations, tags, zones, and network settings. Terraform state, on the other hand, reflects what Terraform knows about deployed resources. Azure live state reflects what is actually running.</p>
<p>These three sources diverge for common reasons:</p>
<ul>
<li>A VM was resized manually in Azure Portal</li>
<li>Accelerated networking was expected in design, defined in Terraform, but the actual NIC does not reflect it</li>
<li>Tags were defined in a workbook but never applied consistently</li>
<li>Storage or disk settings changed during production troubleshooting</li>
<li>Zone placement differs from the architecture baseline</li>
</ul>
<h2>3. Solution Overview</h2>
<p>The proposed solution is a <strong>Terraform Drift Validator for Azure with Live Portal Verification</strong>. At a high level, it works like this:</p>
<ul>
<li>The user uploads an <strong>Excel sheet</strong> or <strong>design document</strong></li>
<li>The solution extracts expected resource configuration</li>
<li>It ingests the <strong>Terraform state file</strong></li>
<li>It queries <strong>Azure live resources</strong></li>
<li>It normalizes values across all three sources</li>
<li>It compares attributes and generates a structured drift report</li>
<li>It optionally presents portal validation steps for manual verification</li>
</ul>
<p>This can run as a <strong>web application, API service, or agent-based validator</strong>, exposed through:</p>
<p><strong>https://ca-aiv-agent.livelyhill-f6d3be20.eastus.azurecontainerapps.io/</strong></p>
<h2>4. Supported Validation Parameters</h2>
<p>A useful validator should support the following checks:</p>
<ul>
<li><strong>SKU</strong><br />Validate expected SKU from design against Terraform and live Azure. This is critical for cost and performance.</li>
<li><strong>IOPS</strong><br />Validate disk performance expectations. Azure documents that some disk types—particularly Ultra Disk and Premium SSD v2—allow direct performance tuning, making IOPS a meaningful validation parameter. <a href="https://learn.microsoft.com/en-us/azure/virtual-machines/disks-performance-options" rel="noopener" target="_blank">[</a></li>
<li><strong>Accelerated Networking</strong><br />Azure states that accelerated networking improves VM network performance by reducing latency and CPU utilization via SR-IOV on supported VM sizes. This is exactly the kind of feature that is frequently missed or changed during deployments.&nbsp;</li>
<li><strong>Tags</strong><br />Azure tags are key-value metadata used for governance, organization, and cost management. Azure also warns that tags are stored as plain text and should not contain sensitive data.&nbsp;</li>
<li><strong>Availability Zones</strong><br />Validate whether resources are placed in the expected zone(s) or zone-resilient configuration.</li>
<li><strong>Region</strong></li>
<li><strong>VM Size</strong></li>
<li><strong>Disk Type</strong></li>
<li><strong>Resource Group</strong></li>
<li><strong>NIC and network configuration</strong></li>
<li><strong>Optional controls</strong> such as NSG expectations, public/private exposure, backup status, or monitoring configuration</li>
</ul>

<h2>7. Workflow</h2>
<ol>
<li>User uploads an Excel sheet or design document</li>
<li>System extracts expected fields such as resource type, name, SKU, IOPS, tags, zones, region, VM size, and network settings</li>
<li>Terraform state file is parsed into resource objects</li>
<li>Azure live resources are queried using Resource Graph and targeted API calls</li>
<li>Attribute names and values are normalized</li>
<li>Comparison engine calculates:
<ul>
<li><strong>Match</strong></li>
<li><strong>Design vs Terraform drift</strong></li>
<li><strong>Terraform vs Azure drift</strong></li>
<li><strong>Design vs Azure drift</strong></li>
</ul>
</li>
<li>Final report is generated with severity and remediation recommendations</li>
</ol>

### Rundeck – AWS Enterprise Rundeck Integration with Azure Runner

<h2>Architecture Overview</h2>
<ul>
<li><strong>Rundeck Server (AWS)</strong> → https://dev.rundeck.xyz.com</li>
<li><strong>Rundeck Runner (Azure Linux VM)</strong></li>
<li><strong>Secure Communication</strong> over HTTPS (Port 4432)</li>
<li>Optional Proxy for enterprise networks</li>
</ul>
<p>1.Ensure that network connectivity is established between the Rundeck endpoint (dev.rundeck.xyz.com) and the Azure subnet over port 443.</p>
<p>2.Request the customer to create a Runner within a new or existing project in the Rundeck portal by providing a suitable name and tags and&nbsp;then proceed to download the corresponding Runner JAR file.</p>
<p>3.Provision an Azure Linux Virtual Machine and deploy the downloaded Runner JAR using a VM extension or through a CI/CD pipeline integrated with BAMS/Artifactory. Below all prerequisite steps are mentioned which needs to be run on Azure VM to ensure Rundeck runner is ready.</p>
<p>4.Additionally, make sure all required prerequisites are installed on the Azure Linux VM that will host the Rundeck Runner.</p>
<p>5.After installation it will establish the connectivity between azure Rundeck runner and Aws Enterprise Rundeck.</p>
<p>6.We can trigger any Rundeck jobs on Azure virtual machines.</p>
<img />
<p>&nbsp;</p>
<p>&nbsp;</p>
<p>By deploying the Rundeck Runner on Azure, enterprises can seamlessly bridge AWS-hosted orchestration with Azure-based execution environments. This setup enables robust, scalable, and secure automation across hybrid cloud ecosystems.</p>
<p><strong>All prerequiste needs to be run on the Azure vm.</strong></p>
<p><strong>Step 1: Network Connectivity Prerequisites:</strong></p>
<p>Ensure proper network connectivity between Rundeck and Azure:</p>
<p>Allow outbound/inbound access: Source: Azure Subnet Destination: dev.rundeck.xyz.com Port: 443 Protocol: HTTP</p>
<p><strong>Step 2: Create Rundeck Runner</strong></p>
<p>Login to Rundeck Portal</p>
<p>Navigate to a project → Runner Management</p>
<p>Create a new runner:</p>
<p>Provide Name</p>
<p>Add Tags</p>
<p>Download the Runner JAR file</p>
<p><strong>Step 3: Azure VM setup</strong></p>
<p>Create a Linux VM (RHEL/CentOS) in Azure.</p>
<p>Deploy the runner jar via:</p>
<p>CI/CD pipeline (BAMS/Artifactory)</p>
<p>VM Extension for automation</p>
<p><strong>Step 4: Install Prerequisites on Azure VM</strong></p>
<p>Install Java 11</p>
<p>sudo bash</p>
<p>yum install java-11-openjdk.x86_64</p>
<p>rpm -qa | grep java-11</p>
<p>java --version</p>
<p><strong>Step 5: Start the Runner -</strong></p>
<p>useradd rundeck</p>
<p><strong>Step 6: Create Rundeck User-</strong></p>
<p>mkdir /opt/rundeck/</p>
<p>chown -R rundeck:rundeck /opt/rundeck/</p>
<p>cp runner-*.jar /opt/rundeck/</p>
<p>ll /opt/rundeck/</p>
<p><strong>Step 7: Start the Runner -</strong></p>
<p><strong>without proxy</strong></p>
<p>/bin/java -jar /opt/rundeck/runner-&lt;id&gt;.jar</p>
<p><strong>With proxy:</strong></p>
<p>/bin/java \</p>
<p>-Dmicronaut.http.client.proxy-type=http \</p>
<p>-Dmicronaut.http.client.proxy-address=webproxy.lo5.mgmt.services:80 \</p>
<p>-jar /opt/rundeck/runner-&lt;id&gt;.jar</p>
<p><strong>Step 8: Configure Runner as a Service</strong></p>
<p>vi /etc/systemd/system/runner.service</p>
<p>Add Configuration</p>
<p>[Unit]</p>
<p>Description=Process Automation Runner</p>
<p>[Service]</p>
<p>WorkingDirectory=/opt/rundeck/</p>
<p>Type=simple</p>
<p>User=rundeck</p>
<p>Group=rundeck</p>
<p>ExecStart=/bin/java -jar /opt/rundeck/runner-&lt;id&gt;.jar</p>
<p>Restart=on-failure</p>
<p>[Install]</p>
<p>WantedBy=multi-user.target</p>
<p>Enable and start service:</p>
<p>chmod 0640 /etc/systemd/system/runner.service</p>
<p>systemctl daemon-reload</p>
<p>systemctl enable runner.service</p>
<p>systemctl start runner.service</p>
<p>systemctl status runner.service</p>
<p><strong>Step 9: Verify Runner Process</strong></p>
<p>ps aux | grep rundeck</p>
<p>systemctl status runner.service</p>
<p><strong>Step 10: Configure Log Rotation</strong></p>
<p>create configuration:</p>
<p>vi /etc/logrotate.d/rundeck_runnerd</p>
<p>/opt/rundeck/runner/logs/operations.log</p>
<p>{</p>
<p>&nbsp;daily</p>
<p>&nbsp;missingok</p>
<p>&nbsp;&nbsp;&nbsp; rotate 8</p>
<p>&nbsp; &nbsp; compress</p>
<p>&nbsp;&nbsp;&nbsp; copytruncate</p>
<p>&nbsp;&nbsp;&nbsp; maxsize 150M</p>
<p>&nbsp;&nbsp;&nbsp; create 644 root root</p>
<p>}</p>
<p><strong>Step 11: Runner Upgrade Process</strong></p>
<p>Regenerate credentials:</p>
<p>curl -k -X POST https://dev.rundeck.xyz.com/api/42/runnerManagement/runner/&lt;runner-id&gt;/regenerateCreds \</p>
<p>--header "Content-Type: application/json" \</p>
<p>--header "X-Rundeck-Auth-Token: &lt;token&gt;"</p>
<p><strong>Step 12: Download Updated runner</strong></p>
<p>curl -k -X GET https://dev.rundeck.xyz.com/api/41/runnerManagement/download/&lt;downloadTk&gt; \</p>
<p>--header "X-Rundeck-Auth-Token: &lt;token&gt;" \</p>
<p>--output runner-${runner_id}.jar</p>

<h2><strong>Introduction</strong></h2>
<p>Generative AI tools such as <strong>ChatGPT, GitHub Copilot, and Google Gemini</strong> are rapidly becoming part of everyday enterprise workflows. Teams use them for code generation, documentation, analysis, support automation, and productivity enhancement.</p>
<p>However, this accelerated adoption has also created a significant governance and security challenge: <strong>Shadow AI</strong>.</p>
<p>Shadow AI refers to the <strong>unauthorized, unmanaged, or unmonitored use of AI tools inside an organization</strong>. Employees may unknowingly paste sensitive enterprise information into external AI platforms, exposing:</p>
<ul>
<li>API keys</li>
<li>Source code</li>
<li>Customer data</li>
<li>Credentials</li>
<li>Internal business documents</li>
</ul>
<p>At the same time, enterprise AI usage is increasingly exposed to:</p>
<ul>
<li>Prompt injection attacks</li>
<li>Malicious API manipulation</li>
<li>Unsafe model outputs</li>
<li>Compliance violations</li>
</ul>
<p>Security and compliance teams currently lack centralized visibility and governance over enterprise AI usage.&nbsp;</p>
<p>Existing tools are fragmented and do not provide unified protection across the complete AI attack surface including Data, Prompt/API, and Model layers.</p>
<p><strong>Organizations require an intelligent, autonomous platform capable of&nbsp;</strong></p>
<p>detecting Shadow AI usage,<br />preventing sensitive data leakage,<br />securing AI interactions,<br />enforcing governance policies,<br />and maintaining compliance in real time.</p>
<p><strong>Proposed Solution:&nbsp;</strong></p>
<p>AI Guardian is an intelligent security and governance platform designed to secure enterprise AI adoption and mitigate Shadow AI risks.</p>
<p><strong>1) The platform continuously monitors AI interactions across enterprise environments and provides autonomous protection across multiple AI attack surfaces.</strong><br /><br />Core Capabilities<br />Shadow AI Detection<br />Detects unauthorized AI tool usage<br />Monitors risky AI interactions<br />Identifies sensitive data exposure<br />Multi-Layer AI Security<br />Data Layer Protection<br />PII detection<br />API key and credential scanning<br />Confidential data leakage prevention<br />Prompt/API Layer Protection<br />Prompt injection detection<br />Malicious prompt analysis<br />API abuse detection<br />Model Layer Protection<br />Unsafe response monitoring<br />AI Compliance Copilot<br />Generates governance reports<br />Recommends remediation actions<br /><br /><strong>2.AI Guardian Extension Automatically performs:</strong><br />prompt blocking,<br />redaction,<br />SOC alerting,<br />incident creation,<br />and compliance logging.</p>
<p><strong>3.AI Guardian Extension Business Value:</strong></p>
<p>This AI Guardian delivers measurable business value by enabling secure and governed enterprise AI adoption.<br /><strong>4.Key Business Benefits</strong><br />1. Prevents Sensitive Data Leakage<br />2. Enables Safe Enterprise AI Adoption<br />3. <p><br /><strong>5. <ul>
