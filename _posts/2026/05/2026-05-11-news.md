<p>When working with Infrastructure as Code (IaC) using Azure Bicep or ARM templates, deployment failures are a common part of day-to-day operations—especially in large-scale enterprise environments.</p>
<p>One such frequently encountered but often misunderstood issue is the quota limitation (800) error, which typically occurs during repeated or automated deployments.</p>

<p><strong>What is the quota limitation (800) Error?</strong></p>
<p>The quota limitation (800) reference is commonly associated with a deployment quota limitation in Azure Resource Manager (ARM).</p>
<p>In simple terms:<br />Azure limits the number of deployment records that can be stored per resource group.</p>
<p>Key detail:</p>
<ul>
<li>Maximum allowed deployment history entries per resource group:&nbsp;<strong>800</strong></li>
</ul>
<p>Once this limit is exceeded:</p>
<ul>
<li>New deployments fail</li>
<li>Error messages such as the following are observed:</li>
</ul>
<p>“DeploymentQuotaExceeded”</p>
<p>The current deployment count is '800'. Please delete some deployments before creating a new one.</p>
<p>This happens because Azure maintains deployment history for auditing, tracking, and troubleshooting purposes. [aka.ms/800]</p>
<p><strong>Use Case: Bicep Deployment Failure in CI/CD</strong></p>
<p><strong>Scenario</strong></p>
<p>An organization is deploying infrastructure using a Bicep template through an automated pipeline.</p>
<p>Example command:</p>
az deployment group create \
  --resource-group prod-rg \
  --template-file main.bicep \
  --parameters @params.bicepparam
<p><strong>Environment Characteristics</strong></p>
<ul>
<li>Continuous deployment using pipelines (Azure DevOps / GitHub Actions)</li>
<li>Multiple deployments triggered daily</li>
<li>Incremental deployment mode enabled</li>
<li>A shared resource group used across multiple deployments</li>
</ul>
<p><strong>Issue Encountered</strong></p>
<p>After repeated deployments over time, the following failure occurs:</p>
<p>Error: DeploymentQuotaExceeded</p>
<p>The current deployment count is '800'</p>
<p>See aka.ms/800 for more information</p>
<p>At this point, no further deployments succeed in that resource group.</p>
<p><strong>Root Cause Analysis</strong></p>
<ol>
<li><strong>Deployment History Limit</strong></li>
</ol>
<p>Azure stores every deployment execution as a record under:</p>
<p>Resource Group → Deployments</p>
<p>These records accumulate over time, and once the count reaches 800, new deployments are blocked.</p>
<p>Important clarification:</p>
<ul>
<li>This is not a resource limit (VMs, VNets, etc.)</li>
<li>This is a metadata limit related to deployment history</li>
</ul>
<ol>
<li><strong>High Frequency CI/CD Deployments</strong></li>
</ol>
<p>In enterprise environments, pipelines may run frequently due to:</p>
<ul>
<li>Minor configuration updates</li>
<li>Validation runs</li>
<li>Automated releases</li>
</ul>
<p>Each run contributes to the deployment count.</p>
<ol>
<li><strong>Absence of Cleanup Mechanism</strong></li>
</ol>
<p>Although Azure manages some cleanup automatically, it is not always sufficient in high-frequency environments. Manual or automated cleanup is often required.</p>
<p><strong>Resolution Approaches</strong></p>
<p><strong>Option 1: Manual Cleanup from Azure Portal</strong></p>
<p>Navigate to:</p>
<ul>
<li>Azure Portal</li>
<li>Resource Group</li>
<li>Deployments</li>
</ul>
<p>Delete older deployment entries manually to free up space.</p>
<p><strong>Option 2: Cleanup Using Azure CLI</strong></p>
#List deployments:

az deployment group list \
  --resource-group prod-rg \
  --query "[].name" -o tsv

#Delete a deployment:

az deployment group delete \
  --resource-group prod-rg \
  --name &lt;deployment-name&gt;
<p><strong>Option 3: Automated Cleanup (Recommended)</strong></p>
<p>Example PowerShell approach:</p>
$deployments = Get-AzResourceGroupDeployment -ResourceGroupName "prod-rg"

if ($deployments.Count -gt 700) {
    $deployments | Sort-Object Timestamp | Select-Object -First 100 | ForEach-Object {
        Remove-AzResourceGroupDeployment -ResourceGroupName "prod-rg" -Name $_.DeploymentName
    }
}
<p>This approach ensures that older deployments are periodically removed, preventing quota exhaustion.</p>
<p><strong>Option 4: Use Multiple Resource Groups</strong></p>
<p>Instead of using a single resource group for all deployments:</p>
<ul>
<li>Separate environments (Dev, Test, Prod)</li>
<li>Temporary or experimental deployments</li>
</ul>
<p>This helps distribute deployment records across multiple scopes.</p>
<p><strong>Best Practices</strong></p>
<ol>
<li><strong>Implement Deployment Retention Policy</strong></li>
</ol>
<ul>
<li>Maintain only recent deployments (for example, last 100–200)</li>
<li>Automate deletion of older entries</li>
</ul>
<ol>
<li><strong>Control Deployment Frequency</strong></li>
</ol>
<ul>
<li>Avoid unnecessary pipeline triggers</li>
<li>Batch multiple changes into a single deployment</li>
</ul>
<ol>
<li><strong>Use Predictable Deployment Naming</strong></li>
</ol>
<p>Example:</p>
name: 'deploy-${utcNow()}'
<p>This improves traceability and cleanup management.</p>
<ol>
<li><strong>Monitor Deployment Count</strong></li>
</ol>
<p>Example:</p>
az deployment group list \
  --resource-group prod-rg \
  --query "length(@)"
<p>Set alerts or monitoring thresholds if required.</p>
<ol>
<li><strong>Understand Deployment Mode Behavior</strong></li>
</ol>
<p>Incremental deployments prevent unwanted deletions of resources but still increase the deployment history count.</p>

<h2>Scaling GitHub Advanced Security in Azure DevOps with a single reusable YAML template</h2>
<p>Managing security scanning across dozens of repositories can quickly become complex—especially when each repository uses different languages, frameworks, and infrastructure patterns.</p>
<p>In our environment, we needed a scalable way to apply <strong>GitHub Advanced Security (GHAS)</strong> consistently across:</p>
<ul>
<li>Application code (Python, C#, Java, JavaScript)</li>
<li>Infrastructure as Code (Terraform, ARM, Bicep)</li>
<li>Mixed (polyglot) repositories</li>
</ul>
<p>Instead of maintaining multiple pipelines, we built a <strong>single reusable Azure DevOps YAML template</strong> that dynamically adapts to any repository.</p>
<h2>The problem</h2>
<p>Most teams struggle with:</p>
<ul>
<li>Multiple pipelines for different tech stacks</li>
<li>Inconsistent security coverage</li>
<li>Maintenance overhead across repositories</li>
<li>Unnecessary scans increasing build time</li>
</ul>
<p>We needed a solution that:</p>
<ul>
<li>Detects repository content automatically</li>
<li>Runs only relevant scans</li>
<li>Standardizes security across all repos</li>
<li>Minimizes duplication</li>
</ul>
<h2>Solution overview</h2>
<p>The solution is a <strong>single-stage pipeline template</strong> with three key jobs:</p>
<ol>
<li>Detect repository content</li>
<li>Run CodeQL for application code</li>
<li>Run IaC security scanning</li>
</ol>
<p>Scanning behavior is driven entirely by detection outputs.</p>
