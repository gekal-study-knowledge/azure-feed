### Golden Image Refresh for Virtual Machines and VM Scale Sets: Driving Consistency at Scale

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/golden-image-refresh-for-virtual-machines-and-vm-scale-sets/ba-p/4521376](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/golden-image-refresh-for-virtual-machines-and-vm-scale-sets/ba-p/4521376)
- **Published**: 2026-05-20 11:56:39
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><strong>Overview:<br /></strong></p>
<p>A&nbsp;<strong>golden image</strong> is a prebuilt, approved system template that represents the ideal baseline for deployment. It includes:</p>
<ul>
<li>Hardened operating system configuration (e.g., RHEL)</li>
<li>Preinstalled software and dependencies</li>
<li>Security patches and updates</li>
<li>Organizational compliance standards</li>
</ul>
<p><strong>Architecture:</strong></p>
<img />
<p><span><strong>Golden Image Refresh for VM Scale Sets (VMSS):</strong></span></p>
<p>Instead of updating instances individually:</p>
<ul>
<li>A <strong>new image version is published</strong></li>
<li>The VMSS is updated to reference the new image</li>
<li>Instances are gradually replaced through a controlled rollout</li>
<li>New instances (based on updated image) are introduced</li>
<li>Traffic is gradually shifted to these new instances</li>
<li>Old instances are decommissioned in phases</li>
<li>Minimizes service disruption</li>
<li>Enables safe rollout of updated environments</li>
<li>Allows real-time validation of new image versions</li>
</ul>
<p>Virtual Machine Scale Set (VMSS) deployments use a&nbsp;<strong>custom image</strong> that is baked on top of a <strong>Golden Image</strong>.<br />The Golden Image version is pinned in the environment-specific <strong>Packer variables (</strong><strong>pkrvariables</strong><strong>) files</strong>.<br />Refreshing a VMSS Golden Image involves baking a new custom image using an updated Golden Image version and deploying it via the VMSS pipelines.</p>
<p><strong>Image Dependency Flow</strong></p>
<ol>
<li><strong>Golden Image</strong>
<ul>
<li>Published and versioned by the Golden Image Team.</li>
<li>Source OS image, pinned in pkrvariables per environment.</li>
</ul>
</li>
<li><strong>Custom Image</strong>
<ul>
<li>Created by the <strong>custom image pipeline</strong>.</li>
<li>Built on top of the pinned Golden Image.</li>
<li>Used by VMSS deployments.</li>
</ul>
</li>
<li><strong>VMSS Deployment</strong>
<ul>
<li>Deploys or updates scale sets using the selected custom image version.</li>
</ul>
</li>
</ol>
<p><strong>Golden Image Version Management (VMSS)</strong></p>
<ul>
<li>Each environment pins the Golden Image version in its respective pkrvariables file.</li>
<li>Golden Image versions are selected from the same Golden Image Galleries:
<ul>
<li>Dev</li>
<li>PPR</li>
<li>Prod</li>
</ul>
</li>
<li>No automatic upgrades occur; changes are explicit and controlled via Git.</li>
</ul>
<p><strong>VMSS Golden Image Refresh Procedure</strong></p>
<p><strong>1.Select Golden Image Version</strong></p>
<ul>
<li>Navigate to the appropriate <strong>Golden Image Gallery</strong> for the target environment.</li>
<li>Identify the Golden Image version to be used for the refresh.</li>
</ul>
<p><strong>2. Update Packer Variables</strong></p>
<ul>
<li>Create a <strong>feature branch</strong>.</li>
<li>Update the pinned Golden Image version in the environment-specific pkrvariables file.</li>
</ul>
<p><strong>3.Merge Changes</strong></p>
<ul>
<li>Raise a <strong>Merge Request (MR)</strong> for the updated version.</li>
<li>After approval, merge the MR into the target branch.</li>
</ul>
<p><strong>Custom Image Creation</strong></p>
<ul>
<li>Trigger the <strong>custom image pipeline</strong>.</li>
<li>This pipeline:
<ul>
<li>Uses the updated Golden Image version</li>
<li>Bakes a <strong>new custom image</strong></li>
<li>Publishes a new custom image version for VMSS consumption</li>
</ul>
</li>
</ul>
<p><strong>VMSS Deployment</strong></p>
<p>Once the custom image is successfully created, deploy it using one of the following approaches:</p>
<p><strong>Option 1: Operational Pipeline</strong></p>
<ul>
<li>Use the&nbsp;<strong>operational pipeline</strong> to deploy the newly created custom image to the VMSS. Operational Pipeline is separate pipeline which will refresh the image.</li>
</ul>
<p><strong>option 2: Infrastructure Pipeline Update</strong></p>
<ul>
<li>Update the infrastructure (Terraform) pipeline code with the new custom image version.</li>
<li>Run:
<ul>
<li>terraform plan to review VMSS updates</li>
<li>terraform apply to roll out the new image</li>
</ul>
</li>
</ul>
<p><strong>Terraform Behavior</strong></p>
<ul>
<li>VMSS instances are updated to use the newly created custom image.</li>
<li>The same remote Terraform backend is used to preserve state consistency.</li>
</ul>
<p><strong>Validation and Verification</strong></p>
<p>After deployment:</p>
<ul>
<li>Validate VMSS instance health</li>
<li>Confirm successful instance provisioning</li>
<li>Verify application and service functionality</li>
<li>Monitor scale set upgrade status and error metrics</li>
</ul>
<p><strong>Image Team will provide the golden image and then we need to create custom image.</strong></p>
<p>After retrieval of Custom image used in Infra code.</p>
<p>The Golden image refresh in infra code, requires a activity which is called upgrade and there are 2 kinds of upgrade in VMSS :</p>
<p><strong>Automatic upgrade -&nbsp;</strong>VMSS instances will upgrade automatically, and this requires downtime.</p>
<p>All VMSS instances will start upgrading simultaneously and application will be down till VMSS instances is up and running.</p>
<p><strong>Manual upgrade -&nbsp;</strong>VMSS instances need to be manually upgraded, and this requires 10 - 15 minutes of degradation.</p>
<p>As part of this Upgrade - we need to manually upgrade VMSS instance one by one and so other instances will be up. There will be no downtime for the application.</p>
<p>&nbsp;</p>
<p>Bydefault VMSS will consider automatic upgrade which requires downtime. If we do not require Automatic upgrade then we need to change the setting in provider like below.</p>
<p>provider "azurerm" {<br />&nbsp; features {<br /><strong>virtual_machine_scale_set {</strong><br /><strong>&nbsp; &nbsp; &nbsp; reimage_on_manual_upgrade &nbsp; &nbsp;= false</strong><br /><strong>&nbsp; &nbsp; &nbsp; roll_instances_when_required = false</strong><br />&nbsp; &nbsp; }<br />&nbsp; }</p>
<p><strong>After updating above code in provider.tf as part of manual upgrade then update the terraform code for new golden image.&nbsp;</strong></p>
<ul>
<li>Create a New Image: Start by creating a new golden image with the latest updates and configurations using YAML pipeline.&nbsp;</li>
<li>Update Terraform Configuration: Modify your Terraform configuration to reference the new image. This involves updating the source_image_id or image_reference in your azurerm_virtual_machine_scale_set resource to point to the new image version.</li>
</ul>
<p>Example:&nbsp;</p>
<p><strong>source_image_id = "/subscriptions/subscriptionid/resourceGroups/rgname/providers/Microsoft.Compute/images/confluence-prd-v-24052450"</strong><br /><br />data_disks = [<br />&nbsp; &nbsp; {<br />&nbsp; &nbsp; &nbsp; storage_account_type &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; = "Premium_LRS"<br />&nbsp; &nbsp; &nbsp; caching &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= "ReadWrite"<br /><strong> create_option &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= "FromImage"</strong><br />&nbsp; &nbsp; &nbsp; lun &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= 0<br />&nbsp; &nbsp; &nbsp; disk_size_gb &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; = "500"<br />&nbsp; &nbsp; &nbsp; disk_encryption_set_id &nbsp; &nbsp; &nbsp; &nbsp; = null<br />&nbsp; &nbsp; &nbsp; ultra_ssd_disk_iops_read_write = null<br />&nbsp; &nbsp; &nbsp; ultra_ssd_disk_mbps_read_write = null<br />&nbsp; &nbsp; }<br />&nbsp; ]<br />instances = 3&nbsp;<br />automatic_instance_repair = [{<br />&nbsp; &nbsp; enabled &nbsp; &nbsp; &nbsp;= false<br />&nbsp; &nbsp; grace_period = "PT30M"<br />&nbsp; }]<br />computer_name_prefix &nbsp; &nbsp; &nbsp; &nbsp; = "Appname-prd"<br />overprovision &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= false<br />edge_zone &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= null<br />health_probe_id &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= null<br /><strong>upgrade_mode &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; &nbsp; = "Manual"</strong><br />single_placement_group &nbsp; &nbsp; &nbsp; = true<br />secure_boot_enabled &nbsp; &nbsp; &nbsp; &nbsp; &nbsp;= false</p>

### Metrics Filtering and Log Aggregation Now GA for Advanced Container Networking Services

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/metrics-filtering-and-log-aggregation-now-ga-for-advanced/ba-p/4516508](https://techcommunity.microsoft.com/t5/azure-networking-blog/metrics-filtering-and-log-aggregation-now-ga-for-advanced/ba-p/4516508)
- **Published**: 2026-05-20 03:13:31
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>We are thrilled to announce that Advanced Container Networking Services (ACNS) for Azure Kubernetes Service (AKS) now delivers two powerful observability features in General Availability: container network metrics filtering and container network log filtering and aggregation. Together, these capabilities set a new standard for Kubernetes network observability, giving you high-fidelity visibility at dramatically lower cost and noise. These capabilities fundamentally redefine how network observability works at scale while delivering up to 97% cost reduction.</p>
<p><strong>Why this is a Milestone?</strong></p>
<p>Most Kubernetes observability solutions face a fundamental tension: collect everything and drown in noise and cost, or sample and miss the signals that matter, with new features of Advanced Container Networking Services that tradeoff has been eliminated.</p>
<p>With this release, Azure becomes the first cloud provider to deliver on-node metrics filtering and flow log aggregation for Kubernetes networking, capabilities now also contributed to the upstream Hubble project, making them available to the broader open-source community.</p>
<p>For AKS customers running Cilium-based clusters, this means:</p>
<ul>
<li>Every flow you care about is captured. Everything else is dropped at the source.</li>
<li>Log volume is compressed by up to 45% through aggregation, without losing security verdicts or error context.</li>
<li>Costs scale with what you monitor, not with cluster size.</li>
</ul>
<p><strong>What’s been improved in observability?</strong></p>
<p>This release introduces two capabilities that work together: container network metrics filtering and container network log filtering and aggregation. Both are available on AKS clusters with the Cilium data plane and give you precise controls to keep observability costs predictable while maintaining the visibility you need.</p>
<p><strong><em>Container Network Metrics Filtering</em></strong></p>
<p>Container network metrics are generated for all pods by default whenever Advanced Container Networking Services is enabled. With metrics filtering, you now control what gets collected at the point of ingestion, on the node, before anything is scraped or transmitted.</p>
<p>A single ContainerNetworkMetric CRD per cluster defines which metric types (dns, flow, tcp, drop), namespaces, pod labels, and protocols to ingest. It supports both include and exclude filters, so you can maintain broad collection while carving out specific workloads or namespaces. Anything that doesn't match is dropped on the node. Changes reconcile in a few seconds, with no Cilium agent or Prometheus restarts required.</p>
<p><strong><em>Container Network Log Filtering and Aggregation</em></strong></p>
<p>Unlike metrics, container network logs are not generated automatically. You start capturing network flows only after applying a ContainerNetworkLog CRD that defines exactly which traffic to capture-by namespace, pod, service, protocol, or verdict. Only matching flows are logged, giving you a precise, targeted view rather than a fire hose.</p>
<p>This is where Azure's first-to-market innovation comes in. Flow log aggregation, now built into Advanced Container Networking Services and contributed upstream to Hubble for the open-source community, groups similar flows into summarized records every 30 seconds. The result is dramatically reduced data volume while preserving security verdicts, service identity, and error context. What previously required custom post-processing pipelines is now built directly into the platform before storage costs are incurred.</p>
<p>Every matched flow log captures: source and destination pods, namespaces, ports, protocols, traffic direction, and policy verdicts.</p>
<p>Logs are stored in a Log Analytics workspace (ContainerNetworkLogs table) with a choice of using the Analytics or Basic tier. Built-in Azure portal dashboards are available for both tiers. Logs can also be exported to external log collectors such as Splunk or Datadog.</p>
<p><strong>First to Market:&nbsp;</strong><strong>Azure and the upstream Hubble Contribution</strong></p>
<p>Advanced Container Networking Services built-in filtering and aggregation capabilities were engineered from the ground up to solve real production observability challenges at scale. Rather than keeping this innovation proprietary, Azure contributed the log aggregation and filtering capabilities to the upstream Hubble project, the observability layer of the Cilium ecosystem.</p>
<p>This means:</p>
<ul>
<li>AKS customers get a fully managed, Azure-native experience with portal dashboards, Log Analytics integration, and Grafana visualization, out of the box.</li>
<li>The broader open-source community gains access to the same filtering and aggregation primitives through upstream Hubble.</li>
</ul>
<p>Azure is the first to ship this capability in a managed Kubernetes service, and the first to give it back to the community.</p>
<p><strong>Key Benefits</strong></p>
<p>💰 Lower observability cost. Metrics filtering drops unwanted data on the node before Prometheus ever scrapes it. Flow log aggregation compresses log data by up to 97% in lab testing. Your cost scales with what you choose to monitor, not with cluster size.</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<p>📉 Less noise, more signal. Metrics filtering carves out the namespaces and workloads that matter, so dashboards show only relevant signals. Log filters scope collection to specific pods and verdicts. Engineers start every investigation with data that's already relevant.</p>
<p>⚡ Faster root-cause isolation. Every metric carries source and destination pod context. Targeted flow logs add the forensic detail, which policy, destination, or port is involved. Together, they cut mean time to resolution from hours of guesswork to minutes of structured investigation.</p>
<p>🔒 Full signal, zero gaps. Within the scope you define, every flow is captured and every pattern is preserved. Aggregation compresses volume without losing security verdicts or error context.</p>
<p><strong>Who Benefits</strong></p>
<p>Platform engineers managing multi-tenant clusters can scope data collection per namespace, so each team gets visibility into their own traffic without contributing to a shared cost pool.</p>
<p>SREs can isolate packet drops, TCP resets, or DNS failures to a specific workload in minutes, starting with data that's already scoped to what matters.</p>
<p>Decision-makers evaluating observability spend get predictable, controllable ingestion costs that scale with intent, not infrastructure size.</p>
<p><strong>How to optimize metrics and logs with filtering?</strong></p>
<ol>
<li>Enable Advanced Container Networking Services ( ACNS) on your AKS cluster with the Cilium data plane:</li>
</ol>
<p><em>az aks create --enable-acns</em></p>
<p>Or on an existing cluster:</p>
<p><em>az aks update --resource-group $RESOURCE_GROUP --name $CLUSTER --enable-acns</em></p>
<ol start="2">
<li>Apply a ContainerNetworkMetric CRD to filter which metrics are collected on each node. Start by excluding noisy system namespaces, then scope to business-critical workloads.</li>
<li>Apply a ContainerNetworkLog CRD to define which flows to capture.</li>
<li>Enable Azure Monitor integration with --enable-container-network-logs to send logs to a Log Analytics workspace, or export logs from the node to an external logging system such as Splunk or Datadog.</li>
<li>Check your dashboards. Open your cluster in the Azure portal and go to Monitor &gt; Insights &gt; Networking for bytes, drops, DNS errors, and flows. For flow logs, use the built-in Azure portal dashboards available for both Basic and Analytics tiers.</li>
</ol>
