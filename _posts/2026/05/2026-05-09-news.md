### Safely Migrating Terraform Managed Disks on Azure Using Stable Keys and Copilot

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/safely-migrating-terraform-managed-disks-on-azure-using-stable/ba-p/4517509](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/safely-migrating-terraform-managed-disks-on-azure-using-stable/ba-p/4517509)
- **Published**: 2026-05-09 01:02:01
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<h2><span style="color: rgb(30, 30, 30); font-size: 32px;">The Root Cause: Index-Based "for_each" Keys:</span></h2>
<h4>Many Terraform modules flatten VM and disk definitions into a list and use the list index as the for_each key:</h4>
<h4><strong>for_each = { for index, sp in local.managed_disks : index =&gt; sp }</strong></h4>
<h4>This pattern looks harmless, but the index is not stable:</h4>
<ul>
<li><em>Adding a disk to one VM shifts downstream indices</em></li>
<li><em>Reordering environment JSON changes flatten order</em></li>
<li><em>Terraform treats shifted indices as new resources</em></li>
</ul>
<h4>The result: Terraform plans to destroy and recreate all affected managed disks—even though nothing changed in Azure.</h4>
<h2>Why This Is Especially Risky on Azure:</h2>
<h4>Azure managed disks are often:</h4>
<ul>
<li><em>Attached to stateful application tiers</em></li>
<li><em>Used for databases, middleware, or batch workloads</em></li>
<li><em>Deployed across zones for resiliency</em></li>
</ul>
<h4>A forced disk replacement can mean:</h4>
<ul>
<li><em>Data loss</em></li>
<li><em>Extended outages</em></li>
<li><em>Failed change windows</em></li>
</ul>
<h4>This makes state stability a first-class design concern—not an implementation detail.</h4>
<h2>The Stable Key Pattern:</h2>
<h4>The fix is conceptually simple: use a domain-stable identifier for each disk.</h4>
<h4>A proven pattern is:</h4>
<h4><strong>"${sp.vm}-${sp.data_disk.lun}"</strong></h4>
<h4>This key is:</h4>
<ul>
<li>Deterministic</li>
<li>Independent of ordering</li>
<li>Human-readable</li>
<li>Stable across environments</li>
</ul>

<h4>Once applied, adding a new disk results in exactly one new resource, with zero churn.</h4>
<h2>The Migration Challenge: Terraform State:</h2>
<h4>Changing <strong>for_each</strong> keys alone is not enough.</h4>
<h4>Terraform tracks resources by their state address, not by Azure resource ID. When keys change, Terraform believes:</h4>
<h4><strong>“The old disks were deleted, and new ones must be created.”</strong></h4>
<h4>To prevent this, we must move the state, not recreate the resource.</h4>
<h4>That is where terraform state mv comes in.</h4>
<h2>Automating the Migration with GitHub Copilot Skills:</h2>
<h4>To remove risk and human error, the team created a reusable Copilot skill for managed disk key migration.</h4>
<h3>What the Skill Does:</h3>
<ul>
<li><em>Inspects Terraform modules for index-based for_each</em></li>
<li><em>Reads environment JSON files (such as ALZ variable abstractions)</em></li>
<li><em>Reconstructs the exact flatten order used by Terraform</em></li>
<li><em>Generates precise terraform state mv commands</em></li>
</ul>
<h5>This ensures:</h5>
<ul>
<li><em>No guessing</em></li>
<li><em>No manual address mapping</em></li>
<li><em>No production surprises</em></li>
</ul>
<h5>The skill is stored directly inside the repository under .github/skills, making it:</h5>
<ul>
<li><em>Discoverable</em></li>
<li><em>Versioned</em></li>
<li><em>Shareable across teams</em></li>
</ul>
<h2>Example: Generating State Move Commands:</h2>
<h4>Based on environment JSON, Copilot can generate commands like:</h4>
<p><strong>terraform state mv \</strong></p>
<p><strong>&nbsp; 'module.managed_disk_windowsvm_app["0"]' \</strong></p>
<p><strong>&nbsp; 'module.managed_disk_windowsvm_app["vm1-0"]'</strong></p>
<h4>This is repeated deterministically for every existing disk—before any plan or apply.</h4>
<h2>Recommended Migration Workflow:</h2>
<ol>
<li>
<h5>Confirm clean state</h5>
<ul>
<li><em>terraform plan shows no pending changes</em></li>
</ul>
</li>
<li>
<h5>Update the module</h5>
<ul>
<li><em>Replace index-based keys with stable keys</em></li>
</ul>
</li>
<li>
<h4>Back up the state</h4>
<ul>
<li><em>Especially critical with remote backends (Azure Storage)</em></li>
</ul>
</li>
<li>
<h4>Run terraform state mv</h4>
<ul>
<li><em>Only after terraform init is connected to the correct backend</em></li>
</ul>
</li>
<li>
<h4>Re-run plan</h4>
<ul>
<li><em>Existing disks should show no changes</em></li>
</ul>
</li>
<li>
<h4>Add new disks safely</h4>
<ul>
<li><em>Terraform creates only the new disk</em></li>
</ul>
</li>
</ol>
<h2>CI/CD and Remote Backend Considerations:</h2>
<h4>A critical finding from this migration:</h4>
<h4><strong>terraform state mv</strong> always modifies the currently initialized backend.</h4>
<h4>In pipeline-driven environments:</h4>
<ul>
<li><em>Ensure the correct environment is initialized</em></li>
<li><em>Run migrations once per environment</em></li>
<li><em>Never merge stable-key code before migrating all environments</em></li>
</ul>
<h4>Failing to align code and state can cause disk destruction in production.</h4>
<h2>Key Takeaways:</h2>
<ul>
<li><em>Index-based for_each keys are unsafe for long-lived Azure disks</em></li>
<li><em>Stable keys such as vm-lun eliminate accidental resource churn</em></li>
<li><em>State migration is mandatory—not optional</em></li>
<li><em>Copilot skills are powerful for institutionalizing safe patterns</em></li>
<li><em>Small Terraform design choices can have enterprise-scale impact</em></li>
</ul>
<h2>Closing Thoughts:</h2>
<h4>This pattern is broadly applicable beyond disks—to NICs, extensions, and any resource where identity must outlive ordering.</h4>
<h4>By combining:</h4>
<ul>
<li>
<p><em>Stable Terraform design</em></p>
</li>
<li>
<p><em>State-aware migrations</em></p>
</li>
<li>
<p><em>GitHub Copilot automation</em></p>
</li>
</ul>
<h4>Teams can make infrastructure changes boring again—and that is the ultimate reliability goal.</h4>

### CHERIoT-Ibex: Closing the door on memory safety vulnerabilities with hardware-enforced protection

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/cheriot-ibex-closing-the-door-on-memory-safety-vulnerabilities/ba-p/4517904](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/cheriot-ibex-closing-the-door-on-memory-safety-vulnerabilities/ba-p/4517904)
- **Published**: 2026-05-09 14:08:11
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><span>Memory safety vulnerabilities—largely arising&nbsp;from widely used programming languages such as C and C++—remain&nbsp;a leading cause of exploitable software defects across systems, from embedded devices to&nbsp;cloud-scale&nbsp;infrastructure. In simple terms, memory safety ensures that software accesses only the data it is intended to use; when this protection fails, attackers can exploit these defects to gain control of devices or disrupt critical services. </span><span>&nbsp;</span></p>
<p><span>Industry data shows that&nbsp;about 70 percent&nbsp;of the vulnerabilities Microsoft assigns as&nbsp;Common Vulnerabilities and Exposures (CVE)&nbsp;each year are memory safety issues, highlighting how&nbsp;frequently&nbsp;these software defects translate into&nbsp;real-world&nbsp;security risk (</span><a href="https://www.cisa.gov/news-events/news/urgent-need-memory-safety-software-products" rel="noopener" target="_blank"><span><span>CISA – The Urgent Need for Memory Safety in Software Products</span></span></a><span>). Hardware-enforced&nbsp;protections such&nbsp;as&nbsp;CHERIoT</span><span>-</span><span>Ibex&nbsp;can help&nbsp;eliminate&nbsp;these vulnerabilities at their source, reducing the likelihood that low-level software flaws can be exploited to compromise devices or disrupt workloads, supporting more trustworthy infrastructure by design. </span>&nbsp;<br />&nbsp;<br /><strong><span>An open and certified foundation for memory-safe embedded systems</span><span>&nbsp;</span></strong></p>
<p><span>CHERIoT-Ibex is the first open-source production-quality implementation of the&nbsp;CHERIoT&nbsp;instruction set architecture and among the first cores certified by the CHERI Alliance (</span><a href="https://cheri-alliance.org/cheri-enabled/cheriot/" rel="noopener" target="_blank"><span><span>CHERI Alliance – CHERIoT</span></span></a><span>). CHERIoT is an extension of&nbsp;the&nbsp;CHERI&nbsp;(Capability Hardware Enhanced RISC Instructions)&nbsp;instruction&nbsp;set,&nbsp;with&nbsp;a focus on embedded and Internet of Things (IoT) applications.&nbsp;Ibex is&nbsp;an&nbsp;open</span>‑<span>source&nbsp;32</span>‑<span>bit RISC</span>‑<span>V core developed by&nbsp;LowRISC.&nbsp;CHERIoT</span>‑<span>Ibex&nbsp;builds on Ibex by including CHERIoT capability extensions to provide&nbsp;hardware</span>‑<span>enforced&nbsp;memory safety and&nbsp;fine</span>‑<span>grained&nbsp;compartmentalization.&nbsp;It&nbsp;is the result of a close partnership between Microsoft Research and Azure Hardware Systems &amp; Infrastructure, combining advanced research innovation with industry-leading silicon IP development expertise. </span><span>&nbsp;</span></p>
<p><span>In 2023, Microsoft&nbsp;open-sourced&nbsp;the CHERIoT&nbsp;Platform&nbsp;to bring hardware-enforced memory safety to embedded systems, including an instruction set architecture, toolchain, real-time operating system, and the&nbsp;RTL implementation of the CHERIoT-Ibex core. The CHERI Alliance certification recognizes its ability to provide spatial and temporal memory safety, fine-grained compartmentalization, and compatibility with the broader CHERI ecosystem. Critically, CHERIoT-Ibex achieves these security guarantees with power and area efficiency comparable to low-cost microcontrollers,&nbsp;demonstrating&nbsp;that security&nbsp;doesn’t&nbsp;have to come at a premium. </span>&nbsp;<br /><span>&nbsp;</span></p>
<p><strong><span>Why memory safety&nbsp;remains&nbsp;a&nbsp;foundational security challenge</span><span>&nbsp;</span></strong></p>
<p><span>Traditional embedded and&nbsp;microcontroller-class&nbsp;designs rely on software hardening and&nbsp;coarse-grained&nbsp;hardware protections that struggle to prevent attacks such as buffer overflows and&nbsp;use-after-free&nbsp;vulnerabilities, often adding complexity while still leaving gaps in protection. </span><span>&nbsp;</span></p>
<p><span>Consider a controller that runs privileged firmware responsible for device initialization, telemetry, and system health monitoring, while also hosting networking functionality exposed to external inputs. A&nbsp;memory-safe&nbsp;vulnerability in the networking stack could allow attackers to execute unauthorized code within the firmware environment, potentially affecting other critical services on the device. In tightly integrated&nbsp;systems,&nbsp;these failures can propagate beyond a single&nbsp;component, increasing overall risk.</span><span>&nbsp;</span></p>
<p>&nbsp;<br /><strong><span>Constraining failures with&nbsp;hardware-enforced&nbsp;isolation</span><span>&nbsp;</span></strong></p>
<p><span>CHERIoT-Ibex&nbsp;enables&nbsp;hardware-enforced&nbsp;isolation between these components, helping ensure that even if the networking stack is compromised, its ability to&nbsp;impact&nbsp;system initialization or telemetry functions&nbsp;remains&nbsp;constrained. By limiting the blast radius of software failures,&nbsp;CHERIoT-Ibex&nbsp;supports a system-level approach to security rather than relying on individual components to defend themselves in isolation.</span><span>&nbsp;</span></p>
<p>&nbsp;<br /><strong><span>Advancing&nbsp;memory-safe&nbsp;infrastructure by design</span><span>&nbsp;</span></strong></p>
<p><span>CHERIoT-Ibex’s certification by the CHERI Alliance marks an important milestone for open-source&nbsp;memory-safe solutions. It&nbsp;validates&nbsp;that strong security guarantees can coexist with efficiency and transparency, reflecting Microsoft’s broader silicon-to-systems strategy&nbsp;of&nbsp;embedding&nbsp;security into&nbsp;the&nbsp;foundational hardware infrastructure.</span><span>&nbsp;</span></p>
<p><span>Explore and engage with the open-source CHERIoT ecosystem by visiting the CHERIoT Platform and the CHERIoT-Ibex GitHub repository (</span><a href="https://github.com/microsoft/cheriot-ibex" rel="noopener" target="_blank"><span><span>microsoft/cheriot-ibex</span></span></a><span>). The repositories enable developers and researchers to experiment with, contribute to, and&nbsp;build on&nbsp;memory-safe hardware and software foundations. </span><span>&nbsp;</span></p>
