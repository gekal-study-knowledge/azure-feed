### Build and govern AI agents across a multitenant organization

<h3>Why this architecture exists</h3>
<p>Enterprises want more people building AI agents, not fewer. Business users understand the processes that should be automated. Makers need low-code tools. Developers need complete control over orchestration, tools, identity, deployment, and runtime behavior.</p>
<p>The difficult part is not creating the first agent.</p>
<p>The difficult part is operating hundreds or thousands of agents safely across business units that may have different Microsoft Entra tenants, different data stores, different regulatory obligations, different budgets, and different levels of autonomy.</p>
<p>A parent organization might want common standards for identity, security, evaluation, observability, and cost while its subsidiaries retain local control of data and runtime operations. In some organizations, those subsidiaries even compete with one another. In that environment, copying all data and agent state into one central tenant would weaken the very boundaries the organization created.</p>
<p>This architecture therefore uses a <strong>federated agent factory</strong>:</p>
<ul>
<li>Centralize standards, deployment patterns, governance views, and operational oversight.</li>
<li>Keep agent identities, business data, detailed telemetry, and runtime enforcement local to the owning tenant unless there is a documented reason to centralize them.</li>
<li>Use the Microsoft service that fits each layer instead of assuming one product is the "control plane" for everything.</li>
<li>Govern both Microsoft-managed agents and custom/pro-code agents, but use different enforcement mechanisms where the runtime model differs.</li>
</ul>
<p>The result is a common enterprise operating model without collapsing tenant boundaries.</p>
<p>&nbsp;</p>
<h1>Five architectural principles</h1>
<h2>1. Centralize governance, not tenant data</h2>
<p>The governing tenant should own shared standards, templates, cross-tenant administrative relationships, and consolidated operational views.</p>
<p>Each subsidiary should continue to own:</p>
<ul>
<li>its Microsoft Entra identities,</li>
<li>its production agents,</li>
<li>its business data,</li>
<li>its tenant-specific permissions,</li>
<li>its detailed prompt/response telemetry where required,</li>
<li>its local audit evidence,</li>
<li>and its runtime policy enforcement.</li>
</ul>
<p>This minimizes the chance that a central governance failure becomes a cross-subsidiary data leak or a runtime outage.</p>
<h2>2. Give every governed agent a clear identity and owner</h2>
<p>AI agents are nonhuman actors. They should not operate through shared secrets or generic service accounts.</p>
<p>Where the platform provides one, use <strong>Microsoft Entra Agent ID</strong> so that each agent has a first-class identity, sponsor, permissions, sign-in history, and lifecycle.</p>
<p>Agent identities are <strong>single-tenant</strong>. A multitenant agent identity blueprint can be published to other tenants, where it creates tenant-local agent identities. This is exactly the pattern needed for a federated organization: one security blueprint, many locally owned identities.</p>
<h2>3. Treat tools as governed enterprise capabilities</h2>
<p>Agents should not receive broad database credentials and unrestricted query access.</p>
<p>Developers should expose narrow, typed capabilities such as:</p>
<p>invoice.lookup invoice.process approval.request order.status customer.lookup case.create sop.search</p>
<p>Those capabilities should be versioned and published through governed APIs or Model Context Protocol (MCP) servers.</p>
<p>This separates responsibilities cleanly:</p>
<ul>
<li>Business experts define what the agent is allowed to do.</li>
<li>Developers implement how tools work.</li>
<li>Security and platform teams enforce who may call them and under what conditions.</li>
</ul>
<h2>4. Make governance a runtime property</h2>
<p>Design-time reviews are necessary but insufficient.</p>
<p>The platform must still check sensitive actions when the agent runs:</p>
<ul>
<li>Who is calling?</li>
<li>Which agent is acting?</li>
<li>What action is being attempted?</li>
<li>Which resource is targeted?</li>
<li>What is the data classification?</li>
<li>Which policy version applies?</li>
<li>Is a human approval required?</li>
<li>Is the action allowed right now?</li>
</ul>
<p>This requires a chain of runtime enforcement points, not a single "AI policy" checkbox.</p>
<h2>5. Observe quality, security, reliability, and value together</h2>
<p>A production agent is not healthy merely because the endpoint returns HTTP 200.</p>
<p>The organization needs to know:</p>
<ul>
<li>Did the agent complete the business task?</li>
<li>Did it choose the correct tool?</li>
<li>Did it follow the SOP?</li>
<li>Did it expose restricted data?</li>
<li>Did the model or tool fail?</li>
<li>What did the invocation cost?</li>
<li>How much human work did the agent avoid?</li>
<li>Did quality regress after a new release?</li>
</ul>
<p>The architecture therefore treats observability and evaluation as part of the runtime operating model, not as optional debugging tools.</p>
<h2 id="architecture">Architecture</h2>
<p>The platform has four parts: authoring surfaces, a control plane, runtime enforcement, and operations. People author agents across three surfaces, from no-code to pro-code. One control plane, Microsoft Agent 365, provides the central inventory and governance view for supported registered agents and connected platforms, and depending on agent type, integration, licensing, and discovery coverage it can also surface unmanaged or shadow-agent activity for investigation and onboarding. Platform-specific runtime controls enforce governance as agents operate, and an operations plane provides visibility. The following diagram shows the platform at a glance.</p>
<img />
<p>The detailed architecture shows the same platform as three planes over a shared data foundation, with the shared services and the federated deployment. Some services, such as Microsoft Purview, appear in more than one plane because a plane shows where a control is configured and where its effect is enforced or observed, not a single owning product. The customer-controlled gateway applies only to pro-code paths that are explicitly configured and network-restricted to use it; Microsoft-managed agent runtimes use their native governance controls, and custom authorization can still apply where those agents call customer-controlled tools or APIs.</p>
<img />
<h3 id="workflow">Workflow</h3>
<p>The reference implementation uses the following workflow, and the numbers match the numbered markers on the detailed diagram. Each marker sits on the capability that performs the step, so a step can appear in the plane that hosts its capability rather than in strict left-to-right order. For example, evaluation (step 5) is a design-time release gate but runs on the operations-plane observability capability. Steps 1 through 6 define, govern, and validate the agent before release. Steps 7 through 10 enforce controls on every action at runtime. Steps 11 through 14 observe, measure, deploy, and federate.</p>
<ol>
<li>
<p><strong>Catalog governed data and knowledge.</strong> A business owner registers the approved data sources and knowledge that an agent can use in a governed catalog. Each entry is versioned, owned, and classified. The catalog keeps bidirectional links between a data source and the agents that use it, so a later change to a source flags the affected agents for review.</p>
</li>
<li>
<p><strong>Author the specification.</strong> A business user or maker uses a no-code or low-code authoring studio to define the agent from a template. The specification declares intent, typed inputs and outputs with classification labels, permitted tools, permitted data sources, escalation and checkpoint rules, the allowed collaboration graph, a budget, and a value baseline for ROI. No code is required to define behavior.</p>
</li>
<li>
<p><strong>Register the agent and capability.</strong> The specification registers in an agent and capability registry. In this architecture, the platform's registration workflow requires a valid approved specification and governed data references before an agent can promote to production. Where the platform provides an agent identity, registration associates the agent with a scoped identity.</p>
</li>
<li>
<p><strong>Build tools with typed contracts.</strong> Developers implement tools behind typed, versioned Model Context Protocol (MCP) contracts and register them in a capability catalog. Developers supply tools, not agent behavior. Each tool has least-privilege scope, so no single tool has broad, unrestricted access.</p>
</li>
<li>
<p><strong>Evaluate before release.</strong> An evaluation and simulation stage runs the agent against golden test sets, runs it in shadow mode, and checks for behavioral drift. This stage is a release toll-gate. An agent that regresses or that doesn't meet its approved specification doesn't promote.</p>
</li>
<li>
<p><strong>Promote through governance.</strong> A stage-gated governance workflow moves the capability through review, approval, and promotion. Higher data classification adds more gates. Every approval is recorded as immutable evidence, and production is pinned to an exact immutable artifact version so that rollback is a pointer change.</p>
</li>
<li>
<p><strong>Route custom-agent invocations through the gateway.</strong> For pro-code agents on Microsoft Foundry, the runtime calls a routing and orchestration gateway that's the enforcement point for that path. The gateway performs a policy pre-check, authenticates the caller, enforces token and rate limits, applies content safety, and routes to the model. The platform makes the gateway mandatory by configuring each Foundry agent's model and tool endpoints to target the gateway and blocking direct network egress, so an agent can't bypass the enforcement point. Agents built in Copilot Studio or Microsoft 365 Copilot run on Microsoft-managed runtime and are governed by the control plane (Agent 365 and Microsoft Purview, plus a Microsoft Entra Agent ID where the platform provides one) rather than this gateway.</p>
</li>
<li>
<p><strong>Enforce policy at runtime.</strong> For the customer-controlled path, the architecture requires every in-scope sensitive action to traverse a policy enforcement point that calls the policy decision point. An in-scope sensitive action is one that the specification or policy designates as consequential, such as writing to a system of record, reaching higher-classification data, or spending budget. In this architecture, the decision point sits on the mandatory customer-controlled execution path. During a brief control-plane outage, the enforcer evaluates against cached policy so that transient unreachability doesn't block legitimate actions; cached decisions expire after a defined time-to-live, and the highest-risk actions are excluded from caching and always require a fresh decision. A request that still can't obtain an applicable decision fails closed, and every denial produces an audit event.</p>
</li>
<li>
<p><strong>Reach data only through governed tools.</strong> The architecture requires production agents to reach governed external systems through approved MCP tools or equivalent governed interfaces. A classification-aware data access layer compares the caller's clearance to the data classification before it returns results, so the access layer prevents data from being returned to a caller or destination that isn't authorized for the data's classification. Source-system controls remain authoritative, and the tool returns governed results rather than bulk extracts.</p>
</li>
<li>
<p><strong>Apply guardrails and human checkpoints.</strong> A guardrails engine validates input for prompt-injection attempts, authorizes tool calls, and checks output for sensitive-data exposure and format compliance. Human-in-the-loop checkpoints that the spec declares pause high-risk actions for approval.</p>
</li>
<li>
<p><strong>Record evidence.</strong> Each invocation emits OpenTelemetry-compatible traces with correlation IDs and writes tamper-evident records to an immutable audit store. Telemetry captures cost and latency. Classification-aware redaction keeps sensitive content out of the central views.</p>
</li>
<li>
<p><strong>Measure value.</strong> A business value and ROI capability quantifies value from execution telemetry against a documented manual baseline, attributes value per capability, rolls up to the business-unit level, and forecasts trends.</p>
</li>
<li>
<p><strong>Deploy and roll back safely.</strong> A deployment and rollback capability pins production to an exact immutable artifact version, so rollback is a pointer change to the prior artifact. Foundry hosted agents serve one active version at a time; to run blue-green or canary releases, implement weighted routing across separate agent endpoints through the gateway rather than relying on native traffic splitting. Automated triggers include evaluation regression, a policy-violation spike, and an error-rate breach of the service-level agreement.</p>
</li>
<li>
<p><strong>Deploy build-once across the federation.</strong> An infrastructure-as-code factory stamps the identical customer-controlled governance and enforcement infrastructure into each participating tenant. The Microsoft-managed services (Agent 365, Copilot Studio, Agent Builder, and Foundry-hosted runtime) are Microsoft-managed platform capabilities that the factory configures rather than deploys. A governing tenant receives delegated operational and identity views through consented, least-privileged relationships. In this architecture, agents, business data, detailed telemetry, and audit records remain in their source tenants; the governing tenant receives delegated administrative access and aggregated operational views rather than a replicated central data store.</p>
</li>
</ol>
<h3 id="components">Components</h3>
<p>The components are grouped by the plane they serve. Most capabilities use Microsoft or Azure services. Where no single Microsoft product provides the required capability, the architecture composes multiple services or uses a standard open-source component hosted on Azure.</p>
<h4 id="data-foundation-and-control-plane">Data foundation and control plane</h4>
<ul>
<li>
<p><a href="https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-intro" rel="noopener" target="_blank">Microsoft Dataverse</a> and <a href="https://learn.microsoft.com/sharepoint/introduction" rel="noopener" target="_blank">SharePoint in Microsoft 365</a> provide governed, versioned stores. In this architecture, either one holds the data and knowledge catalog with ownership, classification, approval workflow, and links to the agents that use each source.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/azure/search/search-what-is-azure-search" rel="noopener" target="_blank">Azure AI Search</a> provides retrieval over enterprise content. In this architecture, it grounds agents in governed knowledge so that answers come from approved sources, and indexed permission and classification metadata, together with application-supplied security filters, restrict retrieval to content the caller is authorized to access.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/microsoft-365/copilot/extensibility/agents-overview" rel="noopener" target="_blank">Agent Builder in Microsoft 365 Copilot</a> builds declarative agents. In this architecture, it's the no-code authoring surface for business users, and declarative agents inherit Microsoft 365 security and compliance controls.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/microsoft-copilot-studio/fundamentals-what-is-copilot-studio" rel="noopener" target="_blank">Microsoft Copilot Studio</a> is a low-code studio for building and managing agents. In this architecture, it's the low-code authoring surface for makers, and an agent built here participates in the same governance model through the Microsoft-managed runtime.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/entra/agent-id/what-is-microsoft-entra-agent-id" rel="noopener" target="_blank">Microsoft Entra Agent ID</a> gives each agent a first-class identity in Microsoft Entra ID. An agent identity is a specialized service principal created from an agent identity blueprint. The agent identity doesn't hold credentials itself; the blueprint authenticates and acquires tokens on its behalf. In this architecture, the registry associates each registered agent with a scoped agent identity that has least-privilege permissions, conditional access, sign-in logs, and lifecycle controls. Agent identities are tenant-local, and for a federated organization a multitenant blueprint creates a corresponding identity in each business-unit tenant.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/microsoft-agent-365/overview" rel="noopener" target="_blank">Agent 365</a> is the control plane for agents across the Microsoft 365 admin center, Microsoft Entra, and Microsoft Purview. In this architecture, it provides the authoritative agent inventory and governance view, and it shows each supported agent's owner, permissions, activity, risk state, and certification. It governs supported agents whatever surface built them, including agents that carry a Microsoft Entra Agent ID and Agent Builder agents that don't, and depending on agent type, integration, licensing, and discovery coverage it surfaces unmanaged ones as shadow agents for investigation and onboarding. A platform-owned capability registry, implemented with Microsoft Dataverse or SharePoint and integrated with Agent 365, stores the approved specification, governed data references, typed tool contracts, evaluation evidence, promotion state, and ROI baseline; those are platform extensions rather than native Agent 365 features. Microsoft Agent 365 is generally available and licensed per user. It is included with Microsoft 365 E7 and is also available as a standalone subscription for eligible Microsoft 365 plans. Licensing and prerequisite requirements vary by capability.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/azure/api-center/overview" rel="noopener" target="_blank">Azure API Center</a> inventories APIs, and its Model Context Protocol support catalogs agent tools. In this architecture, it's the capability catalog that registers vetted tools with typed contracts and classification-aware visibility.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/azure/container-registry/container-registry-intro" rel="noopener" target="_blank">Azure Container Registry</a> is an Open Container Initiative-compliant registry. In this architecture, it's the immutable, content-addressable artifact repository for tool and runtime images, so production pins to exact version hashes.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/azure/logic-apps/logic-apps-overview" rel="noopener" target="_blank">Azure Logic Apps</a> automates workflows across services with connectors and approval steps. In this architecture, it orchestrates the stage-gated governance workflow that moves a capability through review, approval, and promotion, and the workflow writes approval evidence and release metadata to the platform's immutable evidence store at each gate.</p>
</li>
<li>
<p><a href="https://learn.microsoft.com/azure/governance/policy/overview" rel="noopener" target="_blank">Azure Policy</a> evaluates and enforces resource configuration standards. In this architecture, it governs how the platform infrastructure is built across every tenant, such as approved regions, encryption, private networking, required diagnostics, and required tags, and business units can add more restrictive controls. Azure Policy governs resource configuration. It's distinct from the runtime policy decision point, which authorizes individual agent actions.</p>
</li>
<li>
<p>A policy decision point authorizes individual agent actions from declarative, version-controlled rules. In this architecture, it evaluates a hierarchical policy namespace in which the enterprise level is non-overridable and each lower level (business unit, team, agent) can only add restrictions. There's no single Microsoft product for per-action agent authorization, so this component uses a declarative policy-as-code engine such as <a href="https://www.openpolicyagent.org/" rel="noopener" target="_blank">Open Policy Agent</a>, which runs as a container on Azure compute and returns an allow-or-deny decision on every sensitive call.</p>
</li>
</ul>
<h4 id="execution-plane">Execution plane</h4>
<ul>
<li>
<p><a href="https://learn.microsoft.com/azure/foundry/what-is-foundry" rel="noopener" target="_blank">Microsoft Foundry</a> is a platform for building and running AI agents, models, and tools with built-in identity, role-based access control, content filtering, and Azure Policy support. In this architecture, it hosts agents and provides the per-invocation agent runtime with isolation and resource limits.</p>
</li>
<li>

<h2 id="scenario-details">Scenario details</h2>
<p>A governed agent platform addresses a specific tension. Business users and makers, not only developers, understand the work worth automating, but an enterprise can't let arbitrary agents reach data and take actions without governance. This tension grows across the multiple tenants that many enterprises operate. The platform resolves the tension by separating three concerns and enforcing the separation in the platform rather than in a review process.</p>
<ul>
<li><strong>Business users and makers define what an agent does.</strong> They author a specification that references approved, classified data sources. They select permitted tools and data domains from a catalog, and they declare escalation and checkpoint rules.</li>
<li><strong>Developers define how tools work.</strong> They build typed, versioned tool contracts and register them. They don't define agent behavior.</li>
<li><strong>Security and platform enforce both.</strong> Security authors the classification taxonomy and policy rules. The platform enforces those rules at runtime.</li>
</ul>
<h3 id="assumptions">Assumptions</h3>
<p>How completely the control plane governs each agent depends on these conditions being in place:</p>
<ul>
<li><strong>Agents have a platform-issued identity where the platform provides one.</strong> Newly created agents built with Microsoft Copilot Studio and custom agents hosted on Microsoft Foundry receive a Microsoft Entra Agent ID. Agent Builder agents in Microsoft 365 Copilot don't currently use an Entra Agent ID, but Agent 365 still discovers and governs them. An agent identity is a specialized, tenant-local service principal; the agent identity blueprint holds the credentials and acquires tokens on the identity's behalf. An agent that discovery surfaces but that isn't brought under approved management appears as an unmanaged or shadow agent rather than a governed entry; an agent outside available discovery coverage might remain undetected.</li>
<li><strong>Each production agent is registered and has an owner.</strong> Registration brings the agent into the platform's approved production lifecycle and associates it with ownership, governance metadata, and applicable controls. Agent 365 can also discover agents that haven't completed this approved registration workflow and surface them for governance.</li>
<li><strong>The tenant is licensed and enrolled.</strong> Microsoft Agent 365 requires per-user Agent 365 licensing, which the tenant has assigned to the relevant users. In a federated organization, each business-unit tenant is enrolled in the registry, and central administration uses a Microsoft Entra Tenant Governance (preview) relationship.</li>
<li><strong>Several platform dependencies are in preview.</strong> Microsoft Entra Tenant Governance, multitenant agent management in the Microsoft 365 admin center, and the Azure API Management dedicated AI Gateway tier are in preview at the time of writing. The AI Gateway tier has no service-level agreement and is available in limited regions. Confirm current status, service-level agreements, and regional availability before you depend on these capabilities in production.</li>
<li><strong>Cross-tenant governance uses multitenant blueprints.</strong> Because an agent identity receives tokens only in the tenant where it's created, a federated organization publishes multitenant agent identity blueprints that create tenant-local identities, and the governing tenant administers them through consented, least-privileged relationships rather than a central copy.</li>
</ul>
<h3 id="potential-use-cases">Potential use cases</h3>
<ul>
<li>A business operations team in retail or distribution automates documented procedures, such as order status, warranty returns, or pricing lookups, with agents that can't exceed the procedure's scope.</li>
<li>A parent company in manufacturing or consumer goods lets independently operated subsidiaries build their own agents while it keeps consistent, central oversight of posture, cost, and evaluation results.</li>
<li>A regulated organization in finance, healthcare, or government needs every agent action traced to a policy set and an artifact version, with tamper-evident audit evidence held under local custody.</li>
<li>A platform team in a large enterprise industrializes agent delivery, so business experts self-serve within guardrails instead of filing tickets for a central team to build each agent.</li>
<li>An organization in energy or telecommunications with a multicloud data estate lets agents interact with data where it already resides, without moving it into a central store.</li>
</ul>
<h3 id="when-not-to-use-this-pattern">When not to use this pattern</h3>
<ul>
<li>A single team runs a handful of agents in one tenant, with no federation, delegation, or cross-business-unit oversight requirement. The control plane and delegated-governance machinery add overhead that a small, single-owner deployment doesn't need.</li>
<li>Agents don't reach sensitive or classified data and don't take consequential actions, so runtime policy enforcement and classification-aware data access add cost without reducing meaningful risk.</li>
<li>Orchestration is fully deterministic and hard-coded, with no business-user or maker authoring, so the no-code and low-code surfaces and the specification-driven registry provide little value.</li>
<li>Data-residency or regulatory rules require a single, centrally controlled tenant. Use the single-tenant form of this pattern and skip the cross-tenant federation.</li>
</ul>
<h3 id="data-grounded-spec-driven-design">Data-grounded, spec-driven design</h3>
<p>Every agent is grounded in governed data and a reviewed specification, which the platform's registration workflow enforces. This constraint delivers several benefits at once. It gives each agent a documented justification. It bounds each agent's scope to the data sources and actions that its specification approves, which prevents scope creep. It inherits the classification and compliance context of the data it uses. It ties change management to the data catalog, so a change to a source flags the agents to review. It also makes coverage visible, because the catalog shows which data is in use, by which agents, and at what classification.</p>
<h3 id="authoring-across-no-code-low-code-and-pro-code">Authoring across no-code, low-code, and pro-code</h3>
<p>People build agents in the surface that fits them, and the platform applies one governance model with platform-specific enforcement paths and centralized visibility. Business users build no-code declarative agents with Agent Builder in Microsoft 365 Copilot. Makers build low-code agents with Microsoft Copilot Studio. Developers build pro-code agents with Microsoft Foundry. The architecture requires each production agent to be discoverable and governed through Agent 365, with a registry entry, and it constrains enterprise data and tool access to approved governed paths. The authoring surface changes, and the enforcement mechanism differs per surface, but the governance objectives, the audit trail, and the visibility stay consistent.</p>
<h3 id="governance-as-a-runtime-property">Governance as a runtime property</h3>
<p>The platform enforces governance while an agent runs, not only when a human reviews a design. A runtime policy enforcer calls a policy decision point for every sensitive action on the customer-controlled path. The decision point sits on the mandatory execution path for that lane, and a request that can't obtain a decision fails closed. This split of decision from enforcement lets security change rules without touching the enforcement plumbing, and it lets one decision service serve many enforcement points. The enforcement points form a defense-in-depth chain: the gateway checks identity and request validity, tool invocation checks permission and classification, data access checks clearance and domain boundaries, collaboration checks the allowed call graph, output emission checks for sensitive-data exposure, and checkpoints pause for human review. Each check has a defined failure mode, and each denial generates an immutable audit record.</p>
<p>The policy decision point fills a specific gap. Without it, authorization falls back to controls that decide at the identity, content, or data level rather than per action with full context. Microsoft Entra ID with Conditional Access authorizes at token time, and Continuous Access Evaluation can revoke a session, but only on identity and security events. Azure API Management enforces rate and token limits. Azure AI Content Safety screens harmful content. Microsoft Purview applies classification and data loss prevention. These are real controls, but none of them evaluate whether a specific action is allowed at the moment it's attempted, given the caller, the target, the data classification, and the current context. Azure Policy governs resource configuration, not runtime agent decisions. Microsoft doesn't currently ship a first-party engine for per-action agent authorization, so the platform externalizes that decision as policy-as-code. Without a decision point, this authorization logic tends to be hardcoded into each agent and tool, where it becomes scattered, inconsistent, hard to audit, and not centrally fail-closed.</p>
<p>The decision point governs the customer-controlled, pro-code path. Microsoft-managed agents in Copilot Studio and Microsoft 365 Copilot don't call it for their model reasoning, because that runtime isn't a point where you can insert a custom decision service. Those agents still reach governed tools and data through the same enforcement points, so you can authorize their tool actions at the tool boundary, but their internal reasoning is governed by the managed runtime's built-in controls. Removing the decision point therefore weakens per-action authorization mainly for custom, pro-code agents. The managed runtime never applied that layer to its reasoning, which is a limitation inherent to a software-as-a-service runtime rather than a control that you add and then remove.</p>
<h3 id="make-registration-mandatory-for-governed-enterprise-access">Make registration mandatory for governed enterprise access</h3>
<p>The platform makes registration the only workable path by combining preventive gates, detective controls, and a reconciliation loop, rather than relying on any single check.</p>
<p>Within the boundary this architecture controls, preventive gates make an unregistered agent unable to reach governed enterprise resources:</p>
<ul>
<li><strong>Identity is the choke point.</strong> Where the platform issues one, each agent runs under a Microsoft Entra Agent ID from an approved blueprint, and conditional access applies to that identity; agents on managed surfaces that don't issue an Agent ID act with the signed-in user's delegated permissions instead.</li>
<li><strong>Credentials are centrally managed.</strong> Approved production endpoints authorize only identities that are mapped to an approved registry entry. Long-lived personal keys are prohibited, managed identities and short-lived tokens are preferred, and exceptions are managed through the vault and approval process.</li>
<li><strong>Creation surfaces are governed.</strong> Managed environments and data loss prevention policies constrain where and by whom agents are authored in Copilot Studio and Power Platform, role-based access control constrains Microsoft Foundry, and ungoverned surfaces are disabled.</li>
<li><strong>The runtime rejects unknown callers.</strong> Gateway policy allows model and tool access only for identities associated with approved registry entries, and governed tools require a registered identity, so an unregistered agent has no route to a model, a tool, or data.</li>
<li><strong>Promotion requires registration.</strong> A capability can't promote to production without a registry entry, an owner, an approved specification, and a passing evaluation, enforced as policy-as-code in the pipeline and by Azure Policy on the underlying resources.</li>
<li><strong>Third-party agents come from an approved catalog.</strong> Only vetted partner agents deploy from the catalog, and unsanctioned agent services are blocked at network egress.</li>
</ul>
<p>Detective controls find what the gates miss. Microsoft Agent 365 shadow-agent detection, Microsoft Entra workload-identity discovery, Microsoft Purview data security posture management for AI, and Microsoft Defender surface agents and AI usage that aren't in the registry.</p>
<p>A reconciliation loop closes the gap. The platform inventories every creation surface, compares it against the registry, and quarantines, alerts on, or assigns an owner to anything unregistered, unowned, or unmapped. Every agent has an accountable owner, periodic access reviews recertify it, and unowned or unused agents expire automatically.</p>
<p>Within the managed Microsoft identity, Azure, Microsoft 365, endpoint, and network boundary covered by this architecture, production access to approved corporate models, tools, and data requires a registered identity or supported managed-agent context. Agents outside that boundary, such as an unsanctioned software-as-a-service agent or code that uses a personal model key, require separate endpoint, network, SaaS, and data-security controls and might not be fully discoverable.</p>
<h3 id="contract-first-integration-and-immutable-versioning">Contract-first integration and immutable versioning</h3>
<p>Agents reach tools and other agents only through typed, versioned contracts. Tool access uses MCP, and agent-to-agent collaboration is mediated through the gateway with a declared call graph and correlation IDs, so there's no direct, unaudited agent-to-agent path. Every spec, policy, prompt, and contract is versioned and immutable once released. Production pins to exact version hashes, and rollback is a pointer change to a prior immutable artifact rather than a redeployment.</p>
<h3 id="federated-hub-and-spoke-deployment">Federated hub-and-spoke deployment</h3>
<p>The platform deploys build-once into a hub-and-spoke organization. The governing tenant holds the factory (the infrastructure-as-code definition and pipeline) and the shared oversight surfaces. Each business unit runs its own copy of the governed runtime in its own tenant. Only delegated views and delegated administration cross the tenant boundary. Azure Lighthouse and Microsoft Entra Tenant Governance address different layers: Lighthouse delegates Azure resource management, while Tenant Governance delegates Microsoft Entra and supported Microsoft 365 administration. Use both together rather than treating them as interchangeable.</p>
<h2 id="considerations">Considerations</h2>
<p>These considerations implement the pillars of the Azure Well-Architected Framework, which is a set of guiding tenets that you can use to improve the quality of a workload. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/" rel="noopener" target="_blank">Well-Architected Framework</a>.</p>
<h3 id="reliability">Reliability</h3>
<p>Reliability helps ensure that your application can meet the commitments that you make to your customers. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/reliability/checklist" rel="noopener" target="_blank">Design review checklist for Reliability</a>.</p>
<ul>
<li>Keep runtime enforcement local to each tenant so that a loss of connectivity to the governing tenant doesn't create an authorization bypass. Use cached policy to ride out brief control-plane outages, and fail closed when no applicable decision is available.</li>
<li>Treat the central dashboards as an operational view, not as a runtime dependency of any agent.</li>
<li>Use immutable artifacts and pointer-based rollback so that a promotion problem reverts quickly, and wire automated rollback triggers to evaluation regression, policy-violation spikes, and error-rate breaches.</li>
<li>Monitor delegation health, cross-workspace query failures, agent identity health, and missing telemetry as separate signals.</li>
</ul>
<h3 id="security">Security</h3>
<p>Security provides assurances against deliberate attacks and the misuse of your valuable data and systems. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/security/checklist" rel="noopener" target="_blank">Design review checklist for Security</a>.</p>
<ul>
<li>Enforce least privilege everywhere. Scope every agent, tool, and data access to the minimum required, and prefer managed identities and short-lived Microsoft Entra tokens over long-lived secrets. Store any required secrets, keys, or certificates in a vault.</li>
<li>Give each agent a governed identity. Use Microsoft Entra Agent ID where the platform provides one, require an owner for every agent, review agent permissions and risk, and retire unused or unowned agents.</li>
<li>Keep the data access path classification-aware so that data isn't returned to a caller or destination that isn't authorized for the data's classification, and keep source-system permissions authoritative.</li>
<li>Generate an immutable audit record for every policy decision, and retain tamper-evident evidence according to your regulatory requirements.</li>
<li>Keep source prompts, responses, audit records, and business data in the owning tenant unless a documented requirement justifies replication.</li>
<li>Screen prompts and responses with content safety and prompt-injection detection, and validate output for sensitive-data exposure before an agent emits it.</li>
</ul>
<h3 id="cost-optimization">Cost Optimization</h3>
<p>Cost Optimization focuses on ways to reduce unnecessary expenses and improve operational efficiencies. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/cost-optimization/checklist" rel="noopener" target="_blank">Design review checklist for Cost Optimization</a>.</p>
<ul>
<li>Put token and rate limits, a per-spec budget, and a cost circuit breaker at the gateway so that model spend can't run away, and choose the model tier per capability.</li>
<li>Measure ROI from a documented manual baseline so that each automated capability shows value against a real cost, not an estimate.</li>
<li>Query tenant-local telemetry on demand when retention, data residency, and query volume make central ingestion unnecessary, and return aggregates rather than full content for operational views.</li>
<li>Use consumption-based scaling for tool hosts; for the policy decision point, select minimum replicas and scaling behavior based on latency, availability, and outage requirements, and scale to zero only where cold-start latency and temporary unavailability are acceptable. Estimate the cost of gateways, telemetry retention, dashboards, and alerts for the number of tenants.</li>
<li>Account for per-user Agent 365 licensing. Agent 365 is licensed per user, so include that recurring subscription cost in the platform's total cost of ownership alongside Azure consumption.</li>
</ul>
<h3 id="operational-excellence">Operational Excellence</h3>
<p>Operational Excellence covers the operations processes that deploy an application and keep it running in production. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/operational-excellence/checklist" rel="noopener" target="_blank">Design review checklist for Operational Excellence</a>.</p>
<ul>
<li>Deploy the runtime through versioned infrastructure as code, and allow tenant-specific parameters without creating divergent control implementations. Use published modules, such as Azure Verified Modules, so that every deployment meets the same baseline.</li>
<li>Gate promotion on evaluation, and keep golden test sets, shadow-mode results, and drift detection as first-class release signals.</li>
<li>Define an onboarding contract for each tenant that identifies delegation scopes, roles, telemetry tables, data owners, retention, and revocation steps. Test offboarding so that revoking a relationship removes central access without interrupting the runtime.</li>
<li>Track coverage separately for the data catalog, identity signals, Azure telemetry, runtime controls, and data governance, because a tenant might complete one before another.</li>
</ul>
<h3 id="performance-efficiency">Performance Efficiency</h3>
<p>Performance Efficiency refers to your workload's ability to scale to meet user demands efficiently. For more information, see <a href="https://learn.microsoft.com/azure/well-architected/performance-efficiency/checklist" rel="noopener" target="_blank">Design review checklist for Performance Efficiency</a>.</p>
<ul>
<li>Keep latency-sensitive policy evaluation and data access local to the agent runtime, and keep the guardrails budget within the platform's latency target.</li>
<li>Cache policy decisions only when they're bound to the full decision context, including subject or agent identity, action, resource, data classification, policy version, and expiration, and honor revocation. Don't serve cached allow decisions for privilege elevation, destructive actions, high-risk data, or actions that require human approval. Caching stable decisions keeps agents working during brief decision-service outages, within the cache's time-to-live.</li>
<li>Filter cross-workspace queries at the source, and return aggregates when operators don't need event-level data.</li>
<li>Partition dashboards by time range and tenant to avoid unbounded fan-out as the number of tenants grows.</li>
</ul>

<p>We are excited to announce the&nbsp;<strong>general availability (GA) of network security perimeter metrics</strong>, a capability that helps administrators monitor network access patterns, understand the impact of the access rules, and identify unexpected traffic behaviour across protected resources. These metrics are available through Azure Monitor and can be used to create dashboards, alerts, and operational monitoring experiences.</p>
<p><strong>Why use network security perimeter metrics?</strong></p>
<p>Network security perimeter metrics capture access requests evaluated by the data plane and provide visibility into network activity associated with the perimeter-protected resources. Metrics enable monitoring scenarios such as:</p>
<ul>
<li>Tracking approved and denied access requests.</li>
<li>Monitoring inbound and outbound access activity.</li>
<li>Understanding traffic patterns across protected resources, profiles, access modes and access rule versions.</li>
<li>Detecting unexpected access attempts.</li>
<li>Validating the impact of access rules’ changes.</li>
<li>Establishing a baseline before moving a perimeter from Transition mode to Enforced mode.</li>
</ul>
<p>Network security perimeter metrics render aggregated time-series data that is optimized for monitoring, alerting, and trend analysis.</p>
<p><strong>Accessing network security perimeter metrics</strong></p>
<p>Network security perimeter metrics are available through Azure Monitor.</p>
<ol>
<li>In the Azure portal, navigate to your network security perimeter resource.</li>
<li>Select <strong>Metrics</strong> under the <strong>Monitoring</strong> section.</li>
<li>‘Add Metric’</li>
<li>Choose the ‘NSP access metrics’ namespace.</li>
<li>Select a metric and configure filters, splitting as needed.</li>
<li>Use Azure Monitor features to build charts, dashboards, workbooks, and metric alerts.</li>
<li>Multiple charts may be created for different metrics that are intended to be monitored.</li>
</ol>
<p>Regular Azure Monitor features like drilling into the logs, saving the chart as a dashboard or exporting it to a workbook can also be performed.</p>

### Meet the Hosted Skills Canvas: Build, Run, and Debug in GitHub Copilot

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/meet-the-hosted-skills-canvas-build-run-and-debug-in-github/ba-p/4561222](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/meet-the-hosted-skills-canvas-build-run-and-debug-in-github/ba-p/4561222)
- **Published**: 2026-10-01 07:19:50
- **Fetched**: 2026-10-02 01:44:24

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>We have been evolving Azure Functions from the bottom up: first the infrastructure with <a href="https://learn.microsoft.com/en-us/azure/azure-functions/flex-consumption-plan" rel="noopener" target="_blank">Flex Consumption</a>, then the way you write an app, and now the tools you use to build it.<br /><br />We're introducing a new developer experience for event-driven apps: the <a class="lia-external-url" href="" rel="noopener" target="_blank"><strong>Azure Functions Hosted Skills canvas</strong></a> in the <strong>GitHub Copilot app</strong>. Your Function App, plain-English instructions, trigger controls, and live logs sit beside your conversation. From choosing an event to reading the result, the development loop stays in one window, with Copilot there when you need a hand.<br /><br />Let's walk through a daily digest for the Azure Functions host repository on GitHub.</p>
<h2>Start in the canvas</h2>
<p>Open <strong>Azure Functions Hosted Skills</strong> and choose <strong>Local Function App</strong>. Use the generated daily repository digest starter for this walkthrough. The app's source lives in your repo or worktree; you do not need an Azure deployment to test it locally.</p>
<img /><em>The Hosted Skills canvas alongside Copilot, with local setup and developer controls in view.</em>
<h2>Choose the event, then the instructions</h2>
<p>First pick the event that starts the work. For this daily digest, choose <strong>Timer</strong> and set its schedule. HTTP or Queue are other options when a request or message should start the task.</p>
<p>Then use or edit <strong>Skill instructions</strong>. A <a href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-hosted-skills" rel="noopener" target="_blank">hosted skill</a> is a set of instructions for an AI task, written in a Markdown .agent.md file. They describe what the app should do when the event arrives. Here, we ask the app to inspect recent repository activity and write a digest with links to the evidence.</p>
<img /><em>The Timer sets when the skill runs; the instructions describe the job. This app is set to run daily at 09:00 local time.</em>
<p>With the Functions host running, the runtime listens for the configured event and starts the skill automatically. You do not write a polling loop. Hosted Skills is in preview.</p>
<h2>Invoke and read the result</h2>
<p>Click <strong>Invoke Trigger</strong> to run the hosted skill now, without waiting for the next scheduled event. You can change the model or adjust <strong>Parameters</strong> to try another repository or reporting window.</p>
<img />
<p><em>Click <strong>Invoke Trigger</strong> to run the hosted skill now, without waiting for its next scheduled event.</em></p>

<p>That runs the hosted skill. It uses your signed-in GitHub identity to make OAuth-authenticated calls to the GitHub MCP server for issues, pull requests, and workflow activity. The model follows the skill's instructions to reason over that evidence and write the digest.</p>
<p>The starter also uses middleware to trim large tool responses before they reach the model. This run reduced about 181 KB of GitHub results to 2.6 KB.</p>
<p>Read the output in <strong>Agent digest</strong> and the run status in <strong>Trigger activity</strong>. The instructions ask for evidence links and a clear note when access or data is missing, rather than made-up activity.</p>
<img /><em>Actual output from a local Timer run against Azure/azure-functions-host on September 29, 2026. All three GitHub MCP calls completed successfully. This screenshot shows an excerpt; the output will vary with repository activity and the model.</em>
<p>If the result needs work, the canvas gives you the evidence to debug it. The instructions and input stay visible, while&nbsp;<strong>Trigger activity</strong>, <strong>Commands</strong>, and the local Functions host log show what ran, when it ran, and any errors. You can check what happened against your instructions, see where the run went wrong, and either debug it yourself or give the coding agent the same inputs, commands, and error messages to work from.</p>
<p>The event selector, model picker, logs, and editor handoff run directly in code. They do not need another model call to interpret a choice you already made. Those routine controls are fast and deterministic; the hosted skill's AI-generated response can still vary.</p>
<p>Copilot stays available to help with instructions, errors, and code changes.</p>
<h2>Where to take it next</h2>
<p>You now have a local app you can inspect and change. Keep working in the canvas, or take it in one of these directions.</p>
<h3>Open in VS Code</h3>
<p>When you want to edit Python tools, review configuration, or work in your usual editor, select <strong>Open in VS Code</strong>.</p>
<img /><em>A direct handoff to your editor, not another prompt.</em>
<p>The source stays in your repo or worktree, where you can review and commit it. In REDACTED mode, the editor handoff uses a scrubbed copy so credentials are not exposed; the real project stays unchanged.</p>
<p>You can extend the starter with reusable SKILL.md guidance, other MCP servers, and Python tools for the parts that need code. The generated project uses regular files, not a format owned by the canvas.</p>
<h3>Deploy to Azure</h3>
<p>To run beyond your laptop, <strong>Deploy to Azure</strong> uses Azure Developer CLI (azd) from an isolated copy. Your working source and local host stay unchanged.</p>
<img />
<p><em>Select <strong>Deploy to Azure</strong> to deploy your hosted skill from an isolated copy.</em></p>

<p>The supported Timer/HTTP template configures the Function App's <strong>managed identity</strong>, required <strong>RBAC roles</strong>, and remote model and app settings. The deployed app uses its identity for Azure access, not your laptop's CLI session. Gateway credentials, when needed, pass through secure deployment parameters rather than source files.</p>
<p>Deployment needs a subscription, an Azure-backed Foundry or AI Gateway model, and permission to create resources and assign roles. Copilot is local-only; Queue testing remains local. Reuse a model or explicitly approve model creation. Deployment starts only when you choose it, can incur charges, and reports progress and errors in <strong>Deployment output</strong>.</p>
<h3>Expose the Hosted Skill as an MCP tool</h3>
<p>The same digest can become a building block for developer tools and other agents, rather than only a task on your own schedule. Add one line to the skill's front matter:</p>
builtin_endpoints: { mcp: true }
<p>That enables a standard <a href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-hosted-skills-reference#built-in-endpoints" rel="noopener" target="_blank">MCP HTTP endpoint</a> at /runtime/webhooks/mcp for debugging and agent-to-agent use. Connected MCP clients, including Microsoft Foundry and Microsoft Agent 365 (A365) agents, can call the skill with the required mcp_extension system-key authentication.</p>
<p>Other developers and agents get the same capability as a callable tool. Its event trigger still works; you do not write a separate MCP server.</p>
<h2>Doctor is there if you need help</h2>
<p><strong>Doctor</strong> is optional, not a gate before invoking. Use it for initial setup help or if you encounter an issue. Its readiness report shows which tools are ready, what is missing, and what to fix for the selected workflow.</p>
<img /><em>A real local Copilot readiness check. Doctor reads status; it does not install software, sign you in, or change Azure. Azure sign-in is not required for this local path.</em>
<p><strong>We recommend uv</strong> for Python and the isolated environment. Azure-backed workflows use your Azure CLI sign-in; local Copilot testing does not need an Azure deployment or Azure sign-in.</p>
<h2>Shared pieces in canvas-toolkit</h2>
<p>Building this meant solving Azure sign-in, environment checks, command activity, and styling that fits the host.</p>
<p>We put the reusable parts back into <a class="lia-mention lia-mention-user" href="">Microsoft​</a>/canvas-toolkit: Azure authentication, redaction-safe command logs, and shared UI and theme support. Doctor remains app-specific and uses those shared pieces alongside its Functions checks.</p>
<p>Find the <a href="https://github.com/microsoft/azure-dev-tools/tree/main/plugins/canvas-authoring" rel="noopener" target="_blank">toolkit setup and starter examples</a> in the Azure Dev Tools repo.</p>
