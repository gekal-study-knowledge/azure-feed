### Bring Azure SRE Agent into your developer workflow with the new canvas

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/bring-azure-sre-agent-into-your-developer-workflow-with-the-new/ba-p/4564514](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/bring-azure-sre-agent-into-your-developer-workflow-with-the-new/ba-p/4564514)
- **Published**: 2026-10-15 01:35:26
- **Fetched**: 2026-10-15 04:47:19

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>You’re on call. A customer-reported incident lands, Azure SRE Agent picks it up from your incident management system, investigates, and gives you a starting diagnosis.</p>
<p>If you’re like me, you want to check that diagnosis yourself, and you want to do it where you already work: in GitHub Copilot, with your code, your tools, and your own access to the data.</p>
<p>The new <a class="lia-external-url" href="https://aka.ms/sreagent/canvas/doc" rel="noopener" target="_blank">Azure SRE Agent canvas</a> puts the investigation right next to your Copilot chat. A canvas is an interactive panel beside the conversation, with context and actions you and Copilot can both use. You get SRE Agent’s findings plus everything SRE doesn’t have: your code, your private data sources, and what you know about the app.</p>
<p>In the <strong>GitHub Copilot App</strong>, sessions are on the left, Copilot chat is in the middle, and the SRE canvas is on the right. You can use the same canvas in <strong>Copilot CLI</strong> sessions that support canvases.</p>
<p>I now have SRE's findings alongside my own context in Copilot chat. I can keep digging here and decide what to send back to SRE, and when.</p>
<img /><em>The GitHub Copilot App with the September investigation open in the canvas.</em>
<p>Let me show you the inner loop with an incident from September 22. It’s a Contoso demo, but it’s modeled on a real one we hit in production. Gateway health looked available while orders and payments failed. I'll use SRE's diagnosis as a starting point, check the historical telemetry with my own authorized access, and work out what the evidence does and doesn't establish. I’ll share findings with the team, and anything worth keeping goes back to SRE Agent.</p>
<h2>Start with the incident</h2>
<p>With the plugin enabled, I prompt Copilot to open <strong>Azure SRE Agent</strong> and choose my saved demo1-dt-snow favorite. I can also discover agents in a subscription I choose or connect through a caller-authorized external URL. For this investigation, I open <strong>INC0922001</strong>, "Trading order and payment requests failing while gateway health remains available," and choose <strong>Connect this thread</strong>. Selecting a row lets me browse; connecting makes it the investigation for this conversation.</p>
<img />
<p><em>The September incident as recorded in SRE Agent.</em></p>

<p>Then I ask:</p>
<blockquote>
<p>Summarize this connected September 22 investigation. Separate the reported diagnosis from observed evidence. Give the incident time window, and list what still needs independent verification.</p>
</blockquote>
<p>The SRE record reports a stopped PostgreSQL database. It says the gateway passed its health check, but Orders and payments requests failed after about 15 seconds. That's useful context, but a passing health check doesn't mean orders and payments are working. I want to check the logs for myself.</p>
<img />
<p><em>SRE’s diagnosis and suggested recovery. Suggested isn’t the same as confirmed, which is where I start digging.</em></p>

<h2>Get the historical window right</h2>
<p>The first query assumption I check is the date. This incident needs <strong>September 22, 17:30 to 19:45 UTC</strong>, not the last 24 hours.</p>
<p>I use the Log Analytics workspace behind the demo and ask:</p>
<blockquote>
<p>Reconstruct the failure check for this historical window. Show the complete query and target before running it. Then break down the request routes and status codes.</p>
</blockquote>
<p>The reconstructed query and its saved result give me something concrete to inspect. This is my own reconstruction, not a replay of SRE’s query, so the counts differ a little from SRE’s snapshot. The <a href="https://github.com/coreai-microsoft/canvases-cloud-foundation/blob/paulyuk-microsoft-sre-demo-and-blog/docs/blog/azure-sre-agent-canvas-demo-runbook.md#q1-reconstructed-baseline-saved-result" rel="noopener" target="_blank">query runbook</a> includes the complete KQL, working Log Analytics API route, and scope for review.</p>
<img /><em>The reconstructed query, saved as an evidence artifact I can review before anything runs.</em>
<p>The result contains&nbsp;<strong>120 gateway Orders 500 records</strong>, <strong>115 gateway payments 502 records</strong>, corresponding backend failures, and <strong>119 database connection timeouts</strong>. These are telemetry records, not distinct customer requests: the gateway and backend can record the same call. Exporter authentication errors and later route 404s are separate signatures, not more examples of the same database failure.</p>
<h2>Inspect the requests, dependencies, and exceptions</h2>
<p>Grouped counts tell me where to look.</p>
<img /><em>The grouped result. Each error signature stays separate so I don’t lump unrelated failures together.</em>
<p>To understand the failure, I want to look at some of the actual log entries from that time window, not just the totals:</p>
<blockquote>
<p>Show the Orders requests, downstream dependencies, and database timeouts for this window. Where operation IDs are populated, follow the same operation. Tell me what is correlated and what is only nearby in time.</p>
</blockquote>
<p>The saved exception signature says the connection to the database endpoint timed out. That supports a connectivity problem; it doesn't independently prove the database was stopped. To connect a particular exception to a particular request, I need matching trace identifiers, not just nearby timestamps. The raw-record and correlation queries are the next checks, with their own execution approval.</p>
<h2>Widen my check beyond Orders</h2>
<p>An Orders-focused query is a useful starting point, not an impact assessment. I ask:</p>
<blockquote>
<p>Keep the same source and time window, but remove the Orders operation and dependency-target restrictions. What else has 5xx failures or the same database-connectivity signature? Keep unrelated errors separate.</p>
</blockquote>
<p>The saved broader result already includes payments, which SRE also identified. My goal is to verify that scope independently and see whether the wider query adds anything. I won't turn two affected paths into an all-services outage. This data also has blank application-role names, so I use the recorded operations and dependency targets rather than invent an application-name filter.</p>
<h2>Test the competing explanation</h2>
<p>A gateway deployment or connection setting could also cause trouble. I want to compare that explanation with the database diagnosis:</p>
<blockquote>
<p>Preview the historical deployment and configuration records needed for this window, plus independent database state or availability evidence. Do not use today's settings or health as proof of September 22. If the records aren't available, leave the check open.</p>
</blockquote>
<p>The first SRE record reports the database as stopped, but its Activity Log check found no stop event and may not have covered the right scope. Independent incident-window records would help distinguish stopped state from configuration or network problems. Current settings can't establish historical state, and missing or expired change history can't rule out a deployment.</p>
<p>For now, the logs support connectivity trouble. Historical database state and the competing configuration explanation still need checking. The first record also doesn't confirm completed recovery; a later recurrence doesn’t tell us what happened on September 22..</p>
<h2>Bring in evidence SRE may not have, or go where it cannot</h2>
<p>The logs got me to a connectivity problem. The next question is capacity: was something starved? That evidence lives in a Kusto cluster SRE Agent can’t reach, but I can. <strong>Private Connectors</strong> let me use my own authorized access from inside the same investigation.</p>
<img />
<p><em>Copilot-private connections are separate from the SRE Agent connectors. Teams is ready for the update.</em></p>
<p>&nbsp;</p>

<p>For a performance or capacity question, I can choose an authorized connection, review the source and complete query, and approve its time range and filters before execution. Then I can compare the relevant measurements and units. This is an extension of the investigation. Granting capacity is a separate action with its own approval. I can do it from here, but it’s my call, not the agent’s.</p>
<p>The connection stays private to Copilot. Connecting an SRE investigation doesn't give the agent my datasource permissions. If I want SRE to use a finding, I separately preview and approve the evidence to share. For checks I run locally, I use my identity and network access; a cloud-backed connector uses its provider's network path.</p>
<h2>Review the updated team message</h2>
<p>The team update should carry the refined root-cause analysis, including its limits: SRE's reported diagnosis, the independently observed failures, the scope, and the checks still open. Next prompt:</p>
<blockquote>
<p>Draft a September 22 update to send to the team in Teams. Include the reported diagnosis, observed Orders and payments failures, connectivity evidence, competing explanations, and remaining checks. Include the investigation link. Show me the exact message and destination before sending.</p>
</blockquote>
<img /><em>The September 22 demo update posted to the Azure Functions Team's PMs channel after I reviewed and approved it.</em>
<p>That gives the team a useful starting point for the next check, with a link back to the investigation.</p>
<h2>Continue in the terminal</h2>
<p>I can carry the same investigation into a canvas-capable <strong>Copilot CLI</strong> session. I connect <strong>INC0922001</strong> explicitly in that conversation; the App's connection doesn't carry over.</p>
<blockquote>
<p>Connect to INC0922001 from September 22. Give me a TL;DR that separates the reported diagnosis, independently checked evidence, and remaining questions.</p>
</blockquote>
<p>The terminal is another place where I like to work, and I still want to follow the same evidence and use my own context and tools. The SRE canvas provides tools to Copilot CLI too. The <a href="https://techcommunity.microsoft.com/blog/appsonazureblog/access-your-sre-agent-from-any-ide-terminal-or-ai-assistant/4523434" rel="noopener" target="_blank">IDE and terminal guide</a> covers a separate connection through the Azure MCP Server.</p>
<img /><em>The same September investigation, connected again in Copilot CLI.</em>
<p>So who stopped the database? We did, for the demo. The real production incident that inspired this was resource exhaustion, which is less satisfying, because every engineer wants it to be the database. It’s better when you can prove it.</p>
<h2>Try the canvas for your next investigation</h2>
<p>The useful loop isn't just reading an incident summary from an agent. It's taking SRE's starting diagnosis into Copilot, inspecting the evidence, testing alternatives, and bringing in authorized data from my own tools. Sometimes that confirms SRE Agent got it right. Sometimes it doesn’t. Either way, what I learn goes back into the agent’s memory so the next incident starts smarter. In this one, I learned we’re not resilient enough to this kind of failure yet, and we have hardening work to do.</p>

<blockquote>

</blockquote>

<p>We have learned a lot from talking with teams that are bringing <a href="https://learn.microsoft.com/azure/sre-agent/overview" rel="noopener" target="_blank">Azure SRE Agent</a> into their day-to-day operations. Across those conversations, we have seen a common set of questions emerge as teams move from exploring an initial use case to adopting SRE Agent more broadly.</p>
<p>Some teams are starting with a simple question: <strong>“Where should we begin?”</strong> Others have already seen value in reducing operational toil and improving incident response and are asking what comes next. How do we expand from one successful use case to more workflows? Can multiple teams share the same agent safely? When should we use one SRE Agent versus multiple agents? How should agents collaborate? And how do we deploy and govern them consistently across the enterprise?</p>
<p>This two-part guide shares the patterns we have seen and our recommendations for navigating that journey, from the first use case to broader enterprise adoption. <strong>Our recommendation is to start with one operational problem your team understands, learn what the agent needs to solve it effectively, and expand from there.</strong> The goal is not to design your enterprise topology on day one. It is to make each next decision with better evidence.</p>

<h2>1. Which operational problem should we start with?</h2>
<p>A strong first use case is a recurring, bounded problem that the team feels today and understands well enough to judge. Focus on work that affects reliability, consumes engineering time, slows incident response, or creates avoidable cost.</p>
<blockquote>
<p><strong>Start with the operational pain your team feels most. Choose one well-bounded problem that matters to the team and is familiar enough to judge.</strong></p>
</blockquote>
<p>If you are unsure where to begin, start by asking SRE Agent to investigate an issue or incident your team is already looking at. Give it the observed symptom or question, let it bring together telemetry, dependencies, source code, and recent changes, and see whether it can identify where the problem is likely occurring. That investigation can include root-cause analysis, deployment correlation, Azure resource health, and dependency analysis. The examples below are some of the use cases we have seen customers implement.</p>
<ul>
<li><strong>Alert investigation:</strong> correlate alerts with telemetry, dependencies, source code, and recent changes to explain what happened and identify the next step.</li>
<li><strong>Incident auto-triage:</strong> collect the initial evidence, identify likely ownership and severity, remove known false positives, and prepare the incident for the responding team.</li>
<li><strong>Proactive availability:</strong> perform proactive health checks, reliability risks, degraded signals, or unhealthy dependencies before they become customer-facing incidents.</li>
<li><strong>Deployment correlation:</strong> correlate a failure or degradation with recent deployments, configuration changes, feature releases, and infrastructure updates.</li>
<li><strong>Production deployment validation:</strong> evaluate post-deployment telemetry, logs, dependencies, and service-health criteria to confirm that a production release is healthy.</li>
<li><strong>FinOps proactive cost optimization:</strong> identify unexpected cost changes, underused resources, and rightsizing opportunities before spend becomes a larger problem.</li>
<li><strong>Certificate expiry monitoring:</strong> identify certificates approaching expiration, determine the affected services and owners, and initiate the appropriate follow-up.</li>
</ul>
<h2>2. How do I run the first use case? Should I use SRE Agent’s built-in capabilities or customize it?</h2>
<p>Once the team has selected the operational pain it wants to address, the next step is to prove that SRE Agent can improve the outcome. Two questions matter at this stage: how should we set up SRE Agent to execute the first use case, and do we need to customize beyond its built-in capabilities?</p>
<p>Keep the first use case deliberately small. <a href="https://learn.microsoft.com/azure/sre-agent/create-and-set-up#set-up-your-agent" rel="noopener" target="_blank">Connect only the context required</a> to solve the selected problem. For deployment validation, that may be the relevant <a href="https://learn.microsoft.com/azure/sre-agent/connect-telemetry-source" rel="noopener" target="_blank">telemetry source</a>, <a href="https://learn.microsoft.com/azure/sre-agent/connect-code-service" rel="noopener" target="_blank">code repository</a>, deployment history, and runbook, not every repository, monitoring system, or resource the team may eventually use. For more guidance on setting up the first SRE Agent, see <a href="https://techcommunity.microsoft.com/blog/AppsonAzureBlog/getting-the-best-out-of-azure-sre-agent/4559745" rel="noopener" target="_blank">Getting the best out of Azure SRE Agent</a>.</p>
<p>Begin with diagnostic or read-only access. Use the agent’s <a href="https://learn.microsoft.com/azure/sre-agent/permissions" rel="noopener" target="_blank">managed identity and Azure RBAC</a> as the starting point for Azure resource access. Grant only the resource scopes and permissions required for the use case. As the workflow demonstrates a need to perform write actions, add the narrowest permission at the narrowest practical scope rather than granting broad access up front.</p>
<p><a href="https://learn.microsoft.com/azure/sre-agent/first-investigation" rel="noopener" target="_blank">Test the agent</a> against a few recent historical incidents the team understands. Use these cases to confirm that the agent can reach the right telemetry, code, deployment history, and operational knowledge, and to expose missing context before a live incident.</p>
<p>Then use SRE Agent alongside the team’s normal response process when a real issue occurs. This is where teams begin to build trust: the agent surfaces the relevant evidence, identifies where the problem is likely occurring, connects it to a dependency or recent change, explains its reasoning, and helps responders reach the diagnosis faster.</p>
<p>Define the outcomes you want to accomplish. Measure the outcome in the system that already records it, for example, mean time to resolution in the incident platform, alert volume or false-positive rate in monitoring, deployment failure or rollback rate in CI/CD. Choose the measure that matches the pain that justified the use case. Establish a baseline, then use an SRE Agent&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/live-reports" rel="noopener" target="_blank">live report</a> or an existing dashboard to track the result.</p>
<h3>2.1 When do I customize SRE Agent, and do I need a skill, custom subagent, or tool?</h3>
<p>Always start small with SRE Agent’s built-in capabilities. Then add only what the workflow needs.</p>
<ol>
<li><strong>Start with the expert skills and tools that come with SRE Agent.</strong> Out of the box, SRE Agent combines <a href="https://learn.microsoft.com/azure/sre-agent/overview#how-it-works" rel="noopener" target="_blank">Azure-specific product knowledge and built-in operational capabilities</a> for diagnosing issues and finding probable root causes across Azure. This expertise spans all of Azure, including compute, storage, networking, data, monitoring, and management services. Its native integrations connect <a href="https://learn.microsoft.com/azure/sre-agent/log-analytics-app-insights" rel="noopener" target="_blank">Azure Monitor, Application Insights, and Log Analytics</a>, <a href="https://learn.microsoft.com/azure/sre-agent/github-connector" rel="noopener" target="_blank">GitHub</a>, and <a href="https://learn.microsoft.com/azure/sre-agent/azure-devops-connector" rel="noopener" target="_blank">Azure DevOps</a> so the agent can correlate infrastructure state, telemetry, deployments, work items, and source code. General-purpose <a href="https://learn.microsoft.com/azure/sre-agent/tools" rel="noopener" target="_blank">tools</a>, including Azure CLI, Kusto queries, and code analysis, let it gather deeper evidence within its assigned permissions. For example, it can trace network connectivity, troubleshoot gateway and load-balancing paths, query application telemetry and logs, and correlate a degradation with a recent code or deployment change.</li>
<li><strong>Add a custom </strong><a href="https://learn.microsoft.com/azure/sre-agent/skills" rel="noopener" target="_blank"><strong>skill</strong></a><strong> when SRE Agent needs to understand how your environment or organization works.</strong> Before writing a new skill, browse the <a href="https://learn.microsoft.com/azure/sre-agent/plugin-marketplace" rel="noopener" target="_blank">plugin marketplace</a> and the public <a href="https://github.com/Azure/sre-agent-plugins/" rel="noopener" target="_blank">Azure SRE Agent Plugins repository</a> to see whether an existing plugin covers the scenario. A skill can teach the agent how to use and interpret a third-party telemetry source such as Dynatrace, which dashboards or signals matter, how your runbooks and escalation processes work, or how your organization performs a workflow such as pull-request validation, release-risk analysis, or compliance review. Even with a native integration, adding your operating instructions as a skill can help the agent find the right evidence faster.</li>
<li><strong>Add a custom </strong><a href="https://learn.microsoft.com/azure/sre-agent/tools" rel="noopener" target="_blank"><strong>tool</strong></a><strong> when part of the workflow must run consistently.</strong> Use deterministic code when the agent must perform the same calculation, execute a predefined query, call an external API, or generate a report in an exact format every time. A skill explains when and how your organization performs the task; a tool performs the required action consistently. Prefer an existing built-in or connector tool before adding a custom <a href="https://learn.microsoft.com/azure/sre-agent/python-code-execution" rel="noopener" target="_blank">Python tool</a>, HTTP or Kusto tool, or <a href="https://learn.microsoft.com/azure/sre-agent/mcp-connectors" rel="noopener" target="_blank">MCP connector</a>.</li>
<li><strong>Use a skill and tool together when the workflow needs both organizational guidance and deterministic execution.</strong> For example, a skill can describe how your organization evaluates deployment risk, while a tool calculates the risk score or generates the required report.</li>
</ol>
<blockquote>
<p><strong>For most workflows, built-in capabilities plus a custom skill are sufficient. Add a custom tool only when the workflow requires repeatable execution, external-system access, or an exact output.</strong></p>
</blockquote>
<h3>2.2 When do I need a custom subagent?</h3>
<p>A custom subagent is a specialist within SRE Agent designed for a focused operational workflow. For most use cases, start with a skill. A skill is enough when the main SRE Agent needs to understand and apply your team’s instructions as part of a broader conversation or investigation.</p>
<p><a href="https://learn.microsoft.com/azure/sre-agent/create-subagent" rel="noopener" target="_blank">Create a custom subagent</a> when you want to control the scope of that workflow, package a focused set of instructions, skills, and tools, test or invoke it independently, or connect it to a trigger. The use case itself does not determine the choice. The same deployment-validation guidance can remain a skill when an engineer asks the main agent to apply it during an investigation. Package that skill in a deployment-validation agent when the workflow should stay within a defined scope, use selected tools, and run after a deployment through an incident, schedule, HTTP trigger, or another workflow.</p>
<blockquote>
<p><strong>Start with a skill. Use a custom subagent when the workflow needs tighter scope, focused instructions and tools, independent invocation, or trigger-based automation.</strong></p>
</blockquote>
<h2>3. How do we turn a successful first use case into more automated operational workflows?</h2>
<p>Once the first use case proves the value, look at what the team still does manually around it. Where are engineers repeatedly gathering the same evidence, running the same diagnostics, monitoring the same risks, preparing the same updates, or handing off the same follow-up work?</p>
<p>Use <a href="https://learn.microsoft.com/azure/sre-agent/live-reports" rel="noopener" target="_blank">live reports</a> to bring together incident, service-health, reliability, and cost signals so recurring patterns and remaining operational toil are easier to see. When the team understands the work and the result is repeatable, it is ready to become an automated workflow.</p>
<p>Begin with the context already connected to the agent. Reuse the same telemetry, repositories, runbooks, resource access, and team knowledge where they apply. Add another source only when the workflow needs evidence the agent cannot currently reach.</p>
<p>There are different ways to start that automation. Use a:</p>
<ul>
<li><a href="https://learn.microsoft.com/azure/sre-agent/incident-response-plans" rel="noopener" target="_blank"><strong>Response plan</strong></a> when an incident or alert should start the investigation</li>
<li><a href="https://learn.microsoft.com/azure/sre-agent/create-scheduled-task" rel="noopener" target="_blank"><strong>Scheduled task</strong></a> for recurring health, capacity, compliance, or reporting work</li>
<li><a href="https://learn.microsoft.com/azure/sre-agent/http-triggers" rel="noopener" target="_blank"><strong>HTTP trigger</strong></a> when a pipeline, external monitoring system, or another workflow should invoke the agent</li>
</ul>
<p>Start these <a href="https://learn.microsoft.com/azure/sre-agent/workflow-automation" rel="noopener" target="_blank">workflows</a> in <a href="https://learn.microsoft.com/azure/sre-agent/run-modes" rel="noopener" target="_blank">Review mode</a>, where a person can evaluate the agent’s reasoning and proposed actions. <a href="https://learn.microsoft.com/azure/sre-agent/run-modes" rel="noopener" target="_blank">Autonomous mode</a> is a good fit for actions the team has already approved its operators to perform without case-by-case review. Start with a human in the loop, build confidence in the workflow, and move approved actions to Autonomous mode when the team is comfortable allowing the agent to perform them on its own.</p>
<blockquote>
<p><strong>Start automating the work the team now understands. Use the right trigger for each workflow, and use live reports to make the next source of operational toil visible.</strong></p>
</blockquote>

<p>Part 2 shares our recommendations for making those decisions. There is no single topology that fits every organization. Start from the work, context, permissions, and ownership involved, then create boundaries only where they are needed.</p>

<ol>

<h2>1. How do we share an SRE Agent with more users?</h2>
<p>Once the first use case is producing useful results, you will likely want to share the agent with more users who can benefit from it. Sharing is not simply about giving people access to use the agent. It is about determining what each user is allowed to do. Teams must decide who can use the agent, who can change it, who can approve sensitive actions, and which safeguards should apply to everyone.</p>
<p><strong>Azure SRE Agent is a team agent:</strong> its connected knowledge, investigation history, <a href="https://learn.microsoft.com/azure/sre-agent/memory" rel="noopener" target="_blank">memory</a>, <a href="https://learn.microsoft.com/azure/sre-agent/skills" rel="noopener" target="_blank">skills</a>, <a href="https://learn.microsoft.com/azure/sre-agent/sub-agents" rel="noopener" target="_blank">custom agents</a>, <a href="https://learn.microsoft.com/azure/sre-agent/connectors" rel="noopener" target="_blank">connectors</a>, and configuration are shared within the agent. It does not create private context or state partitions for different users or teams.&nbsp;</p>
<p>Once you decide that users can work within the same shared agent, Azure SRE Agent provides controls to define what each person can do, enforce guardrails on agent actions, and audit how the agent is used. The following sections walk through those controls.</p>
<h3>1.1 Give each person the role required for their responsibility</h3>
<p>SRE Agent provides RBAC roles to control who can view, use, build, approve, or administer the agent. They govern actions within the shared agent; they do not create separate resource or context boundaries.&nbsp;</p>
<p>Assign <a href="https://learn.microsoft.com/azure/sre-agent/user-roles" rel="noopener" target="_blank">built-in SRE Agent roles</a> according to what each person needs to do:</p>
<ul>
<li>use <strong>SRE Agent Reader</strong> for stakeholders who only need to view investigations and outcomes;</li>
<li>use <strong>SRE Agent Standard User</strong> for team members who need to chat, investigate, and operate the agent;</li>
<li>add <strong>SRE Agent Author</strong> for the smaller group that creates <a href="https://learn.microsoft.com/azure/sre-agent/create-subagent" rel="noopener" target="_blank">custom agents</a> and <a href="https://learn.microsoft.com/azure/sre-agent/incident-response-plans" rel="noopener" target="_blank">response plans</a>; and</li>
<li>reserve <strong>SRE Agent Administrator</strong> for the few people who manage the agent and approve sensitive actions.</li>
</ul>
<p>A person who creates and tests workflows may need both Standard User and Author because the Author role alone does not provide chat or approval access.&nbsp;<a href="https://learn.microsoft.com/azure/role-based-access-control/built-in-roles" rel="noopener" target="_blank">Azure Owner and Contributor roles</a> also do not by themselves grant SRE Agent data-plane permissions.</p>
<blockquote>
<p>Start with these built-in roles. If none provides the required separation, use the <a href="https://learn.microsoft.com/azure/sre-agent/user-roles#what-each-role-can-access" rel="noopener" target="_blank">SRE Agent permission matrix</a> to define an <a href="https://learn.microsoft.com/azure/role-based-access-control/custom-roles" rel="noopener" target="_blank">Azure custom role</a> containing only the necessary control-plane and data-plane actions.</p>
</blockquote>
<h3>1.2 Apply guardrails to the shared agent</h3>
<p>User roles determine what each person can do. As more people share the agent, its owners also need a consistent way to shape behavior, restrict sensitive operations and validate outputs. The following controls apply those guardrails across the shared agent.</p>
<p>Use&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/tool-access-policies" rel="noopener" target="_blank"><strong>tool access policies</strong></a> to control which tools the shared agent may invoke, which operations require approval, and which operations are denied. Enable <strong>approval expiration</strong> so unreviewed approval and temporary authorization requests expire automatically. Set the timeout to match the expected administrator response window.</p>
<p>Use&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/agent-hooks" rel="noopener" target="_blank"><strong>hooks</strong></a> when inputs, tool calls, or outputs require deterministic validation, cleanup, or policy checks that should not depend on instructions alone.</p>
<p>Choose the appropriate <a href="https://learn.microsoft.com/azure/sre-agent/network-integration" rel="noopener" target="_blank"><strong>network control mode</strong></a>. For production agents that handle sensitive data or require egress controls, use Azure VNet so non-platform traffic follows enterprise DNS, firewall, NSG, and logging policies. Review the documented traffic exceptions because platform and connector traffic do not follow the same path.</p>
<p>Use <strong>custom instructions</strong> to add administrator-defined instructions to the main SRE Agent's prompt. These instructions can establish which sources to prioritize, what evidence to include, how to structure an investigation, and when to stop and ask for approval. They augment the agent’s default behavior, so users do not have to repeat the same operating guidance in every request. Common prompts guide behavior; they are not a hard enforcement boundary.</p>
<p>Set a&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/monitor-agent-usage#adjusting-your-allocation" rel="noopener" target="_blank"><strong>maximum AAU limit</strong></a> as a cost budget for shared-agent usage. Start with a limit appropriate for the expected users and workflows, monitor consumption, and adjust it as adoption grows rather than leaving usage unconstrained.</p>
<h3>1.3 Audit how the shared agent is used</h3>
<p>As more people use the agent, use its&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/audit-agent-actions" rel="noopener" target="_blank">Application Insights audit telemetry</a>&nbsp;to review tool calls, model invocations, agent activity and handoffs, incident activity, Azure CLI commands, and approval decisions. Use thread and call identifiers to follow a specific investigation and correlate related events.</p>
<p>Use the&nbsp;<a href="https://learn.microsoft.com/azure/azure-monitor/fundamentals/activity-log" rel="noopener" target="_blank">Azure Activity Log</a> to review who created, updated, or deleted the SRE Agent resource and its related managed identity and Application Insights resources.</p>
<p>Together, roles, common prompts, tool access policies, hooks, and usage limits make it safer to share one agent. They do not create separate context boundaries inside it. That distinction leads to the next decision: when to keep expanding one SRE Agent and when to create another.&nbsp;</p>
<h2>2. How do we expand from one team to multiple teams, and do we need one SRE Agent or multiple?</h2>
<p>Most enterprises want to transform how operations work across the organization. Once the teams adopt their first SRE Agent and saw their operational toil go down, the questions quickly shift: <strong>How do we expand from here? How many SRE Agents do we need? Where should the boundaries sit? And how should teams collaborate when work crosses those boundaries?</strong></p>
<p>When teams first think about this topology, they often start with the size of their environment. They look at the number of subscriptions, resource groups, applications, resources, or teams and assume that a larger environment automatically requires more SRE agents. Azure SRE Agent does not require one agent per subscription, resource group, application, resource, or team, and there is no platform-defined count at which another agent is required. A single agent can work across multiple Azure management groups, subscriptions, resource groups, and Azure regions when it has the required access and context.</p>
<p>The way to think of topology is based on how your organization manages operations today, across the people responsible for the work and the systems they use. Consider the operational problems and workflows the SRE agent will support, the telemetry, source code, data, and knowledge required to perform that work, and the teams with domain expertise in the systems involved. Also consider what each group of users is permitted to see, what actions the agent is permitted to take, and who will create and maintain its workflows.&nbsp;</p>
<p>The following factors can help you think through which work belongs together and where a separate agent may be useful.</p>

<h3>2.2 How can multiple SRE Agents collaborate?</h3>
<p>Once teams operate separate SRE Agents, operational work can still cross the systems those teams own. <strong>Collaboration does not require teams to combine their agents or share all of their context.</strong> It means passing work, evidence, and ownership to the team responsible for the next step.</p>
<p>Common use cases include:</p>
<ul>
<li><strong>An investigation crosses a team boundary.</strong> A team determines that the evidence points to another application, platform, network, identity, database, or data layer. It passes the evidence, what it has already checked, and the requested analysis or action to the team with the required ownership, domain expertise, permissions, or authority.</li>
<li><strong>A planned change spans several owners.</strong> Each team validates its part of the system before and after the change and records the results in the shared change record.</li>
<li><strong>A central team identifies work for a resource owner.</strong> A compliance, security, or cost-management team assigns the work with the supporting evidence and required outcome.</li>
</ul>
<p>Across these use cases, collaboration requires three things: pass enough context for the next team to act, choose how the work will move between agents, and preserve a shared record of the outcome.</p>
<p><strong>Pass the work as a structured handoff.</strong>&nbsp;Include the problem or task, its impact, links to the supporting evidence, what has already been checked, the current findings and uncertainty, and the specific analysis or action requested. This prevents the receiving team from repeating the investigation. The receiving team then returns its findings or completed action so the originating team can continue or close the broader task.</p>
<p><strong>Choose the handoff mechanism that fits the existing workflow:</strong></p>
<ul>
<li><strong>Operational tools and automation.</strong>&nbsp;One agent can reassign an incident, create a Jira ticket, or post a summary in Teams. Automation on the incident or ticket can invoke the receiving team’s SRE Agent and write the result back. This enables collaboration without requiring one agent to invoke another directly.</li>
<li><a href="https://learn.microsoft.com/azure/sre-agent/http-triggers" rel="noopener" target="_blank"><strong>HTTP triggers</strong></a><strong>.</strong>&nbsp;An agent workflow or external automation can invoke a workflow in another SRE Agent and pass the context required for the next step.</li>
<li><strong>MCP-compatible clients and orchestrators.</strong>&nbsp;They can use the&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/mcp-server" rel="noopener" target="_blank">SRE Agent MCP server</a> to ask the appropriate agent to investigate a question or continue work in an existing thread.</li>
</ul>
<h3>2.3 Two common multi-agent scenarios</h3>
<p>These examples show how enterprises can configure multiple SRE Agents while preserving the context and authority each team needs.</p>
<h4>Scenario 1: A shared platform agent collaborates with team-owned agents</h4>
<p>Imagine an organization with a platform team that operates infrastructure, networks, shared data services, and other common dependencies for many application teams. Frontline operations or the service desk routes an incident to the platform team’s SRE Agent first.</p>
<p>The platform agent investigates using centralized infrastructure telemetry, infrastructure-as-code repositories, change history, and platform knowledge. It orchestrates work across its specialized platform capabilities and collaborates laterally with team-owned agents. If the issue is in the shared platform, the platform team continues the investigation and takes the actions within its authority. If the platform is healthy or the evidence points to an application, the agent hands the incident to the appropriate application team’s agent with the evidence already collected and the dependencies already checked.</p>
<p>Application agents can also have permitted read visibility into shared platform dependencies. This helps application teams identify whether a problem originates in their service or the platform, while the platform team retains authority over platform changes.</p>
<img />
<h4>Scenario 2: Team-owned agents coordinate directly</h4>
<p>In another organization, each product or application team operates the services it builds and owns its operational context, telemetry, code, permissions, and workflows. Each team’s SRE Agent is the first responder for its services.</p>
<p>When an investigation points to another service or shared dependency, the initiating agent packages the evidence and hands the work directly to the owning team’s agent. Teams whose operational work does not cross can continue to operate independently. Each agent investigates and acts within its own boundary, while collaborating teams use the same incident or ticket to maintain an end-to-end record.</p>
<p>Shared enterprise standards can provide consistent identity, logging, security, deployment, and governance controls. Teams can also reuse approved skills, tools, and workflow templates without combining their runtime context or agent configuration.</p>
<img />
<h2>3. How do we codify, deploy, and govern SRE Agents at enterprise scale?</h2>
<p>Whether an organization operates one SRE Agent or many, those agents continue to change after deployment. Teams add skills, subagents, tools, prompts, hooks, automations, and policies, while the agents accumulate knowledge and memories through operational use. Because these changes can affect how an agent investigates, analyzes, and acts, manage the agent’s configuration, artifacts, and learnings with the same discipline used for production code.</p>
<p>This becomes especially important when teams move from a proof-of-concept or test agent to a production agent. They may need to create the production agent in the same region or another region while preserving the configuration, knowledge, memories, and operational refinements accumulated during testing. They also need to understand whether changes to a skill, subagent, tool, prompt, or policy changed the agent’s behavior.</p>
<p>Our recommendation is to export an agent that has already been refined through real use, bring the export under version control, and use it as a repeatable baseline. Teams can then preserve its learnings, create production agents in the required environments, track how the configuration changes, and decide which parts should remain agent-specific or be shared with other agents.</p>
<h3>3.1 Export the working agent as code</h3>
<p>The Azure SRE Agent team maintains the public&nbsp;<a href="https://github.com/microsoft/sre-agent" rel="noopener" target="_blank">microsoft/sre-agent repository</a>&nbsp;with templates and scripts for deploying, exporting, cloning, and verifying agents. The repository includes&nbsp;<a href="https://github.com/microsoft/sre-agent/blob/main/sreagent-templates/bin/export-agent.sh" rel="noopener" target="_blank">Bash</a>&nbsp;and&nbsp;<a href="https://github.com/microsoft/sre-agent/blob/main/sreagent-templates/bin/ps/Export-Agent.ps1" rel="noopener" target="_blank">PowerShell</a>&nbsp;scripts that create a deploy-ready export of a working agent.</p>
<p>The export includes the agent settings, connectors, skills, subagents, tools, hooks, common prompts, repositories, plugin configuration, scheduled tasks, incident filters, HTTP triggers, incident-platform configuration, knowledge, and expected configuration. By default, it also includes synthesized knowledge and workspace memories developed through prior investigations and interactions. Repository instructions can be included when needed.</p>
<p>Review the export for sensitive information and keep connector credentials and other secrets outside the repository. Commit the approved export to Git so teams can preserve the agent’s accumulated knowledge, track configuration changes that may affect its behavior, identify drift, recreate the agent in the same or another region, and use a known agent-as-code baseline for future changes.</p>
<h3>3.2 Standardize what should be shared</h3>
<p>Decide which parts of the baseline should apply to every agent. Use&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/deploy-iac" rel="noopener" target="_blank">Bicep or Terraform</a>&nbsp;and Git to define common identity, network, security, logging, audit, and deployment controls, while parameterizing the values that differ by agent or environment.</p>
<p>The public&nbsp;<a href="https://github.com/microsoft/sre-agent/tree/main/sreagent-templates" rel="noopener" target="_blank">SRE Agent templates</a>&nbsp;provide examples for infrastructure as code, export, deployment, verification, and CI/CD. For reusable operational capabilities, use a&nbsp;<a href="https://learn.microsoft.com/azure/sre-agent/plugin-marketplace" rel="noopener" target="_blank">private plugin marketplace</a>&nbsp;backed by private GitHub or GitHub Enterprise. Teams can maintain approved skills and MCP integrations once, while agent owners install only the capabilities relevant to their agents. Each installation is pinned to a Git commit so teams can control when updates are adopted.</p>
<p>Together, the version-controlled export, infrastructure as code, shared baseline, and private plugin marketplace provide a repeatable way to expand SRE Agent without making every agent identical.</p>
