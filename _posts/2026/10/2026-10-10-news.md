### Multi-NIC Support on AKS powered by DRANET – Now in Public Preview

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/multi-nic-support-on-aks-powered-by-dranet-now-in-public-preview/ba-p/4563257](https://techcommunity.microsoft.com/t5/azure-networking-blog/multi-nic-support-on-aks-powered-by-dranet-now-in-public-preview/ba-p/4563257)
- **Published**: 2026-10-10 03:24:27
- **Fetched**: 2026-10-10 10:20:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Kubernetes was designed around a simple networking model, every pod gets one network interface, and every pod on a node shares the same flat network. For most stateless microservices, this works well as it keeps the model simple and the platform portable.</p>
<p>But a large class of workloads don't fit that shape. Some need network separation, with management, control, and data traffic on separate and isolated networks rather than multiplexed over one interface. Other workloads need predictable performance, a dedicated path for high-throughput or latency-sensitive traffic. Until now, meeting these requirements on Kubernetes meant adding and manually integrating multiple components, or keeping the workload on VMs.</p>
<p><strong>Today we're announcing the public preview of multi-NIC support for pods on AKS, powered by the AKS managed </strong><a href="https://github.com/kubernetes-sigs/dranet" rel="noopener" target="_blank"><strong>DRANET driver.</strong></a><strong> You can now provision worker nodes with multiple network interfaces connected to different subnets, and attach a dedicated interface directly to a pod using standard upstream Kubernetes APIs, with no Multus, no custom CNI extensions, and no manual interface wiring.</strong></p>
<div class="lia-video-container lia-media-is-center lia-media-size-large"></div>
<h2>Two ways to use multi-NIC on AKS</h2>
<p><strong>Use case 1: A dedicated NIC attached directly to a pod</strong></p>
<p><em>“As a networking engineer, I want to attach a dedicated network interface directly to a Kubernetes pod so the workload can connect to different networks and route traffic natively, without relying on host-level DPDK/VPP forwarding, custom routing rules, or gateway-based NAT.”</em><br /><em>“I also want the secondary interface on my pod to send and receive traffic on a specific, known public IP address, so that downstream partners can allow-list my traffic by IP and no NAT hop adds latency to time-sensitive streams."</em></p>
<p>This is the pattern where the workload itself expects to see multiple interfaces. The pod asks for a network device the same way it would ask for any other resource, and the interface shows up inside the container alongside the standard CNI interface. No host-level forwarding layer, no NAT gateway in the middle.</p>
<p><strong>What you get</strong></p>
<ul>
<li>The DRANET driver is deployed automatically. Once a node pool is configured with secondary interfaces, AKS installs and manages the driver for you; there is no add-on to install and no CRDs to author by hand.</li>
<li>Declarative, scheduler-aware requests. Interfaces are advertised to Kubernetes as allocatable devices, so a pod that asks for one is placed on a node that can actually provide it, using standard Dynamic Resource Allocation (DRA) objects rather than vendor-specific annotations.</li>
<li>A predictable interface lifecycle. The driver handles attach, release, and recovery as pods are rescheduled or restarted.</li>
<li>A public IP address can be assigned directly to a secondary interface, configured at node pool creation time using IP tags. The pod's secondary interface talks to the outside world without going through the load balancer or any address translation layer.</li>
<li>Both IPv4 and IPv6 addresses are supported on the secondary interface.</li>
</ul>
<p><strong>What to plan around</strong></p>
<ul>
<li>Interfaces are dedicated, not shared. When a NIC is attached to a pod, it moves into that pod's network namespace and is no longer available to the node or to any other pod. Sharing a secondary NIC across pods isn't supported in this release.</li>
<li>Because of that, pod density on a multi-NIC node pool is bounded by the number of interfaces on the node.</li>
<li>All interfaces must be attached to the same virtual network as the primary NIC. On a bring-your-own VNet cluster, different subnets within that VNet are supported, but different VNets are not, in this preview. On an AKS-managed VNet, secondary interfaces are currently limited to the same subnet as the primary NIC , since creating a new subnet on a managed VNet isn't supported yet.</li>
<li>Each pod's secondary interface gets its own dedicated public IP, so plan node pool sizing around how many pods need a tagged public IP of their own. Public IP assignment is configured at node pool creation time through IP tags, so decide your IP range and tagging strategy before you provision the node pool.</li>
<li>Kubernetes network policy is enforced on the primary interface only. Plan isolation for secondary interfaces at the subnet and NSG layer.</li>
</ul>
<p><strong><span>Use Case 2: Multi-NIC nodes with your own NIC management</span></strong></p>
<p><em>“As a platform/networking engineer, I want to provision Kubernetes worker nodes with multiple network interfaces connected to different networks and use my own&nbsp; VPP, DPDK, or any custom routing logic to steer traffic at the node level, without attaching additional interfaces to pods.” </em>&nbsp;</p>
<p>This is the pattern for teams who already own their dataplane. The node is multi-homed, each interface lands on its own subnet, and your own software decides which traffic goes where. Pods keep a single CNI-assigned interface and stay unaware of the underlying topology.</p>
<p><strong>What you get</strong></p>
<ul>
<li>Depending on the selected SKU size, you can configure nodes with multiple network interfaces.</li>
<li>Full control, and full ownership of the additional nics. AKS provisions the interfaces and keeps them attached to the node. How traffic is steered across them is entirely yours to design, configure, operate, and support. That includes your routing rules, your userspace dataplane, and any troubleshooting of the forwarding path itself.</li>
<li>The same-VNet constraint applies here too, secondary interfaces can span subnets, but not virtual networks. This applies to bring-your-own VNet clusters. On an AKS-managed VNet, secondary interfaces are restricted to the primary NIC's subnet for now.</li>
</ul>
<p>Both patterns start from the same node pool configuration. The difference is whether you stop there and manage the interfaces yourself, or let the DRANET hand them to your pods.</p>
<h2>How it works</h2>
<p>Multi-NIC on AKS starts with a single configuration step: you add secondary network interfaces to a node pool. AKS provisions the NICs on every VM in the pool and installs the DRANET driver alongside them. From there, what happens to those NICs depends on your workload. Reference a resource claim in your pod spec, and DRANET moves an interface into the pod Or Leave them on the node and steer traffic yourself with VPP, DPDK, or custom routing.</p>
<img />
<h3>Step 1: Provision the node pools with secondary NICs</h3>
<p>Secondary interfaces are declared when you create the node pool. The agent pool's network profile carries a secondaryNetworkInterfaces array, and each entry points at a subnet in the same virtual network as the primary NIC:</p>
"networkProfile": {
  "secondaryNetworkInterfaces": [
    { "type": "Standard", "vnetSubnetId": "&lt;VNET_SUBNET_ID&gt;" } 
    { "type": "Standard", "vnetSubnetId": "&lt;VNET_SUBNET_ID&gt;" }
  ] 
}
<p>AKS extends VMSS provisioning to attach those NICs to every VM in the pool. Add more entries for more interfaces, up to what the VM SKU allows. The array length is validated against the SKU at creation time, so a pool with mixed sizes has to be planned around the smallest one.</p>
<p>The node is now multi-homed and the interfaces are visible on the host. If you are building for use case 2, this is where you stop. AKS provisions and keeps the interfaces attached to the node, and how traffic is steered across them, the routing rules, the userspace dataplane, the troubleshooting of the forwarding path, is yours to design, operate, and support.</p>
<h3>Step 2: Using AKS managed DRANET driver to hand an interface to the pod</h3>
<p>Once a node pool has secondary interfaces configured, and the cluster is using AKS-managed CNI (Azure CNI or Azure CNI Powered by Cilium), AKS automatically installs the DRANET driver as a DaemonSet, packaged and delivered through an AKS-managed Helm chart. There is nothing to deploy yourself and no CRDs to author by hand. <br />If you're running a BYO CNI cluster, AKS still provisions the secondary NICs, but you're responsible for deploying DRANET (or your own driver of choice) yourself.</p>
<p>The driver does three things:</p>
<ul>
<li>Discovers the additional interfaces present on each node.</li>
<li>Advertises them to Kubernetes as allocatable DRA devices, published in a ResourceSlice.</li>
<li>Manages the lifecycle: exclusive per-pod allocation, attachment, release, and recovery as pods move or restart.</li>
</ul>
<p>Inspect the DRANET deamonset, pods, and deviceclass using the following commands:</p>
kubectl get deviceclasses
kubectl get daemonset -A
kubectl get pods -A -o wide
<p>Now you can create a “ResourceClaimTemplate” that defines how each pod requests a device.</p>
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
   name: nic-dev-template
spec:
  spec:
    devices:
      requests:
      - name: nic
        exactly:
        deviceClassName: standard-secondary-nic
        allocationMode: ExactCount
        count: 1
<p>Configure the pod references the template, and the scheduler places it on a node that has a matching NIC available:</p>
apiVersion: v1
kind: Pod
metadata:
  name: multi-nic-test
spec:
  containers:
  - name: multi-nic
    image: nicolaka/netshoot
    resources:
      claims:
      - name: nic
  resourceClaims:
  - name: nic
    resourceClaimTemplateName: nic-dev-template
<p>A pod referencing a claim comes up with its usual CNI-assigned eth0 plus the allocated secondary interface, and you can confirm both from inside the container.</p>
<p>When DRANET attaches a secondary NIC to a pod, that interface moves into the pod's network namespace and is no longer available on the node or to any other pod. It returns to the node's pool of available devices when the pod terminates. That gives you a clean isolation boundary and deterministic performance, with the trade-off that pod density on a multi-NIC pool is bounded by interface count, not just CPU and memory.</p>
<p><br /><strong>For the full walkthrough including feature flag registration, more examples visit </strong><a href="https://aka.ms/aks/multi-nic" rel="noopener" target="_blank">https://aka.ms/aks/multi-nic.</a></p>
<h2>Try it now</h2>
<p>Multi-NIC support for pods on AKS is available now in public preview. Start with the documentation for the full walkthrough: provisioning a node pool with secondary interfaces, defining a resource claim, and validating that both interfaces appear inside the pod.&nbsp;</p>
<ul>
<li>Documentation: <a href="https://aka.ms/aks/multi-nic" rel="noopener" target="_blank">https://aka.ms/aks/multi-nic</a></li>
<li>Upstream project: <a href="https://github.com/kubernetes-sigs/dranet" rel="noopener" target="_blank">DRANET on GitHub</a></li>
</ul>
<p>Preview is when your input can actually shape the feature. If you hit a limitation or have a use case we haven’t covered, comment below and share your feedback.</p>

### Qwen3.8-27B on a $2 H100 Azure Spot VM: does it pay off?

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/qwen3-8-27b-on-a-2-h100-azure-spot-vm-does-it-pay-off/ba-p/4563387](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/qwen3-8-27b-on-a-2-h100-azure-spot-vm-does-it-pay-off/ba-p/4563387)
- **Published**: 2026-10-10 16:27:28
- **Fetched**: 2026-10-11 03:59:41

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>For three hours on the morning of October 9, a single H100 in Azure served 1,434 requests to Qwen3.8-27B: 168.7 million input tokens in, 1.27 million output tokens out. At a public list price for this model that day ($0.425 per million input tokens, $0.085 per million cached input tokens and $2.55 per million output tokens), those tokens are worth $24.35. The three hours of VM time cost $4.65 at that region's Spot price; the dashboard below counts them at a round $2 an hour.</p>
<p>This post is the guide I'd have wanted before I started: how to run Qwen3.8-27B on an Azure GPU VM, how to tune it, and how to monitor it end to end, with metrics, logs and traces, using Application Insights and Grafana. The answer to the title comes at the end. The dashboard that measured it comes from the monitoring setup in the middle.</p>
<img />
<h2>What you're running</h2>
<p>Qwen3.8-27B is a 27-billion-parameter dense model from Qwen, released under the Apache 2.0 license. A few of its properties shape how you serve it:</p>
<ul>
<li><strong>Hybrid attention.</strong> 48 of its 64 layers use Gated DeltaNet linear attention, which keeps a fixed-size state instead of a per-token KV cache. Only the 16 full-attention layers grow with the context, which is why long contexts fit on one GPU.</li>
<li><strong>A 262,144-token context window,</strong> which Qwen documents how to extend to about one million tokens with YaRN.</li>
<li><strong>Thinking on by default,</strong> with a per-request switch to turn it off.</li>
<li><strong>Multi-token prediction (MTP) layers,</strong> which vLLM can use for speculative decoding.</li>
<li><strong>Vision:</strong> it reads images and video as well as text.</li>
</ul>
<p>The GPU is a <code>Standard_NC40ads_H100_v5</code>: one H100 NVL with 94 GB of memory and 40 vCPUs. Both official checkpoints fit on it:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>&nbsp;</th><th>BF16 (<code>Qwen/Qwen3.8-27B</code>)</th><th>FP8 (<code>Qwen/Qwen3.8-27B-FP8</code>)</th></tr></thead><tbody><tr><td>Download</td><td>55.6 GB</td><td>30.9 GB</td></tr><tr><td>Weights in GPU memory</td><td>51.9 GiB</td><td>29.0 GiB</td></tr><tr><td>KV cache left over</td><td>805K tokens</td><td>1.45M tokens</td></tr><tr><td>One request, 512 tokens, thinking off</td><td>124 tok/s</td><td>172 tok/s</td></tr></tbody><colgroup><col style="width: 40.60%;" /><col style="width: 28.13%;" /><col style="width: 31.27%;" /></colgroup></table></div>
<p>Use FP8. The H100 runs FP8 natively, each decode step reads fewer bytes, and the memory the smaller weights free up nearly doubles the KV cache. The NVFP4 builds you'll see in vLLM's recipes target Blackwell GPUs, since the H100 has no FP4 tensor cores.</p>
<h2>Step 1: Get a Spot H100 VM</h2>
<p><a href="https://learn.microsoft.com/azure/virtual-machines/spot-vms" rel="noopener" target="_blank">Azure Spot Virtual Machines</a> sell spare capacity at a discount, with no SLA, and Azure can evict them with 30 seconds' notice. In October 2026 this size cost $1.55 to $1.84 an hour on Spot in the regions I settled on, which this post rounds to $2 (prices change; check <a href="https://azure.microsoft.com/pricing/details/virtual-machines/linux/" rel="noopener" target="_blank">the pricing page</a>). Spot draws on your regional low-priority vCPU quota, 40 vCPUs for this size, not on the H100 family quota, which was zero in my subscription.</p>
<p>Pick the region with data rather than habit. The sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/infra/spot-regions.sh" rel="noopener" target="_blank">infra/spot-regions.sh</a> lists each region's eviction-rate bucket and Spot price history, and the current placement score per zone; there's more on that in the Spot section below. Then create the VM with <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/infra/provision-spot-vm.sh" rel="noopener" target="_blank">infra/provision-spot-vm.sh</a>:</p>
<pre class="lia-code-sample language-bash" contenteditable="false" tabindex="0"><code>LOCATION=southeastasia ZONE=2 IDENTITY_RG=rg-llm-telemetry infra/provision-spot-vm.sh
</code></pre>
<p>In about five minutes that gives you:</p>
<ul>
<li>a resource group, a VNet and a network security group with only the default rules, which deny inbound traffic from the internet</li>
<li>a NAT gateway for outbound traffic: Docker images, Hugging Face downloads and telemetry</li>
<li>the VM: Ubuntu 24.04 and no public IP. It uses Trusted Launch with Secure Boot off, because Secure Boot rejects the unsigned NVIDIA kernel modules. It has a 512 GB data disk for weights and images, the Spot <em>Deallocate</em> eviction policy so an eviction keeps the disks, and a managed identity for telemetry</li>
</ul>
<p>With no public IP and no SSH, you administer the VM through <code>az vm run-command</code>, which the sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/scripts/vm-run.sh" rel="noopener" target="_blank">scripts/vm-run.sh</a> wraps: <code>scripts/vm-run.sh &lt;script&gt;</code> runs a local script on the VM as root and prints the output.</p>
<h2>Step 2: Prepare the host</h2>
<pre class="lia-code-sample language-bash" contenteditable="false" tabindex="0"><code>scripts/vm-run.sh scripts/bootstrap-host.sh
</code></pre>
<p><a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/scripts/bootstrap-host.sh" rel="noopener" target="_blank">The bootstrap</a> takes about four minutes. It mounts the data disk at <code>/data</code>, installs the NVIDIA datacenter driver (the 595 branch with open kernel modules, which loads without a reboot), installs Docker Engine with its data root on <code>/data</code>, and registers the NVIDIA Container Toolkit with Docker. At the end, <code>nvidia-smi</code> should report one H100 NVL with 95,830 MiB.</p>
<h2>Step 3: Serve the model with vLLM</h2>
<p>The stack is a Docker Compose project: a one-shot job that downloads the pinned checkpoint, vLLM, a LiteLLM gateway, and optional overlays for telemetry and a public URL. The sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/scripts/deploy.sh" rel="noopener" target="_blank">scripts/deploy.sh</a>, run with <code>up</code>, copies the folder to the VM through run-command and starts it in the background. On a new VM everything is healthy about 20 minutes later. Most of that is image pulls and the 31 GB download, and later restarts of the model take a few minutes.</p>
<p>The model runs in NVIDIA's NGC vLLM container, release 26.07 (vLLM 0.24). One fix was needed there: tool calls failed with HTTP 500 because the bundled xgrammar 0.2.0 lacks a function vLLM's frontend imports, so <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/images/vllm/Dockerfile" rel="noopener" target="_blank">the sample's image</a> adds xgrammar 0.2.3. The checkpoint is pinned to a revision and downloaded once to the data disk, so restarts don't depend on Hugging Face.</p>
<p>This is the serve command:</p>
<pre class="lia-code-sample language-bash" contenteditable="false" tabindex="0"><code>vllm serve /models/Qwen3.8-27B-FP8 \
  --served-model-name qwen3.8-27b \
  --trust-remote-code \
  --max-model-len 262144 \
  --gpu-memory-utilization 0.93 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 16384 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --spec-method mtp --spec-tokens 3 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_coder \
  --limit-mm-per-prompt '{"image":{"count":4,"width":1024,"height":1024},"video":0}'
</code></pre>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Flag</th><th>Why</th></tr></thead><tbody><tr><td><code>--max-model-len 262144</code></td><td>The native context window.</td></tr><tr><td><code>--gpu-memory-utilization 0.93</code></td><td>Lets vLLM use 93% of the GPU's memory. After the weights, that leaves 1.5 million tokens of KV cache, about 5.7 full-length requests at once.</td></tr><tr><td><code>--max-num-seqs 32</code></td><td>Throughput barely grows beyond 32 concurrent requests on this GPU (measured below).</td></tr><tr><td><code>--max-num-batched-tokens 16384</code></td><td>The prefill chunk per step. 32K gained nothing and cost 5% of the KV cache.</td></tr><tr><td><code>--kv-cache-dtype fp8</code></td><td>Halves the KV cache's memory compared with BF16.</td></tr><tr><td><code>--enable-prefix-caching</code></td><td>Reuses the KV blocks of a repeated prefix instead of recomputing them. <h2>Step 4: Call it</h2>
<p>vLLM serves an OpenAI-compatible API, and so does the LiteLLM gateway in front of it, under one stable alias, <code>local-llm</code>, so clients don't change when the model does:</p>
<pre class="lia-code-sample language-bash" contenteditable="false" tabindex="0"><code>curl http://127.0.0.1:4000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "local-llm",
  "messages": [{"role": "user", "content": "Explain prefix caching in two sentences."}],
  "temperature": 0.7, "top_p": 0.8, "presence_penalty": 1.5,
  "chat_template_kwargs": {"enable_thinking": false}
}'
</code></pre>
<p>Thinking is on unless a request turns it off with <code>chat_template_kwargs</code>. Qwen's <a href="https://huggingface.co/Qwen/Qwen3.8-27B" rel="noopener" target="_blank">model card</a> recommends temperature 1.0, top_p 0.95 and top_k 20 with thinking on, and temperature 0.7, top_p 0.8, top_k 20 and presence_penalty 1.5 with it off. Tool calls work as they do with OpenAI: send <code>tools</code>, and the parser turns the model's tool-call markup into <code>tool_calls</code>.</p>
<p>The sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/scripts/smoke-test.sh" rel="noopener" target="_blank">smoke test</a> (<code>scripts/vm-run.sh scripts/smoke-test.sh</code>) checks an exact answer, a required tool call and the decode speed. On this VM, one request generates about 166 tokens a second with thinking off.</p>
<p>The VM has no public IP, so the gateway is published through an ngrok tunnel with an IP allow-list. The gateway has no authentication of its own, so that allow-list is the only access control on the public URL. That suited my own tests. For anything more, add a LiteLLM key or an authentication policy at the tunnel.</p>
<h2>Step 5: Tune it</h2>
<p>Two settings were worth measuring.</p>
<p><strong>How many tokens to draft.</strong> Speculative decoding drafts tokens with the MTP layers and verifies them in one pass. On natural-language prompts with 512-token replies:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Draft tokens</th><th>1</th><th>2</th><th>3</th><th>4</th></tr></thead><tbody><tr><td>One request (tok/s)</td><td>105</td><td>131</td><td>151</td><td>146</td></tr><tr><td>32 requests (tok/s)</td><td>1,497</td><td>1,546</td><td>1,548</td><td>1,342</td></tr></tbody><colgroup><col style="width: 42.32%;" /><col style="width: 14.42%;" /><col style="width: 14.42%;" /><col style="width: 14.42%;" /><col style="width: 14.42%;" /></colgroup></table></div>
<p>Three came out on top at both ends. vLLM warns that drafting more than one token reuses the same MTP layer and can lower acceptance, so watch the acceptance rate on the dashboard rather than trusting the setting.</p>
<p><strong>How many requests at once.</strong> On synthetic 2,000-token prompts, output grows to 32 concurrent requests and then flattens: 150 tokens a second at 1, 821 at 16, 1,187 at 32 and 1,212 at 48, while each stream slows from 150 to 25 tokens a second. On natural text, where more drafts are accepted, 32 requests reach about 1,550 output tokens a second. That's the measured ceiling: 5.6 million output tokens an hour, worth $14.23 an hour at $2.55 per million.</p>
<h2>Step 6: Monitor it: metrics, logs and traces</h2>
<p>A self-hosted model has no provider status page. When it's slow, you need to know whether the cause is the queue, the cache, the GPU or the client, and when it's idle, you're still paying for it. Azure Monitor ingests OpenTelemetry natively (<a href="https://techcommunity.microsoft.com/blog/azureobservabilityblog/direct-opentelemetry-ingestion-into-azure-monitor-is-now-generally-available/4524044" rel="noopener" target="_blank">generally available since June 2026</a>), so one Application Insights resource can receive all three signals.</p>
<h3>Create the destination</h3>
<ol>
<li>Create an Application Insights resource with <strong>OTLP support</strong> set to <strong>On</strong>. That provisions a Log Analytics workspace for logs and traces, an Azure Monitor workspace that stores metrics as Prometheus data, and the data collection endpoint and rule that route OTLP into them. <a href="https://learn.microsoft.com/azure/azure-monitor/containers/opentelemetry-protocol-ingestion" rel="noopener" target="_blank">Ingest OTLP data into Azure Monitor with the OpenTelemetry Collector</a> walks through it.</li>
<li>On the resource's <strong>Overview</strong> page, copy the OTLP connection info: the endpoint URLs for traces, logs and metrics, and the data collection rule ID.</li>
<li>Give the VM's managed identity the <strong>Monitoring Metrics Publisher</strong> role on that data collection rule. The collector signs in with Microsoft Entra ID, so you don't have to store a key on the VM. The sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/infra/telemetry-identities.sh" rel="noopener" target="_blank">infra/telemetry-identities.sh</a> creates one identity per region you run in and assigns the role.</li>
</ol>
<h3>Point a collector at it</h3>
<p>One OpenTelemetry Collector (the contrib distribution) runs next to the model and gathers everything:</p>
<ul>
<li><strong>Metrics:</strong> it scrapes vLLM's and LiteLLM's Prometheus endpoints and NVIDIA's DCGM exporter for the GPU, and reads host and container statistics.</li>
<li><strong>Traces:</strong> LiteLLM sends its spans to the collector over OTLP. Each model call is a span with the token counts, time to first token and finish reason as <code>gen_ai.*</code> attributes.</li>
<li><strong>Logs:</strong> it tails every container's log, plus the host's syslog, where GPU Xid errors and out-of-memory kills appear.</li>
</ul>
<p>The part that talks to Azure Monitor is short (abridged from the sample's <a href="https://github.com/1w2w3y/wuyi-labs/blob/main/2610-h100-qwen-38-27b/observability/otelcol/config.yaml" rel="noopener" target="_blank">observability/otelcol/config.yaml</a>, collector 0.161):</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>extensions:
  azure_auth:
    managed_identity:
      client_id: ${env:TELEMETRY_UAMI_CLIENT_ID}
    scopes: [https://monitor.azure.com/.default]

processors:
  resource:
    attributes:
      - {key: microsoft.applicationId, value: "${env:AZMON_APPLICATION_ID}", action: upsert}

exporters:
  otlp_http/azuremonitor:
    traces_endpoint: ${env:AZMON_TRACES_ENDPOINT}
    logs_endpoint: ${env:AZMON_LOGS_ENDPOINT}
    metrics_endpoint: ${env:AZMON_METRICS_ENDPOINT}
    auth:
      authenticator: azure_auth
</code></pre>
<p>Here's where each signal lands and how you query it:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Signal</th><th>Sources</th><th>Stored in</th><th>Query with</th></tr></thead><tbody><tr><td>Metrics</td><td>vLLM, LiteLLM, GPU (DCGM), host, containers</td><td>Azure Monitor workspace</td><td>PromQL</td></tr><tr><td>Traces</td><td>LiteLLM request and model-call spans</td><td>Application Insights (Log Analytics)</td><td>KQL, or the Application Insights transaction view</td></tr><tr><td>Logs</td><td>every container, host syslog</td><td>Application Insights (Log Analytics)</td><td>KQL</td></tr></tbody><colgroup><col style="width: 6.41%;" /><col style="width: 32.81%;" /><col style="width: 25.74%;" /><col style="width: 35.04%;" /></colgroup></table></div>
<h3>Four things that tripped me up</h3>
<ul>
<li><strong>Set <code>microsoft.applicationId</code> on everything you send.</strong> The data collection rule that Application Insights creates routes data on that resource attribute, which is why the processor above sets it on every resource.</li>
<li><strong>Metrics keep only a few resource attributes.</strong> The metrics rule keeps <code>service.*</code>, <code>host.name</code> and <code>cloud.region</code>, and drops the rest, so per-container series merged into one until a <code>transform</code> processor copied the container name onto each data point. The sample does the same for an <code>upstream_model</code> label, so a second model on the same VM shows up as its own series. In logs, fields you want to filter on also belong on the record, not the resource.</li>
<li><strong>OTLP histograms arrive as native histograms.</strong> <code>histogram_quantile</code> takes the bare metric name, with no <code>_bucket</code> suffix and no <code>le</code> label, and OpenTelemetry-native names keep their dots, so you write <code>{__name__="system.cpu.utilization"}</code>.</li>
<li><strong>Check what your spans carry.</strong> LiteLLM records the useful parts of each call (token counts, time to first token, finish reason) without prompts or responses when message capture is off. It still records every tool definition the client declares, though. Decide whether that's acceptable in your Application Insights resource, and choose the fields carefully before you share a dashboard.</li>
</ul>

<p>It has ten rows: overview, token economics, throughput, the gateway, traffic and latency, cache and scheduling, the GPU, host and containers, the telemetry pipeline itself, and traces and logs. These are the questions I look at first:</p>

<h3>Change the dashboard and ask the data with an agent</h3>
<p>You don't have to edit dashboard JSON or write every query by hand. Azure Managed Grafana instances in the Azure public cloud include a remote MCP server at <code>https://&lt;grafana-endpoint&gt;/api/azure-mcp</code> (<a href="https://aka.ms/amg-mcp" rel="noopener" target="_blank">Configure an Azure Managed Grafana Remote MCP server</a>). Connect an MCP client to it, and an AI agent can work with this dashboard and the telemetry behind it. GitHub Copilot in Visual Studio Code signs in with Microsoft Entra ID; Claude Code and other clients can use a Grafana service account token.</p>
<ul>
<li><strong>Author and change dashboards.</strong> <code>amgmcp_dashboard_inspect</code> reads a dashboard's panels, variables and queries, and <code>amgmcp_dashboard_update</code> creates a dashboard or patches one panel, query or title at a time. A request such as "add a panel for preemptions per minute next to KV cache usage" becomes a targeted patch instead of a JSON edit.</li>
<li><strong>Query the telemetry.</strong> <code>amgmcp_prometheus_query</code> runs PromQL against the Azure Monitor workspace, <code>amgmcp_query_resource_log</code> runs KQL against Application Insights, and <code>amgmcp_query_application_insights_trace</code> fetches a trace. Questions like "which requests waited longest for their first token this morning?" or "how many output tokens did the model generate per VM hour this week?" come back with numbers from the same data the dashboard shows.</li>
</ul>
<p>The agent acts with the Grafana permissions of the identity it signs in with, so give that identity the role the job needs: Grafana Viewer to ask questions, Grafana Editor to change dashboards. My previous post, <a href="https://techcommunity.microsoft.com/blog/appsonazureblog/dashboards-are-for-ai-agents-too-not-just-humans/4556383" rel="noopener" target="_blank">Dashboards are for AI agents too, not just humans</a>, shows the other half: how an agent uses a dashboard's queries and descriptions as context.</p>
<h2>What the dashboard showed</h2>
<p>The traffic in these screenshots is a real agentic workload: long-running sessions that call tools and send the whole conversation back with each request. In the busy window it looked nothing like the benchmark:</p>
<ul>
<li><strong>Prompts were long.</strong> The median request carried about 120,000 input tokens, and the 95th percentile 186,000.</li>
<li><strong>Most of it was cached.</strong> 88% of input tokens were prefix-cache hits.</li>
<li><strong>Output was small.</strong> There were 133 input tokens for every output token, and 62% of the output tokens were reasoning.</li>
<li><strong>Concurrency was low.</strong> At most 10 requests ran at once, with room for 32.</li>
</ul>
<img />
<p>Output averaged 117 tokens a second, under 8% of the 1,550 ceiling, yet the GPU was busy 77% of the time. The work went into prefill (19.9 million computed input tokens in three hours) and into attention over contexts of 100,000 tokens and more. A single request saw about 34 tokens a second at the median, not 166.</p>
<p>Long contexts also fill the KV cache with only a few requests. Around 08:00 the cache reached 88.6%, and at the same moment the 95th-percentile time to first token jumped to 2.6 minutes: new requests were waiting for memory, not compute. The traces show it request by request, with 200,000-token prompts waiting 40 seconds or more for their first token. About 60 of the window's 64 failed requests were prompts that had outgrown the 262K-token context window, which is where the dashboard's 4.47% error rate comes from.</p>
<img />
<p><strong>Measure the shape of your own traffic, not the shape of a benchmark.</strong> For this workload the numbers that matter are prefill throughput, the cache hit rate and how many long contexts fit in memory at once.</p>

</ul>

<h2>Does it pay off?</h2>
<p>The token economics row at the top of this post turns the dashboard into a running answer. VM hours are the minutes in which the collector could scrape vLLM, so stopped or evicted time doesn't count. The prices are dashboard variables: the VM's hourly price and the per-million prices for input, cached input and output, defaulting to the list prices above. Every stat is an instant query, so after an eviction it reads "Off" instead of holding its last value.</p>
<p>Over the busiest three hours it reads $8.12 of tokens per VM hour, about four times the VM's price. Over the first week it's a different story:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>&nbsp;</th><th>Busiest 3 hours (Oct 9, 05:35–08:35 UTC)</th><th>First week (Oct 3–10)</th></tr></thead><tbody><tr><td>Hours the model server was up</td><td>3.0</td><td>37.9</td></tr><tr><td>Requests</td><td>1,434</td><td>5,469</td></tr><tr><td>Input tokens (share served from the prefix cache)</td><td>168.7M (88%)</td><td>564.2M (88%)</td></tr><tr><td>Output tokens</td><td>1.27M</td><td>6.11M</td></tr><tr><td>Worth at the list price</td><td>$24.35</td><td>$85.94</td></tr><tr><td>Per hour the model server was up</td><td><strong>$8.12</strong></td><td><strong>$2.27</strong></td></tr></tbody><colgroup><col style="width: 42.29%;" /><col style="width: 37.47%;" /><col style="width: 20.24%;" /></colgroup></table></div>
<p>The VMs actually ran about 46 hours that week, counting setup, model loading, benchmarks and the first runs before the telemetry existed. At each region's Spot price that was about $98 of compute, plus a little for disks and the NAT gateway, against $86 of tokens. The first nine and a half hours ran in West US 3 at $3.95 an hour, before I started choosing regions with the data above; the rest averaged $1.67 an hour.</p>
<p>Look at where the value comes from, too. In the busy window, cached input brought in 52% of it ($12.65), computed input 35% ($8.48) and output only 13% ($3.23). Benchmarks measure output tokens per second, but for this workload output was less than a fifth of the value.</p>
<p>So the answer to the title is: <strong>it pays off when it's busy.</strong> At $8.12 of tokens per busy hour against about $2 of VM, the H100 needs to be busy roughly a quarter of the time to break even, and it can't earn while it's evicted, loading or idle. Self-hosting on an H100 Spot VM makes sense when:</p>
<ul>
<li>traffic is steady and its prompts share long prefixes, which is where prefix caching makes input cheap to serve</li>
<li>you want control over the exact checkpoint, the serving flags and where requests go</li>
<li>the workload tolerates an occasional restart, or you pay for regular capacity</li>
</ul>
<p>It makes less sense for bursty traffic that leaves the GPU idle most of the day, or for anything that needs an SLA on a Spot VM.</p>
