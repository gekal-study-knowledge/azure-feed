<p><span><span>New and upcoming controls, where they apply</span><span>, and how they fit into </span><span>sovereign</span><span> Azure architecture.</span> <span>At </span><span>the October</span><span> Frontier</span><span> Tour</span><span>, we are announcing new and expanded capabilities for Microsoft Sovereign Public Cloud. This post explains what each capability does, where it applies, and how customers can combine controls within an Azure architecture.</span></span><span>&nbsp;</span></p>
<p><span><span>It is written for the platform engineer responsible for the landing zone, the security engineer answering operator-access questions, the compliance prof</span><span>essional translating requirements into controls and evidence, and the architect deciding where and how an AI workload can run. The </span></span><a href="http://www.aka.ms/SovMoment2026" rel="noopener" target="_blank"><span><span>O</span><span>ne</span><span> Microsoft Blog</span></span></a><span><span> provides the broader business framing.</span></span><span>&nbsp;</span></p>
<h2>Why the control surface changed</h2>
<p><span><span>For years, residency addressed many sovereignty questions: select the </span><span>appropriate region</span><span>, understand commitments such as the EU Data Boundary and in-country processing, and design the workload accordingly. Those commitments continue to provide an important foundation.</span></span><span>&nbsp;</span></p>
<p><span><span>AI makes the choice of controls increasingly important</span><span>. An AI workload can </span><span>help organizations </span><span>create and process sensitive information across prompts, retrieved context, model responses, embeddings, model artifacts, and operational data. Each can have its own residency, protection, and </span><span>access</span><span> considerations</span><span>. Sovereignty therefore needs to extend across the workload architecture, not only the location in which the workload runs.</span> <span>Sovereignty is not one-size-fits-all. With Microsoft Sovereign Public Cloud, organizations can select and combine sovereign controls based on the requirements of each workload while </span><span>benefiting</span><span> from the innovation and scale of the public cloud. </span><span>Data residency controls, including the choice of more than 80 Azure regions and the EU Data Boundary, help customers address where data is stored and processed.&nbsp;</span></span><span>&nbsp;</span></p>
<p><span><span>Customer-managed keys with Azure Key Vault Managed HSM strengthen customer control over data at rest; Private Link and TLS protect data in transit; and </span><span>Azure </span><span>C</span><span>onfidential </span><span>C</span><span>omputing</span> <span>helps</span><span> extend</span> <span>protection to data while it is being processed. Customer Lockbox provides </span><span>additional</span><span> control over Microsoft access to customer data, while Sovereign Landing Zone uses policy-based guardrails to help organizations apply sovereignty requirements at scale. Together, these complementary controls allow customers to tailor architectures to specific sovereignty, regulatory, and workload requirements while </span><span>benefiting from</span><span> Azure’s hyperscale infrastructure and advanced cloud and AI capabilities.</span></span><span>&nbsp;</span></p>
<p><span><span>Prompts, retrieved context, and model responses are processed in memory. For supported workloads, Azure confidential computing helps protect this data during processing using hardware-based, attested trusted execution environments. For supported workloads configured for secure key release, Microsoft Azure Attestation provides claims about the execution environment’s identity and security state. Azure Key Vault Managed HSM evaluates those claims against the configured release policy before releasing a key. Residency and encryption protections for stored embeddings, vector indexes, and model artifacts depend on the services and configurations used. Operational telemetry should be assessed separately against the applicable service’s data handling and residency commitments.</span></span><span>&nbsp;</span></p>
<p><span><span>We</span><span> are </span><span>now </span><span>expanding this portfolio with new and enhanced capabilities that give customers </span><span>additional</span><span> choices across sovereignty posture, encryption-key control, the protection of data in use, policy enforcement, operator-access transparency, and business continuity.</span></span><span>&nbsp;</span></p>
<h2>Start with the workload</h2>
<p><span><span><span>Consider an AI-powered application that uses sensitive organizational information to answer questions</span>. Information moves from the source records to a search index, then to an AI model that generates a response. Instead of using every available sovereignty control, the o</span><span>rganization first reviews the requirements and risks for this workload. It then chooses the controls that best address those needs.</span></span><span>&nbsp;</span></p>
<p><span><span>Each stage of that pipeline raises a different question. Source records raise residency and encryption-at-rest questions. Embedding and indexing </span><span>determine</span><span> where vector representations of </span><span>sensitive</span><span> data </span><span>live. Inference </span><span>determines</span><span> where prompts and retrieved context are processed, and whether that processing is </span><span>hardware-isolated</span><span>. Responses and operational telemetry raise retention, logging, and access questions. The sections that follow introduce each new capability against these stages, and the table at the end </span><span>consolidates</span><span> the mapping.</span></span><span>&nbsp;</span></p>
<h2>Sovereign Control Panel Public Preview at Microsoft Ignite</h2>
<p><span><span>Organizations increasingly need to&nbsp;</span><span>demonstrate</span><span> not only where their data </span><span>resides</span><span>, but also how sovereignty controls are applied, </span><span>monitored</span><span>, and </span><span>evidenced</span><span>. Answering questions from executives, auditors, regulators, and risk teams can require information spread across policy, security, monitoring, and operational processes. This fragmentation </span><span>can </span><span>make sovereignty posture difficult </span><span>for organizations </span><span>to assess and </span><span>demonstrate</span><span> consistently</span><span>.</span> <span>Sovereign Control Panel, currently in private preview, will enter public preview at Microsoft Ignite.</span> <span>Delivery timelines are subject to change.</span></span><span>&nbsp;</span></p>
<p><span><span>Just as Microsoft Defender for Cloud</span><span> helps organizations understand and improve their security posture, and Microsoft Purview brings visibility and governance to data,</span><span> Sovereign Control Panel is designed to bring </span><span>organizations </span><span>greater clarity and operational focus to sovereignty.</span></span><span>&nbsp;</span></p>
<p><span><span>Sovereign Control Panel is an Azure-based posture and evidence experience designed to help organizations assess, </span><span>monitor</span><span>, and </span><span>demonstrate</span><span> their sovereignty posture from a centralized position. Instead of manually assembling information across tools and teams for every assessment, customers can gain a more continuous and actionable understanding of their posture across their existing Azure estate</span><span>.</span></span><span>&nbsp;</span></p>
<p><span><span>The experience is organized around a continuous Discover, Control, Act model. Discover helps organizations understand where they stand and why by </span><span>establishing</span><span> their actual sovereignty posture, surfacing evidence, </span><span>identifying</span><span> gaps and risks, and explaining the underlying drivers. It also supports business </span><span>continuity</span><span> readiness by helping organizations assess dependencies and </span><span>readiness for portability across operating environments, if </span><span>required</span><span>. </span><span>Control helps organizations define what </span><span>should</span> <span>be true and how it should be maintained by selecting and configuring controls, assigning ownership, applying guardrails, and detecting deviations.</span> <span>Act helps organizations </span><span>address</span> <span>identified gaps through guided remediation and verify the resulting posture.</span></span><span>&nbsp;</span></p>
<img />
<p><span><span>By connecting posture assessment, control management, remediation, and verification, Sovereign Control Panel is designed to help customers move from manually assembling sovereignty information toward a continuous, insight-driven approach to managing sovereignty. It complements the policy-based guardrails provided by Sovereign Landing Zone and provides a foundation for progressively bringing sovereignty posture and operator-access </span><span>visibility together in one experience.</span></span><span>&nbsp;</span></p>
<h2>Data Guardian and Production Touch Ledger</h2>
<p><span>Customers increasingly expect cloud-provider access to be governed, monitored, and evidenced. Existing controls already govern access before it begins. Just-in-Time Access reviews time-bound Microsoft engineer access, while Customer Lockbox adds customer approval when customer data is in scope.</span><span>&nbsp;</span></p>
<p><span>We are rolling out two complementary additions to these operator-access controls for customers in the EU and EFTA: Data Guardian and Production Touch Ledger.</span><span>&nbsp;</span></p>
<p><span>Data Guardian strengthens operational oversight by enabling European-resident oversight by a trusted EU partner to monitor qualifying Microsoft engineer remote access to in-scope production systems in EU and EFTA regions. This oversight spans Azure, Microsoft 365, and Dynamics 365 workloads.</span><span>&nbsp;</span></p>
<p><span>Production Touch Ledger, also launched with phased rollout, complements this oversight with tamper-evident records of the actions performed during qualifying remote Microsoft engineer access to in-scope production systems in EU and EFTA regions. </span><span>&nbsp;</span></p>
<p><span>Together, these capabilities extend the operator-access lifecycle from access governance to oversight and evidence:</span><span>&nbsp;</span></p>

</ul>
<ul>
<li><span>Monitor: Data Guardian provides EU-resident oversight by a trusted EU partner during qualifying Microsoft engineer access to in-scope production environments.</span><span>&nbsp;</span></li>
</ul>

<li><span>Record: Production Touch Ledger preserves tamper-evident records of access and the actions performed for validation reconstruction.</span><span>&nbsp;</span></li>

<h2>External Key Management with Azure Managed HSM, generally available</h2>
<p><span><span>Azure Managed HSM already provides customers with </span><span>dedicated, single-tenant protection and control over the encryption keys used by supported Azure services</span><span>. </span><span>We are now announcing the general availability of External Key Management with Azure Managed HSM, </span><span>allowing customers to keep the root encryption key in hardware they own and </span><span>operate</span><span> on-premises or through a trusted third party.</span></span><span>&nbsp;</span></p>
<p><span><span>With External Key Management, the key-encryption key </span><span>remains</span><span> in a customer-owned and customer-operated HSM, either on-premises or hosted by a trusted third party. When a supported Azure service needs to wrap or unwrap a data-encryption key, Azure Managed HSM delegates the cryptographic operation to the external HSM through an External Key Management proxy.</span></span><span>&nbsp;</span></p>
<p><span><span>Azure Managed HSM </span><span>remains</span><span> the Azure-facing </span><span>service for </span><span>authorization and key</span> <span>management, while </span><span>External Key Management allows</span><span> the key-encryption key</span><span> to remain in an HSM physically </span><span>controlled </span><span>by the customer or a third-party provider</span><span>.</span></span><span>&nbsp;</span></p>
<p><span><span>Because the external HSM, proxy, and connectivity become part of the </span><span>workload’s</span><span> critical path, organizations should design and test availability, failover, key rotation, rewrapping, and recovery procedures before production deployment. </span><span>External Key Management is </span><span>available</span><span> to customers</span><span> globally</span><span>. </span></span><span>&nbsp;</span></p>
<h2>Azure Confidential Clean Rooms: In Limited Preview</h2>
<p>&nbsp;Some of the most valuable insights require organizations to bring data together, but sensitive data often can’t simply be shared. Azure Confidential Clean Rooms, currently in Limited Preview, is designed to help organizations collaborate on sensitive data while keeping the underlying data protected. Participants can analyze approved datasets together using Spark SQL within a hardware-protected environment, helping enable scenarios such as advertising measurement, customer matching, joint risk analysis, and other multiparty analytics without broadly exposing each participant’s raw data.</p>
<p><span><span>Built on Azure&nbsp;</span><span>c</span><span>onfidential </span><span>c</span><span>omputing, Azure Confidential Clean Rooms brings a verifiable trust model to these collaborations.</span><span> Participants encrypt their data, agree to the analysis being performed, and can use attestation to verify the expected environment and code before encryption keys are released. Only approved results leave the protected environment, while tamper-resistant audit </span><span>trails </span><span>help </span><span>record </span><span>important activity</span><span>.</span> <span>Azure Confidential Clean Rooms is moving toward making confidential, multiparty data collaboration available to a broader set of customers and scenarios.</span></span><span>&nbsp;</span></p>

<p><span><span>Sovereign Landing Zone provides a policy-based foundation for implementing sovereign controls across Azure environments, using a management group hierarchy and Azure Policy definitions, initiatives, and assignments to help organizations apply sovereignty requirements consistently</span><span>.</span></span>&nbsp;<br />&nbsp;<br /><span><span>W</span><span>e’re announcing an updated Sovereign Landing Zone implementation supporting both Bicep and Terraform, using Azure Verified Modules to provide reusable infrastructure-as-code building blocks that platform teams can integrate into their existing deployment practices</span><span>-</span></span>&nbsp;<br />&nbsp;<br /><span><span>In the current geopolitical environment, organizations are revisiting how they maintain control, continuity, and resilience for critical workloads. Azure Local can support these requirements by </span><span>providing</span><span> an option to run workloads in a customer-controlled environment, including disconnected operations when needed.</span></span><span>&nbsp;</span></p>
<p><span><span>The new Local management group in the </span><span>Sovereign </span><span>landing zone hierarchy gives customers a clear place to govern Azure Local clusters and the workloads running on them. It also helps teams design workloads in Azure public cloud today with a potential exit path to Azure Local later, so business continuity planning is built into the architecture rather than addressed only during a disruption.</span></span></p>

<h2>Business Continuity and Portability</h2>
<p>Sovereign business continuity extends beyond traditional high availability and disaster recovery. It starts with understanding what should remain operational when disruptions affect access, connectivity or cloud-platform assumptions.</p>
<p>Sovereign Control Panel introduces portability evaluations that help customers assess continuity risks and measure readiness for portability across operating environments, if required. These evaluations help identify baseline considerations such as service availability and compatibility, while recognizing that porting the applications may require additional architectural work.</p>
<p>We are also publishing a new <a href="https://aka.ms/BizContinuityGuidance" rel="noopener" target="_blank">Sovereign Business Continuity guidance and architecture patterns </a>starting with an initial set, with more to follow in the coming months. The library provides prescriptive architecture guidance in the form of flexibly composable patterns for designing continuity paths across Azure, <a href="https://aka.ms/SovMoment2026Private" rel="noopener" target="_blank">Azure Local, and Azure Local disconnected operations</a>. Combined with governance capabilities in Sovereign Landing Zone for Azure Local, these resources can help customers inform risk-based continuity planning and establish recovery ready architectures.</p>

<p>Choosing between these controls is usually a small number of concrete decisions. If a customer requires the root encryption key to remain in hardware outside Microsoft infrastructure, External Key Management applies, and the external HSM, proxy, and connectivity become part of the workload's critical path. If the requirement is strong customer control of keys without external custody, customer-managed keys in Managed HSM may be sufficient. If prompts, retrieved context, or model weights must be protected while in use, the workload needs confidential computing SKUs and attestation-gated key release rather than encryption at rest alone. If the requirement is record of who accessed the environment, the operator-access controls apply. And if the requirement is the ability to keep operating through disruption, continuity and portability planning belongs in the architecture from the start rather than at the point of failure.</p>
<p>&nbsp;</p>
<p>The result is not a single prescribed sovereign architecture. It is a tailored sovereignty architecture in which organizations combine the controls that meet the requirements and risk profile of each workload while continuing to benefit from the innovation and scale of the public cloud. Service, region, SKU, and workload support vary by capability, so validate availability before making any control an architectural dependency.</p>

<h2>Understand how Azure SRE Agent handles security and data</h2>
<p>Security questions often come first when teams evaluate Azure SRE Agent: What can it access? Where does data go? How are actions controlled? Our updated security overview and data residency guidance answer those questions in one place.</p>
<p>Our latest guidance brings those answers together. It explains how Azure SRE Agent approaches security through execution isolation, secretless credential management, customer separation, encryption, network controls, and logging. It also covers how data such as prompts, responses, conversation history, and resource analysis is stored and processed, including important data residency considerations when choosing a model provider.</p>
<p>Explore the guidance docs:&nbsp;<a href="https://learn.microsoft.com/en-us/azure/sre-agent/security-overview" rel="noopener" target="_blank">Security overview for Azure SRE Agent</a>, <a href="https://learn.microsoft.com/en-us/azure/sre-agent/data-privacy" rel="noopener" target="_blank">Data residency and privacy in Azure SRE Agent</a> and <a href="https://techcommunity.microsoft.com/blog/appsonazureblog/stop-restricting-the-agent-start-restricting-its-environment-/4548726" rel="noopener" target="_blank">If you want a secure AI agent, start restricting its environment.</a></p>
<h2>Plan a governed enterprise deployment</h2>
<p><strong>Get more from your agent from day one</strong></p>
<p>Creating an agent is the easy part. The real value comes from giving it the right scope, data, and operational context. Our new practical setup guide explains the choices that make the biggest difference. ### GPU Memory Profiling on AKS: Find the Code Behind Memory Pressure

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/gpu-memory-profiling-on-aks-find-the-code-behind-memory-pressure/ba-p/4566375](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/gpu-memory-profiling-on-aks-find-the-code-behind-memory-pressure/ba-p/4566375)
- **Published**: 2026-10-21 10:00:40
- **Fetched**: 2026-10-21 14:27:51

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>By <a class="lia-external-url" href="https://www.linkedin.com/in/brianbenz/" rel="noopener" target="_blank">Brian Benz</a>, <a class="lia-external-url" href="https://www.linkedin.com/in/yupaul" rel="noopener" target="_blank">Paul Yu</a>, <a class="lia-external-url" href="https://www.linkedin.com/in/mayasingh95/" target="_blank">Maya Singh</a>, <a class="lia-external-url" href="https://www.linkedin.com/in/johnsonshi" rel="noopener" target="_blank">Johnson Shi</a></p>
<p>GPU memory allocation can be tricky to get right. Allocate too little and your AI workload can slow down or fail with an out-of-memory error, often during peak traffic when reliability matters most. Allocate too much and expensive GPU capacity sits unused. Getting an informed view of your workload's actual memory needs from the start helps you avoid both problems.</p>
<p>Kubernetes dashboards can show that GPU memory is under pressure, but they cannot tell you which functions in your AI workload are responsible. Without that detail, teams are left shrinking the workload, moving it to a larger GPU, or restarting it and hoping the problem does not return. That guesswork gets expensive fast.</p>
<p><a href="https://learn.microsoft.com/azure/aks/gpu-profiling" rel="noopener" target="_blank">GPU memory profiling on Azure Kubernetes Service (AKS)</a> provides the evidence to show which functions allocate GPU memory while the workload runs. You can use that visibility to size memory with an informed perspective from the beginning, troubleshoot unexpected pressure, and validate that later adjustments work as intended.</p>
<blockquote>
<p><strong>Preview</strong></p>
<p>This preview covers GPU <strong>memory</strong> allocations, not GPU <strong>compute</strong> utilization. Your existing GPU metrics tell you that something is going on; the profile gives you specific details on where it is happening.</p>
</blockquote>
<h2>From guessing to seeing</h2>
<p>A GPU memory profile is a record of where allocations occur across your application's function call paths while the workload runs. Instead of showing only how much memory is in use, it connects that memory to the functions that requested it. This gives you a path from the symptom to the code responsible.</p>
<p>In Grafana, the profile is visualized as a flame graph displayed in an icicle-style, top-down layout. Each block represents a function in a call path, and wider bars represent more attributed GPU memory. That helps you identify where to investigate and make targeted changes.</p>
<img />
<p>GPU memory profile flame graph showing allocation call paths</p>

<p>You don't add profiling code to your app, and you don't need a sidecar or pod restart to turn it on. Enable profiling on the cluster before deploying your workload, or enable it while an existing workload is running so its CUDA allocation calls can be captured. Profiling won't decide for you that an allocation is wasteful, and it won't tune your workload automatically. It gives you the evidence to decide what your workload needs.</p>
<h2>How it works</h2>
<p>GPU memory profiling on AKS runs on <a href="https://inspektor-gadget.io/" rel="noopener" target="_blank">Inspektor Gadget</a>, an open-source, eBPF-based observability framework for Kubernetes and a CNCF project that Microsoft helps maintain. For GPU profiling, it traces CUDA memory-allocation calls directly from the node, which is why there's no profiling code or sidecar container needed. Enable profiling before deploying the workload, or restart it afterward when you need to capture allocations that occurred during startup.</p>
<p>It's also secure: the Inspektor Gadget project recently completed its <a href="https://inspektor-gadget.io/blog/2026/04/inspektor-gadget-security-audit" rel="noopener" target="_blank">first independent security audit</a>; three issues were found and fixed in version 0.51.1.</p>
<p>Results flow into <a href="https://grafana.com/oss/pyroscope/" rel="noopener" target="_blank">Pyroscope</a> and show up in Grafana as flame graphs rendered in a top-down layout. Pair that with Azure Monitor managed service for Prometheus, and you get memory pressure in one panel and the code path behind it in another.</p>
<p>For more details and to get started, check out the <a href="https://learn.microsoft.com/azure/aks/gpu-profiling" rel="noopener" target="_blank">AKS GPU profiling documentation</a>, which covers the prerequisites, extension installation, and wiring up Pyroscope, Grafana, and the dashboard.</p>
<h2>A real before and after</h2>
<p>A GPU memory flame graph shows which function call paths are responsible for GPU memory allocations. Unlike a distributed trace, it doesn't show operations in chronological order. Instead, it combines many allocation call stacks into a single aggregated view.</p>
<p>The diagram below illustrates the basic idea in the same top-down orientation used by Grafana. Each block represents a function in a call path, stacked blocks show caller-to-callee relationships, and wider blocks represent more attributed GPU memory. The diagram is conceptual, not an actual AKS profile; its colors and example hotspot are illustrative rather than indicators of memory waste.</p>
<img />Conceptual top-down flame graph diagram showing function call paths as stacked bars and bar width as attributed GPU memory
<p><em>Conceptual flame graph illustration in the same top-down, icicle-style orientation used by Grafana. Read from top to bottom. Wider blocks mean more GPU memory is attributed to that function or call path.</em></p>
<p>In the Grafana view below, read the graph <strong>from top to bottom</strong>. Start at the total allocation at the top and follow the function calls downward. Each horizontal bar represents a function. Its width represents the memory attributed to that function and the functions it calls, while horizontal position does not represent time. A tall stack of equally wide bars does not mean each function allocated that memory separately; the same allocation is attributed through the call path.</p>
<p>The AKS documentation includes a vLLM inference example. At the top, the profile shows <strong>65.9 GiB</strong> of attributed allocations. One wide branch accounts for <strong>55.1 GiB</strong>. Follow that branch downward through the Python and vLLM call stack to find where the memory was allocated.</p>
<img />
<p>Expanded Grafana flame graph for a vLLM workload showing GPU memory allocation call stacks</p>

<p><em>Expanded flame graph from the AKS documentation. Read from top to bottom, following the widest allocation path toward the function with high self memory allocation.</em></p>
<p>Two terms help you interpret the bars:</p>
<ul>
<li><strong>Total</strong>: memory attributed to a function, including allocations made by functions it calls.</li>
<li><strong>Self</strong>: memory allocated directly by that function, rather than deeper functions in the recorded stack.</li>
</ul>
<p>A bar can show 55.1 GiB of total allocation with little or no self allocation because the memory was allocated further down its call path. Keep following the branch downward until you find high self allocation. In this example, that leads to <code>GPUModelRunner._allocate_kv_cache_tensors</code>, which the profile attributes with approximately <strong>55.1 GiB of self allocation</strong>. This function creates the KV cache tensors that vLLM uses to reuse previously computed attention keys and values during inference.</p>
<p>The flame graph identifies <strong>where memory was allocated</strong>, not whether that allocation is unnecessary or the underlying cause of an out-of-memory error. The profile also describes recorded allocations, which are not necessarily the same as the amount of GPU memory simultaneously in use.</p>
<p>A large KV cache isn't automatically a problem; it's doing real work. The real question is whether it's sized for the traffic you actually serve. For a vLLM service, that usually means comparing your configured context length and concurrency against real-world usage, then right-sizing the settings that control them.</p>
<p>Here's a loop to find and fix issues in the flame graph data:</p>
<ol>
<li>See the memory pressure.</li>
<li>Find the allocation path in the flame graph.</li>
<li>Change one setting, based on what your workload actually needs.</li>
<li>Run the same load again, and profile it again.</li>
<li>Compare memory, performance, and reliability before you call it done.</li>
</ol>
<h2>What this means for reliability, capacity, and cost</h2>
<p>Reliability is the most direct win. When you can trace an out-of-memory failure back to a specific allocation, you fix the actual cause instead of guessing, and you can prove it by profiling again.</p>
<p>Memory efficiency comes next. You might find memory you can safely give back, or confirm the workload genuinely needs what it has. Both answers are useful: one frees up headroom, the other stops you from "optimizing" something that didn't need it.</p>
<p>Capacity and cost are downstream of both. A validated drop in memory use might let you fit more work on the GPUs you already have, or reconsider the GPU size you're requesting; call it responsible resourcing. The profiler isn't a cost calculator and won't resize nodes for you, so you still have to test the change and do the math yourself.</p>
<p>Either way, the decision is now backed by a real allocation path and a repeatable test, not a hunch.</p>
<h2>One more example: fine-tuning Stable Diffusion XL on KubeRay</h2>
<p>Everything so far has focused on inference, but the same workflow applies to training. The <a href="https://github.com/pauldotyu/awesome-aks/tree/main/2026-07-17-kubecon-gpuprofiling" rel="noopener" target="_blank">KubeRay GPU profiling demo for AKS with Anyscale</a> spins up an AKS Automatic cluster with GPU Node Autoprovisioning, Inspektor Gadget, Pyroscope, Azure Monitor managed Prometheus, and Azure Managed Grafana.</p>
<p>The demo runs Anyscale's <a href="https://console.anyscale.com/template-preview/finetune-stable-diffusion" rel="noopener" target="_blank">Fine-tuning Stable Diffusion XL with Ray Train</a> template: DreamBooth LoRA fine-tuning across four GPU workers, moving through model loading, training, checkpointing, and image generation.</p>
<p>It's a useful reminder that profiling isn't just for inference. Watch the metrics, find the allocation path, make one change, profile again; the loop works whether you're serving a model or training one.</p>
