### Making ACR Data Transfer Visible: The Storage Activity Platform Behind GetBlob Metrics

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/making-acr-data-transfer-visible-the-storage-activity-platform/ba-p/4564893](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/making-acr-data-transfer-visible-the-storage-activity-platform/ba-p/4564893)

- **Fetched**: 2026-10-20 12:39:29

<details class="entry-summary">

<h2>Learn More</h2>

<li><strong>Monitor Azure Container Registry</strong> - <a class="lia-external-url" href="https://learn.microsoft.com/azure/container-registry/monitor-container-registry#monitoring-data" rel="noopener" target="_blank">Monitor Azure Container Registry - Azure Container Registry | Microsoft Learn</a></li>

<h2>Introduction</h2>
<p>Azure Container Registry (ACR) can now show customers something it never could before:&nbsp;<em><strong>how much data leaves their registry, and which operations caused it. </strong></em>A new customer-facing&nbsp;<strong>Data Transfer</strong> metric in Azure Monitor breaks egress down by API Name, GetManifest, GetBlob, GeoReplication, and ImportSource so customers can finally attribute and plan for traffic that used to be invisible.</p>
<p>The hard part of that metric is&nbsp;<strong>GetBlob</strong>. Blob and layer downloads, the bulk of pull traffic, are redirected to Azure Storage, so the registry serving path never sees those bytes. Making that redirected egress&nbsp;<strong>observable, fresh, and attributable</strong>&nbsp;is what required real engineering investment.</p>
<p>To close that gap we built a&nbsp;<strong>Storage Activity Platform</strong>: a reusable, scalable ingestion foundation that turns raw storage activity into fresh, attributable telemetry in&nbsp;<strong>minutes instead of days</strong>. The Data Transfer metric&nbsp;<strong>GetBlob</strong>&nbsp;registry path is the first customer-facing capability it unlocks.</p>
<h2>What Customers Can Now See: The Data Transfer Metric</h2>
<p>For the first time, ACR exposes a customer-facing&nbsp;<strong>Data Transfer</strong> metric in Azure Monitor. It measures&nbsp;<strong>egress</strong>, the bytes actually transferred out of a registry, in bytes, captured per operation.</p>
<p>What makes it useful is the&nbsp;<strong>ApiName</strong>&nbsp;<strong>dimension</strong>, which attributes every byte to the operation that generated it. The operations visible today include:</p>
<ul>
<li><strong>GetManifest</strong> - manifest retrieval.</li>
<li><strong>GetBlob</strong>&nbsp;- blob and layer downloads (the bulk of pull traffic).</li>
<li><strong>GeoReplication</strong> - data transferred during geo-replication sync across regions as well as geo-replication initial sync.</li>
<li><strong>ImportSource </strong>- traffic pulled from a source registry during import.</li>
</ul>
<p>Because egress is split this way, customers can finally answer questions they never could before, for example "<em><strong>How much of my egress is geo-replication sync versus pulls?"</strong></em></p>
<p>The metric is:</p>
<ul>
<li>Dimensioned by <strong>Region </strong>and <strong>ApiName</strong>, consistent with the Transaction metric.</li>
<li>Inclusive of <strong>service-initiated</strong> egress such as geo-replication sync, not just customer pulls.</li>
<li>Reported on a <strong>PT1M </strong>time grain, aligned with Azure Storage metrics.</li>
</ul>
<p>&nbsp;</p>
<blockquote>
<p><strong>Why customers care</strong>:&nbsp; Egress can be significant and hard to predict, especially for geo-replicated registries with large initial syncs. Attributing it by operation is the foundation for cost planning, capacity planning, and faster troubleshooting.</p>
</blockquote>
<h2>The Engineering Challenge: GetBlob Is Invisible to the Registry</h2>
<p>Most of these operations are straightforward to measure: the registry serves them directly, so it can emit the metric as it does the work. <em><strong>GetBlob is the exception, and it is the hard one.</strong></em></p>
<p>When a client pulls an image, the registry does not stream the blob and layer bytes itself. It<strong> redirects the client to Azure Storage</strong>, which serves the download directly. That redirect is great for performance and scale, but it means the&nbsp;<strong>registry never observes the transferred bytes.</strong> The single largest component of egress is invisible to the very service that would normally report it.</p>
<img />
<p>Before: a client pull is redirected from ACR to Azure Storage, so the transferred bytes are invisible to the registry; after: storage activity flows through the Storage Activity Platform into the Data Transfer metric in Azure Monitor</p>

<p>That is the observability gap. To turn GetBlob into a customer-facing metric, we needed those redirected bytes to be:</p>
<ul>
<li><strong>Observable </strong>- captured from where the transfer actually happens (Azure Storage), not the registry serving path.</li>
<li><strong>Fresh </strong>- available in minutes, not days, so the metric reflects current behavior.</li>
<li><strong>Attributable </strong>- tied back to the right registry, region, and operation.</li>
</ul>
<p>None of that existed. Closing this gap is what motivated the <strong>Storage Activity Platform built by the Azure Container Registry team.</strong></p>
<h2>The Freshness Problem</h2>
<p>Even where storage activity <strong>was </strong>available, it was too slow to build on.</p>
<p>Our previous storage log ingestion pipeline could not keep up. In several regions, telemetry arrived in&nbsp;<strong>days rather than minutes</strong>. By the time data reached our analytics platform it was frequently no longer actionable, which made troubleshooting harder and, just as importantly,&nbsp;<strong>blocked entire classes of customer-facing metrics that simply cannot exist on stale data</strong>, GetBlob egress among them.</p>
<p>&nbsp;</p>
<blockquote>
<p><strong>Why customers care: </strong>Fresh, trustworthy storage telemetry is the prerequisite for faster troubleshooting, better planning, and every new customer-facing metric that depends on it.</p>
</blockquote>
<h2>Why It Was Hard</h2>
<p><span>ACR operates globally at significant scale, serving a large and continuously growing volume of registry traffic. Rebuilding the telemetry ingestion foundation under that load, without affecting the core service, was the central challenge.</span></p>
<ul>
<li><strong>Finding the real bottleneck.</strong> We knew telemetry was slow, but not <strong>where </strong>the delay came from, log generation, delivery, ingestion, processing, aggregation, or persistence. Without that answer, any fix would be a guess.</li>
<li><strong>Sustaining production-scale volume continuously.&nbsp; </strong>The platform had to keep up with the highest-volume regions all the time, not just in a benchmark.</li>
<li><strong>Producing trustworthy data.</strong> For egress to become a customer-facing metric, the underlying data had to be accurate and correctly attributable per operation.</li>
</ul>
<h2>The Engineering Story: A Platform, Not a Pipeline</h2>
<h3>Design principles</h3>
<p>Rather than patching the old pipeline, we rebuilt ingestion around a small set of principles:</p>
<ol>
<li><strong>Decouple ingestion from analytics.</strong> Getting storage activity in quickly should not be entangled with how any single downstream scenario consumes it. This separation is what lets new metrics attach later without touching ingestion.</li>
<li><strong>Instrument every stage independently.</strong> We built visibility <strong>into the pipeline itself</strong>, measuring latency at each stage separately, so we could locate the real bottleneck instead of guessing.</li>
<li><strong>Design for reuse from day one.</strong> The target was a scalable ingestion&nbsp;<strong>platform</strong>, not a bespoke path for one metric. New telemetry should inherit the infrastructure, not rebuild it.</li>
<li><strong>Scale and reliability without core-service impact.&nbsp;</strong>Ingestion had to sustain production volume continuously and independently of the registry's serving path.</li>
</ol>
<h3>Measuring what matters</h3>
<p>We instrument the platform across a few conceptual signals:</p>
<img />Pipeline latency signals: log delivery is the dominant segment, consumer processing is near-instant, end-to-end latency spans the whole pipeline, and throughput stays high.
<p><strong>The surprise.</strong>&nbsp;We expected the <strong>consumer</strong> to be the scaling challenge. The data showed the opposite: once events are available, the platform processes them almost immediately, even under production load. The overwhelming majority of remaining latency lives <strong>upstream</strong>, in log delivery, which redirected our optimization focus to where it will actually help.</p>
<p>The outcome is telemetry that now arrives in&nbsp;<strong>minutes instead of days</strong> in many regions, and more durably, a foundation the next capability can build on.</p>
<h3>High-Level Architecture</h3>
<p>The platform is <strong>one path among several</strong> into Azure Monitor. The registry still emits most metrics <strong>directly</strong>&nbsp;as it serves requests. The storage activity platform runs alongside that direct path, specialized for the redirected-download (<strong>GetBlob</strong>) egress the registry cannot see for itself. It is an addition to the metric pipeline, not a replacement for it.</p>
<img />ACR storage activity architecture showing direct service metrics and redirected-download telemetry
<blockquote>
<p><strong>Why customers care:</strong>&nbsp;A reusable ingestion platform means new metrics - starting with the previously-invisible redirected-download egress - can be onboarded faster, with far less engineering overhead, so observability keeps improving over time.</p>
</blockquote>
<h2>The Payoff: GetBlob Data Transfer Is Now Visible</h2>
<p>The clearest proof that this was a platform investment, not just a latency fix, is what it closed: the&nbsp;<strong>GetBlob observability gap</strong>.</p>
<p>The redirected blob and layer downloads that make up the bulk of egress, and that the registry never sees, are now populated&nbsp;<strong>entirely</strong>&nbsp;from the storage activity platform and surfaced through the&nbsp;<strong>Data Transfer</strong> metric in Azure Monitor. For the first time, customers can see that egress, attributed by <strong>ApiName</strong>.</p>
<p>Critically, exposing that redirected-download egress required&nbsp;<strong>no new ingestion infrastructure of its own</strong>. It attached to the storage activity platform we had already built, which is exactly the point: the platform did the hard part once, and the metric inherited it.</p>
<h2>The Customer Experience</h2>
<p>Both the freshness improvement and the new metric surface through tools customers already use, no new workflow to learn.</p>
<ul>
<li><strong>Fresher telemetry</strong> flows into the analytics and dashboards teams already rely on, so what they see reflects what is happening <strong>now</strong>&nbsp;rather than days ago.</li>
<li><strong>The Data Transfer metric</strong> appears in&nbsp;<strong>Azure Monitor</strong>&nbsp;alongside existing registry metrics, and can be charted, alerted, and forecast like any other Azure Monitor metric, split by Region and ApiName.</li>
</ul>
<img /><span>Image showing the Data Transfer metric split by Api Name and Region.</span>
<blockquote>
<p><strong>Why customers care:</strong> Egress attribution leads directly to better cost and capacity planning and faster troubleshooting, and it is only the first of many capabilities the platform can now serve.</p>
</blockquote>
<h2>Engineering Lessons Learned</h2>
<ul>
<li><strong>Instrument the pipeline before optimizing it. </strong>Measuring each stage independently turned a guessing game into a targeted fix and revealed the bottleneck was not where we assumed.</li>
<li><strong>Invest in the platform, not the feature.</strong> Building ingestion as a reusable foundation meant the first customer-facing metric attached in a fraction of the time it would have otherwise taken.</li>
</ul>
<h2>Outcomes &amp; What's Next</h2>
<p>What changes for customers is the bottom line:</p>
<ul>
<li><strong>Egress is no longer invisible.</strong>&nbsp;Customers can see how much data leaves their registry and attribute it by operation, including the redirected GetBlob downloads that were never observable before.</li>
<li><strong>What they see reflects now, not days ago</strong>. Telemetry that arrives in&nbsp;<strong>minutes instead of days</strong>&nbsp;means troubleshooting, cost planning, and capacity planning act on current reality.</li>
</ul>
<p>The platform matters because of what it lets customers observe next. Because new metrics can now be onboarded on top of this foundation, the Data Transfer metric is a beginning, not an endpoint, richer analytics and additional customer-facing metrics follow, each one deepening the visibility customers have into their own registries.</p>

### Plan Your Java Upgrade Ahead of Microsoft’s 2027 Support Milestones

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/plan-your-java-upgrade-ahead-of-microsoft-s-2027-support/ba-p/4565984](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/plan-your-java-upgrade-ahead-of-microsoft-s-2027-support/ba-p/4565984)
- **Published**: 2026-10-20 06:34:23
- **Fetched**: 2026-10-20 12:39:29

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>In April 2021, we <a href="https://devblogs.microsoft.com/java/announcing-preview-of-microsoft-build-of-openjdk/" rel="noopener" target="_blank">announced the Microsoft Build of OpenJDK</a>. We were starting with a preview of our Java 11 builds for Windows, Linux, and macOS. Today, if you’re planning a Java upgrade on Azure, you have several generations of that work to build on: 11, 17, 21, and now 25.</p>
<p>Java 8 has been part of that work too, with help from the fine folks at the Eclipse Foundation’s&nbsp;<a href="https://adoptium.net/" rel="noopener" target="_blank">Eclipse Adoptium project</a>. Microsoft has supported Java 8 on Azure using their Eclipse Temurin builds of OpenJDK 8, rather than producing a Microsoft Build of OpenJDK 8. That collaboration goes back to the launch: our first Java 11 builds also used Adoptium’s build scripts and quality assurance suite.</p>
<p>Supporting those releases has meant years of updates. Now it’s time to plan the next move. The&nbsp;<a href="https://learn.microsoft.com/en-us/java/openjdk/support" rel="noopener" target="_blank">Microsoft Build of OpenJDK support roadmap</a>&nbsp;lists September 2027 as the&nbsp;<strong>earliest end-of-support date for Java 11 and 17</strong>. That’s a distribution-wide milestone: if you use those Microsoft builds on a VM, in a container, on Kubernetes, on Azure platform services, or evem outside Azure, it belongs in your upgrade planning. These dates are initial targets, and Microsoft may extend them. However, consider taking action now.</p>
<p>Azure services also have their own deadlines.&nbsp;<a href="https://azure.microsoft.com/en-us/updates/?id=568585" rel="noopener" target="_blank">Azure App Service and Azure Functions support for Java 8, 11, and 17 ends on September 1, 2027</a>. Existing applications will continue to run, but the affected Java versions will no longer receive security updates, improvements, or related customer support.</p>
<p>If that’s your application, the practical question is how to get to Java 21 or 25 while keeping it working.&nbsp;<a href="https://learn.microsoft.com/en-us/azure/developer/github-copilot-app-modernization/" target="_blank">GitHub Copilot modernization</a> gives you a tool: the <strong>Modernize CLI</strong>, which can assess your code, help plan the upgrade, and actually perform and apply changes for you to review.</p>
