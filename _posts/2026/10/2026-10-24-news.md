### Making Azure Container Registry Activity Visible at Scale

<h2>Learn More</h2>
<ul>
<li><a href="https://learn.microsoft.com/en-us/azure/container-registry/container-registry-dashboards-with-grafana" rel="noopener" target="_blank">Use Grafana dashboards in Azure Container Registry</a></li>
<li><a href="https://learn.microsoft.com/en-us/azure/container-registry/monitor-container-registry" rel="noopener" target="_blank">Monitor Azure Container Registry</a></li>
</ul>
<p>Azure Container Registry (ACR) now publishes two new metrics: <strong>Transactions</strong> and <strong>Data Transfer</strong>. For the first time, you can see which operations your registry serves, which region serves them, and how much data (egress) they move, for each registry and each of its geo-replicas.</p>
<p>ACR often serves as a shared distribution point for containerized workloads. Build systems push container images and other artifacts, Kubernetes clusters pull images during deployments, and security and lifecycle tools scan artifacts throughout the day. As those environments grow, high-level signals such as a total pull count or storage used can tell you <em>that</em> activity changed, but not <em>why</em>. Transactions and Data Transfer fill that gap, so you can explain a traffic spike, catch a failing or throttled pipeline, and see where your data goes.</p>
<p>A customer-facing metric is a stream of data points, attributed to one resource, that you can chart, split, and alert on in Azure Monitor. Building these metrics meant producing data points for very high-throughput signals, counting them accurately, attributing each one to the right registry in every region, and not exhausting the metrics system underneath.</p>
<p>In this post, we'll cover what these metrics show you, what it took to deliver them at scale, and the sharded design that made it possible.</p>
<h2>What you couldn't see before</h2>
<p>Before this work, push and pull counts, alongside storage used, were the only registry traffic metrics we published. They showed <em>that</em> activity happened, but not <em>what kind</em> of operations drove it, <em>whether</em> each operation succeeded, or <em>where</em> it was served.</p>
<p>Take a sudden jump in pulls:</p>
<ul>
<li><strong>Before:</strong> total pull count is up, with no way to tell which geo-replication drove the traffic.</li>
<li><strong>Now:</strong> the extra requests are blob downloads in one geo-replication region, many of them Throttled, while Data Transfer from that geo-replication stays flat.</li>
</ul>
<p>Those gaps matter most when traffic changes. An increase may come from a deployment, a retry loop, metadata polling, a regional workload shift, or larger image layers, and each looks different underneath: a surge in manifest and blob reads, repeated errors or throttled responses, a steady stream of tag and listing calls, traffic moving between replicas, or more bytes per pull without more requests. To tell them apart, you need to know which operations are changing, how much artifact data is moving, where requests are being served, and whether the pattern matches the workload you intended to run.</p>
<p>Push and pull counts summarize outcomes. Transactions and Data Transfer describe behavior, and describing behavior takes far more data.</p>
<h2>Why scale is the hard part</h2>
<p>These signals are high throughput by nature, because every counted request becomes its own data point: a single sampled registry's activity can exceed 100,000 transactions and hundreds of gigabytes of data transferred (egress) in one hour.</p>
<p>All of those data points land in internal metrics accounts, and each account has a finite budget for how much data it can take in and process. Our previous emission strategy sent metrics to a single backing account. That worked for the metrics we already had but signals this large would eventually exhaust that account's quota.</p>
<p>Scale wasn't an optimization we could add later. It was a prerequisite for launching these metrics at all.</p>
<h2>Sharding the metrics without splitting the view</h2>
<p>The answer to the capacity problem is to stop relying on one account. Instead, we shard our metrics across multiple internal metrics accounts. A <em>shard</em> is one slice of a larger system that holds part of the data and has its own capacity. Each shard has its own headroom, which we monitor and manage independently, so no single account caps growth.</p>
<p><strong>Geo-replication complicates this.</strong> A geo-replicated registry is served from many regions at once, and a single request can pass through more than one component: one answering API calls, another serving blob bytes, another delivering webhooks. However capacity is divided, every data point from every region and every component still has to be attributed to the registry it belongs to. Otherwise, you'd see your registry's activity in pieces and have to stitch it back together yourself.</p>
<img />
<p><em>Activity from every geo-replication and component is attributed to its registry and counted once. Each registry's metrics land on one shard, different registries are spread across shards, and you still query one registry in the portal.</em></p>
<p>When you open the Azure portal or query Azure Monitor, you query your registry. You never see or choose where that information is coming from.<br /><br /></p>
<p><strong>Counting each request once.</strong> Multi-hop requests raise the same question for accuracy. One blob pull can touch more than one component: the registry may answer with a redirect, and a different component serves the bytes. Each step is counted once, by the component that handled it: the redirect appears as its own&nbsp;<strong>Redirect</strong> transaction, the download as a <strong>Success</strong> transaction, and the bytes appear once in Data Transfer. Failed requests count as Transactions, so errors stay visible, but not as Data Transfer, because no bytes were delivered. Every emitting component uses the same <strong>ApiName</strong> and <strong>ResponseType</strong>&nbsp;vocabulary, and we verify that each counted request produces exactly one data point.</p>
<img />
<p><em>Each step is counted once, by the component that handled it, and bytes count only when they're served.</em></p>
<p>The result is one view of each registry, across every region and component, with each step of a request counted exactly once.</p>
<h2>What customers get</h2>
<p>Both metrics appear where you already look: <strong>Azure portal &gt; your registry &gt; Monitoring &gt; Metrics</strong>, and through Azure Monitor for programmatic queries and alerts.</p>
<p><strong>Transactions</strong> counts registry API operations, with three dimensions:</p>
<ul>
<li><em>ApiName</em>: the registry operation, such as manifest, tag, and blob operations, referrer and catalog listings, token requests, etc.</li>
<li><em>ResponseType</em>: Success, Redirect, ClientErrorUnauthorized, ClientErrorNotFound, Throttled, etc.</li>
<li><em>Region</em>: the geo-replication of the registry that served the request</li>
</ul>
<p><strong>Data Transfer</strong> reports the total outbound data your registry transfers, in bytes, when it serves content such as blob and manifest downloads. You can split it by ApiName and Region.</p>
<ul>
<li><em>ApiName</em>: the flow that moved the data, such as layer downloads, manifest downloads, image imports, replicating content to your geo-replicas, etc.</li>
<li><em>Region</em>: the geo-replication of the registry that served the request</li>
</ul>
<p>A typical investigation takes a few steps. Open <strong>Monitoring &gt; Metrics</strong>, choose <strong>Transactions</strong>, and split by ResponseType to see successes, redirects, throttling, and errors at a glance. Switch the split to Region to see which geo-replication is serving the change. Then select <strong>New alert rule</strong> from the same chart. For example, filter to Throttled and alert when the total over 5 minutes exceeds a threshold you choose.</p>
<p>To understand egress by region, chart Data Transfer over time and split it by Region to see how much data each geo-replication serves and whether that data transfer traffic is growing.</p>
<p>Match the view to what you suspect:</p>
<ul>
<li><strong>A deployment or metadata polling:</strong> split Transactions by ApiName to see whether blob and manifest reads or tag and listing calls are driving the change.</li>
<li><strong>A retry loop:</strong> filter ResponseType to Throttled, ClientErrorUnauthorized, or ServerErrorOther.</li>
<li><strong>A regional workload shift:</strong> split metric by Region.</li>
<li><strong>Larger image layers:</strong> compare the two metrics. Data Transfer rising while Transactions stays flat points to bigger artifacts, not more requests.<br /><br /></li>
</ul>
<img />
<p><em>Transactions split by ResponseType: successes, redirects, throttling, and errors at a glance.</em></p>
<h2>Built for the metrics that come next</h2>
<p>Transactions and Data Transfer run on the same sharded metrics path, and we built it so future metrics onboard onto that same path instead of competing for one account's capacity. The design scales with customer workloads and with the metrics we add next, without a redesign.</p>
<h2>Conclusion</h2>
<p>Transactions and Data Transfer give you a direct view of what your registry is doing: which operations it serves, whether they succeed, where they're served, and how much data moves. Sharding is how we delivered that view at scale without giving up accuracy, and it's the path future metrics will onboard onto.</p>
<p>A few lessons generalize beyond metrics:</p>
<ul>
<li><strong>Design for scale before you launch a high-throughput signal, not after.</strong></li>
<li><strong>Attribute by resource, not by location.</strong> Activity spread across many regions still needs one source of truth per resource.</li>
<li><strong>Keep the complexity on the service side.</strong> Customers query a registry, not a shard, so how we manage capacity can evolve without changing what you query.</li>
</ul>
