<p><em>Co-written by </em><a href="https://www.linkedin.com/in/nikoloz-buligini/" rel="noopener" target="_blank"><em>Nikoloz Buligini</em></a><em>, Front End Developer at </em><a href="https://www.templafy.com/" rel="noopener" target="_blank"><em>Templafy</em></a><em>, and </em><a href="https://www.linkedin.com/in/jankalis/" rel="noopener" target="_blank"><em>Jan Kalis</em></a><em>, Azure Container Apps Sandboxes, Core AI, Microsoft</em></p>
<p>Every team building with multi-tenant AI agent platforms hits the same wall. The agent is smart enough to read your code, reason about a bug, and propose a fix. But the moment it needs to <em>take an action</em> - clone a repo, install tooling, run a command, hit an internal endpoint - you have to answer some uncomfortable questions: where does it run, what permissions does it have and what can it access?</p>
<p>Run it on your own infrastructure and inherit the blast radius. Give it broad network access and you have handed an autonomous process the keys to your environment. Lock it down too hard and the agent cannot do its job.</p>
<p>This is exactly the problem <a href="https://sandboxes.azure.com" rel="noopener" target="_blank">Azure Container Apps Sandboxes</a> was built to solve. And it is exactly the problem the team at Templafy solved in production. This post walks through what Sandboxes are, the features that make them a good fit for agentic workloads and how Templafy put ACA Sandboxes to work.</p>
<h2>What are Azure Container Apps Sandboxes?</h2>
<p><a href="https://sandboxes.azure.com/docs/sandboxes/" rel="noopener" target="_blank">Azure Container Apps Sandboxes</a> (Preview) are secure, isolated compute environments that start in seconds, scale to thousands, and do not charge you for compute while stopped. Each sandbox runs inside its own hardware-isolated microVM, fully separated from the host, the platform, and every other sandbox. Bring your own container image or use an included one, and Sandboxes handle provisioning, isolation, and lifecycle.</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<p>This is the same compute fabric behind products like Cloud sandboxes in GitHub Copilot, Foundry Hosted Agents, and Azure Container Apps Express, and now you can build directly on it. For platform builders, that means enterprise-grade, multi-tenant isolation as a building block you would otherwise spend years creating. For AI agents, a sandbox becomes a self-configurable tool: spin up a fresh environment in seconds, run untrusted code, compile a project, or explore a codebase, then throw it away. On one side you empower humans to build platforms. On the other you empower agents to extend their own capabilities.</p>
<h2>The features that make Sandboxes fit agentic work</h2>
<p>A fast microVM is table stakes. What makes Sandboxes practical for real agent workloads is the control around them. <strong>Snapshots</strong> capture a fully configured environment and resume from it, ideal for long-running tasks or cloning setups. <strong>Egress</strong> controls declare exactly what a sandbox may reach, so an agent can pull from source control and package registries but nothing you did not approve. <strong>Managed identities</strong> authenticate to Azure with no secrets in the image. <strong>Automatic suspend and resume</strong> map cleanly onto how conversational agents behave, warming back up with full context when a conversation continues. <strong>Ports</strong> give your orchestrator a channel to a long-running agent process inside the sandbox.</p>
<p>Two newer capabilities go further: <strong>virtual network integration</strong> puts an agent workspace inside your own Azure VNet with access to private endpoints, and <strong>bring your own storage</strong> lets data and artifacts outlive a session under your compliance rules. Together these turn a fast disposable VM into something you can hand to an autonomous agent in production. Which brings us to Templafy.</p>
<h2>How Templafy uses Sandboxes, in their own words</h2>
<p><em>The following section is written by <a class="lia-external-url" href="https://www.linkedin.com/in/nikoloz-buligini/" rel="noopener" target="_blank">Nikoloz</a>, Front End Developer at Templafy.</em></p>
<img />
<p>At <a class="lia-external-url" href="https://www.templafy.com/" rel="noopener" target="_blank">Templafy </a>we built an AI agent that helps our teams by doing longer-running source-code&nbsp;<span style="color: rgb(30, 30, 30);">exploration on their behalf. Someone asks a question in a Slack thread, and behind the scenes the agent needs a real, isolated workspace where it can clone repositories, run tooling, and dig through code without touching anything it should not. It started as an engineer-facing tool for deep technical questions, but we recently opened it up to our product team for questions about undocumented product behavior. There, the agent first checks our Help Center through Azure AI Search with no sandbox required and only spins up a sandbox to explore the code when the docs come up short. Since these users aren't engineers, we summarize what the exploration finds into something more approachable. Funnily enough, the product team has been using it more than engineering does, and the feedback since launch has been great.</span></p>
<p>We needed strong isolation, fast startup, and tight control over what each workspace could reach. Azure Container Apps Sandboxes gave us exactly that. We were sold on the model early enough that we built our own TypeScript SDK for Sandboxes before there was an official one, so we could drive the whole lifecycle from our Node stack.</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<p>Here is what happens when the AI decides to start a workflow for a Slack thread:</p>
<ol>
<li>Create a sandbox from the public&nbsp;node-24&nbsp;image.</li>
<li>Install Git and other development tools.</li>
<li>Clone our repositories and configure OpenCode.</li>
<li>Restrict egress to only the Azure DevOps, package registry, and service endpoints the agent actually needs.</li>
<li>Expose a port used to communicate with the agent runtime.</li>
<li>Create and reuse snapshots so we do not repeat the bootstrap process on every run.</li>
<li>Associate successful sessions with their Slack threads for a short period, so users can make follow-up requests against the same warm workspace.</li>
<li>Stop or suspend idle sandboxes and resume them when a conversation continues.</li>
<li>Delete failed or expired sessions.</li>
</ol>
<p>To do all of this we lean on the SDK for the full surface area: sandbox lifecycle operations, command execution, files, snapshots, ports, egress policies, public disk-image inspection, and sandbox state.</p>
<p>Two features carry most of the weight for us. The first is&nbsp;<strong>restricted egress</strong>. Our agent is autonomous and works with our source code, so we are not comfortable letting it talk to the open internet. Declaring a narrow allow-list of endpoints means the workspace can do its job and nothing more, and that control is what let us ship this with confidence. The second is&nbsp;<strong>snapshots</strong>. Cloning repositories and configuring the toolchain is not free and doing it on every Slack message would make the agent feel slow. With snapshots we pay that cost once and resume from a ready-to-work state, so follow-ups in a thread start fast.</p>
<p>This is only the first workflow. We are already looking at background investigations using Application Insights and eventually letting the agent open pull requests for quick bug fixes. The same isolated-workspace pattern extends cleanly to all of it.</p>
<h2>Who this is for</h2>
<p>If you are building an AI agent that needs to run code, explore a repository, or reach into your systems, and you have been nervous about where that runs, ACA Sandboxes is for you. You do not have to choose between a capable agent and a safe one. Give it a hardware-isolated workspace, declare exactly what it can touch, snapshot the setup, and let it work. Templafy went from "how do we let an agent safely explore our source code" to a production workflow running out of Slack threads, on infrastructure they controlled end to end. The building blocks are the same ones you can pick up today.</p>
