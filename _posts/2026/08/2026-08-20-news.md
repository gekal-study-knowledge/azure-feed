## Azure Architecture Blog

### Choosing the Right Agent in Microsoft Foundry

- **Link**: [https://techcommunity.microsoft.com/t5/azure-architecture-blog/choosing-the-right-agent-in-microsoft-foundry/ba-p/4547827](https://techcommunity.microsoft.com/t5/azure-architecture-blog/choosing-the-right-agent-in-microsoft-foundry/ba-p/4547827)
- **Published**: 2026-08-20 07:52:13
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Many discussions about Microsoft Foundry Agent Service eventually arrive at the same question: should this workload be implemented as a Prompt Agent or a Hosted Agent? While the documentation explains both options well, the architectural decision usually comes down to something much simpler: where do you want the orchestration logic to live?</p>
<h4><strong>First, what actually makes something an agent?</strong><span>&nbsp;</span></h4>
<p><span>A basic AI assistant generates an answer. An agent can also decide what to do next, call tools, access data, maintain context and complete work across multiple steps.</span><span>&nbsp;</span></p>
<p><span>At the center of most agents are three building blocks:</span><span>&nbsp;</span></p>
<ul>
<li><span><span>Model: provides language understanding, generation, and reasoning.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Instructions: define the job, boundaries, role, and expected behaviour.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Tools: connect the agent to knowledge and actions such as search, APIs, databases, code execution, MCP servers or business systems.</span></span><span>&nbsp;</span></li>
</ul>
<p>&nbsp;</p>
<img />
<p><span>For enterprise use, that is only the starting point. You also need identity, authorization, network controls, content safety, session management, evaluation, tracing, versioning, rollback, and cost controls. Foundry Agent Service provides the surrounding platform capabilities, while letting you choose how much runtime logic your team owns.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<h4><strong>Where should orchestration logic live and who should own the runtime?</strong></h4>
<p><strong>Understanding the Runtime Boundary</strong></p>
<p>When evaluating Foundry Agent Service, many teams focus on models. In practice, models are rarely the architectural differentiator.</p>
<p>Most architecture reviews eventually come down to three questions:</p>
<ul>
<li>Who owns orchestration?</li>
<li>Who owns state?</li>
<li>Who owns operations?</li>
</ul>
<p>Foundry Agent Service provides a managed platform for these concerns, but the amount of control retained by engineering teams depends on the selected agent type.</p>
<p>For most teams, the architectural decision usually comes down to one of two operating models</p>
<ul>
<li><span><span>Prompt agents: declarative agents defined by a model, instructions, and tools, with a managed runtime.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Hosted agents: code-based agents that you package and run in Foundry, while the service manages the endpoint, identity, scaling, sessions, and observability.</span></span><span>&nbsp;</span></li>
</ul>
<h4><strong>Prompt Agents</strong></h4>
<p>With a Prompt Agent, engineering teams focus primarily on defining the model, instructions, tools, knowledge sources and identity configuration, while Foundry takes responsibility for the surrounding runtime.</p>
<h6><strong>Why teams start here</strong><span>&nbsp;</span></h6>
<p><span>Prompt agents are usually the fastest route from an idea to a working, governed agent. They are a good fit when the behaviour can be expressed clearly through instructions and supported tools.</span><span>&nbsp;</span></p>
<ul>
<li><span><span>You need to deliver quickly.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>The agent follows a fairly straightforward reasoning and tool-use loop.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Foundry-supported tools cover the required integrations.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>You do not need custom libraries, middleware, or orchestration code.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>You want Foundry to own compute, scaling, and patching.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Reviewers need an </span><span>agent</span><span> definition that is easy to inspect.</span></span><span>&nbsp;</span></li>
</ul>
<h6><strong>Good examples&nbsp;</strong></h6>
<p><span>Enterprise knowledge assistant. Employees ask about policies, engineering standards, procedures, or product information. The agent retrieves approved content and cites its sources.</span><span>&nbsp;</span></p>
<p><span>Document review assistant. The agent checks a proposal or design against an approved rubric and returns structured findings, while a human keeps responsibility for the final decision.</span><span>&nbsp;</span></p>
<p><span>Employee self-service agent. The agent answers questions and performs a small number of tightly scoped actions, such as checking request status or creating a support case.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<blockquote>
<h6><strong>A useful warning sign </strong><span>A Prompt agent is probably becoming the wrong fit when the prompt starts looking like application code. Large branching instructions, retry logic written in prose, state-machine behaviour, custom payload handling, framework middleware or real-time media are all signs that runtime logic belongs in code instead.</span><span>&nbsp;</span></h6>
</blockquote>
<p>&nbsp;</p>
<h4><strong>Hosted Agents</strong></h4>
<p>Hosted Agents move the responsibility boundary. Instead of defining behaviour through configuration alone, engineers deploy an actual application into Foundry Agent Service. Hosted Agents are framework-agnostic. Whether your team builds with Agent Framework, LangGraph, Semantic Kernel, OpenAI Agents SDK, or a custom runtime, Foundry can host the application while managing the surrounding operational services.</p>
<h6><strong>When Hosted agents make sense</strong><span>&nbsp;</span></h6>
<ul>
<li><span><span>You need a particular agent framework or custom orchestration engine.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>The flow includes branching, parallel work, fan-out and fan-in, or human approvals.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Business rules require a deterministic state machine around model reasoning.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>You need custom packages, middleware, algorithms, retries, caching, or error handling.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>The client sends custom payloads or webhooks.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>The session needs persistent files or custom state.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>The design includes multi-agent orchestration or real-time voice.</span></span><span>&nbsp;</span></li>
</ul>
<h6><strong>Good examples</strong></h6>
<p>A bank onboarding workflow where uploaded documents must be validated, checked against multiple systems, and routed to a human when confidence drops below a threshold.</p>
<p>A fraud investigation agent that gathers transaction history, enriches data from multiple internal systems, applies bank-specific risk rules, requests additional evidence when required, and generates a recommended outcome for an investigator. The process involves long-running workflows, branching logic and audit requirements that are better suited to code-based orchestration.</p>
<p>A lending workflow that coordinates document collection, credit bureau checks, income verification, affordability assessments, policy exceptions, and approval routing. The process spans multiple systems and often requires deterministic decision paths that extend beyond prompt-driven orchestration.</p>
<p>A security operations agent that aggregates alerts from SIEM platforms, enriches incidents with threat intelligence, executes automated containment actions, opens tickets, requests approvals for high-impact remediation steps, and maintains a complete audit trail of decisions and actions.</p>
<blockquote>
<h6><strong>The trade-off&nbsp;</strong></h6>
<p><span>More control also means more ownership. Your team must secure and patch the code and dependencies, test the runtime, manage supply-chain risk, and think about compute sizing, cold starts, session lifecycle, and cost. Hosted agents reduce platform plumbing, but they do not remove application engineering.</span><span>&nbsp;</span></p>
</blockquote>
<p>&nbsp;</p>
<h4><em><span>Choosing Prompt Agent/Hosted Agents&nbsp;</span></em></h4>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><strong>1)&nbsp; Runtime Control Is Usually the Real Requirement</strong></div>
<p>&nbsp;</p>
<p>A pattern I see quite often is teams arriving at the solution before they've fully articulated the requirement. The conversation usually starts with "We need a Hosted Agent," but after digging into the workload, the real requirements turn out to be things like persistent state, webhook processing, custom orchestration, background execution, framework-specific capabilities, or human approval workflows.</p>
<p>These are runtime concerns, not agent concerns and they're usually the factors that determine whether a Hosted Agent is necessary. Hosted Agents are valuable because they give engineering teams control over those aspects of execution while still offloading much of the operational infrastructure to Foundry.</p>
<p>This is also where teams most commonly choose the wrong agent type. A frequent assumption is that existing investments in frameworks such as LangGraph or Semantic Kernel automatically imply a Hosted Agent architecture. In practice, many of these workloads are relatively simple orchestration scenarios that can be implemented effectively as Prompt Agents, with lower operational overhead and less infrastructure to manage.</p>
<p>My advice is usually to start by identifying the runtime requirements rather than selecting an agent type. Once those requirements are clear, the right architecture often becomes obvious.</p>
<p>&nbsp;</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><strong>2)&nbsp; When Hosted Agents become mandatory</strong></div>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><br />The moment you need custom Python packages, long-running workflows, external SDKs, deterministic orchestration or framework-specific capabilities, the conversation shifts from Prompt Agents to Hosted Agents.</div>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN">&nbsp;</div>
<h3 class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><strong>What I would choose today</strong></h3>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><br />
<p>If I were starting a new project today, I'd begin with a Prompt Agent unless there was a clear reason not to. In my experience, Prompt Agents cover far more enterprise use cases than many teams initially expect. The best projects tend to start simple, prove value, learn where the limitations are, and then introduce Hosted Agents only when runtime customization becomes a genuine requirement. That progression is usually far less risky than leading with a fully custom solution.</p>
