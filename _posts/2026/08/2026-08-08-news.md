### Build Durable, Long-Running MCP Tasks on Azure App Service

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/build-durable-long-running-mcp-tasks-on-azure-app-service/ba-p/4545170](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/build-durable-long-running-mcp-tasks-on-azure-app-service/ba-p/4545170)

- **Fetched**: 2026-08-27 21:13:50

<p>Not every tool call finishes in a few seconds.</p>
<p>A compliance scan might inspect hundreds of resources. A deployment might wait for an approval. A batch import might run for an hour. Holding an HTTP connection open for that entire operation is fragile: clients restart, proxies time out, networks drop, and the App Service instance that accepted the request might recycle or scale in.</p>
<p>The <code>2026-07-28</code> Model Context Protocol release addresses this with the official <a class="lia-external-url" href="https://modelcontextprotocol.io/extensions/tasks/overview" rel="noopener" target="_blank">MCP Tasks extension</a>. Instead of blocking until the final result is ready, an MCP server can return a task handle immediately. The client can disconnect, reconnect later, poll for progress, provide input when required, cancel the operation, and retrieve the result when it is complete.</p>
<p>That is the protocol story. The infrastructure story needs one more step:</p>
<blockquote>
<p>A durable task ID does not automatically make the underlying work durable.</p>
</blockquote>
<p>I built a complete <a class="lia-external-url" href="https://github.com/seligj95/app-service-mcp-tasks-dotnet" rel="noopener" target="_blank">.NET sample for durable MCP Tasks on Azure App Service</a> to make that distinction concrete.</p>
<h2 id="mcp-tasks-in-about-60-seconds">MCP Tasks in about 60 seconds</h2>
<p>A Tasks-capable client advertises <code>io.modelcontextprotocol/tasks</code> in its per-request capabilities. For a long-running tool call, the server can then return a <code>CreateTaskResult</code> containing:</p>
<ul>
<li>a stable task ID;</li>
<li>the current status;</li>
<li>a time-to-live;</li>
<li>and a suggested polling interval.</li>
</ul>
<p>The lifecycle looks like this:</p>
<pre class="text"><code>tools/call    -&gt; taskId, status=working
tasks/get     -&gt; status=working, progress message
tasks/get     -&gt; status=input_required
tasks/update  -&gt; approval or other requested input
tasks/get     -&gt; status=completed, final result</code></pre>
<p>Tasks can move through <code>working</code>, <code>input_required</code>, <code>completed</code>, <code>failed</code>, and <code>cancelled</code>. The client does not need to maintain the original connection. Polling from a new process with the same task ID is part of the design.</p>
<p>The client also does not force every call to become asynchronous. It declares support for Tasks, and the server decides whether a particular operation should return a task handle. If the client does not support the extension, a server can fall back to an ordinary synchronous tool result.</p>
<h2 id="the-durability-trap">The durability trap</h2>
<p>The official MCP C# SDK includes <code>ModelContextProtocol.Extensions.Tasks</code> and a convenient <code>WithTasks()</code> registration path. In version <code>2.1.0</code>, that default is a good fit for a single-process server: the SDK creates the task and runs the tool body in an in-process <code>Task.Run</code>.</p>
<p>For a horizontally scaled App Service deployment, however, that is not the durability guarantee I wanted for this sample.</p>
<p>If the instance running that <code>Task.Run</code> recycles, crashes, or scales in, the task record might still exist while the work itself disappears. Another instance can answer <code>tasks/get</code>, but nothing tells it that the underlying operation still needs to run.</p>
<p>So I used the SDK for the protocol surface and replaced only the execution dispatch:</p>
<ul>
<li><strong>Azure Table Storage</strong> stores task status, progress, pending input requests, resolved input, final results, errors, and TTL.</li>
<li><strong>Azure Service Bus</strong> stores the work item that still needs to execute.</li>
<li>A worker running in every App Service instance receives queued work, executes the tool, and updates the shared task row.</li>
<li><code>clientAffinityEnabled=false</code> allows any App Service instance to serve <code>tasks/get</code>, <code>tasks/update</code>, or <code>tasks/cancel</code>.</li>
</ul>
<p>The important distinction is that both halves are durable:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Concern</th><th>Durable home</th></tr></thead><tbody><tr><td>What state is this task in?</td><td>Azure Table Storage</td></tr><tr><td>Does this work still need to run?</td><td>Azure Service Bus</td></tr></tbody><colgroup><col style="width: 50.00%;" /><col style="width: 50.00%;" /></colgroup></table></div>
<p>If an instance disappears after receiving a message but before completing it, Service Bus can redeliver the work to another available instance. The task is not tied to the HTTP connection or the process that accepted the original call.</p>
<h2 id="architecture">Architecture</h2>
<img />
<p>The sample uses a system-assigned managed identity for both Azure Storage and Service Bus. Storage shared-key access is disabled, Service Bus local authentication is disabled, and there are no storage or broker connection strings in App Service configuration.</p>
<p>The App Service identity receives only:</p>
<ul>
<li><strong>Storage Table Data Contributor</strong> on the storage account; and</li>
<li><strong>Azure Service Bus Data Owner</strong> on the Service Bus namespace.</li>
</ul>

<p>The custom durable filter is registered before it. The SDK's automatic execution mode is forced to synchronous so it cannot start the in-process background path:</p>

<p>For a Tasks-capable client calling a durable tool, <code>WithDurableTaskDispatch()</code>:</p>
<ol type="1">
<li>creates the task row;</li>
<li>serializes the tool name and arguments;</li>
<li>sends a Service Bus message whose ID is the task ID;</li>
<li>returns <code>CreateTaskResult</code> immediately.</li>
</ol>
<p>For a client that did not advertise Tasks support, the filter falls through and the same tool executes synchronously. The companion client demonstrates both paths.</p>
<h2 id="cross-instance-approvals-need-durable-input-too">Cross-instance approvals need durable input too</h2>
<p>Long-running operations often need a decision in the middle of execution. The sample's <code>generate_compliance_report</code> tool pauses after identifying a high-severity finding and moves to <code>input_required</code>.</p>
<p>The original client is deliberately disconnected before that happens. A completely new client connection polls the task, sees the input request, submits approval through <code>tasks/update</code>, and continues polling until completion.</p>
<p>This uncovered another distributed-systems detail: an in-memory event can wake an awaiter only in the process where that event exists. If <code>tasks/update</code> lands on a different App Service instance than the worker awaiting approval, an in-memory callback is not enough.</p>
<p>The sample therefore persists both pending and resolved input in Table Storage. The worker reads the resolved response from the shared store, regardless of which instance received <code>tasks/update</code>.</p>
<p>The same terminal-state guards apply to every update. Once a task is <code>completed</code>, <code>failed</code>, or <code>cancelled</code>, a stale approval or redelivered message cannot move it back to <code>working</code>.</p>
<h2 id="cancellation-retries-and-duplicate-delivery">Cancellation, retries, and duplicate delivery</h2>
<p>MCP cancellation is cooperative. <code>tasks/cancel</code> records the terminal state, and the running tool checks that state between stages. When it observes cancellation, the worker completes the queue message cleanly rather than treating the expected cancellation as a failure.</p>
<p>Unexpected failures follow the Service Bus retry policy:</p>
<ul>
<li>transient failures abandon the message for redelivery;</li>
<li>the queue enforces <code>maxDeliveryCount</code>;</li>
<li>exhausted messages move to the dead-letter queue;</li>
<li>and the durable task records a failed result.</li>
</ul>
<p>The design assumes at-least-once delivery. Duplicate work is handled at two levels:</p>
<ul>
<li>Service Bus duplicate detection uses <code>MessageId = TaskId</code>;</li>
<li>Table Storage uses optimistic ETag concurrency and refuses to overwrite terminal task states.</li>
</ul>
<p>That second guard matters even after the broker has accepted a message. A process could complete the work and lose its message lock before acknowledging completion. If Service Bus redelivers, the next worker sees the terminal task state and treats the delivery as a duplicate instead of running the operation again.</p>
<h2 id="app-service-durable-functions-or-container-apps-jobs">App Service, Durable Functions, or Container Apps Jobs?</h2>
<p>MCP Tasks defines how a client and server talk about long-running work. It does not prescribe where that work must execute.</p>
<p>App Service, Durable Functions, and Azure Container Apps Jobs are all good options. The right choice depends on the workload you already have and the execution model you want.</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>&nbsp;</th><th>App Service</th><th>Durable Functions</th><th>Container Apps / Jobs</th></tr></thead><tbody><tr><td><strong>Strong fit</strong></td><td>Adding MCP to an existing always-on web app or API and sharing its deployment, networking, scaling, authentication, domains, and operational lifecycle</td><td>Orchestration-first workflows with checkpoints, durable timers, fan-out/fan-in, retries, sub-orchestrations, and human interaction</td><td>Container-native or isolated workers, custom runtimes and dependencies, event-driven scaling, scale-to-zero, or workers that should scale independently from the MCP endpoint</td></tr><tr><td><strong>Durability</strong></td><td>You connect external state and queue services explicitly, as this sample does</td><td>Durable orchestration state and replay are framework capabilities</td><td>You bring the state/queue; Jobs provides an execution and scaling model around it</td></tr><tr><td><strong>Operational model</strong></td><td>Always-on web processes; background workers can run beside the MCP endpoint</td><td>Serverless functions and orchestrator/activity code</td><td>Independently versioned containers or job executions, often scaled through KEDA rules</td></tr><tr><td><strong>Trade-off</strong></td><td>More durability plumbing to own, but direct control over storage, queue, latency, and cost choices</td><td>Less custom plumbing for workflows, with deterministic orchestrator/replay constraints</td><td>More separation and container flexibility, but a different operational model from an existing App Service application</td></tr></tbody><colgroup><col style="width: 25.00%;" /><col style="width: 25.00%;" /><col style="width: 25.00%;" /><col style="width: 25.00%;" /></colgroup></table></div>
<p>My practical rule:</p>
<ul>
<li>If MCP is another capability inside an App Service application you already operate, this pattern is a natural extension of that app.</li>
<li>If the task is fundamentally a durable orchestration, I would look closely at <a class="lia-external-url" href="https://learn.microsoft.com/azure/durable-task/durable-functions/durable-functions-overview" rel="noopener" target="_blank">Durable Functions</a> before writing the plumbing myself.</li>
<li>If the workers are naturally container-shaped or should scale independently from the MCP endpoint, <a class="lia-external-url" href="https://learn.microsoft.com/azure/container-apps/jobs" rel="noopener" target="_blank">Azure Container Apps Jobs</a> is likely the cleaner fit.</li>
</ul>
<p>This is not a ranking. MCP Tasks is the protocol abstraction; Azure gives you multiple execution backends so you can match the workload.</p>

<h2 id="the-takeaway">The takeaway</h2>
<p>MCP Tasks solves an important protocol problem: long-running work no longer has to stay attached to one fragile request or one client connection.</p>
<p>On a scaled cloud service, the implementation still has to answer two separate questions:</p>
<ol type="1">
<li>Where does the task's state live?</li>
<li>What guarantees that unfinished work will run again if the current process disappears?</li>
</ol>
<p>For this App Service sample, the answers are Table Storage and Service Bus. The MCP endpoint stays stateless, any instance can answer task requests, clients can reconnect safely, approvals work across instances, and queued execution survives process boundaries.</p>
<p>That is the difference between returning a task ID and actually running a durable task.</p>

<h4>Enhanced Dashboarding and Visualization Experience</h4>
<p>Grafana 13 introduces a number of improvements that make dashboards easier to build, reuse, and manage at scale. Teams can create richer observability experiences while reducing duplication and improving consistency across environments. These improvements include Dynamic Dashboards, Saved Queries, enhanced filtering and grouping experiences, dashboard templates, and additional usability enhancements that streamline dashboard authoring and discovery. From enhanced dashboard authoring experiences and reusable queries to Git-based dashboard lifecycle management, Grafana 13 helps teams build and operate observability solutions more efficiently at scale.&nbsp;</p>
<h4>Git Sync: Manage Dashboards as Code</h4>
<p>One of the most anticipated capabilities associated with Grafana 13 is Git Sync: enabling organizations to manage Grafana dashboards using Git-based workflows. Dashboards can be stored as JSON files in a Git repository, making it easier to version, review, and automate dashboard changes using existing engineering practices.</p>
<p>With Git Sync, teams can:</p>
<ul>
<li>Track dashboard changes through source control.</li>
<li>Review updates through pull requests.</li>
<li>Integrate dashboard deployments into CI/CD pipelines.</li>
<li>Collaborate on dashboard development using familiar Git workflows.</li>
</ul>
<p>Git Sync supports <strong>bidirectional synchronization</strong>. Changes made in Grafana can be committed back to a repository, while changes committed to the repository are automatically synchronized to Grafana.</p>
<p>Configuration is managed directly from the Grafana UI, with authentication supported through either a GitHub App or a Personal Access Token. For customers managing large observability estates, Git Sync helps bring dashboards into existing infrastructure-as-code and platform engineering workflows. <a class="lia-external-url" href="https://learn.microsoft.com/azure/managed-grafana/how-to-create-dashboard#manage-dashboards-as-code-with-git-sync" target="_blank">Visit MSLearn to check out Git Sync on Azure Managed Grafana</a>.</p>
<h4>Prometheus Authentication Changes in Grafana 13</h4>
<p>One of the most important changes in Grafana 13: using Prometheus with Azure authentication. Starting with Grafana 13, Azure authentication is no longer supported in the standard open-source Prometheus data source. Instead, Azure authentication is exclusively available through the Azure Monitor Managed Service for Prometheus plugin. This change aligns with Grafana Labs' updated Prometheus data source strategy and deprecation guidance.</p>
<p>Customers do not need to modify existing dashboards as part of this transition. Dashboards remain compatible across both plugin versions, and existing visualizations, imports, exports, and dashboard definitions continue to work as expected. Connectivity and query execution against Azure Monitor Workspaces and Azure Monitor Managed Service for Prometheus endpoints will use the Azure-specific plugin that now owns Azure authentication support.</p>
<p>Prometheus data sources configured with non-Azure authentication methods are unaffected by this change and continue to operate without modification.&nbsp;</p>

<p>Existing dashboards continue to work without changes. Customers do <strong>not</strong> need to:</p>
