### Simplify secure, zone-resilient outbound connectivity with Azure Firewall and StandardV2 NAT Gateway

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/simplify-secure-zone-resilient-outbound-connectivity-with-azure/ba-p/4542573](https://techcommunity.microsoft.com/t5/azure-networking-blog/simplify-secure-zone-resilient-outbound-connectivity-with-azure/ba-p/4542573)

<p><span>As organizations&nbsp;modernize their applications in Azure,&nbsp;secure&nbsp;and resilient outbound connectivity has become just as critical as&nbsp;inbound security. Workloads need reliable access to external APIs, SaaS services, operating system updates, and partner endpoints, while&nbsp;still meeting&nbsp;strong security controls, predictable&nbsp;egress&nbsp;IPs, and high availability.&nbsp;</span><span>&nbsp;</span></p>
<p><span>Achieving&nbsp;all of&nbsp;this consistently requires using the right networking services together.</span><span>&nbsp;</span></p>
<p><span>To make this easier,&nbsp;we’ve&nbsp;updated the Azure Firewall&nbsp;create&nbsp;experience in the Azure portal to include&nbsp;</span><a href="https://aka.ms/standardv2natgw" rel="noopener" target="_blank"><span><span>StandardV2 NAT Gateway</span></span></a><span>&nbsp;</span><span>directly in&nbsp;the deployment flow. This&nbsp;new&nbsp;experience&nbsp;makes it quick and seamless to&nbsp;adopt a secure, scalable, and zone‑resilient outbound&nbsp;architecture&nbsp;from day one&nbsp;by using&nbsp;</span><strong><span>Azure Firewall</span></strong><span>&nbsp;and</span><span>&nbsp;<strong>Azure&nbsp;NAT Gateway</strong>&nbsp;</span><span>together.</span><span>&nbsp;</span></p>
<p><span>In this post,&nbsp;we’ll&nbsp;cover:</span><span>&nbsp;</span></p>
<ul>
<li><span>Why pairing Azure Firewall with StandardV2 NAT Gateway is a recommended design</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>How this combination simplifies secure and resilient outbound connectivity</span><span>&nbsp;</span></li>

<ul>
<li><span>What’s&nbsp;new in the Azure Firewall portal experience&nbsp;and how to get started</span><span>&nbsp;</span></li>
</ul>
<h2><span>Why Azure Firewall and StandardV2 NAT Gateway?</span></h2>
<p><span><span>Azure Firewall and Azure NAT Gateway are designed to complement each other, each focusing on what they do best:</span><span>&nbsp;</span></span></p>
<img />Azure NAT Gateway and Azure Firewall deployed in a hub and spoke architecture.
<ul>
<li><strong><span>Azure Firewall</span></strong><span>&nbsp;provides centralized traffic inspection and policy enforcement, including&nbsp;IP address and&nbsp;FQDN filtering, threat intelligence, and logging.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><strong><span>StandardV2 NAT Gateway</span></strong><span>&nbsp;delivers high‑scale outbound SNAT, static egress IPs, and built‑in zone&nbsp;redundancy.</span> <span>&nbsp;</span></li>
</ul>
<p><span><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/reliability/reliability-nat-gateway?toc=/azure/nat-gateway/toc.json&amp;bc=/azure/nat-gateway/breadcrumb/toc.json#resilience-to-availability-zone-failures" rel="noopener" target="_blank">StandardV2 NAT Gateway</a> is </span><strong><span>zone‑redundant by default</span></strong><span>, automatically spanning availability zones within a region.&nbsp;This means outbound connectivity&nbsp;remains&nbsp;available even during a zonal failure&nbsp;without requiring multiple zonal NAT gateways or&nbsp;additional&nbsp;routing&nbsp;configurations.</span><span>&nbsp;</span></p>
<p><span>Together, this pairing cleanly separates:</span><span>&nbsp;</span></p>
<ul>
<li><strong><span>Security policy&nbsp;and inspection</span></strong><span>&nbsp;handled by Azure&nbsp;Firewall</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><strong><span>Outbound scale,&nbsp;resiliency, and IP predictability</span></strong><span><strong>&nbsp;</strong>handled&nbsp;by&nbsp;NAT Gateway</span><span>&nbsp;</span></li>
</ul>
<p><span>This separation is key for modern, large‑scale cloud workloads.</span><span>&nbsp;</span></p>
<h2><span>A recommended outbound architecture</span></h2>
<p><span>In a typical hub‑and‑spoke design:</span><span>&nbsp;</span></p>
<ol>
<li><span>Workloads in spoke virtual networks route outbound traffic to Azure Firewall in the hub</span><span>&nbsp;</span></li>
<li><span>Firewall&nbsp;policies inspect and allow the traffic</span><span>&nbsp;</span></li>
<li><span>StandardV2 NAT&nbsp;Gateway is&nbsp;attached to the&nbsp;AzureFirewallSubnet&nbsp;in the Hub</span><span>&nbsp;</span></li>
<li><span>Approved traffic flows through StandardV2 NAT Gateway for SNAT</span><span>&nbsp;</span></li>
<li><span>Traffic exits Azure using static, predictable public IPs</span><span>&nbsp;</span></li>
</ol>
<p><span>This approach provides&nbsp;several important benefits:</span><span>&nbsp;</span></p>
<ul>
<li><span>Scalable SNAT capacity for high‑connection workloads</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Static outbound IPs for partner allow‑listing&nbsp;and compliance</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Zone‑resilient outbound connectivity by default</span></li>
</ul>
<p><span>For&nbsp;step-by-step&nbsp;architectural guidance, see&nbsp;</span><a href="https://learn.microsoft.com/en-us/azure/nat-gateway/tutorial-hub-spoke-nat-firewall?tabs=portal" rel="noopener" target="_blank"><span><span>Integrate NAT gateway with Azure Firewall in a hub and spoke architecture</span></span></a><span>.</span><span>&nbsp;</span></p>
<h2><span>Built for secure and resilient Azure environments</span></h2>

### Microsoft Foundry Now Has an AI Gateway Control Plane — What Changes for App Service

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/microsoft-foundry-now-has-an-ai-gateway-control-plane-what/ba-p/4538320](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/microsoft-foundry-now-has-an-ai-gateway-control-plane-what/ba-p/4538320)
- **Published**: 2026-08-04 03:24:20
- **Fetched**: 2026-08-27 21:13:50

<p>In May, I published a <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/appsonazureblog/you-can-build-a-framework-agnostic-ai-gateway-on-azure-app-service-%E2%80%94-heres-how/4522004" rel="noopener" target="_blank">runnable sample that put Azure API Management in front of an AI agent on Azure App Service</a>. APIM handled token limits, semantic caching, token metrics, and access to the model. The point was simple: keep the agent framework interchangeable and put the production controls at the gateway.</p>
<p>A recent Apps on Azure post, <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/appsonazureblog/from-ai-adoption-to-ai-governance---using-apim-as-the-gateway-for-azure-ai-found/4536247" rel="noopener" target="_blank">From AI Adoption to AI Governance</a>, arrived at the same architectural conclusion from a platform-governance angle. It uses APIM to turn model identity and token consumption into a per-model chargeback signal for Microsoft Foundry workloads.</p>
<p>That is useful validation, but the more interesting update is in the product itself: <strong>Microsoft Foundry can now create or associate an APIM-based AI Gateway directly from its Admin console.</strong> The data path is still APIM. What changed is who can configure and govern it.</p>
<p>This post explains what that means for an App Service-hosted agent, what Foundry now manages, what still belongs in APIM, and what I would change in the sample we built earlier.</p>
<blockquote>
<p><strong>Update (August 2026):</strong> Azure API Management now offers a dedicated <strong>AI Gateway tier</strong> in public preview. This article describes Foundry’s integration with APIM-based gateways. The new tier adds an AI-focused portal and resource experience for models and MCP tools and is expected to integrate with Foundry separately. See the <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/integrationsonazureblog/ai-gateway-tier-of-api-management-now-in-public-preview/4540170." target="_blank">announcement</a>.</p>
</blockquote>
<h2>The short version: same gateway, new control plane</h2>
<p>The architecture is still familiar:</p>
<p><strong>Client -&gt; App Service agent -&gt; APIM AI Gateway -&gt; Foundry model</strong></p>
<p>APIM remains the traffic gateway. It authenticates callers, applies policies, forwards requests, and emits telemetry. App Service remains the application runtime for the agent and its APIs.</p>
<p>The new piece is the Foundry control plane. From <strong>Operate &gt; Admin console &gt; AI Gateway</strong>, a platform team can now:</p>
<ul>
<li>Create a new APIM instance or associate a supported existing instance.</li>
<li>Enable the gateway for individual Foundry projects.</li>
<li>Apply independent token limits to projects sharing the gateway.</li>
<li>Verify gateway traffic and inspect logs.</li>
</ul>
<p>Once the gateway is enabled, separate Foundry experiences can also register custom agents and govern supported MCP tools. Those actions do not happen in the AI Gateway tab itself, but the gateway provides their governed traffic path.</p>
<p>That is a meaningful shift. In the original sample, the infrastructure owner created APIM, imported the model API, deployed policy XML, and wired the agent to the gateway. Foundry does not remove APIM or replace those advanced capabilities. It gives Foundry administrators a first-party path into the same architecture.</p>
<h2>What Foundry now owns</h2>
<h3>Project onboarding</h3>
<p>An AI Gateway is associated with a Foundry resource, then enabled for projects inside it. New projects can inherit the gateway automatically. Existing projects must be added explicitly.</p>
<p>This creates a useful governance boundary: multiple teams can share the same APIM instance without sharing one undifferentiated token pool. Each project can receive its own token ceiling. If a project exceeds its configured limit, the gateway returns <code>429 Too Many Requests</code> while other projects continue using their allocations.</p>
<h3>Foundry-level limits</h3>
<p>Our earlier sample used an APIM token-limit policy keyed by an APIM subscription. That is still a valid pattern, especially when the consumer boundary is an application, business unit, or external customer.</p>
<p>The Foundry integration adds another natural counter key: the Foundry project. For organizations already organizing models and agents by project, limits can now follow that structure instead of being recreated independently in every client application.</p>
<h3>Inventory for agents and tools</h3>
<p>The AI Gateway experience is expanding beyond model endpoints in two distinct ways. Foundry can register custom agents running outside Foundry, including agents that use A2A as their communication protocol. Separately, AI Gateway can govern supported MCP tools. The current tools-governance preview is scoped to MCP; it does not cover every Foundry or OpenAPI tool type.</p>
<p>That matters for App Service because the runtime does not need to move. An agent can continue running on App Service while participating in Foundry's inventory, and its supported MCP traffic can flow through the gateway.</p>
<p>These experiences are still preview features, so I would treat them as a control-plane integration to evaluate, not a reason to redesign a working production agent.</p>
<h2>What still belongs in APIM</h2>
<p>Foundry makes the common path easier. It does not make the full APIM surface unnecessary.</p>
<p>I would still use APIM directly for:</p>
<ul>
<li>Custom policy expressions and organization-specific headers or claims.</li>
<li>Semantic caching backed by Azure Managed Redis.</li>
<li>Backend pools, priority routing, and circuit breakers.</li>
<li>Private networking, multi-region gateways, and advanced topology decisions.</li>
<li>Custom metrics and dimensions needed for internal chargeback.</li>
</ul>
<p>The clean mental model is: <strong>Foundry manages the AI assets and common project guardrails; APIM manages the traffic contract and advanced gateway behavior.</strong></p>
<h2>Applying this to the App Service sample</h2>
<p>The existing <a class="lia-external-url" href="https://github.com/seligj95/app-service-ai-gateway-mcp-apim-python" rel="noopener" target="_blank">framework-agnostic AI Gateway sample</a> hosts a Microsoft Agent Framework agent and an MCP server on one Linux App Service. The agent reaches its model through APIM, which applies token limits, semantic caching, token metrics, and managed-identity authentication.</p>
<p>Most of that architecture should stay exactly as it is.</p>
<h3>1. Keep the App Service application unchanged</h3>
<p>The agent should continue calling a stable gateway endpoint. It should not need to understand whether APIM was provisioned by Bicep, associated in Foundry, or managed by a central platform team. That separation was the reason to introduce the gateway in the first place.</p>
<h3>2. Choose the APIM ownership model deliberately</h3>
<blockquote>
<p><strong>Update (August 2026):</strong> Foundry can now associate eligible API Management instances on classic (v1) SKUs as AI Gateways, in addition to v2 instances. If you already operate a classic-tier gateway, check <strong>Use existing APIM</strong> before planning a migration. Association does not change that tier’s SLA, scaling, networking, or feature limitations.</p>
</blockquote>
<p>For a new proof of concept, Foundry can create a Basic v2 APIM instance. For production, Microsoft recommends evaluating Standard v2 or Premium v2 based on throughput and networking requirements.</p>
<p>For an existing enterprise gateway, use the Foundry option to associate an APIM instance only after confirming that it meets the eligibility requirements: it must be in the same Microsoft Entra tenant and Azure subscription as the Foundry resource, you need the <strong>API Management Service Contributor</strong> role (or Owner), and the instance must use a currently supported APIM tier.</p>
<h3>3. Add existing projects explicitly</h3>
<p>Creating or associating the gateway at the Foundry resource level does not automatically enable every existing project. Add each existing project to the gateway, then verify its status is <strong>Enabled</strong>.</p>
<h3>4. Decide where each limit belongs</h3>
<p>Avoid layering limits without a clear ownership model. A Foundry project limit, an APIM subscription limit, and a model deployment TPM limit answer different questions:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Control</th><th>Best boundary</th><th>Question it answers</th></tr></thead><tbody><tr><td>Foundry project limit</td><td>Team or workload project</td><td>How much shared capacity can this project consume?</td></tr><tr><td>APIM policy limit</td><td>Subscription, user, tenant, or application</td><td>How much can this specific consumer use?</td></tr><tr><td>Model deployment quota</td><td>Backend deployment</td><td>What capacity exists at the model endpoint?</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>Use all three when the boundaries are intentional. Otherwise, operators end up debugging a <code>429</code> without knowing which layer produced it.</p>
<h3>5. Verify the data path</h3>
<p>After enabling a project, make a model request and confirm that the APIM request metric increments. Microsoft also recommends checking the <code>GatewayLogs</code> table for a successful response and an API name matching the AI Gateway.</p>
<p>Then test the failure path. Set a deliberately small project limit, exceed it, and confirm that the gateway returns <code>429</code>. A governance feature is not finished until the team has observed both the allowed and denied behavior.</p>
<h2>Which path should you choose?</h2>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Scenario</th><th>Recommended approach</th></tr></thead><tbody><tr><td>New Foundry proof of concept</td><td>Create the AI Gateway from Foundry and start with project-level limits.</td></tr><tr><td>Existing v2 enterprise APIM</td><td>Associate the existing instance and preserve central networking and policy ownership.</td></tr><tr><td>Existing classic-tier APIM</td><td>
<p>Associate the existing instance with Foundry if eligible; migrate only when production, networking, or scale requirements justify it.</p>
</td></tr><tr><td>Advanced routing or custom policy needs</td><td>Use Foundry for inventory and common guardrails, then manage the advanced behavior in APIM.</td></tr><tr><td>Strict isolation between project groups</td><td>Use separate Foundry resources and separate gateways rather than assuming one gateway per project.</td></tr></tbody><colgroup><col style="width: 50.00%;" /><col style="width: 50.00%;" /></colgroup></table></div>
<h2>The architecture was right; the experience caught up</h2>
<p>The most important takeaway is not that everyone should rebuild an AI Gateway in a new portal. It is that the composable architecture now has a more accessible control plane.</p>
<p>App Service still runs the agent. APIM still governs the traffic. Foundry now gives model and platform owners a direct way to connect projects, allocate capacity, and bring agents and tools into the same governance view.</p>
<p>If you already built the earlier sample, the application boundary does not need to change. Evaluate the Foundry integration, decide whether its project model matches your organization, and check the APIM tier before planning any migration. The gateway remains the contribution; Foundry now makes it easier to operate.</p>

### Built-In Observability for Serverless AI Agents on Azure Functions

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/built-in-observability-for-serverless-ai-agents-on-azure/ba-p/4542087](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/built-in-observability-for-serverless-ai-agents-on-azure/ba-p/4542087)
- **Published**: 2026-08-04 07:29:13
- **Fetched**: 2026-08-27 21:13:50

<p>Azure Functions Agents - the markdown-first runtime that turns a folder of *.agent.md files into a serverless Azure Functions app - now ships with OpenTelemetry tracing built into the runtime itself. Every agent run becomes a real, structured trace in Application Insights: the model used, the session, and every tool call or sub-agent hand-off along the way. None of it requires writing a line of telemetry code in your app.</p>
<h4><a class="lia-external-url" href="https://aka.ms/serverless-agents-quickstart" rel="noopener" target="_blank">Click here to create and run a Serverless Agent using Azure Functions</a></h4>
<h1>Full visibility, zero code</h1>
<p>Bootstrapping an agent app is still two lines:</p>
from azure_functions_agents import create_function_app app = create_function_app()
<p>Turning on export is two settings, no code:</p>
<p>In requirements.txt -&nbsp;</p>
pip install azurefunctions-agents-runtime[monitor]
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN">In your App Settings -</div>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN">APPLICATIONINSIGHTS_CONNECTION_STRING=&lt;your-app-insights-connection-string&gt;&lt;/your-app-insights-connection-string&gt;</div>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN">&nbsp;</div>
<p>From there, every run shows up automatically in Application Insights' <strong>Agents</strong> view, tagged with a consistent set of attributes the runtime adds for you: which agent ran, which model answered, which tools it called, and how the run finished. You don't pick and choose what to instrument - you get the whole run, every time, the same way, regardless of what the agent is doing underneath.</p>
<p>That consistency is what makes the tracing useful for more than debugging. It's also the simplest way to <em>see</em> something that would otherwise happen invisibly inside a single API call.</p>
<h1>Example: watching a model decision happen in real time</h1>
<p>One good illustration is <a href="https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/model-router" rel="noopener" target="_blank">Model Router</a> - a model you deploy yourself in your Foundry resource, like any other model deployment. Point an agent's model setting at that deployment, and Model Router picks a different underlying LLM per prompt: a smaller model for simple requests, a larger one once a prompt actually needs it.</p>
<p>Normally that choice is invisible - it happens inside one API call. But because Azure Functions Agents traces every run the same way no matter which model is behind it, the decision shows up for free. Same chat session, two prompts:</p>

<p><strong>Prompt</strong></p>

<p><strong>Model Router picked</strong></p>

<p><strong>Why</strong></p>
</td></tr></thead><tbody><tr><td>
<p>Easy, one-shot question</p>
</td><td>
<p>gpt-5-mini</p>
</td><td>
<p>Small model is comparable quality for a fraction of the cost.</p>
