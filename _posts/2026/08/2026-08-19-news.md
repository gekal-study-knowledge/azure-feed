## Azure Networking Blog

### Azure DNS introduces Traffic Manager linked records (Public Preview)

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-dns-introduces-traffic-manager-linked-records-public/ba-p/4547112](https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-dns-introduces-traffic-manager-linked-records-public/ba-p/4547112)
- **Published**: 2026-08-19 01:14:39
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>We're excited to announce the <strong>public preview of Traffic Manager linked records</strong>, a new Azure DNS capability that enables customers to directly associate Azure Public DNS record sets with Azure Traffic Manager profiles without using a CNAME to trafficmanager.net.</p>
<p>With this capability, customers can use Traffic Manager's DNS-based load balancing capabilities without exposing the intermediate trafficmanager.net domain in DNS responses. Azure DNS and Traffic Manager now work together to provide a more seamless, integrated DNS experience for applications running across Azure, hybrid, and multi-cloud environments.</p>
<h3>Simplifying DNS-based traffic routing</h3>
<p>Traditionally, customers using Azure DNS with Traffic Manager relied on CNAME records that returned a Traffic Manager hostname. DNS clients would then perform an additional lookup to resolve that hostname before reaching the application endpoint.</p>
<p>Traffic Manager linked records<strong> </strong>simplifies this process by allowing Azure DNS to resolve Traffic Manager routing decisions internally and return the appropriate endpoint information directly to clients.</p>
<p>The result is a cleaner DNS resolution path while preserving all of Traffic Manager's existing routing methods, health monitoring, and failover capabilities.</p>
<img />
<h3>Key benefits</h3>
<p><strong>Better integration between Azure DNS and Azure Traffic Manager</strong></p>
<p>Traffic Manager linked records allow Azure DNS record sets to directly reference Traffic Manager profiles, including nested profile configurations.</p>
<p>This enables sophisticated traffic routing architectures without relying on intermediate CNAME records, making complex global deployments easier to build and manage.</p>
<p><strong>Improved security and DNS hygiene</strong></p>
<p>Because DNS responses no longer expose the intermediate <strong>trafficmanager.net</strong> domain, organizations can simplify firewall rules and reduce reliance on intermediate DNS names.</p>
<p>Traffic Manager linked records also help eliminate a common source of dangling subdomains caused by orphaned or misconfigured <strong>trafficmanager.net</strong> records, strengthening overall DNS hygiene and reducing operational risk.</p>
<p><strong>DNSSEC for Traffic Manager</strong></p>
<p>Traffic Manager routing decisions are now resolved within Azure DNS, If the DNS zone is a DNSSEC signed zone the answers supplied by linked Traffic Manager&nbsp;profiles are automatically signed as well. This enables customer to use Traffic Manager profiles with DNSSEC, unlike a CNAME to trafficmanager.net which would break the DNSSEC end to end validation chain as trafficmanager.net is not a signed zone.</p>
<p><strong>Zone apex load balancing</strong></p>
<p>Traffic Manager Linked Records enable DNS-based load balancing directly at the <strong>zone apex</strong> (for example, <strong>contoso.com</strong>), where traditional CNAME records are prohibited by DNS standards. Customers can now bring Traffic Manager routing to root domains without complex workarounds. This is similar to ALIAS records but with much better integration and scale.</p>
<p><strong>Cleaner &amp; faster DNS responses</strong></p>
<p>Clients now receive the final endpoint directly from Azure DNS instead of first resolving a <strong>trafficmanager.net</strong> hostname. By removing an extra DNS lookup, applications can experience lower DNS resolution latency while benefiting from Traffic Manager's intelligent routing decisions.</p>
<p><strong>Built-in operational safeguards with strictly typed profiles</strong></p>
<p>Traffic Manager Linked Records integrate with <strong>strictly typed profiles </strong>in Azure Traffic Manager, providing validation that helps ensure DNS record types remain compatible with their associated Traffic Manager profiles. In simpler words this features ensures that type of response served by the traffic manager profile matches the type of DNS records it is linked to.</p>
<p>The feature also prevents accidental deletion of Traffic Manager profiles that are still referenced by Azure DNS records, reducing the risk of configuration errors and improving operational safety.</p>
<h3>Getting started</h3>
<p>Traffic Manager linked records are available today in <strong>public preview</strong>.</p>
<p>Following record types can be used with Traffic Manager Linked Records</p>
<ul>
<li><strong>A </strong></li>
<li><strong>AAAA </strong></li>
<li><strong>CNAME </strong></li>
</ul>
<p>Traffic Manager linked records are designed to make DNS-based load balancing simpler, faster, and more secure while preserving the flexibility and reliability customers expect from Azure Traffic Manager.</p>
<p>To learn more and start using Traffic Manager linked records today, see the <a class="lia-external-url" href="https://learn.microsoft.com/azure/dns/dns-traffic-manager-linked-records" rel="noopener" target="_blank">DNS Traffic Management</a> documentation.</p>

### What the New API Management AI Gateway Tier Changes for App Service-Hosted Agents

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/what-the-new-api-management-ai-gateway-tier-changes-for-app/ba-p/4543974](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/what-the-new-api-management-ai-gateway-tier-changes-for-app/ba-p/4543974)
- **Published**: 2026-08-19 22:54:21
- **Fetched**: 2026-08-27 21:13:50

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>In May, I published <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/appsonazureblog/you-can-build-a-framework-agnostic-ai-gateway-on-azure-app-service-%E2%80%94-heres-how/4522004" rel="noopener" target="_blank">a runnable sample that put Azure API Management in front of an AI agent on Azure App Service</a>. The agent framework was replaceable; the gateway was the contribution. APIM handled model access, token limits, semantic caching, token metrics, and the MCP traffic contract.</p>
<p>I followed that with <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/appsonazureblog/microsoft-foundry-now-has-an-ai-gateway-control-plane-%E2%80%94-what-changes-for-app-ser/4538320" rel="noopener" target="_blank">a look at Foundry's new AI Gateway control plane</a>. The data path was still APIM, but Foundry gave model and platform owners a first-party way to associate gateways, onboard projects, and allocate capacity.</p>
<p>Now <a class="lia-internal-link lia-internal-url lia-internal-url-content-type-blog" href="https://techcommunity.microsoft.com/blog/integrationsonazureblog/ai-gateway-tier-of-api-management-now-in-public-preview/4540170" rel="noopener" target="_blank">API Management has a dedicated AI Gateway tier in public preview</a>. That raises a different question for App Service users: does the application runtime change, or does the boundary around models and tools change?</p>
<p>The short answer is that App Service still owns the web application, agent orchestration, streaming experience, deployment lifecycle, scaling, managed identity, and application telemetry. The dedicated tier gives the model-and-tool boundary an AI-focused resource, portal, and runtime experience. To make that distinction concrete, I built a new runnable sample in which a Python agent on App Service can reach both its model and its MCP tools only through the dedicated AI Gateway.</p>
<p><strong>Get the sample:</strong> <a class="lia-external-url" href="https://github.com/seligj95/app-service-ai-gateway-tier-python" rel="noopener" target="_blank">Deploy and explore the complete App Service + AI Gateway sample on GitHub</a>.</p>
<blockquote>
<p><strong>Preview notice:</strong> The dedicated AI Gateway tier is in public preview. It has no SLA, is currently available only in East US 2 and Sweden Central, and does not yet have an announced pricing or business model. APIs, limits, regions, policy behavior, and portal experiences may change. The sample is designed for learning and validation, not as a production-ready reference architecture.</p>
</blockquote>
<h2>The short version: App Service is the runtime; AI Gateway is the governed boundary</h2>
<p>The architecture separates application concerns from AI access concerns:</p>
<ul>
<li><strong>App Service</strong> hosts the FastAPI application, browser UI, Microsoft Agent Framework agent, server-sent event stream, retry behavior, and a small read-only MCP server.</li>
<li><strong>AI Gateway</strong> exposes the OpenAI-compatible model endpoint and MCP ToolServer endpoint used by the application. It owns the runtime access key, model registration, structured token policy, backend tool credential, and gateway telemetry exporter.</li>
<li><strong>Microsoft Foundry / Azure AI Services</strong> supplies the backing model. AI Gateway reaches it with managed identity.</li>
<li><strong>Key Vault</strong> stores the gateway runtime key and a separate MCP backend secret. App Service resolves both through managed identity-backed Key Vault references.</li>
<li><strong>Application Insights</strong> receives application OpenTelemetry and the preview gateway token-usage export.</li>
</ul>

<h2>What the sample actually does</h2>
<p>The sample deploys a Python 3.12 FastAPI application to Linux App Service. The browser presents a small chat interface, but the useful part is behind it:</p>
<ul>
<li>Microsoft Agent Framework configured with an <code>OpenAIChatCompletionClient</code> whose base URL is the gateway OpenAI v1 route.</li>
<li>An <code>MCPStreamableHTTPTool</code> configured with the gateway ToolServer route and a fixed allow-list of two read-only tools.</li>
<li>Server-sent event streaming from App Service to the browser.</li>
<li>A stable gateway model name, <code>appservice-chat</code>, initially mapped to a <code>gpt-5-mini</code> deployment.</li>
<li>A separate MCP endpoint on App Service that rejects direct callers unless AI Gateway injects the expected backend secret.</li>
<li>Bounded handling for 401, 404, 429, and transient 5xx responses.</li>
<li>Application Insights and OpenTelemetry with correlation IDs and a strict telemetry attribute allow-list.</li>
<li>Complete azd and Bicep infrastructure using the published preview resource contracts.</li>
</ul>
<h3>The model path</h3>
<ol>
<li>The browser posts a message to <code>/api/chat/stream</code> on App Service.</li>
<li>FastAPI creates or accepts a correlation ID and returns a server-sent event stream.</li>
<li>The Agent Framework client sends an OpenAI-compatible request to <code>/default/models/openai/v1/</code> on AI Gateway with the gateway runtime access key.</li>
<li>AI Gateway resolves the stable catalog name <code>appservice-chat</code>, applies its structured token policy, and calls the backing Foundry deployment with the gateway system-assigned managed identity.</li>
<li>Text fragments return through AI Gateway and App Service as <code>delta</code> events. The browser renders them as they arrive.</li>
<li>Application spans and gateway token usage are correlated in Application Insights without capturing prompts, responses, keys, or backend secrets as custom attributes.</li>
</ol>
<p>This is the first practical benefit for an App Service user: application code targets one governed OpenAI-compatible boundary. The app does not contain a Foundry endpoint, a Foundry key, or a direct-provider fallback.</p>
<h3>The tool path</h3>
<p>The sample deliberately hosts its MCP server on the same App Service application so the complete tool path is visible:</p>
<ol>
<li>For the two documented operational prompts, the application sets Agent Framework <code>tool_choice</code> to the matching read-only tool. Other prompts retain automatic tool selection.</li>
<li>Agent Framework invokes the <code>appservice-ops</code> MCP ToolServer through AI Gateway using the same runtime access key.</li>
<li>AI Gateway validates the caller and injects a different <code>x-appservice-mcp-secret</code> header only on the backend hop.</li>
<li>The ToolServer calls <code>/mcp</code> on App Service.</li>
<li>App Service compares the backend secret and executes one of two fixed, read-only tools.</li>
<li>The tool result travels back through AI Gateway to the agent, which uses it in the streamed answer.</li>
</ol>
<p>This explicit choice matters in a demonstration. Strong instructions make tool use more likely, but they do not make a model decision deterministic. The application therefore recognizes the exact status and deployment-context prompts shown below and requires the matching function. The backend publishes raw names such as <code>get_service_status</code>; the AI Gateway ToolServer advertises them to the client as <code>appservice-ops_get_service_status</code> and <code>appservice-ops_get_deployment_context</code>. Agent Framework must allow the gateway-advertised names without adding a second prefix.</p>
<p>The two tools are intentionally small:</p>

<h2>Proving the gateway is actually in the path</h2>
<p>A successful chat response alone is not sufficient evidence. The sample includes several tests that make the gateway boundary observable.</p>
<h3>1. Confirm the application has no provider fallback</h3>
<p>The application accepts only gateway-shaped model and MCP URLs. Configuration validation rejects other endpoint shapes, and there is no provider endpoint or provider credential setting. If the gateway is unavailable or misconfigured, the application fails visibly rather than silently bypassing policy.</p>
<h3>2. Test runtime-key enforcement</h3>
<p>Call the gateway model route with a deliberately invalid key. The expected result is HTTP 401. The application treats this as a deployment or configuration failure and does not retry it.</p>
<h3>3. Test model catalog routing</h3>
<p>Request an unknown model name through the OpenAI-compatible route. The expected result is HTTP 404. A normal application request uses the stable name <code>appservice-chat</code>, showing that the gateway catalog—not a provider-specific name embedded in application source—controls resolution.</p>
<h3>4. Test the structured token policy</h3>
<p>The model registration includes a JSON-backed token-limit policy. In a disposable test environment, temporarily lower the limit, send enough requests to exceed it, and capture HTTP 429. Restore the normal value immediately afterward. During preview validation, the gateway returned 429 without a <code>Retry-After</code> header, so the sample honors the header when present and otherwise uses bounded fallback backoff.</p>
<h3>5. Prove direct MCP access is denied</h3>
<p>Call the App Service <code>/mcp</code> endpoint without the backend header. The expected response is HTTP 401. Then ask the agent for live service status and confirm the same tool succeeds through the AI Gateway ToolServer. The contrast proves that the gateway is adding backend authentication rather than exposing an anonymous tool endpoint.</p>
<h3>6. Verify telemetry on both sides of the boundary</h3>
<p>Use the correlation ID returned by the chat stream to locate the App Service request and agent span in Application Insights. For a tool prompt, confirm the safe application <code>mcp_tool_called</code> trace and the AI Gateway <code>tools/call</code> dependency with its <code>gen_ai.tool.name</code> attribute. Separately confirm token-usage telemetry for the model request. These views prove different parts of the path: the application executed the backend tool, the gateway mediated the ToolServer call, and the model route emitted usage telemetry.</p>

<h2>Operating the boundary</h2>
<h3>Who authenticates to whom</h3>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Connection</th><th>Authentication</th><th>Why</th></tr></thead><tbody><tr><td>App Service to AI Gateway</td><td>Gateway runtime access key in the lowercase <code>api-key</code> header</td><td>This is the current preview runtime-caller authentication model. The sample does not claim managed identity support where it does not exist.</td></tr><tr><td>AI Gateway to Foundry</td><td>AI Gateway system-assigned managed identity with Foundry User</td><td>No Foundry key is stored in the application.</td></tr><tr><td>App Service to Key Vault</td><td>App Service managed identity with Key Vault Secrets User</td><td>The runtime key and MCP backend secret are resolved through Key Vault references.</td></tr><tr><td>AI Gateway to the App Service MCP backend</td><td>Separate gateway-injected backend header secret</td><td>Direct anonymous callers cannot invoke the MCP tools.</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>The post-provision hook retrieves the generated gateway runtime key through the documented management action, writes it and a newly generated MCP backend secret to Key Vault without printing them, and completes the ToolServer credential configuration. No runtime key is committed to source control or written to the azd environment.</p>
<h3>Changing the model without rewriting the application</h3>
<p>The application always requests <code>appservice-chat</code>. Both the Foundry deployment and gateway model registration use that stable client-facing alias, while model name and version remain deployment parameters. This lets the platform team evaluate a backing model update at the gateway and infrastructure layer without changing the FastAPI or Agent Framework source.</p>
<h3>The gateway governs; the application still has to be resilient</h3>
<ul>
<li>401 and 404 are not retried.</li>
<li>429 and transient 5xx responses use a maximum of three attempts by default, bounded exponential backoff, and jitter.</li>
<li><code>Retry-After</code> is honored when the gateway supplies it.</li>
<li>HTTP status and retry metadata are recovered from Agent Framework exception wrappers before classification.</li>
<li>Retries occur only before the first streamed token.</li>
<li>A partially emitted stream is never replayed.</li>
<li>Prompts, model responses, secrets, and upstream response bodies are excluded from application error messages and custom telemetry.</li>
</ul>
<p>This is another important division of responsibility: the gateway governs access and policy; the application remains responsible for trustworthy interaction behavior.</p>

<h2>The boundary is the product</h2>
<p>This is the through line across all three posts. The first sample showed that the agent framework can change while APIM remains the traffic boundary. The Foundry post showed that the same boundary can gain a model- and project-focused control plane. This sample shows what changes when the gateway itself becomes an AI-focused tier.</p>
<p>App Service still runs the agent. AI Gateway still does not replace application logic, deployment, or resilience. The better-together story is that App Service gives the agent a managed application runtime while AI Gateway gives that runtime a governed, observable, and replaceable boundary for models and tools.</p>
<p><strong>One final preview boundary:</strong> This sample demonstrates a governed model and tool path, separated identities, model indirection, policy enforcement, and telemetry. It does not establish production readiness, scale limits, final pricing, or live multi-provider routing; the deployment uses one Foundry provider.</p>

<h2>Why Markdown for Agents?</h2>
<p>Web pages often contain scripts, styles, and HTML markup that are useful to browsers but add noise when the content is sent to an AI model. Markdown for Agents removes that extra markup and returns a smaller, text-focused response that is easier for agents to process and can reduce token usage.</p>
<p>In internal testing across more than 637,000 pages, converted Markdown responses were 97 percent smaller at the median than the source HTML, with a median conversion time of 2 milliseconds. Results vary based on the page and its content.</p>
<h2>Public preview availability</h2>
<p>Markdown for Agents is available in public preview for <strong>Windows apps on Azure App Service in all public regions</strong>. The app must use an App Service plan in the Basic tier or higher.</p>
<p>No additional authentication setup is required for Markdown conversion. Your app's existing authentication, authorization, and network access controls continue to apply.</p>
<blockquote>
<p>This feature is only supported on Windows App Service at this time. Support for Linux apps will come later this year.</p>
</blockquote>
<h2>Enable Markdown for Agents</h2>
<p>During the public preview, you can enable the feature through the REST API, ARM/Bicep template, or the Azure CLI using&nbsp;<code>az rest</code>. Dedicated Azure CLI commands and portal support are planned for a future update.</p>
<h3>Azure CLI with az rest</h3>
<p>Replace the placeholders with your subscription ID, resource group, and app name:</p>
az rest --method patch --url "https://management.azure.com/subscriptions/&lt;SUBSCRIPTION_ID&gt;/resourceGroups/&lt;RESOURCE_GROUP&gt;/providers/Microsoft.Web/sites/&lt;APP_NAME&gt;?api-version=2026-03-15" --headers "Content-Type=application/json" --body '{"properties":{"aiIntegration":{"markdown":{"enabled":true}}}}'
<p>Verify the setting:</p>
az rest --method get --url "https://management.azure.com/subscriptions/&lt;SUBSCRIPTION_ID&gt;/resourceGroups/&lt;RESOURCE_GROUP&gt;/providers/Microsoft.Web/sites/&lt;APP_NAME&gt;?api-version=2026-03-15" --query "properties.aiIntegration.markdown"
<p>To disable the feature, send the same PATCH request with <code>enabled</code> set to <code>false</code>.</p>
<h3>ARM template</h3>
<p>Add the following property to your <code>Microsoft.Web/sites</code> resource using API version <code>2026-03-15</code>:</p>
"properties": {
  "aiIntegration": {
    "markdown": {
      "enabled": true
    }
  }
}
<h3>Bicep</h3>
resource webApp 'Microsoft.Web/sites@2026-03-15' = {
  name: appName
  location: location
  properties: {
    serverFarmId: appServicePlanResourceId
    aiIntegration: {
      markdown: {
        enabled: true
      }
    }
  }
}
<h2>Request a Markdown response</h2>
<p>After enabling the feature, request an HTML page from your app with the <code>Accept: text/markdown</code> header:</p>
curl -i -H "Accept: text/markdown" "https://&lt;APP_NAME&gt;.azurewebsites.net/"
<p>A successfully converted response includes these headers:</p>
<pre><code>Content-Type: text/markdown; charset=utf-8
x-markdown-source: easy-markdown</code></pre>
<p>The response body contains Markdown generated from the page's HTML. Common content such as headings, paragraphs, links, lists, images, emphasis, and code is preserved, while script and style content is removed.</p>
<p>Pages that cannot be safely converted may return their original HTML. Clients should check the <code>Content-Type</code> and <code>x-markdown-source</code> response headers before processing the response as Markdown.</p>
