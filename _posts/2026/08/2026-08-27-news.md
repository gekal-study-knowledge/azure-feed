### Azure DNS + Traffic Manager linked records

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-dns-traffic-manager-linked-records/ba-p/4548221](https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-dns-traffic-manager-linked-records/ba-p/4548221)
- **Published**: 2026-08-27 00:59:25
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><strong>Introduction</strong></p>
<p>Traffic Manager linked records creates a direct, managed link between an Azure DNS record set and a Traffic Manager profile. When a query arrives, Azure DNS evaluates the linked Traffic Manager profile internally and returns the appropriate endpoint response directly. For A and AAAA records, this means the client receives endpoint IP addresses without an intermediate CNAME response to trafficmanager.net.</p>
<p>This practical guide uses a small multi-region Contoso scenario to explain the architecture, configure the feature in the Azure portal, validate the DNS response, and demonstrate endpoint failover. The feature is currently in public preview, so the walkthrough should be tested in a non-production environment before broader adoption.</p>
<p><strong>Note</strong>: DNS-based global routing is powerful, but the traditional integration between a custom domain and Traffic Manager adds an intermediate name that customers must understand, resolve, and govern.</p>
<h1>The scenario and the problem</h1>
<p>Contoso operates a public application across North America, Europe, and Asia. Users browse to contoso.com. Azure Traffic Manager monitors the regional endpoints and selects the preferred healthy destination according to the profile routing method.</p>
<ul>
<li>Traditional CNAME integration can expose the intermediate trafficmanager.net name in the DNS response.</li>
<li>A CNAME cannot be placed at the zone of apex, which makes root-domain routing harder.</li>
<li>An unsigned intermediate DNS hop can interrupt end-to-end DNSSEC validation.</li>
<li>Operations teams must understand which system is authoritative for the customer zone, and which system makes the routing decision.</li>
</ul>
<p><strong>Design objective</strong></p>
<p>Preserve Traffic Manager routing methods, endpoint health monitoring, and automatic failover while returning the effective endpoint answer directly from Azure DNS.</p>
<h1>The solution: Traffic Manager linked records</h1>
<img />
<p><em>Figure 1. Traditional CNAME resolution compared with Traffic Manager linked record.</em></p>

<p>As you see in figure 1 above, the left side shows the traditional path. The client queries the application name in Azure DNS, receives a CNAME that points to a trafficmanager.net profile name, and then performs another lookup before receiving the selected endpoint address. The right side shows the linked-record path. Azure DNS remains authoritative for the Contoso zone, consults the linked Traffic Manager profile internally, and returns the selected endpoint directly.</p>
<p>The key point is that the Traffic Manager still performs the routing decision and health evaluation. Linked records change the DNS integration and the answer returned to the client; they do not turn Traffic Manager into a reverse proxy or place it in the application's data path.</p>
<h1>Reference architecture</h1>
<img />
<p><em>Figure 2. Practical multi-region architecture for testing direct resolution and failover.</em></p>

<p>Reference architecture in figure 2 above shows the client queries contoso.com. Azure Public DNS hosts the authoritative zone and contains a record set linked to the tm-profile Traffic Manager profile. The profile uses a configured routing method and continuously evaluates the health of the regional endpoints. Azure DNS uses the Traffic Manager decision and returns the effective endpoint answer to the client.</p>
<p>For a simple lab, two endpoints are enough. Configure the first endpoint with priority 1 and the second with priority 2. The third regional endpoint in the diagram illustrates how the same design scales to additional regions. The record set can be created at the zone apex by leaving the record name empty, or for a subdomain such as www.</p>
<p><strong>Note:</strong> Traffic Manager is DNS based. After name resolution, the client connects directly to the selected public endpoint. Application traffic does not pass through the Traffic Manager.</p>
<h1>Prerequisites</h1>
<ul>
<li>An Azure subscription and permissions to create or update Azure DNS and Traffic Manager resources.</li>
<li>A public domain hosted in Azure DNS and delegated to the Azure DNS name servers.</li>
<li>Two public application endpoints that can return visibly different responses for failover testing.</li>
<li>The Microsoft.Network resource provider is registered in every subscription that contains the DNS zone or Traffic Manager profile.</li>
</ul>
<h1>Implementation in the Azure portal</h1>
<p>The portal workflow has two main parts: create a strictly typed Traffic Manager profile, then create an Azure DNS record set that links to that profile.</p>
<h2>Create the Traffic Manager profile</h2>
<p><strong>Step1:</strong> Open Traffic Manager profiles, select create.</p>
<img />
<p><strong>Step 2:</strong>&nbsp;Configure the profile and instance details, fill out the subscription, resource group, name(tm-profile), routing method: priority, record type: A, and resource group location.</p>
<img />
<p><strong>Step 3:</strong>&nbsp;Add endpoints (Add tmendpoint-1 as the public IP address and external endpoint type with priority 1.</p>
<img /><img />
<p><strong>Step 4:</strong>&nbsp;Repeat Step 3 to add the secondary endpoint (Add tmendpoint-2 as the public IP address and external endpoint type with priority 2)</p>
<p><strong>Step 5:</strong> Confirm endpoint health (Wait until both endpoints report online before testing DNS behavior.)</p>
<img />
<p><strong>Note:</strong>&nbsp;The record type selection creates a strictly typed profile. Select A for IPv4 answers, AAAA for IPv6 answers, or CNAME for canonical-name answers. The type is used to validate compatibility between the Traffic Manager profile and the linked DNS record.</p>
<h2>Create the linked record in Azure DNS</h2>
<p><strong>Step 1: </strong>Open the Azure DNS zone, select the zone that hosts the application domain, for example contoso.com.</p>
<img />
<p><strong>Step 2:&nbsp;</strong>Add DNS record sets, select + record set.</p>
<img />
<p><strong>Step 3:</strong>&nbsp;Choose the record name, leave name empty for the zone apex or enter www for a subdomain.</p>
<img />
<p><strong>Step 4:</strong> Choose the type, select the record type that matches the Traffic Manager profile, for example, A.</p>
<p><strong>Step 5: </strong>Enable Traffic Management, select Enable Traffic Management (Preview).</p>
<p><strong>Step 6: </strong>Select the profile, choose the profile subscription and tm-profile, then save the record set.</p>
<p><strong>Note</strong>: The record set contains a managed association to the Traffic Manager profile. The linked record inherits its TTL from the Traffic Manager profile.</p>

<h1>Validate the DNS response</h1>
<p>Use both the Azure portal and direct DNS query. The portal confirms the resource association; the DNS query confirms the serving behavior.</p>
<h2>Portal validation</h2>
<ul>
<li>The record exists in the expected Azure DNS zone.</li>
<li>The record type matches the strictly typed Traffic Manager profile.</li>
<li>The linked profile is tm-profile.</li>
<li>The Traffic Manager endpoints show their expected health state.</li>
</ul>
<h2>Command-line validation</h2>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><img />

<p>A successful A-record test returns the selected healthy endpoint IP address and does not include a trafficmanager.net CNAME in the answer. Querying for an Azure DNS authoritative name server directly is useful during testing because it reduces ambiguity from local recursive resolver caches.</p>
<p>The specific endpoint returned depends on the routing method, endpoint health, source resolver location, and cached TTL behavior. Validate the result against the profile configuration rather than expecting one universal IP address.</p>

<h1>Preview and operational considerations</h1>
<ul>
<li>Treat the feature as preview and review the Microsoft Azure preview supplemental terms before production use.</li>
<li>Confirm that the DNS zone and Traffic Manager profile subscriptions have the required resource provider registration.</li>
<li>Plan the record type before creating the Traffic Manager profile because the strictly typed profile value cannot be changed after creation.</li>
<li>Remember that the record TTL is inherited from the Traffic Manager profile.</li>
<li>Test routing, endpoint health, DNSSEC behavior, zone-apex resolution, and rollback in a controlled environment.</li>
<li>Document the previous DNS record so the change can be reversed if the validation plan fails.</li>
</ul>
<h1>Conclusion</h1>
<p>Traffic Manager linked records is a focused DNS improvement with meaningful architectural impact.</p>
<p>The feature keeps Azure DNS authoritative for the customer domain, preserves Traffic Manager health-aware routing, and removes the need for the client to follow an intermediate trafficmanager.net hop. That creates a cleaner DNS response path and enables scenarios that were difficult with a traditional CNAME, especially zone-apex routing and DNSSEC-protected domains.</p>
<p>The strongest way to evaluate the feature is through a small, observable lab: create a strictly typed profile, link an Azure DNS record, query the authoritative DNS server, and deliberately fail the primary endpoint. When the DNS response changes to the secondary healthy destination without exposing an intermediate Traffic Manager name, the value becomes immediately clear.</p>
<p>&nbsp;</p>
<p><strong>Final takeaway</strong></p>
<p>A small change in DNS integration can simplify the client experience without giving up Traffic Manager routing intelligence, monitoring, or failover.</p>

### Stop restricting the agent. Start restricting its environment.

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/stop-restricting-the-agent-start-restricting-its-environment/ba-p/4548726](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/stop-restricting-the-agent-start-restricting-its-environment/ba-p/4548726)
- **Published**: 2026-08-27 03:48:33
- **Fetched**: 2026-08-27 21:13:50

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Thanks to <a class="lia-mention lia-mention-user" href="">visagarwal​</a> for co-authoring this post. Cross-posted from: <a class="lia-external-url" href="https://commandline.microsoft.com/azure-sre-agent-restricting-environment-ai-safety/" rel="noopener" target="_blank">https://commandline.microsoft.com/azure-sre-agent-restricting-environment-ai-safety/</a></p>
<hr />
<p>&nbsp;</p>
<p><a href="https://azure.microsoft.com/en-us/products/sre-agent" rel="noopener" target="_blank">Azure SRE Agent</a> gives an LLM tools, a code execution environment, and access to production resources. The first question most people ask is: “How is that safe?”</p>
<p>The instinctive answer is to restrict the agent. Least-privileged scopes. Short-lived credentials. A human approval gate in front of anything that mutates state. All of that helps, and we do all of it.</p>
<p>But after a year in production, we learned that restriction is only half the answer. A useful agent needs the capability to reason, the authority to act, and the agency to carry work through to completion. It must gather evidence, choose between tools, and act on what it finds. The same authority that makes an agent useful is also what makes it risky.</p>
<p>Human review is the obvious mitigation, and it remains the right boundary for irreversible, high-consequence actions. But if every meaningful action requires approval, the human is still operating the system one click at a time. The agent hasn’t removed the operational burden; it has only changed the interface. Rather than simply restricting the agent, the design problem is figuring out how to make a much larger class of actions safe enough to execute autonomously.</p>
<p>So, we start from a harder assumption: the agent will eventually do the wrong thing—whether it’s talked into it by a poisoned log line or simply going wrong on its own. A prompt can tell the agent what it <em>should </em>do, but it can't guarantee what the agent <em>will </em>do. The same is true of controls implemented inside the environment the agent can inspect or influence. To the agent, a control within reach is just one tool call away from being bypassed.</p>
<p>The enterprise version of this problem is harder, because a shared agent serves readers, operators, and admins at once. “Can the agent do this?” splits into multiple questions: <em>Who is asking? What authority do they carry? What can the execution environment reach? Where do the credentials live while it runs?</em></p>
<p>But the safer platform isn’t the one with the most approval gates. To maximize safety, you need to move the controls outside the agent’s reach. Inside its execution environment, the agent stays fully capable. Outside it, the enforcement layer decides what the environment can reach, what authority each operation carries, and when a human enters the loop. Authority is issued per task and expires with it. Prohibited behavior isn’t discouraged; it fails to execute.</p>
<p>We rebuilt Azure SRE Agent around this model. What follows traces each boundary we introduced, the gap it exposed, and how moving enforcement out of the agent let us increase autonomy without treating safety as a matter of trust.&nbsp;</p>
<h2>Right intentions, unsafe outcomes</h2>
<p>Let’s start with where we got it wrong. The failures that changed our architecture weren’t clever attacks. They were normal agent behavior pointed at an environment that allowed the wrong outcome.</p>
<ul>
<li><strong>The agent issued itself a credential, bypassing its harness. </strong>During an early test of PR-creation flow, the agent’s short-lived GitHub token expired. It inspected its own source, reconstructed the OAuth device-code flow, and prompted a researcher to complete the login, then wrote the new access and refresh tokens to its filesystem for reuse. The harness was supposed to fetch credentials and determine what authority the agent received. Instead, the agent rebuilt that machinery from inside its runtime and replaced the system-provided credential with one it had acquired itself.</li>
<li><strong>It exfiltrated an image by trying to read it.</strong> Asked to interpret a screenshot in an alert payload, and lacking a vision tool, the agent found a free OCR service on the public internet, POSTed our test image to it, and read back the text. That’s a perfectly reasonable chain of thought—and it showed the possibility for customer data could be shipped to an unvetted third party and logged onto someone else’s server.</li>
<li><strong>It found a customer’s secret and memorized it.</strong> A credential was committed in a customer repo. The agent found it during an investigation, quoted it in its findings, and saved it to memory with a note never to use it. This was well-intentioned, but now the secret lived in an investigation summary and a memory store, neither of which is in anyone’s rotation playbook.</li>
<li><strong>It deallocated a VM on a pattern match.</strong> The agent was instructed to deallocate VMs after five safety checks. During one run, the logging service became unavailable after the third check. Instead of stopping, the agent matched the situation to a past memory where deallocation had been safe and deallocated anyway. Right authority, wrong action.</li>
</ul>
<p>None of these needed an adversary—that’s the point. An adversary just makes it all worse for free: every channel the agent reads can be written to by someone you don’t trust, and at the execution layer, a hallucinated command and an injected one are the same command. The <a href="https://www.microsoft.com/en-us/security/blog/2026/06/05/securing-ci-cd-in-agentic-world-claude-code-github-action-case/?utm_source=chatgpt.com" rel="noopener" target="_blank">recent public disclosure</a> of a coding agent steered into reading `/proc/self/environ` and finding a live API key is just the OCR story with malice added.</p>
<p>If you strip away the good intentions, there are three classes of attacks:</p>
<ul>
<li>Bypassing the harness itself</li>
<li>Exfiltrating sensitive information or secrets</li>
<li>Taking disruptive actions against production resources</li>
</ul>
<p>Underneath all four incidents is the same interaction pattern: the agent sits between things it reads and things it can act on. Every inbound channel can carry untrusted instructions. Every outbound channel can leak sensitive data or change production.</p>
<p>&nbsp;</p>
<img />
<p>That forced the shift:</p>
<blockquote>
<p>If the environment permits it, the agent will eventually do it—intentionally, maliciously, or by accident. <strong>The environment is the policy.</strong></p>
</blockquote>
<p>So, we moved the policy boundary outside the agent’s reach, converging on four enforcement layers that close the gaps.</p>
<p>&nbsp;</p>
<img />
<p class="lia-clear-both">&nbsp;</p>
<h2>1. Sandboxing: Get execution out of the trust boundary</h2>
<p>Like many agents, our first design ran the harness itself, model-authored code, tools, and credentials together on the same machine—a pattern inherited from coding assistants. The harness is the control plane: it drives the loop, enforces policy, registers tools, and fetches credentials. Every path from the agent to the rest of the platform runs through it. That works better when there’s a human in the loop. Autonomous agents keep the layout but lose that immediate oversight, leaving model-authored code with the host’s network, filesystem, and identity.</p>
<p>The GitHub incident was possible because the harness sat on a filesystem the agent could read: when the agent’s token expired, it pulled the OAuth flow out of the harness’s own source and ran it itself. Better in-process checks wouldn’t have closed the gap: a policy hook can inspect a command before it runs, but the agent can inspect the hook right back - modify it, kill it, route around it. The code being governed can interfere with the machinery governing it.</p>
<img />
<p>Co-residency cut the&nbsp;other way, too: model-authored code had the host’s network. The OCR incident was possible because nothing stood between the agent deciding to send customer data and the request leaving the machine. The prompt said not to. The network still allowed it. The same co-residency also puts platform secrets within reach, often one file read away in places like /proc/self/environ from model-authored code, injected or not.</p>
<p>&nbsp;</p>
<p>So, we split the system into two. Agent reasoning and orchestration stay in a trusted runtime. Model-authored code and tools run in a per-agent microVM, connected back to the runtime over a narrow API surface. Inside the VM, the agent keeps full control: inspect files, launch processes, install packages. The agent can’t touch the machinery governing it—provisioning, tool mounting, policy, credential flows—none of which shares its filesystem. Platform secrets stay outside it, and egress is default-deny at a boundary the model can’t modify. The agent may still attempt the OCR call; it simply can’t leave.</p>
<p>We chose microVMs—built on <a href="https://sandboxes.azure.com/docs/sandboxes" rel="noopener" target="_blank">ACA Sandboxes</a>—over containers because containers share the host kernel. For arbitrary model-authored code, we wanted each agent to have its own kernel behind a hardware-virtualized boundary without sacrificing interactive startup times.</p>
<p>But isolation leaves a gap: tools still need to authenticate. Put credentials inside a microVM, and they become accessible to everything running there, including model-authored code, dependencies, and local MCP servers.</p>
<p>&nbsp;</p>
<blockquote>
<p>The sandbox needs to use credentials without possessing them.</p>
</blockquote>
<h2>2. Nothing worth stealing</h2>
<p>Isolation moved platform secrets out of the runtime into the tool execution sandbox. But tools still need to authenticate. az needs an Azure token. git needs repository access. kubectl, MCP servers, and package registries need credentials of their own.</p>
<p>Put those credentials inside the microVM, and it’s still a credential-bearing environment. Every tool, generated script, dependency, and local MCP server runs beside the agent’s working identity.</p>
<p>Egress allowlists aren’t enough. The destinations a stolen credential would be sent to are often the same ones the agent must reach. GitHub, Azure, Kubernetes, and registries must all remain accessible.</p>
<p>So we adopted a stronger rule:</p>
<p>The sandbox can use credentials, but it can’t possess them.</p>
<p>We did not rewrite git, az, kubectl, or existing SDKs. They still request authentication through their normal paths but receive an opaque handle instead of a real credential. The handle is useless outside the egress proxy that transforms it.</p>
<p>&nbsp;</p>
<img />
<p>The proxy does the real exchange at the boundary. Each handle is valid for exactly one tool call, one destination, one operation, and one use:</p>
<ul>
<li><strong>Call-bound:</strong> Valid only for the active tool call—the git push that requested it, not the rest of the session.</li>
<li><strong>Destination-locked:</strong> Usable only for the endpoint authorized for that call. A handle for github.com/organizationA/repoB does not get filled for repoC, a public gist, or any other GitHub path.</li>
<li><strong>Scope-limited:</strong> Restricted to the approved operation. A handle for pushing one branch is not repo-admin auth.</li>
<li><strong>Single use:</strong> Dead once the request is completed. Replay doesn’t produce another credential.</li>
</ul>
<p>Only after those checks pass does the proxy inject a short-lived credential into the outbound request. The credential never enters the VM’s filesystem, environment, process memory, tool output, model context, logs, or memory.</p>
<p>This closes the failure mode from our GitHub incident. An expired token no longer gives the agent an opportunity to reconstruct OAuth, capture refresh credentials, and turn its sandbox into a credential store. Credential issuance and refresh terminate outside the VM.<strong> </strong></p>
<p>But authentication credentials are only one class of sensitive data. A legitimate tool call can return secrets as data: az command can retrieve a key or connection string, just as a repository, configuration file, or log can contain passwords, tokens, or keys as ordinary text. In those cases, the secret can still enter the sandbox as part of the requested operation.</p>
<p>That was our memorized secret incident. The agent found a customer credential during an investigation, quoted it in its findings, and saved it to memory with a note never to use it. But the ordering was already wrong: once the value had entered model context, a note not to use it couldn't undo the exposure. The secret had already propagated into memory, sub-agents, and investigation notes.</p>
<p>This requires a second boundary, which we are piloting internally: inspecting and scrubbing sensitive tool output before it enters model context.</p>
<p>The rules are simple:</p>
<blockquote>
<p><em>Real credentials never enter the sandbox. Raw secrets never enter the model.</em></p>
</blockquote>
<p>At this point, the agent can authenticate without acquiring durable credentials and investigate without ingesting recognized secrets. But neither guarantee prevents an authorized action from being wrong.</p>
<h2>3. Authority without blanket approval</h2>
<p>Secretless authentication determines how the agent reaches production systems—but not which production effects may proceed unattended.</p>
<p>The VM incident exposed that gap. The agent didn’t steal a token, bypass egress, or leak data. It used a valid path to take a production action, but the action was wrong. When its safety checks became unavailable mid-run, it should have stopped and escalated. Instead, it matched the situation to a past trajectory and deallocated the VM—through a path the approval policy never intercepted.</p>
<p>That’s the other half of agent safety: not whether the agent <em>can</em> perform an operation, but whether it <em>should</em> perform this operation, now, against this target, given this evidence.</p>
<p>Our current production boundary is simple: every mutation requires human approval. Reads stay autonomous, writes wait for approval, deletes are blocked. It’s safe, but it treats every change alike. The hard cases sit in between - restart this instance, scale this service, drain this node, deallocate this VM. No policy can classify these from the command alone. The same operation is routine or catastrophic depending on three inputs:</p>
<ul>
<li><strong>The operation:</strong> Restart vs. deallocate.</li>
<li><strong>The target:</strong> A disposable test VM vs. a critical production dependency.</li>
<li><strong>The evidence:</strong> A proven-unresponsive host vs. a missing or hallucinated check.</li>
</ul>
<p>Anthropic’s <a href="https://www.anthropic.com/engineering/claude-code-auto-mode" rel="noopener" target="_blank">Claude Code auto mode</a> and <a href="https://atscaleconference.com/metas-journey-to-safely-unleash-agents-at-scale/" rel="noopener" target="_blank">Meta’s agent guardrails</a> point in the same direction: classify each action before letting it run unattended. So, we treat approval as a risk-classification problem rather than a permission check. Before execution, an independent guard - outside the agent's reasoning loop - scores the proposed action against all three inputs: what it does, what it touches, and whether the evidence behind it is current and corroborated. Low-risk actions with current evidence proceed. Critical targets, or actions with insufficient evidence, stop for review.</p>
<p>We’re still building this layer out, and it’s where our design is least settled. But it already unlocks event-driven operation: an incident, a failed deployment, or a scheduled task can start an investigation with no human in the chat. The agent gathers evidence, takes the actions classified as low-risk, and pauses exactly where the remaining authority requires a person.</p>
<blockquote>
<p>The unit of approval is not the command. It’s the operation, its target, and its evidence.</p>
</blockquote>
<p>Everything above assumes the agent is acting autonomously. But when a human enters the loop, it acts on behalf of that person—and with the agent being a shared team resource, the question shifts from, “Is this action safe?” to, “Is this user allowed to cause this action?” That’s the next boundary.</p>
<h2>4. Nothing to borrow</h2>
<p>The previous layer decides whether an action is safe enough for the agent to perform unattended. A shared agent can’t answer that question with one sandbox, one tool set, one memory, and one identity for everyone. Doing so creates a confused deputy: a low-privilege user can borrow capabilities they don’t hold directly or modify shared state that influences a more privileged session later.</p>
<p>Shared memory makes the problem concrete. A user can teach the agent behavior that persists beyond that user’s authority. The same path exists through connectors, skills, hooks, and other shared configurations. The agent can’t be expected to remember which parts each user may influence.</p>
<p>The caller’s role must shape the environment before reasoning begins. Readers can observe but not drive the agent. Users can chat without modifying shared behavior. Operators can manage shared surfaces without approving high-privilege actions. Administrators can explicitly approve or delegate that authority.</p>
<p>These roles aren’t prompt instructions. They determine which tools and MCP servers are mounted, which resources the sandbox can reach, which memory is visible or writable, which credentials may be injected, and which actions require approval.</p>
<p>The rule is monotonic: the caller’s authority may be narrowed by the environment, but it must never be widened by the agent. A low-privilege request can’t be laundered through shared memory, a shared connector, an alternate tool path, or a high-privilege service identity.</p>
<p>The agent has nothing to borrow because there is no ambient authority outside the caller’s delegation chain. Rather than something the model remembers, policy is the environment instant for that user.</p>
<h2>Autonomy through constraint</h2>
<p>Model guardrails matter, but production safety can’t depend on them working every time. We already accept this with people: no one hands an operator root and promises to be careful. We give them scoped identities, just-in-time access, network boundaries, change control, and audit trails. Judgment is the first line of defense—never the only one.</p>
<p>Agents need the same backstops at a different cadence. An agent can make hundreds of tools calls in a single incident, replan between any two of them, and reach the same effect through three different tools. Approve every step and autonomy disappears; approve only the plan and everything after it runs unchecked. So, the question was never whether to keep policy gates. Instead, the question was where to put them: at runtime, as close as possible to each production effect, with human review reserved for the consequences the system can’t bound on its own.</p>
<p>That's what the four layers are: one move, repeated. We opened with the questions a shared agent forces: Who is asking? What authority do they carry? What can the environment reach? Where do the credentials live? Each layer answers one of those questions in the runtime instead of the prompt.</p>
<p>Across the four layers, the design principles are the same:</p>
<ul>
<li>Enforce constraints outside the agent’s access</li>
<li>Prefer deterministic enforcement over model judgment</li>
<li>Define invariants that hold even as architecture evolves</li>
</ul>
<h3>Where it still breaks</h3>
<p><strong><br /></strong>The system isn't complete, and we still discover gaps in our enforcement layers. Examples of gaps we closed recently: an action blocked through one tool could still be reached through a different execution channel that bypassed hooks. In another case, an MCP server could silently widen its contract after onboarding, and the protocol had no mechanism to detect the change.</p>
<p>As these gaps surface, we improve our implementation. But our security principles stay invariant:</p>
<img />
<p class="lia-clear-both">&nbsp;</p>
<p>Better models will make mistakes rarer. They won’t shrink the blast radius when a mistake still happens. A smarter model shifts where the line falls between autonomous action and human review—more actions cleared as low-risk, more investigations that run start to finish without a human in the chat. But that line is drawn by the controls, not by the model. What microVM can reach, where credentials live, whose authority a session carries.</p>
<h3>Five questions for agent platform builders</h3>
<p>The four incidents ultimately changed the questions we asked in review:</p>
<ul>
<li>Can the agent inspect, modify, or bypass the machinery that provisions its tools, identity, policy, or credentials?</li>
<li>Can the same effect be reached through another tool or execution path that avoids the intended control?</li>
<li>Through which paths can sensitive data enter the agent-controlled environment or leave the system?</li>
<li>For every consequential effect, can the platform identify who asked, what it did, what it touched, what data it carried, what evidence supported it, and whose authority it ran under?</li>
<li>When evidence is missing, stale, or ambiguous, does the operation reliably leave the autonomous path?</li>
</ul>
<p><br />If the answer to any of those questions was “no,” we weren’t running a guarded agent. These are questions worth asking of any agent platform, including our own.</p>
<p>That’s what we mean when we say: <strong><em>The environment is the policy.</em></strong></p>

<h3>When do AI agents need a browser</h3>
<p>Enterprise AI agents are becoming increasingly capable of reasoning over data, calling APIs, and orchestrating workflows. Yet many business-critical systems still expose functionality only through a web interface. ERP systems, supplier portals, internal applications, dashboards, legacy enterprise systems or any other web application that may have incomplete, incompatible or no API support will require users to interact through a browser.</p>
<p>This creates a challenge for agent builders: how can an AI agent complete workflows when the only interface available is a web page?<br />Azure AI Foundry's <a href="https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/browser-automation-hosted-agent-quickstart?pivots=python" rel="noopener" target="_blank">Browser Automation Tool</a> (BAT) addresses this challenge by giving agents the ability to navigate websites, interact with UI elements, extract information, and complete multi-step browser workflows using cloud-hosted browser sessions (powered by <a href="https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/overview-what-is-microsoft-playwright-workspaces" rel="noopener" target="_blank">Playwright Workspaces</a>).</p>
<h3>The authentication challenge</h3>
<p>When humans hear a request like “Log into the supplier portal and download today’s invoice report,” it sounds simple. For an AI agent operating a browser, while the browser automation is often the easy part, there are challenges associated with authentication.</p>
<p>Many enterprise applications rely on modern identity controls such as multi-factor authentication (MFA), conditional access policies, device compliance checks, single sign-on (SSO), and identity federation. These mechanisms are designed for human users and trusted devices, not autonomous agents. The challenge becomes even greater when the agent runs in a cloud-hosted browser session rather than on a user’s local machine. In these environments, credentials, session tokens, cookies, and authentication artifacts must be protected from unauthorized access while still being available to the agent when needed. As a result, AI agents must navigate a complex balance between usability and security, privacy, and compliance considerations that go far beyond clicking buttons on a webpage.</p>
<p>Real-world scenarios where agents need authenticated browser access:</p>
<ul>
<li>Accessing supplier and procurement portals that require SSO or MFA authentication.</li>
<li>Updating records in legacy business applications that are only available through authenticated web interfaces.</li>
<li>Reconciling customer data across CRM, billing, and compliance systems behind enterprise login.</li>
<li>Executing procurement, approval, and invoice processing workflows requiring user authorization.</li>
<li>Completing multi-step enterprise workflows across multiple authenticated web systems.</li>
</ul>
<p>Ultimately, enabling secure browser automation is not just a browser problem, it is an identity problem. The success of AI agents in enterprise environments depends on providing secure, governed ways to authenticate, manage sessions, and access protected resources while maintaining the security guarantees organizations expect from their identity infrastructure. From this perspective, authentication is often the most critical and technically challenging component of deploying AI-powered browser agents at scale.</p>
<p>This is where the Browser Automation Tool (BAT) inside Azure AI Foundry Toolbox becomes incredibly powerful.</p>
<h3>What’s covered in this blog</h3>
<p>In this article, we'll explore how you can build agents capable of securely interacting with authenticated websites while maintaining enterprise-grade security controls by combining:</p>
<ul>
<li>Azure AI Foundry Hosted Agents</li>
<li>Toolbox</li>
<li>Browser Automation Tool</li>
<li>Playwright Workspaces</li>
<li>Azure Key Vault</li>
</ul>
<p>We’ll look at how these different building blocks work together to build a secure authenticated browser workflow.</p>
<h2>Understanding the Architecture</h2>
<p>Before diving into implementation details, let's understand the key technologies that are used.</p>
<h3>Azure AI Foundry Hosted Agents</h3>
<p><a href="https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents" rel="noopener" target="_blank">Hosted Agents</a> are containerized applications managed by Azure AI Foundry that provide managed deployment, built-in scaling, session management, observability, secure execution environments, Azure AI model integration, and tool-calling capabilities. They are best suited for solutions requiring custom business logic, external integrations, stateful workflows, enterprise security controls, and custom tool orchestration, allowing developers to focus on application development while Azure AI Foundry manages the underlying infrastructure and runtime environment.</p>
<h3>Toolbox</h3>
<p><a href="https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/toolbox-overview" rel="noopener" target="_blank">Toolbox</a> provides a centralized way to manage and share tools across agents by allowing teams to configure tools once, publish them centrally, and reuse them across multiple agents. Through a unified MCP-compatible endpoint, Toolbox simplifies tool discovery, governance, authentication, and lifecycle management. This approach delivers consistent authentication, improved reusability across projects, centralized administration, and reduced operational complexity, enabling organizations to scale agent development while maintaining security and governance standards.</p>
<h3>Browser Automation Tool</h3>
<p><a href="https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/browser-automation-hosted-agent-quickstart?pivots=python" rel="noopener" target="_blank">Browser Automation Tool (BAT)</a> is a built-in tool in Azure AI Foundry that enables agents to navigate websites, fill forms, click buttons, extract information, complete end-to-end workflows, and interact with dynamic web applications. BAT executes the automation using cloud hosted browsers powered by Playwright Workspaces. BAT provides enterprise-ready capabilities such as live view, take control, observability and governance, private website access, and MCP-based integration through Toolbox, enabling secure, scalable, and governed browser automation for AI agents.</p>
<h3>Playwright Workspaces</h3>
<p>The cloud-hosted browsers in Browser Automation Tool are powered by <a href="https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/overview-what-is-microsoft-playwright-workspaces" rel="noopener" target="_blank">Playwright Workspaces</a>, providing managed browser infrastructure, isolated browser sessions, cloud execution, observability into browser activity, and support for private websites. Each automation task runs in its own isolated browser session, ensuring strong separation between workflows and preventing unintended data sharing, while enabling secure, scalable, and enterprise-ready browser automation in Azure-managed infrastructure.</p>
<h3>Azure Key Vault</h3>
<p><a href="https://learn.microsoft.com/en-us/azure/key-vault/general/basic-concepts" rel="noopener" target="_blank">Azure Key Vault</a> provides secure credential management by serving as the trusted source for all authentication secrets. It offers secret storage, fine-grained access control, auditing, automatic secret rotation, encryption, and Azure RBAC integration, enabling organizations to securely manage credentials for websites and applications while maintaining governance, compliance, and operational security across workflows.</p>
<img />
<h2>When Should You Use Azure Key Vault?</h2>
<p>Many customers immediately assume every browser automation workflow that requires authentication needs to go through Azure Key Vault. That isn't always true.</p>
<p>Use Azure Key Vault when browser automation requires secrets such as:</p>
<ul>
<li>Username/password credentials</li>
<li>API keys</li>
<li>Service account credentials</li>
<li>Database connection strings</li>
<li>OAuth client secrets</li>
<li>Certificates</li>
</ul>
<p>Scenarios where Key Vault acts as the system of record for credentials:</p>
<ul>
<li>Logging into a supplier portal</li>
<li>Accessing a partner dashboard</li>
<li>Downloading reports from a third-party system</li>
<li>Accessing legacy web applications</li>
<li>Using service account credentials for automation</li>
</ul>
<p>There are several situations where passwords should not be stored at all. For example, Microsoft Entra ID Protected Applications. These types of applications prefer managed identities, agent identities, OAuth, On-Behalf-Of (OBO) instead of storing user passwords. Hosted Agents receive a dedicated Microsoft Entra agent identity that can authenticate to downstream services and Azure resources.</p>
<p>Examples include:</p>
<ul>
<li>Applications using Entra authentication</li>
<li>Azure resources</li>
<li>Microsoft Graph</li>
</ul>
<h2>Scenario: Username and Password Authentication</h2>
<p>Many external systems still rely on traditional credentials. For these systems, Key Vault becomes extremely valuable. A secure workflow typically looks like this:</p>
<ol>
<li>Store credentials in Azure Key Vault.</li>
<li>Grant the Hosted Agent access to Key Vault using RBAC.</li>
<li>Launch the browser workflow.</li>
<li>Retrieve secrets when needed.</li>
<li>End the session.</li>
</ol>
<h2>Recommended Credential Flow</h2>
<img />
<h3>Step 1: Store credentials in Azure Key Vault</h3>
<p>The foundation of a secure credential strategy is centralized secret management. Usernames, passwords, API keys, and other authentication secrets should be stored in Azure Key Vault rather than embedded in code, prompts, or agent configurations. This provides a single-governed location for managing credentials while supporting secret rotation and auditing.</p>
<p>Example:</p>
supplier-portal-username
supplier-portal-password
<h3>Step 2: Grant the Hosted Agent Access Through RBAC</h3>
<p>Once secrets are stored securely, the hosted agent must be granted permission to retrieve them. Azure role-based access control (RBAC) should be used to assign the minimum permissions required. In most cases, the “Key Vault Secrets User” role provides sufficient access, allowing the agent to read secrets without granting broader administrative permissions.</p>
<h3>Step 3: Retrieve Secrets Only When Needed</h3>
<p>Credentials should be accessed on a just-in-time basis. Rather than caching secrets for extended periods, agents should retrieve them immediately before authentication occurs. Organizations should avoid long-lived credential storage, logging secret values, or embedding credentials in prompts and workflow definitions. This approach minimizes exposure and aligns with least-privilege security practices.</p>
<p>Example:</p>
credential = DefaultAzureCredential()

secret_client = SecretClient(
               vault_url=vault_url,
               credential=credential
)

username = secret_client.get_secret(
               "supplier-username"
).value
<h3>Step 4: Launch the Browser Workflow and Authenticate</h3>
<p>With credentials available, the agent can start its browser workflow. The agent opens an isolated browser session, navigates to the target application, reaches the authentication page, and supplies the required credentials to establish access. Authentication becomes a controlled part of the workflow rather than a manually managed step.</p>
<h3>Step 5: Execute the Intended Business Task</h3>
<p>After authentication is complete, the agent performs only the business action it was authorized to execute. Depending on the scenario, this may involve downloading reports, validating information across systems, extracting data from portals, reconciling records, or submitting approved forms. Restricting the agent's scope helps maintain security, predictability, and auditability.</p>
<h3>Step 6: End the Session and Dispose of State</h3>
<p>When the workflow finishes, the browser session should be terminated and temporary runtime state removed. Disposing of the session reduces the persistence footprint of sensitive information and helps ensure credentials are not retained longer than necessary. The result is a secure, governed authentication lifecycle from secret retrieval through task completion.</p>
<h2>Understanding Secret Flow</h2>
<p>One of the most frequently asked questions is: “Does the LLM have access to my credentials?”</p>
<p>The answer depends entirely on how your application is implemented.</p>
<p>Using the architecture shown in the previous section,</p>
<ul>
<li>Key Vault stores credentials.</li>
<li>Hosted Agent code retrieves credentials.</li>
<li>Browser Automation Tool uses credentials.</li>
<li>The LLM never needs to reason about or manipulate passwords.</li>
</ul>
<p>The model should never need visibility into credentials. The secret handling occurs inside application code. Only the result of the action is returned to the model.</p>
<h2>Security Best Practices</h2>
<ul>
<li><strong>Managed Identity:</strong> Use managed identities whenever possible. Avoid designs where secrets are injected into prompts</li>
<li><strong>Apply the least privilege</strong>: Grant only the minimum permissions required.</li>
<li><strong>Rotate Secrets: </strong>Treat credentials as temporary assets by enforcing regular rotation, monitoring expiration dates, and automating renewal processes wherever possible.</li>
<li><strong>Audit Everything:</strong> Enable Key Vault logging, Azure Monitor, and Activity Logs to maintain end-to-end visibility and auditing of all authenticated agent actions.</li>
<li><strong>Limit Target Sites:</strong> Restrict automation to approved domains only to reduce the risk of prompt injection, malicious websites, and credential theft.</li>
<li><strong>Require Human Approval:</strong> Enforce human approval for sensitive actions such as financial transactions, and administrative operations to ensure agents do not act autonomously in high-risk scenarios.</li>
</ul>
<h2>Conclusion</h2>
<p>Browser automation is easy. Secure browser automation is the real challenge.</p>
<p>By treating Azure Key Vault as the system of record for credentials, leveraging managed identities wherever possible, and using Browser Automation Tool as the execution layer, you can build authenticated browser workflows that balance productivity with security.</p>
<p>As more enterprise systems continue to rely on web interfaces, this pattern will become an increasingly important building block for the next generation of AI-powered agents.</p>
