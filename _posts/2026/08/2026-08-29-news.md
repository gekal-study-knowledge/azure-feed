<h1>Introduction</h1>
<p>Large Azure hub-and-spoke environments can advertise a significant number of routes toward on-premises networks. By default, Azure VPN Gateway and ExpressRoute Gateway advertise the address spaces of the hub virtual network and the address spaces of peered spoke virtual networks that use gateway transit. As the number of spokes and address spaces grows, the border gateway protocol (BGP) route table grows as well.</p>
<p>Advertised gateway prefixes provide a native way to summarize those Azure-side routes. The feature is configured on the hub virtual network through the <strong>summarizedGatewayPrefixes</strong> property, which is exposed in the Azure portal as <strong>Advertised gateway prefixes</strong>.</p>

<p class="lia-align-center"><strong>Fewer BGP prefixes</strong></p>
<p class="lia-align-center">Replace many individual networks with one or more aggregated CIDRs.</p>
</td><td>
<p class="lia-align-center"><strong>Better scale management</strong></p>
<p class="lia-align-center">Help large hub-and-spoke designs stay within advertised-prefix limits.</p>
</td><td>
<p class="lia-align-center"><strong>Cleaner route visibility</strong></p>
<p class="lia-align-center">Make the intended Azure address plan easier to recognize on provider and on-premises route views.</p>
</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>In this blog we will demonstrate leveraging Advertised gateway prefixes to summarize many Azure advertised prefixes into one.&nbsp;&nbsp;</p>
<h1>What are advertised gateway prefixes?</h1>
<p>Advertised gateway prefixes are summarized CIDR blocks that an Azure hybrid gateway advertises toward on-premises instead of advertising every covered hub and spoke address space individually. The configuration belongs on the gateway virtual network, usually the hub VNet that contains GatewaySubnet and the ExpressRoute or VPN gateway.</p>

<h1>When should you use it?</h1>
<ul>
<li>You use a hub-and-spoke topology with gateway transit and many spoke address spaces.</li>
<li>You want to advertise a covering prefix, such as a /16, instead of many smaller prefixes, such as multiple /24 networks.</li>
<li>You are approaching ExpressRoute advertised-prefix limits or want to reduce route-table growth before scale becomes a problem.</li>
<li>Your Azure address plan is sufficiently structured to create safe, intentional summary ranges.</li>
</ul>
<p>&nbsp;</p>
<p class="lia-align-left"><strong>Note:</strong> ExpressRoute scale context: Microsoft documentation lists a maximum of 1,000 IPv4 prefixes and 100 IPv6 prefixes advertised from a virtual network to on-premises on a single ExpressRoute connection through private peering. Exceeding the connection prefix limit can cause the connection between the circuit and gateway to disconnect until the prefix count is reduced.</p>
<h1>Prerequisites</h1>
<ul>
<li>A hub virtual network with GatewaySubnet.</li>
<li>An ExpressRoute gateway or VPN gateway deployed in the hub virtual network.</li>
<li>One or more peered spoke virtual networks if you want to demonstrate route summarization across spokes.</li>
<li>A planned IPv4 and, when applicable, IPv6 summary that covers the intended hub and spoke address spaces.</li>
<li>Access to the provider or on-premises BGP route view for validation. In this walkthrough, Megaport is used as the external verification point.</li>
</ul>

<h1>Important design considerations</h1>
<p><strong>Configure the hub, not the spokes: </strong>Only the virtual network containing the gateway subnet uses the summarizedGatewayPrefixes property for this behavior. A value placed on a spoke VNet is ignored.</p>
<p><strong>Avoid overlap within the prefix list:&nbsp;</strong>Do not configure overlapping entries in the advertised gateway prefixes list.</p>
<p><strong>Expect uncovered networks to remain visible: </strong>If a hub or spoke address space is not covered by a configured summary, the gateway continues to advertise it individually.</p>
<p><strong>Plan dual-stack explicitly: </strong>IPv4 and IPv6 summaries must be added separately.</p>
<p><strong>Removing all entries restores default behavior: </strong>When every advertised gateway prefix is removed, Azure returns to advertising hub and peered spoke address spaces individually.</p>
<p><strong>Protect the on-premises edge: </strong>Use appropriate route policies so only expected prefixes are accepted. Summarization simplifies advertisements, but it does not replace routing governance.</p>
<h1>Conclusion</h1>
<p>Advertised gateway prefixes give Azure networking teams a straightforward, native method to control route scale from a gateway-enabled hub VNet. Instead of sending every hub and spoke prefix across ExpressRoute or VPN connections, the gateway can advertise a concise list of summarized prefixes. The result is a smaller and more intentional route advertisement, while uncovered address spaces remain visible for compatibility.</p>
