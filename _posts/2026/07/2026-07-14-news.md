<h2 id="from-clicking-to-conversing-architecture-chat">From clicking to conversing: Architecture Chat</h2>
<p>The single most common request after the launch post was some version of <em>“I love the first diagram, but I want to iterate without re-writing the whole prompt.”</em> Regenerating from scratch every time you tweak a requirement is slow and loses context.</p>
<p><strong>Architecture Chat</strong> solves this. It’s a conversational panel that sits alongside the canvas and treats your diagram as a living document. Each message is a turn in an ongoing design session:</p>
<ul>
<li><em>“Add an Azure Front Door with WAF in front of the app tier.”</em></li>
<li><em>“Now make the data layer zone-redundant.”</em></li>
<li><em>“Swap the SQL Database for Cosmos DB and update the connections.”</em></li>
</ul>
<p>Every turn reads the <strong>current state of the canvas</strong> — not the original prompt — so refinements compound naturally the way they would with a human architect at a whiteboard. The conversation auto-saves to history, so you can step back through the evolution of a design or branch from an earlier point.</p>
<figure><br />
<figcaption>Architecture Chat panel beside the canvas, showing a multi-turn conversation that incrementally adds and modifies services on the diagram.</figcaption>
</figure>
<img />
<blockquote>
<p><strong>Figure 1.</strong> Architecture Chat treats the diagram as a living document. Each message refines the current canvas — adding services, changing SKUs, or reorganizing groups — and the full exchange is saved to history.</p>
</blockquote>
<p>The shift is subtle but important: architecture design stops being a one-shot prompt and becomes an <strong>iterative dialogue</strong>.</p>
<hr />
<h2 id="the-whiteboard-deliverable-blueprint-diagrams-beta">The whiteboard deliverable: Blueprint Diagrams (BETA)</h2>
<p>Formal topology diagrams with official Azure icons are perfect for documentation and stakeholder decks. But early-stage design conversations often want something looser — the hand-drawn feel of a whiteboard sketch that communicates intent without implying finality.</p>
<p><strong>Blueprint Diagrams</strong> generate exactly that: a whiteboard-style render with nested zones (subscription → VNet → subnet), numbered flow arrows, and a deliberately sketchy aesthetic. You choose the output mode:</p>
<ul>
<li><strong>Topology</strong> — the formal, icon-based diagram from the launch post</li>
<li><strong>Blueprint</strong> — the hand-drawn whiteboard style</li>
<li><strong>Both</strong> — generate the two side by side</li>
</ul>
<figure><br />
<figcaption>The formal topology diagram of an architecture shown next to a Blueprint-style hand-drawn version of the same design with nested zones and numbered flow arrows.</figcaption>
</figure>
<img />

<p><strong>Figure 2.</strong> The same architecture in two visual languages. <strong>Left:</strong> the formal, icon-based topology. <strong>Right:</strong> Blueprint mode — a whiteboard-style render with nested zones and numbered flow steps, plus a numbered legend explaining each hop. Use Blueprint for early design conversations and Topology for final documentation.</p>
</blockquote>
<p>It’s the same underlying architecture — two visual languages for two different moments in the design lifecycle.</p>

<h2 id="a-fleet-of-13-models-pick-the-right-brain-per-task">A fleet of 14 models: pick the right brain per task</h2>
<p>The launch post shipped with multi-model support. That fleet has grown to <strong>13 models across five providers</strong>, so you can match the model to the job — fast models for iteration, reasoning models for complex designs, code-optimized models for Bicep generation:</p>
<ul>
<li><strong>OpenAI GPT-5.x</strong> — GPT-5.1, GPT-5.2, GPT-5.6 Sol, Terra and Luna, GPT-5.4, GPT-5.4 Mini</li>
<li><strong>DeepSeek</strong> — V3.2 Speciale, V4 Pro</li>
<li><strong>xAI Grok</strong> — 4.1 Fast, 4.3</li>
<li><strong>Mistral</strong> — Large 3</li>
<li><strong>MoonshotAI Kimi</strong> — K2.5, K2.7 Code</li>
</ul>
<p>The <strong>Compare Models</strong> feature runs the same prompt through any subset of these in parallel and ranks them on service count, token usage, latency, and cost — with <em>Fastest / Cheapest / Most Thorough</em> badges — so you can make an evidence-based choice rather than a guess.</p>

<h2 id="the-headline-the-diagram-builder-is-now-an-mcp-server">The headline: the Diagram Builder is now an MCP server</h2>
<p>Here’s the change that reframes the project. Everything above is about a <em>person</em> using a <em>web app</em>. But the same capabilities — generating a diagram, validating it against WAF, estimating its cost, producing Bicep — are exactly the things an <strong>AI agent</strong> needs when it reasons about Azure architecture.</p>
<p>So we exposed them. The Azure Architecture Diagram Builder now runs as a <strong>Model Context Protocol (MCP) server</strong>. Any MCP-capable agent can call its tools with typed inputs and structured outputs:</p>

<p><strong>What the agent gets</strong></p>
</th></tr></thead><tbody><tr style="height: 35.434px;"><td style="height: 35.434px;"><code>list_services</code></td><td>
<p>The catalog of supported Azure services and categories</p>
</td></tr><tr style="height: 35.434px;"><td style="height: 35.434px;"><code>validate_architecture</code></td><td>
<p>A WAF assessment with pillar scores and findings</p>
</td></tr><tr style="height: 59.1146px;"><td style="height: 59.1146px;"><code>estimate_costs</code></td><td>
<p>Multi-region cost estimates from the Azure Retail Prices API</p>
</td></tr><tr style="height: 35.434px;"><td style="height: 35.434px;"><code>generate_bicep</code></td><td>

<p><strong>This means an agent can hold a conversation like <em>“design a HIPAA-compliant platform, check it against the Well-Architected Framework, tell me the monthly cost in West Europe, and give me the Bicep”</em> — and the Diagram Builder answers each part programmatically, returning structured data the agent can reason over and chain.</strong></p>

<h2 id="grounded-in-microsoft-learn-and-sharper-output">Grounded in Microsoft Learn, and sharper output</h2>
<p>Two smaller-but-meaningful improvements round out the release:</p>
<ul>
<li><strong>Microsoft Learn grounding.</strong> Deployment guides now search official <a href="https://learn.microsoft.com/" rel="noopener" target="_blank">Microsoft Learn</a> documentation at generation time and cite it, so the guidance reflects current, authoritative practice rather than a model’s training snapshot.</li>
<li><strong>Output enhancements (July 2026).</strong> Rendered diagrams now carry per-service <strong>cost badges</strong>, support <strong>light and dark render themes</strong>, and include <strong>metadata panels</strong> that summarize the architecture — service counts, regions, and estimated cost — directly on the image.</li>
</ul>

<h2 id="highlights">Highlights</h2>
<p>Since the May launch, the Azure Architecture Diagram Builder has grown from a design tool into an agent-ready platform:</p>
<ul>
<li><strong>Conversational design</strong>: iterate on a diagram by chatting over the live canvas, with full history</li>
<li><strong>Two visual languages</strong>: formal topology and hand-drawn Blueprint, from the same architecture</li>
<li><strong>13 models, five providers</strong>: choose the right brain per task, with evidence-based comparison</li>
<li><strong>Agent-ready</strong>: an MCP server exposing generation, validation, costing, and IaC as callable tools</li>
<li><strong>Grounded guidance</strong>: deployment guides cite live Microsoft Learn documentation</li>
<li><strong>Still open source</strong>: every capability above is available to inspect, extend, and contribute to</li>
</ul>
