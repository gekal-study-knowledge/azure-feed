### Skill or Sub-Agent. Choosing AI Capabilities You Will Actually Reuse

- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><strong>Audience:</strong> Cloud architects, platform engineers, engineering leaders</p>
<hr />
<h2>The wrong first question</h2>
<p>Most teams building AI capabilities start with the wrong question. They ask which model to use.</p>
<p>The model matters less than the shape of the capability around it. The first real fork is this. Are you building a skill or a sub-agent? Get that wrong and no model choice will save you. A skill and a sub-agent are two different delivery shapes, and each one fails at the other one's job.</p>
<h2>The insight</h2>
<p>The choice between a skill and a sub-agent is not about model power. It comes down to four checks. How the work iterates, whether the output carries a voice, how far an early wrong turn spreads, and how often it recurs. Score each, count which way they lean, and the shape falls out. An even split means build both, and let the skill drive the sub-agent.</p>
<p>The three sections below take the checks worth a pause. Frequency is the plain one: a one-off craft piece leans to a skill, a repeatable batch job to a sub-agent.</p>
<p>A skill lives inside the conversation. It reads files, asks a question, refines with the author, and keeps a human in the loop mid-flight. A sub-agent takes one prompt, runs to completion, and returns one report. Both are useful, for different work.</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><tbody><tr><th>Dimension</th><th>Skill</th><th>Sub-agent</th></tr><tr><td>Iteration</td><td>Conversation, many turns</td><td>One hand-off, one pass</td></tr><tr><td>Voice</td><td>Holds a style profile and applies it</td><td>Drifts toward generic by design</td></tr><tr><td>Human gate</td><td>Every turn</td><td>Once, at the end</td></tr><tr><td>Best for</td><td>Craft, subjective output</td><td>Bounded, structured output</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p><em>Table 1. The same three dimensions decide the shape every time.</em></p>
<h2>1. Decide the iteration model first</h2>
<p>Before anything else, architects should ask how the work actually happens. Is it a conversation or a hand-off? That single answer removes most of the ambiguity.</p>
<ul>
<li>Craft work needs back and forth</li>
<li>Batch work needs one clean pass</li>
<li>Conversations need memory of the thread</li>
<li>Hand-offs need a bounded input and a clear output</li>
</ul>
<p>A skill is right when the value comes from iteration. A blog post, a design review, a tricky refactor. A sub-agent is right when the work is well defined and the output is the deliverable.</p>
<p><strong>In practice</strong></p>
<p>The pattern that works: use a skill when the team expects three or four rounds of "close, but change this". The trade-off: a skill costs more attention per run because a human stays involved. The trap to avoid: forcing iterative craft into a one-shot agent and then editing the output by hand every time.</p>
<h2>2. Voice fidelity decides craft work</h2>
<p>Some outputs have a voice. An article, a customer email, an architecture narrative. Others do not. A query result, a data export, a status summary. The line between them is not cosmetic. It decides which shape survives review.</p>
<ul>
<li>Voice-heavy work favours a skill</li>
<li>Voice-neutral work favours a sub-agent</li>
<li>Skills can hold a style profile and apply it</li>
<li>Sub-agents drift toward generic by design</li>
</ul>
<p>When the output carries a name, fidelity is the whole game. A capable model with no voice anchor produces text that reads like it came from a committee.</p>
<p><strong>In practice</strong></p>
<p>The pattern that works: give a skill an explicit voice profile with banned phrases and cadence rules. Let it self-check before it shows anyone anything. The trade-off: the profile takes real effort to write once. The trap to avoid: expecting a stateless agent to match a personal style from a single prompt.</p>
<h3>Implementation note</h3>
<p>A voice profile is not documentation. It lives in the skill definition, an executable contract the skill checks itself against before a draft is ever shown. A small profile goes a long way.</p>
# voice-profile (excerpt)
banned_phrases: [seamless, robust, game-changing, leverage the power]
forbid: [em-dash, semicolon, exclamation in body]
max_avg_sentence_words: 20
require:
  - one "In practice" block per section
  - a closing discussion question
self_check: run before any draft is shown to a human

<h2>3. Put the human gate where the risk is</h2>
<p>Every AI capability needs a human review gate. The design question is where that gate sits. Placement is the difference between catching a problem early and unpicking it later.</p>
<ul>
<li>Skills gate continuously, turn by turn</li>
<li>Sub-agents gate once, at the end</li>
<li>Continuous gates catch drift early</li>
<li>End gates are cheaper but riskier for craft</li>
</ul>
<p>If a wrong turn early corrupts everything after it, the team wants a skill. If the work is bounded and a bad output is easy to spot and discard, an end gate is fine.</p>
<p><strong>In practice</strong></p>
<p>The pattern that works: match the gate to the blast radius. High blast radius and subjective quality point to a skill. Low blast radius and objective output point to a sub-agent. The trap to avoid: a one-shot agent doing forty minutes of unattended work that a human then has to unpick.</p>
<h2>4. The pattern that scales is both</h2>
<p>The mature answer is not one or the other. It is a skill on top of a sub-agent. The two shapes compose cleanly when each one keeps to its own job.</p>
<ul>
<li>The skill orchestrates and holds the voice</li>
<li>The sub-agent executes bounded sub-tasks</li>
<li>The human reviews at the skill layer</li>
<li>Each layer does what it is good at</li>
</ul>
<img />
<p><em>Figure 1. In the combined pattern the human reviews at the skill layer, and the sub-agent only touches the bounded task.</em></p>
<p>The skill runs the conversation and keeps quality. When it needs a bounded, repeatable job done, it delegates to a sub-agent. The result is iteration where craft lives and automation where the work is mechanical.</p>
<p><strong>In practice</strong></p>
<p>The pattern that works: a skill drafts and refines an article with the author, and calls a sub-agent to fetch and summarise reference material. The trade-off: two layers are more to build than one. The trap to avoid: collapsing both into a single agent and losing either the voice or the automation.</p>
<h2>The operational trade-offs</h2>
<p>Shape is not only a design choice. It shows up in cost, latency, and how you debug a bad run. Architects should price these in before committing to a pattern.</p>
<ul>
<li>A skill spends more tokens and more human minutes per run</li>
<li>A sub-agent spends compute once and returns fast</li>
<li>A skill fails in small, visible steps you can correct</li>
<li>A sub-agent fails as one block you inspect after the fact</li>
</ul>
<p>The cost of a skill is attention. Someone stays in the loop and that time is real. The cost of a sub-agent is rework. When a one-shot run goes wrong, the whole output is suspect and someone redoes it. Observability follows the same split. A skill leaves a turn-by-turn trail you can read. A sub-agent leaves one input and one output. You instrument the boundary and log the prompt and the result. Pick the shape whose failure mode your team can afford. The wrong shape does not announce itself. It shows up later as a cost line or a rewrite.</p>
<h2>Two capabilities, one team</h2>
<blockquote>
<p>Consider a team standardising its engineering work with AI. Two capabilities land on the backlog in the same week. The first is recurring status queries. Well defined input, structured output, no voice. A stateless sub-agent fits. One prompt in, one report out, gate at the end. It works on day one and keeps working.</p>
<p>The second is authored technical content. Subjective, voice-heavy, many rounds of refinement. The reflex is to reuse the sub-agent that just shipped. That reflex is the mistake. The queries stay clean. The content reads flat and generic, and every draft needs a heavy human rewrite. Rebuilt as a skill with a voice profile and a turn-by-turn gate, the same work compounds instead of fighting back. Same team, same models, two different shapes of work, and only one right tool for each.</p>
</blockquote>
<h2>What teams get wrong</h2>
<p>The common pattern is defaulting to whichever shape the team built first. A team ships one sub-agent, likes it, and forces every new problem into a sub-agent. Or it builds one skill and runs everything as a conversation, including batch work that should be automated.</p>
<p>It looks like consistency. It feels like reuse. But it leads to craft work that reads generic and batch work that needs babysitting. The fix is not a better model. It is naming the shape of the work before picking the tool.</p>
<p>The three shapes to watch for in your own stack:</p>
<ul>
<li>A voiced deliverable coming out of a one-shot agent, rewritten by hand every run. A skill wearing a sub-agent costume.</li>
<li>A batch job run as a conversation and babysat turn by turn. A sub-agent wearing a skill costume.</li>
<li>A large workflow forced into one agent that holds neither the voice nor the automation. Two shapes collapsed into one.</li>
</ul>
<p>Name which one you are looking at, and the fix picks itself.</p>
<h2>A quick way to decide</h2>
<p>When a new capability lands on the backlog, run four checks before picking a tool.</p>
<ul>
<li>Iteration: conversation or one hand-off</li>
<li>Output: subjective and voiced, or structured and neutral</li>
<li>Blast radius: does an early wrong turn corrupt the rest</li>
<li>Frequency: a one-off craft piece, or a repeatable batch job</li>
</ul>
<p>Three or more answers leaning subjective and iterative point to a skill. Three or more leaning structured and repeatable point to a sub-agent. A split answer usually means a skill orchestrating a sub-agent underneath.</p>
<img />
<p><em>Figure 2. Score the four checks and count the leanings. Three or four one way pick the shape. An even split means a skill orchestrating a sub-agent.</em></p>
<h2>Where to start depends on what you have already built</h2>
<p>The framework is the destination. Where you start depends on what your team has shipped so far. Find your stage and take the one first move for it this week.</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><tbody><tr><th>Stage</th><th>First move, this week</th><th>Watch out for</th></tr><tr><td>Just starting, nothing built yet</td><td>Pick the single task you repeat most and write a one-paragraph capability brief for it, iteration, output, blast radius, and frequency, before you build. The brief names the shape, and the shape names the tool.</td><td>Building a general assistant before you have named one concrete job.</td></tr><tr><td>One capability, reused for everything</td><td>List every job you push through the one tool, find the one whose shape does not match, and rebuild just that one in the right shape. You do not need to replace what works.</td><td>Forcing new work into the tool you already have.</td></tr><tr><td>A small fleet, a handful of capabilities</td><td>Take your largest layered workflow and split it, a skill that holds the voice and the human gate on top, a sub-agent that does the bounded work underneath.</td><td>Capabilities that duplicate each other with no composition between them.</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p><em>Table 2. Same framework, different first move. What you have already built decides where the leverage is this week.</em></p>
<p>Your setup also shapes the answer. A solo builder should optimise for their own voice and iteration speed, where one strong skill beats three thin ones. A platform team should standardise the capability brief and a shared voice profile, so the fleet stays consistent as more people add to it, and a new capability inherits the house style instead of drifting from it.</p>
<img />
<p><em>Figure 3. Whatever you have built so far, the first move has the same shape. Name the work before the tool, then match the shape to the tool.</em></p>
<h2>The shift</h2>
<p>The shift is from "what can the model do" to "what shape is the work". Model capability is table stakes now. The advantage is in matching the capability to the work. Our own capability fleet is built this way, interactive skills and autonomous sub-agents in separate places with an orchestrator on top, and that split is what keeps it maintainable as it grows.</p>
<p>Iterative and voice-heavy points to a skill. Bounded and mechanical points to a sub-agent. Large and layered points to a skill orchestrating sub-agents. Decide that first, and the model becomes a detail the team can change later without rebuilding anything.</p>
<p>Most teams collapse both ideas into "automation" and end up with neither. The teams that separate them build capabilities they actually reuse.</p>

<p><span class="lia-text-color-15"><strong>Why this is trickier than it looks&nbsp;</strong></span></p>
<p>A group transfer in GitLab isn't just a rename. It re-parents the project under a new namespace, which changes every path-based assumption downstream: inherited group variables, group-scoped runners, and any external system that hardcoded the old your-source-group/your-project path. For a plain application repo that's a minor cleanup. For a project that manages infrastructure, four things can bite at once:&nbsp;</p>
<p>-Terraform state can appear to "reset" if the backend address was built from the old project path instead of the stable project ID.&nbsp;<br />-Pipelines can fail because CI/CD variables that were inherited from the old group are no longer in scope.&nbsp;<br />-Terraform jobs can fail on permissions because the runner or service account in the new group has different access.&nbsp;<br />-Cloud authentication can break because a service principal's federated credentials were mapped to the old GitLab repo path.&nbsp;</p>
<p>&nbsp;</p>
<p><span>Get ahead of those four and the transfer itself is the easy part.</span> <span>Here's&nbsp;the shape of the move: the project keeps its identity (and its ID), but everything it inherited from the old parent stays behind.</span><span>&nbsp;</span></p>
<p><span>Group transfer overview — project ID stays the same, inherited resources do not follow:</span><span>&nbsp;</span></p>

<p><span>BEFORE: your-source-group</span><span>&nbsp;</span></p>
<p><span>your-project&nbsp; |&nbsp; ID 4021</span><span>&nbsp;</span></p>
<p><span>&nbsp; ├─ GitLab-managed Terraform state</span><span>&nbsp;</span></p>
<p><span>&nbsp; ├─ Group CI/CD variables (inherited)</span><span>&nbsp;</span></p>
<p><span>&nbsp; └─ Group runners (inherited)</span><span>&nbsp;</span></p>
</td><td>
<p><span>→</span><span>&nbsp;</span></p>
</td><td>
<p><span>AFTER: your-target-group</span><span>&nbsp;</span></p>
<p><span>your-project&nbsp; |&nbsp; ID 4021 (unchanged)</span><span>&nbsp;</span></p>

<p><span>&nbsp; ├─ Group CI/CD variables (re-create)</span><span>&nbsp;</span></p>

<p><span class="lia-text-color-15"><strong>Prerequisites and assumptions&nbsp;</strong></span></p>
<p>This guide assumes the project you're moving includes:&nbsp;</p>
<p>-Terraform code spread across multiple folders and environments.&nbsp;<br />-Multiple Git branches and tags.&nbsp;<br />-GitLab-managed Terraform state.&nbsp;<br />-GitLab CI/CD pipelines, variables, and related configuration.&nbsp;</p>
<p>You'll also want Owner access in both the source and target groups, and a maintenance window you can announce in advance.</p>
<p><span style="color: rgb(30, 30, 30);">&nbsp;</span></p>
<p><span class="lia-text-color-15"><strong>Before the move&nbsp;</strong></span></p>
<p><span>Everything that makes the move safe happens here, while the project is still quiet and reversible.</span><span>&nbsp;</span></p>
<ul>
<li><strong><span class="lia-text-color-15">Confirm governance and access -&nbsp;</span></strong><span style="font-weight: 400; color: rgb(30, 30, 30);">Announce the change window and the expected freeze period so nobody pushes into a moving target. <li><strong><span class="lia-text-color-15">Capture a baseline inventory</span><span style="color: rgb(30, 30, 30);"><span class="lia-text-color-15"> -</span> </span></strong>Write down what "good" looks like now so you can&nbsp;compare&nbsp;after the move. <p><span>&nbsp;</span></p>
<p><span class="lia-text-color-15"><strong>Executing the move&nbsp;</strong></span></p>
<p><span>With the project frozen and backed up, the transfer itself is quick. Keep your eyes on one number: the project ID.</span><span>&nbsp;</span></p>
<ul>
<li><span class="lia-text-color-15"><strong>Run the transfer - </strong></span>In the project's&nbsp;<span style="color: rgb(30, 30, 30);">Settings &gt; General &gt; Advanced</span><span style="color: rgb(30, 30, 30);">&nbsp;section, transfer the project to the target group. <li><span class="lia-text-color-15"><strong>Validate immediately</strong></span><span style="color: rgb(30, 30, 30);"><span class="lia-text-color-15"><strong> -</strong></span> </span>Right after the move, confirm the repository is&nbsp;present&nbsp;and that branches, tags, merge requests, and issues are all visible. Check that the default branch and protected branches&nbsp;survived, and&nbsp;confirm the&nbsp;project&nbsp;visibility level (the target&nbsp;group's&nbsp;settings can constrain it).<span style="color: rgb(30, 30, 30);"> </span></li>

<p><span class="lia-text-color-15"><strong>Gotchas that will bite you&nbsp;</strong></span></p>
<p><span>This is the part I wish someone had handed me before the move. Each gotcha follows the same shape: a symptom&nbsp;you'll&nbsp;see, the cause underneath it, and the fix.</span> <span>&nbsp;</span></p>
<p><span>&nbsp;</span>⚠️&nbsp; WARNING — Re-point the service principal's federated credentials -</p>
<div>If your Terraform authenticates to the cloud with a service principal using workload-identity federation, the App Registration's federated credential is mapped to the old GitLab repo path. After the transfer, authenticated Terraform runs fail even though the state is fine, because the identity no longer matches the new namespace.&nbsp;</div>
<div>&nbsp;</div>
<div><strong>Symptom:</strong> plans or applies fail on authentication or token issuance after an otherwise clean move.&nbsp;</div>
<div><strong>Cause:</strong> the federated credential subject still references your-source-group/your-project.&nbsp;</div>
<div><strong>Fix:</strong> update the federated credential in the App Registration to point at the new your-target-group/your-project path.&nbsp;</div>
<p>&nbsp;</p>
<ul>
<li><span class="lia-text-color-15"><strong>The backend built from project ID versus project path - </strong></span>GitLab-managed Terraform state lives at an HTTP backend address. When that address is keyed to the stable project ID, it survives a group transfer untouched. When&nbsp;it's&nbsp;keyed to the&nbsp;project&nbsp;path, the address changes the moment the namespace&nbsp;changes, and&nbsp;Terraform can no longer find the existing state — so a plan looks like a brand-new, empty deployment.<span style="color: rgb(30, 30, 30);"> </span>
<ul>
<li>
<p><span><strong>Symptom:</strong>&nbsp;</span><span>after the move,&nbsp;terraform&nbsp;plan proposes to create everything from scratch.</span></p>
</li>
<li>
<p><span><strong>Cause:</strong> </span><span>the backend address was derived from the old project path.</span></p>
</li>
<li>
<p><span><strong>Fix:</strong>&nbsp;</span><span>point the backend at the project-ID form of the address (which is unchanged by the move) and re-run the plan. See the&nbsp;</span><span>Terraform GitLab-managed state docs</span><span>&nbsp;for the exact address format.</span><span>&nbsp;</span></p>
</li>
</ul>
</li>
</ul>

<li><strong>Fix:</strong> <span style="color: rgb(30, 30, 30);">re-create them at the target&nbsp;group, or&nbsp;pull the essential ones down to project&nbsp;scope&nbsp;so they travel with the project.</span><span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
</ul>
</li>
<li><span>&nbsp;</span><span class="lia-text-color-15"><strong>Runner and service-account permission differences -</strong></span>

<li><strong>Cause:</strong> <span style="color: rgb(30, 30, 30);">the new group offers different runners, or the&nbsp;runner's&nbsp;service account has different access than the old&nbsp;group's.</span><span style="color: rgb(30, 30, 30);"> </span></li>

</li>

<p><strong><span class="lia-text-color-15">How to verify (evidence to capture)&nbsp;</span></strong></p>
<p><span>Treat verification as a read-only exercise first. The goal is proof that nothing changed under you, captured one environment at a time.</span><span>&nbsp;</span></p>
<p><span>Work through the environments individually rather than all at once. For each one, run a read-only plan before anything else, investigate any proposed create or destroy before you apply, and confirm the state key name stays&nbsp;exactly identical&nbsp;to what it was before the move. If the state key naming drifts, stop and fix the backend address before&nbsp;proceeding.</span><span>&nbsp;</span></p>
<p><span>Capture this evidence as you go:</span></p>
<ul>

<p><span>&nbsp;</span></p>
<p><span class="lia-text-color-15"><strong>If something goes wrong: how to roll back&nbsp;</strong></span></p>
<p><span>Your rollback plan is already in place if you did the prep. It rests on three facts from earlier in this process, and it needs nothing you&nbsp;haven't&nbsp;already prepared.</span><span>&nbsp;</span></p>
<ul>
<li><span>You took a state backup for every active state before the move (from the readiness step). If a plan looks wrong, you can&nbsp;restore from&nbsp;those backups rather than letting an apply run.</span><span>&nbsp;</span></li>
<li><span>The merge&nbsp;freeze&nbsp;and paused schedules are still holding, so nothing is racing your recovery. The freeze window is the safe point to restore a state backup or reverse the move.</span><span>&nbsp;</span></li>
<li><span>The project ID never changed, which means the project can be transferred back to the source group the same way it came, and the same GitLab-managed state (keyed to that ID) remains valid.</span><span>&nbsp;</span></li>
</ul>
<p><span>&nbsp;</span><span class="lia-text-color-15"><strong>CAUTION - </strong></span><span>Only lift the freeze and&nbsp;unpause&nbsp;schedules once your read-only plans are clean. The freeze is what keeps rollback simple; releasing it early is what turns a small correction into an incident.</span><span>&nbsp;</span></p>
<p><span>&nbsp;</span></p>
<p><span class="lia-text-color-15"><strong>Lessons learned&nbsp;</strong></span></p>
<ul>
<li><span>Key your Terraform backend to the project ID, not the project path.&nbsp;It's&nbsp;the single decision that makes a group transfer boring instead of terrifying.</span><span>&nbsp;</span></li>
<li><span>Federated credentials are&nbsp;path-shaped. If a cloud identity trusts your old repo path, it&nbsp;won't&nbsp;trust the new one until you re-map it.</span><span>&nbsp;</span></li>
<li><span>Inventory before you inherit. Group-inherited variables and runners don't move with the project, so know what you depend on before you cut the cord.</span></li>
<li><span>A freeze plus off-project backups is your whole rollback plan. Keep both until your plans come back clean.</span><span>&nbsp;</span></li>
<li><span>Verify read-only, one environment at a time. Drift is easy to reason about in isolation and painful to untangle in bulk.</span><span>&nbsp;</span></li>
</ul>

### Azure Front Door edge actions: programmable compute for a secure, resilient, AI-ready edge

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-front-door-edge-actions-programmable-compute-for-a-secure/ba-p/4542177](https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-front-door-edge-actions-programmable-compute-for-a-secure/ba-p/4542177)
- **Published**: 2026-07-31 02:53:35
- **Fetched**: 2026-08-27 21:13:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<h2>The need for secure edge programmability</h2>
<p>As modern web applications increasingly move decision-making closer to users, programmable compute at the edge is becoming a foundational capability for delivering low-latency, personalized, and intelligent experiences. Azure Front Door edge actions introduces lightweight customer-defined logic that executes close to users at Microsoft's global edge (<a href="https://aka.ms/edgeactionsblog" rel="noopener" target="_blank">https://aka.ms/edgeactionsblog</a>). The engineering challenge extends well beyond moving code closer to the request path. It is about enabling edge programmability while preserving the core guarantees customers expect from a global edge platform: hyperscale performance and acceleration, strong security and tenant isolation, resiliency, and fast, controlled recovery.</p>
<p>That sets up a much higher engineering bar than simply bringing a serverless runtime to the edge. Programmability introduces customer code, new execution paths, runtime dependencies, and additional failure modes directly into the critical request path. Architecture therefore must make flexibility a first-class capability without compromising the operational characteristics of a hyperscale edge platform.</p>
<h2>Preserving performance at hyperscale</h2>
<p>The first architectural challenge was preserving the performance characteristics of Azure Front Door while introducing programmable execution into the request path. Every additional execution step has the potential to increase latency, amplify failures, or reduce throughput at global scale. Edge actions was therefore designed to add programmability without changing the fundamental performance profile customers already expect from Azure Front Door.</p>
<p>At request time, Azure Front Door evaluates the request, determines whether an edge action should be executed based on the associated rule, invokes the edge actions runtime, and applies the result inline. Because the runtime sits directly in the request path, every design decision was guided by a common principle: keep execution local whenever possible, bound latency when dependencies degrade, and ensure optional compute never becomes a platform-wide latency amplifier.</p>
<p>&nbsp;</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<h3>Performance design principles</h3>
<ul>
<li><strong>Node-local execution</strong> keeps request processing on the same machine whenever possible, minimizing cross-node communications and preserving low latency.</li>
<li><strong>Minimized inter-node hops</strong> keep the common path compact while still enabling cluster-level fallback when local dependencies deteriorate.</li>
<li><strong>Connection reuse </strong>through Edge Action Agent reduces gRPC invocation overhead and improves hot path efficiency.</li>
<li><strong>Lightweight Hyperlight isolation</strong> provides strong tenant isolation with an execution model suitable for latency-sensitive edge workloads.</li>
<li><strong>Fast-fail and circuit-breaker </strong>protects latency by bounding waits on degraded dependencies and preventing cascading pressure.</li>
</ul>
<p>Together, these architectural choices introduce programmable compute without turning the Azure Front Door data plane into a distributed orchestration layer. The hot path remains local, predictable, and bounded, with fallback used only when necessary to preserve performance across the global edge.</p>
<h2>Security and tenant isolation by design</h2>
<p>Running customer-defined code on a shared global edge fundamentally changes the security model. Unlike traditional request processing, programmable execution introduces untrusted customer code directly into the request path, making strong isolation a foundational architectural requirement rather than an operational safeguard. For Azure Front Door edge actions, every execution is designed to run within a dedicated Hyperlight micro-VM, providing hardware-enforced isolation between customer workloads, the Azure Front Door data plane, and the underlying host environment.</p>
<h3>Security design principles</h3>
<ul>
<li><strong>Hypervisor-backed isolation </strong>ensures customer code executes within dedicated Hyperlight micro-VM boundaries rather than shared execution environments.</li>
<li><strong>Data plane separation</strong> isolates edge actions execution from Azure Front Door's core traffic-processing path.</li>
<li><strong>Minimal host surface area</strong> reduces the attack surface and limits privileged interactions.</li>
<li><strong>Restricted execution context</strong> exposes only the request information required to process a request.</li>
<li><strong>Reduced operational blast radius</strong> helps contain compromised or misbehaving workloads.</li>
</ul>
<p>These architectural boundaries extend beyond workload isolation. Azure Front Door's data plane remains physically separated from the edge actions orchestration service, while each execution receives only the minimum context required to perform its task. This defense-in-depth approach reduces both security risk and operational blast radius without compromising performance.</p>
<h3>Hyperlight: Security without sacrificing performance</h3>
<p>A key differentiator of Azure Front Door edge actions is its use of <a href="https://opensource.microsoft.com/blog/2024/11/07/introducing-hyperlight-virtual-machine-based-security-for-functions-at-scale/" rel="noopener" target="_blank">Hyperlight</a> micro-VMs to provide hardware-backed isolation without introducing the traditional performance penalties associated with virtual machines. Hyperlight was designed to make VM-level protection practical for high-throughput function execution, enabling strong tenant isolation while remaining suitable for latency-sensitive edge workloads.</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<p>Edge actions builds this foundation through the edge action orchestrator, which maintains a pool of warm Hyperlight sandboxes ready to serve requests. By reusing pre-initialized sandboxes instead of creating a new execution environment for every request, edge actions minimizes initialization overhead, reduces request latency, and sustains higher throughput under load. The result is a security model based on VM isolation that remains compatible with the performance expectations of a hyperscale edge platform.</p>
<p>Critically, performance optimizations do not weaken isolation guarantees. After each execution, sandbox state is cleaned before reuse, ensuring that subsequent invocations cannot access data from prior executions while preserving the efficiency benefits of warm sandboxing. In internal benchmarking, lightweight edge actions <strong><em>executed in less than 2 ms inside Hyperlight, with approximately 1.27 ms of total sandbox overhead,</em></strong> demonstrating that strong isolation and high-performance edge execution can coexist.</p>
<h3>Security enables resiliency</h3>
<p>Security and resiliency are closely related architectural goals. Isolation helps contain malformed inputs, unexpected behavior, and execution failures, preventing individual workloads from affecting the broader platform. In a multitenant edge service, isolation is not only a security requirement; it is also a key resiliency mechanism.</p>
<h2>Resiliency built into the platform</h2>
<p>Strong isolation is not only a security property, but also a foundational resiliency mechanism. By containing malformed inputs, unexpected behavior, and execution failures within dedicated execution boundaries, the platform prevents individual workloads from affecting neighboring tenants or the broader service. At hyperscale, robust isolation is essential for maintaining customer trust and predictable platform reliability.</p>
<p>Building on that foundation, Azure Front Door edge actions was designed around a simple operating principle: failures are inevitable, but their impact must be predictable, bounded, and recoverable. Because programmable compute introduces additional execution paths and runtime dependencies into the request path, resiliency must be built into the control points that determine when to execute, stop waiting, or fall back.</p>
<p>The platform incorporates lessons learned from operating Azure services at a global scale, with a focus on minimizing blast radius, maintaining service continuity, and enabling controlled recovery when dependencies fail, overload, or time out.</p>
<h3>Resiliency principles</h3>
<ul>
<li>Bound failure impact through isolation and containment.</li>
<li>Recover predictably using health-aware routing and fallback paths.</li>
<li>Protect customer availability first through graceful degradation.</li>
<li>Fail fast rather than fail slowly to avoid latency amplification.</li>
<li>Continuously validate assumptions through Game Days and fault injections.</li>
</ul>
<p>These principles translate into request-time behavior through deadlines, circuit breakers, fail-open behavior, and health-based fallback. Together, they ensure that optional programmable execution enhances application capabilities without compromising the stability of Azure Front Door's core request-processing pipeline.</p>
<h2>Continuous validation of resiliency assumptions</h2>
<p>Resilient architecture is credible only when validation becomes part of the operating model. For edge actions, Game Days and Fault Injections provide recurring opportunities to verify that architectural assumptions continue to hold under production-like stress.</p>
<p>Validation includes chaos and failure injections, timeout and dependency-loss exercises, overload and queue-growth scenarios, mixed-workload testing, and interface fuzzing. These exercises answer practical production questions: Does fail-open behavior protect the request path? Do circuit breakers engage early enough? Does fallback routing preserve service continuity? Do malformed inputs remain contained?</p>
<p>Repeated validation also strengthens operations. Detection improves, mitigation becomes more predictable, and recovery evolves from architectural intent into demonstrated operational capability.</p>
<h2>Built for future intelligent &amp; modern workloads</h2>
<p>Edge actions is designed for lightweight programmable execution today, but the underlying architecture is intended to support increasingly intelligent decision-making over time. The engineering requirement remains unchanged: future intelligence workloads must operate within the same architectural constraints that govern today's request processing - bounded execution, strong isolation, predictable fallback, and protection of the common request path.</p>
<h3>Architectural implications for intelligence workloads</h3>
<ul>
<li>Real-time AI inferencing for request classification and policy evaluation.</li>
<li>Intelligent bot, abuse, and fraud detection closer to users.</li>
<li>AI-assisted origin selection and traffic-routing decisions.</li>
<li>Application-specific SLM-powered decision making at the edge.</li>
</ul>
<p>In that model, the objective is not simply to introduce more intelligence at the edge, but to ensure that intelligence inherits the same platform guarantees as every other component of the request path.</p>
<h2>Closing thoughts</h2>
<p>Programmable edge execution is becoming a foundational capability for modern distributed applications. The engineering challenge, however, extends far beyond running customer code closer to users. It is about preserving the system properties that customers already depend on while introducing a new execution surface into the critical request path.</p>
<p>Edge actions demonstrates that edge programmability, performance, security, tenant isolation, and resiliency are not independent design goals - they are a single architectural problem that must be solved together. By keeping the common path protected, failures bounded, tenants strongly isolated, and recovery predictable, Azure Front Door edge actions extends the platform's capabilities without compromising the engineering principles that underpin a global hyperscale edge service.</p>
