### From Policy to Proof: Governing AI to Scale Human Ambition and Machine Intelligence

- **Link**: [https://techcommunity.microsoft.com/t5/azure-architecture-blog/from-policy-to-proof-governing-ai-to-scale-human-ambition-and/ba-p/4535137](https://techcommunity.microsoft.com/t5/azure-architecture-blog/from-policy-to-proof-governing-ai-to-scale-human-ambition-and/ba-p/4535137)
- **Published**: 2026-07-16 04:51:51
- **Fetched**: 2026-08-27 21:13:49

<p><span>Enterprises are moving from AI experiments to AI in production. Copilots are in the flow of daily work, custom applications are built on foundation models, and autonomous agents are beginning to take actions on behalf of the business. As organizations combine&nbsp;</span><strong><span>human ambition with machine intelligence</span></strong><span><strong>, trust becomes the defining requirement</strong> for scaling AI responsibly and realizing AI's full potential.</span><span>&nbsp;</span></p>
<p><span>That shift changes the governance question from&nbsp;</span><em><strong><span>"can we use AI responsibly?"</span></strong></em><span><em><strong>&nbsp;</strong></em>to&nbsp;a harder one:<em><strong>&nbsp;</strong></em></span><em><strong><span>"can we prove, continuously, that every AI system and agent in our estate is safe, compliant, observable, and accountable?"</span><span>&nbsp;</span></strong></em></p>
<p><span>The organizations getting this right have stopped treating governance as a static document that lives in a policy binder. They treat it as an operating system: a connected set of policies, controls, telemetry, and evidence that runs alongside AI everywhere it&nbsp;operates.&nbsp;Governance defines what should happen.&nbsp;Observability and evaluations verify what is actually happening.&nbsp;Audit and response prove it, and feed what they learn back into policy. The loop, not any single control, is what makes governance real.</span><span>&nbsp;</span></p>
<p><span>Every control in this map ladders up to a principled foundation:&nbsp;</span><a href="https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/Microsoft-Responsible-AI-Standard-General-Requirements.pdf?culture=en-us&amp;country=us" rel="noopener" target="_blank"><span><span>Microsoft's Responsible AI Standard</span></span></a><span>, whose six principles (fairness, reliability and safety, privacy and security, inclusiveness, transparency, and accountability) set the bar these controls exist to meet.</span><span>&nbsp;</span></p>
<p><span>This post lays out a practical reference map for that operating system: the&nbsp;domains&nbsp;AI governance must cover, the cross-cutting runtime enforcement layer that operationalizes them, and the Microsoft services that support each one.</span><span>&nbsp;</span></p>
<h2><u><span class="lia-text-color-21"><strong>The four pillars of AI governance</strong></span></u></h2>
<p>At its core, AI governance does four things. Skip any one of them and a gap opens up -policy without control is aspirational, control without visibility is blind, and visibility without proof cannot withstand an audit.</p>
<ol>
<li><strong>Policy - Define the rules</strong>, and who owns them. What's acceptable use, which use cases are approved, how each is classified by risk, and -critically -who is accountable for outcomes at each stage.</li>
<li><strong>Control - Enforce the boundaries</strong>, proportionate to risk. Turn policy into guardrails, access decisions, and lifecycle gates that constrain systems at runtime -with tighter controls on higher-risk use cases.</li>
<li><strong>Visibility - Observe behavior</strong>, including fairness and quality. Capture logs, metrics, traces, token consumption, tool calls, and runtime signals that reveal what AI is truly doing -not just latency and cost, but grounding, drift, and fairness signals.</li>
<li><strong>Proof - Audit, prove, and improve</strong>. Produce the evidence to demonstrate compliance and transparency (explainability and traceability you can show regulators and customers), investigate incidents, and feed what you learn back into policy.</li>
</ol>
<h1><u><span class="lia-text-color-21"><strong>What AI governance covers: the domain map</strong></span></u></h1>
<p>A complete AI governance program spans nine core domains, with runtime enforcement operating as a cross-cutting layer across several of them. Use this taxonomy to map your own requirements to concrete controls:&nbsp;&nbsp;</p>
<ul>
<li><strong>Policy:</strong> Responsible AI policies, approval workflows, and guardrails.</li>
<li><strong>Data governance:</strong> Classification, sensitivity labels, DLP, retention, and lineage.</li>
<li><strong>Model governance:</strong> Validation, versioning, documentation, and change control.</li>
<li><strong>Observability:</strong> Logs, metrics, traces, token usage, and runtime signals.</li>
<li><strong>Evaluations:</strong> Quality, safety, grounding, drift, and agent task success.</li>
<li><strong>Security:</strong> Threat detection, posture management, proactive AI red teaming, and prompt-injection resistance.</li>
<li><strong>Identity &amp; access:</strong> RBAC, least privilege, conditional access, and agent identities.</li>
<li><strong>Audit &amp; compliance:</strong> Evidence, eDiscovery, legal hold, and reporting.</li>
<li><strong>Agent governance:</strong> Registry, lifecycle, policy enforcement, and fleet visibility.</li>
</ul>
<p><strong>Cross-cutting runtime enforcement:</strong> Runtime enforcement is not a separate governance program. It is the control layer that operationalizes policy, security, identity, data protection, observability, and agent governance while AI systems are running. It governs live interactions between users, agents, models, tools, APIs, MCP servers, A2A agent APIs, and enterprise systems through authentication, authorization, traffic controls, token governance, quotas, policy checks, and operational guardrails.</p>
<h3><strong>The Microsoft governance stack</strong></h3>
<p>Microsoft's approach is a composed platform rather than a single product — AI lifecycle, data governance, identity, security, observability, and audit working together:</p>
<img />
<h3>1. Policy and the control plane: define and enforce</h3>
<p>Governance starts with a place to define the rules and decide who owns them. This is where responsible AI and acceptable use policies are authored; where new use cases come in through intake, get classified by risk, and are approved or rejected; where you decide up front which decisions and agent actions require human sign-off versus running autonomously within guardrails; and where accountability is assigned across the deploy, update, and retire lifecycle. Enforcing those rules through runtime guardrails, security posture, agent-level controls, and API-level controls is the job of the sections that follow; the work here is defining what “acceptable” means before anything is switched on.&nbsp;</p>
<p><strong>Services that support it:</strong></p>
<ul>
<li><strong>Microsoft Foundry</strong> -Compliance workspace for authoring and housing responsible AI policies and use case approvals.</li>
<li><strong>Azure Policy</strong> -Resource level governance to codify those rules as enforceable baselines.</li>
<li><strong>Azure API Management (AI Gateway):&nbsp;</strong>Runtime enforcement for AI applications, models, agents, tools, and APIs, including authentication, authorization, token governance, quota management, and policy enforcement.&nbsp;</li>
</ul>
<p>(Agent specific policy and lifecycle controls via Microsoft Agent 365 are covered in Section 6.)</p>
<p><strong>Practical takeaway: </strong>establish a governance baseline before AI and agent adoption scales -including deciding up front where a human stays in the loop. Retrofitting controls onto a sprawling estate is far harder than starting from one.</p>
<h3>2. Data governance and compliance: Purview at the center</h3>
<p><span>Most AI risk is&nbsp;ultimately data&nbsp;risk: the&nbsp;wrong information&nbsp;reaching a model, leaving through a response, or being&nbsp;retained&nbsp;without a policy.&nbsp;</span><a href="https://www.microsoft.com/en-us/security/business/microsoft-purview" rel="noopener" target="_blank"><span><span>Microsoft Purview</span></span></a><span>&nbsp;is the primary governance engine for AI interactions and enterprise data controls, and it works in three moves:</span><span>&nbsp;</span></p>
<ul>
<li><strong>Discover - </strong>Identify AI usage, sensitive prompts and responses, and overall risk posture with DSPM for AI.</li>
<li><strong>Protect - </strong>Apply sensitivity labels, DLP, access boundaries, and retention policies.</li>
<li><strong>Prove - </strong>Generate audit trails, eDiscovery evidence, and compliance reporting.</li>
</ul>
<p>If the question is <em>“how do we govern the data flowing through AI?”</em> - Purview is the anchor.</p>
<h3>3. Model governance, safety, and evaluations: quality at build time and runtime</h3>
<p>Evaluations are what make governance measurable, and they belong at two points in the lifecycle:</p>
<ul>
<li><strong>Pre-deployment - </strong>Release gating on safety, grounding, quality, fairness, and task success before anything ships.</li>
<li><strong>Post-deployment - </strong>Runtime scoring for drift, quality thresholds, and harmful-output alerts once a system is live.</li>
</ul>
<p><strong>Services that support it:&nbsp;</strong></p>
<ul>
<li><a href="https://learn.microsoft.com/en-us/azure/foundry/concepts/built-in-evaluators" rel="noopener" target="_blank"><span><span>Microsoft Foundry evaluators</span></span></a><span>:</span><span>&nbsp;quality, safety, RAG grounding, and agent task metrics</span><span>&nbsp;</span></li>
<li><a href="https://learn.microsoft.com/en-us/azure/ai-services/content-safety/overview" rel="noopener" target="_blank"><span><span>Azure AI Content Safety</span></span></a><span>:</span><span>&nbsp;detects unsafe or harmful content in prompts and responses. This is also integrated in Microsoft Foundry as guardrails that protect against unsafe content and direct and indirect&nbsp;jailbreak&nbsp;prompt injection attacks.</span><span>&nbsp;</span></li>
<li><a href="https://github.com/responsibleai/ASSERT" rel="noopener" target="_blank"><span><span>ASSERT</span></span></a><span>&nbsp;(open source):</span><span>&nbsp;Microsoft's open-source, policy-driven evaluation framework, short for Adaptive Spec-driven Scoring for Evaluation and Regression Testing. ASSERT turns your&nbsp;specific requirements and&nbsp;organizational policies into targeted, safety-focused test cases rather than generic benchmarks, and runs across frameworks such as&nbsp;LangChain,&nbsp;CrewAI,&nbsp;LiteLLM, and OpenAI, so evaluation is not locked to any single stack. ASSERT also pairs with runtime controls to close the loop: measure a failure rate, apply a control (see&nbsp;</span><a href="https://commandline.microsoft.com/agent-control-specification-runtime-governance/" rel="noopener" target="_blank"><span><span>Agent Control Specification</span></span></a><span>&nbsp;in section 6), then re-run the same evaluation to prove the rate dropped. That turns "we mitigated it" into a measured before-and-after.</span><span>&nbsp;</span></li>
</ul>
<p>Evaluations are not separate from governance - they are what turn governance from a promise into measurable proof.&nbsp;</p>
<h3>4. Observability and runtime monitoring: know what is actually happening</h3>
<p><span>Once AI is in production, you need to see its behavior in real time. Capture four kinds of signal:</span><span>&nbsp;</span></p>
<ul>
<li><strong><span>Logs:</span></strong><span>&nbsp;prompts, responses, and decisions</span><span>&nbsp;</span></li>
<li><strong><span>Metrics:</span></strong><span>&nbsp;latency, token usage, quality scores, request volume, and quota consumption</span><span>&nbsp;</span></li>
<li><strong><span>Traces:</span></strong><span><strong>&nbsp;</strong>agent reasoning paths, tool calls, model calls, and inter-service dependencies</span><span>&nbsp;</span></li>
<li><strong><span>Alerts:</span></strong><span><strong>&nbsp;</strong>policy violations, drift, harmful outputs, and abnormal traffic patterns</span><span>&nbsp;</span></li>
</ul>
<p><span>Microsoft Foundry provides purpose-built observability for AI applications and agents across three connected capabilities. Evaluation measures quality, safety, and reliability throughout development. Monitoring tracks deployed systems in real-world conditions. Tracing, built on OpenTelemetry standards, captures the execution flow of LLM calls, tool invocations, and agent decisions, so you can debug multi-step reasoning rather than guess at it, across frameworks including LangChain, LangGraph, the OpenAI Agents SDK, and the Microsoft Agent Framework. The Agent Monitoring Dashboard brings these signals together for production traffic: token usage, latency, run success rates, evaluation scores, and red-teaming results in one view, backed by Azure Monitor, Application Insights. From the same surface you can turn on continuous evaluation to score sampled live responses, scheduled evaluations to detect drift against benchmarks, scheduled red team scans to probe deployed agents for emerging risks, and alerts that fire when outputs fail quality thresholds or produce harmful content.</span><span>&nbsp;</span></p>
<p><span>Critically, this coverage is not limited to agents built on Foundry. Agents running elsewhere can be onboarded through the AI Gateway and instrumented with&nbsp;OpenTelemetry&nbsp;semantic conventions to send telemetry to the same Application Insights instance, so one dashboard, one evaluation pipeline, and one alerting surface cover the whole estate.</span><span>&nbsp;</span></p>
<p><strong><span>The broader observability fabric</span><span>&nbsp;</span></strong></p>
<p><span>Foundry observability composes with the rest of the platform: Azure Monitor, Application Insights, Log Analytics, Purview Audit, and Microsoft Agent 365 dashboards. Azure API Management (AI Gateway) extends visibility further by capturing AI traffic patterns, token consumption, API usage, policy violations, and agent-to-tool interactions,&nbsp;providing&nbsp;runtime insight into AI workloads at the network boundary.</span><span>&nbsp;</span></p>
<p><strong><span>Practical takeaway:</span></strong><span><strong>&nbsp;</strong>wire&nbsp;observability&nbsp;before launch, not after the first incident. Continuous evaluation on sampled production traffic is the cheapest early-warning system you can buy, and the trace data it rides on is the same evidence an auditor will ask for later.</span><span>&nbsp;</span></p>
<h3>5. Security and identity governance: protect the AI estate</h3>
<p>AI expands the attack surface, so governance has to include security and identity across the following:</p>
<ul>
<li><strong>Threat protection -</strong>Prompt injection, jailbreak, data exfiltration, and unsafe actions -with Microsoft Defender for Cloud and Microsoft Defender XDR.</li>
<li><strong>Proactive adversarial testing -</strong>Find failures before attackers do, with the AI Red Teaming Agent in Microsoft Foundry for automated agent probing and PyRIT, Microsoft’s open-source red-teaming framework.</li>
<li><strong>Security posture -</strong>Misconfigurations, exposed endpoints, and risky resources -with Defender for Cloud and Azure Policy.</li>
<li><strong>Identity &amp; access -</strong>Who can use AI, and what data, apps, and agents it can reach -with Microsoft Entra ID and RBAC.</li>
<li><strong>Runtime access enforcement:&nbsp;</strong>Who can call which model, tool, API, or MCP server, under which conditions, and with what level of throttling, inspection, and monitoring.&nbsp;</li>
<li><strong>Secrets &amp; network -</strong>Protecting keys and enforcing private access and network boundaries -with Azure Key Vault and Private Link.</li>
<li><strong>Device management</strong>-Discover, monitor, and govern unmanaged AI agents and the endpoints they run on -with Microsoft Intune and Microsoft Defender for Endpoint (MDE).</li>
</ul>
<p><strong>Cross-cutting runtime enforcement&nbsp;</strong></p>
<p>As AI systems increasingly rely on APIs, tools, MCP servers, enterprise applications, and agent-to-agent interactions, governance must extend beyond model build-time controls to the live interactions that&nbsp;connect&nbsp;those systems. Runtime enforcement helps operationalize the broader AI governance program by enforcing who can call what, under which conditions, at what scale, and with what level of monitoring.&nbsp;</p>
<p><strong>Services that support it&nbsp;:</strong></p>
<ul>
<li><strong>Azure API Management (AI Gateway):&nbsp;</strong>Centralized authentication, authorization, token controls, traffic shaping, quota enforcement, content safety policies, and policy governance for AI models, agents, tools, MCP servers, A2A agent APIs, and enterprise APIs.&nbsp;</li>
<li><strong>Microsoft Entra ID: </strong>Identity and access control for applications, users, and agents.&nbsp;</li>
<li><strong>Azure RBAC:&nbsp;</strong>Fine-grained authorization for AI resources and workloads.&nbsp;</li>
</ul>
<p><strong>The mindset shift: </strong>treat agents as non-human identities with their own permissions, lifecycle, runtime access and monitoring.</p>
<h3>6. Agent governance: the emerging control plane</h3>
<p>Agents are a new kind of enterprise actor, and governing them takes two complementary pieces: a control plane to manage the whole fleet, and a portable control standard to enforce safety inside each agent's workflow.</p>
<h5><strong>Microsoft Agent 365: govern the agent fleet</strong></h5>
<p>Agents introduce a new problem - sprawl. As teams build agents on different platforms, organizations need one way to see and govern all of them. Microsoft Agent 365, now generally available, is the control plane for AI agents: it gives each agent its own identity and manages agents with the admin tools you already use - Microsoft Entra, Defender, Purview, Intune, and the Microsoft 365 admin center. It works across agents built on Microsoft, open-source, and third-party platforms, through five core capabilities:</p>
<ul>
<li><strong>Registry - </strong>Discover and catalog every agent - including shadow agents - and quarantine the unsanctioned ones.</li>
<li><strong>Access control - </strong>Give each agent a unique Microsoft Entra Agent ID, and enforce least-privilege, risk-based access with policy templates.</li>
<li><strong>Visualization - </strong>Unified dashboards, telemetry, and alerts across the entire agent fleet.</li>
<li><strong>Interoperability - </strong>Works with agents from Microsoft, open-source, and third-party frameworks, alongside your Microsoft 365 apps and data.</li>
<li><strong>Security - </strong>Threat detection, data protection, and compliance for agents at scale, through Defender, Purview, and Entra.</li>
</ul>
<h5><strong>Agent Control Specification (ACS): portable runtime controls</strong></h5>
<p><span>Governing agents also means enforcing controls consistently, no matter which framework an agent is built on. The&nbsp;</span><a href="https://commandline.microsoft.com/agent-control-specification-runtime-governance/" rel="noopener" target="_blank"><span><span>Agent Control Specification (ACS)</span></span></a><span>&nbsp;is an open industry standard, part of Microsoft's Agent Governance Toolkit, for placing deterministic safety and security controls at defined checkpoints in an agent's workflow. Just as the Model Context Protocol (MCP) standardized how agents connect to tools, and A2A standardized how agents communicate with each other, ACS aims to standardize how agents are governed: one portable control layer that any framework can adopt, with Microsoft providing reference implementations.</span><span>&nbsp;</span></p>
<ul>
<li><strong><span>Control checkpoints:</span></strong><span>&nbsp;validation at defined intervention points across the agent's lifecycle, spanning input, model invocation, state, tool selection and execution, and output</span><span>&nbsp;</span></li>
<li><strong><span>Composable controls:</span></strong><span>&nbsp;deterministic checks (allow/deny rules, custom filters) alongside model-based checks (classifier endpoints, LLM judges), each placed exactly where it is needed</span><span>&nbsp;</span></li>
<li><strong><span>Portable and auditable:</span></strong><span>&nbsp;expressed as a declarative manifest with policy-as-code evaluation, so controls are&nbsp;versionable, auditable, and travel with the agent across any stack</span><span>&nbsp;</span></li>
</ul>
<p>Together they cover both altitudes of agent governance: Agent 365 governs the fleet from the outside, while ACS enforces safety inside each agent's workflow. Those checkpoints can also&nbsp;<strong>route to a human for approval before a high-impact action</strong> -the runtime side of human-in-the-loop -while Agent 365 defines which agents and actions require sign-off.</p>

<h1><u><strong>A practical path forward</strong></u></h1>
<p>You do not have to govern everything at once. A pragmatic sequence gets you to a defensible position quickly:&nbsp;</p>
<ul>
<li><strong>Start with scope:&nbsp;</strong>Inventory the AI apps, Copilots, agents,&nbsp;APIs, tools, MCP servers,&nbsp;and custom Microsoft Foundry workloads that exist today.&nbsp;</li>
<li><strong>Classify risk: </strong>Determine&nbsp;what data is used, what actions AI can take,&nbsp;what systems it can reach,&nbsp;and which regulations apply.&nbsp;</li>
<li><strong>Apply controls: </strong>Bring in Purview, Entra, Defender, Microsoft Foundry guardrails,&nbsp;Azure API Management AI Gateway policies,&nbsp;Agent 365 policies, and portable ACS checkpoints for agents.&nbsp;</li>
<li><strong>Measure and prove: </strong>Add evaluations, including policy-driven ASSERT runs and adversarial testing with the AI Red Teaming Agent, plus observability,&nbsp;APIM runtime telemetry,&nbsp;audit evidence, and operational dashboards.&nbsp;</li>
</ul>
<p>Governance works best when it follows the business rather than leading it. This journey view shows how the controls layer in progressively starting from a high-value business use case and adding only what each next step requires, so governance&nbsp;<em>accelerates</em>&nbsp;safe delivery instead of gating it. The path runs through four stages:&nbsp;<strong>align</strong>&nbsp;on the use case and its value, stand up a&nbsp;<strong>safe foundation</strong>&nbsp;of minimum viable controls,&nbsp;<strong>build and validate</strong>&nbsp;quality and safety, then&nbsp;<strong>operate and scale</strong>&nbsp;-monitoring, auditing, enforcing runtime controls and governing agents in production.</p>

## Apps on Azure Blog

### MCP Enterprise Authorization Is Here — What Entra and App Service Can Do Today

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/mcp-enterprise-authorization-is-here-what-entra-and-app-service/ba-p/4537433](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/mcp-enterprise-authorization-is-here-what-entra-and-app-service/ba-p/4537433)
- **Published**: 2026-07-16 23:31:39
- **Fetched**: 2026-08-27 21:13:50

<p>A few weeks ago I wrote about what the latest MCP changes meant for scaling on Azure App Service. This time, the protocol change is about a different kind of scale: how an enterprise connects hundreds or thousands of employees to MCP servers without making every person authorize every server one at a time.</p>
<p><a class="lia-external-url" href="https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization" rel="noopener" target="_blank">Enterprise-Managed Authorization (EMA)</a> is now a stable MCP extension. It makes the organization's identity provider the policy decision point, replaces repeated server-by-server browser prompts with an identity assertion grant, and gives security teams a central place to grant and revoke access.</p>
<p>That sounds a lot like Microsoft Entra preauthorization and App Service Authentication. But while building the sample for this post, I found an important distinction:</p>
<blockquote>
<p>A centrally governed OAuth experience is not automatically the EMA protocol.</p>
</blockquote>
<p>App Service and Entra can give you a strongly governed MCP endpoint today. The full EMA flow additionally requires the enterprise identity provider to issue an Identity Assertion JWT Authorization Grant, or ID-JAG, and the MCP authorization server to exchange it. Same goal, related building blocks, different wire protocol.</p>
<p>So I built both.</p>
<h2>Why the normal OAuth flow gets expensive</h2>
<p>Standard MCP authorization is user-driven. A client discovers an MCP server, sends the user through that server's authorization flow, receives an access token, and repeats the process for the next server.</p>
<p>That is a good property for consumer scenarios. The user chooses which application can reach which data.</p>
<p>At enterprise scale, the same pattern becomes an authorization tax:</p>
<ul>
<li>Every employee has to connect every approved MCP server.</li>
<li>Consent and account-selection prompts create inconsistent setup.</li>
<li>Security teams have to reason about access across many separate authorization relationships.</li>
<li>Offboarding and policy changes are harder to apply from one control plane.</li>
<li>Work and personal identities can get mixed together at the worst possible boundary: the tool that can act on a user's behalf.</li>
</ul>
<p>EMA moves the authoritative decision back to the enterprise IdP.</p>
<h2>What EMA changes on the wire</h2>
<p>The user still signs in to the MCP host with the corporate identity provider. The difference comes when the client needs an access token for an MCP server.</p>
<ol>
<li>The MCP client exchanges the user's identity assertion at the enterprise IdP for an ID-JAG. The stable extension uses OAuth token exchange semantics from <a class="lia-external-url" href="https://datatracker.ietf.org/doc/html/rfc8693" rel="noopener" target="_blank">RFC 8693</a>.</li>
<li>The IdP evaluates enterprise policy for the requested client, MCP resource, user, and scopes.</li>
<li>If policy allows access, the IdP issues a short-lived, audience-bound ID-JAG.</li>
<li>The client presents that JWT to the MCP authorization server using the JWT bearer grant from <a class="lia-external-url" href="https://datatracker.ietf.org/doc/html/rfc7523" rel="noopener" target="_blank">RFC 7523</a>.</li>
<li>The authorization server validates the assertion and returns the resource access token the client uses for MCP calls.</li>
</ol>
<p><img alt="Standard Entra OAuth on App Service compared with the EMA ID-JAG exchange" src="https://raw.githubusercontent.com/seligj95/app-service-ema-mcp/main/assets/authorization-paths.png" /></p>
<p>The user never goes through a second browser flow at the MCP authorization server. The enterprise IdP already made the decision.</p>
<p>That gives the organization three useful properties:</p>
<ul>
<li><strong>Authorize once, inherit everywhere.</strong> Admins enable approved servers and users receive access according to their existing groups and roles.</li>
<li><strong>Central policy and revocation.</strong> Conditional access, employment state, device requirements, and other policy remain in the IdP.</li>
<li><strong>A cleaner identity boundary.</strong> The enterprise login is the source of authority instead of an account picker at every MCP server.</li>
</ul>
<h2>What Entra and App Service provide today</h2>
<p>Azure App Service already has a very good home for an enterprise MCP resource server: <a class="lia-external-url" href="https://learn.microsoft.com/azure/app-service/configure-authentication-mcp" rel="noopener" target="_blank">App Service Authentication</a> sits in front of the application and validates Microsoft Entra access tokens before a request reaches your Python process. App Service Authentication’s MCP authorization integration and protected resource metadata support are currently in preview.</p>
<p>In the deployable half of the sample, App Service:</p>
<ul>
<li>publishes OAuth protected resource metadata for MCP discovery;</li>
<li>requires authentication on <code>/mcp</code> and returns <code>401</code> to unauthenticated requests;</li>
<li>validates token signature, issuer, audience, and lifetime;</li>
<li>allows only the configured client application IDs;</li>
<li>injects the validated principal into platform-controlled request headers;</li>
<li>leaves only <code>/</code> and <code>/health</code> public;</li>
<li>sends OpenTelemetry data to Application Insights with managed identity.</li>
</ul>
<p>The Entra application exposes <code>user_impersonation</code> and preauthorizes Visual Studio Code and Azure CLI. Tenant administrators can then apply Conditional Access to the enterprise application and inspect Entra sign-in logs.</p>
<p>That is centrally governed OAuth. It removes consent prompts for known clients and puts token validation at the platform edge.</p>
<p>It is not native EMA because this path does not ask Entra to issue an ID-JAG through RFC 8693, and there is no RFC 7523 assertion exchange at a separate MCP authorization server.</p>
<p>Here is the practical comparison:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>Capability</th><th>Entra + App Service path</th><th>EMA path</th></tr></thead><tbody><tr><td>Central tenant policy</td><td>Yes</td><td>Yes</td></tr><tr><td>Protected resource metadata</td><td>Yes</td><td>Yes</td></tr><tr><td>Known-client preauthorization</td><td>Yes, through Entra preauthorization</td><td>Often still required at the IdP and authorization server</td></tr><tr><td>Per-server browser flow</td><td>Avoided for preauthorized clients</td><td>Avoided by protocol design</td></tr><tr><td>Enterprise IdP issues an ID-JAG</td><td>No</td><td>Yes</td></tr><tr><td>MCP authorization server exchanges the ID-JAG</td><td>No</td><td>Yes</td></tr><tr><td>Included in the sample</td><td>Deployable Azure app</td><td>Local interoperability lab</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>The distinction matters because "no consent prompt" describes a user experience, not a protocol proof.</p>
<h3>Could you run full EMA on App Service today?</h3>
<p>Yes. App Service does not prevent you from deploying the complete EMA flow. If your enterprise IdP can issue ID-JAGs, you can implement the resource authorization server and MCP token validation in application code—or point the MCP server at a separate authorization service. App Service then remains the compute platform rather than the authorization boundary.</p>
<p>That approach replaces Easy Auth’s platform-managed token validation with responsibilities such as token issuance, signing-key management, ID-JAG validation, replay protection, scope enforcement, and audit logging. The remaining prerequisite is still an enterprise IdP and MCP client that support the ID-JAG exchange.</p>
<h2>I built both paths on purpose</h2>
<p>The companion repository is <a class="lia-external-url" href="https://github.com/seligj95/app-service-ema-mcp" rel="noopener" target="_blank">seligj95/app-service-ema-mcp</a>.</p>
<p>The Azure path is a FastAPI MCP server running on Linux App Service. It exposes two read-only tools:</p>
<ul>
<li><code>whoami</code> returns the tenant, client, subject, roles, and scopes that App Service Authentication validated.</li>
<li><code>authorization_model</code> states exactly which authorization model protects the deployment.</li>
</ul>
<p>The local path runs four components in one process:</p>
<ul>
<li>a stand-in enterprise IdP;</li>
<li>an MCP authorization server;</li>
<li>an MCP resource server;</li>
<li>an MCP client using the official Python SDK's identity-assertion APIs.</li>
</ul>
<p>The SDK's <code>IdentityAssertionOAuthProvider</code> covers the second leg: the RFC 7523 JWT bearer grant from the MCP client to the MCP authorization server. The first leg, the RFC 8693 exchange with the enterprise IdP that produces the ID-JAG, is deployment-specific and supplied through the SDK's <code>assertion_provider</code> callback. The lab fulfills that callback with its in-process stand-in IdP.</p>
<p>The lab validates the ID-JAG signature, <code>typ</code>, issuer, audience, client ID, resource, scopes, expiration, and single-use <code>jti</code>. It also tests rejection cases for the wrong issuer, wrong audience, wrong resource, scope escalation, expiration, and replay. The lab deliberately requires a <code>resource</code> claim, which is stricter than the stable specification's optional claim; production authorization servers should choose that posture explicitly.</p>
<p>The stand-in IdP and in-memory token store are deliberately not production components. They make the protocol visible and testable without pretending Entra currently exposes the exact issuance flow used by the lab.</p>
<h2>Run the EMA flow locally</h2>
<p>Clone the repository and install the project:</p>
<pre class="language-bash" contenteditable="false" tabindex="0"><code>git clone https://github.com/seligj95/app-service-ema-mcp
cd app-service-ema-mcp
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
</code></pre>
<p>Then run the complete ID-JAG exchange:</p>
<pre class="language-bash" contenteditable="false" tabindex="0"><code>python -m examples.ema_lab.client
</code></pre>
<p>The final result is the identity and authorization context returned by the MCP server:</p>
<pre class="language-text" contenteditable="false" tabindex="0"><code>{'subject': 'alice@example.com', 'client_id': 'finance-agent',
 'scopes': ['mcp:whoami'], 'resource': 'http://localhost/mcp'}
</code></pre>
<p>Run the test suite to see both the successful exchange and the rejection boundaries:</p>
<pre class="language-bash" contenteditable="false" tabindex="0"><code>python -m ruff check .
python -m pytest
</code></pre>

<h2>Deploy the Entra-governed MCP server</h2>
<p>The repository includes azd and Bicep for a Basic B1 Linux App Service plan, Python 3.14, App Service Authentication, protected resource metadata, Log Analytics, Application Insights, and managed-identity telemetry.</p>
<p>After choosing a subscription:</p>
<pre class="language-bash" contenteditable="false" tabindex="0"><code>azd auth login

azd env set AZURE_SUBSCRIPTION_ID &lt;subscription-id&gt;

</code></pre>
<p>The Entra bootstrap runs once before <code>azd up</code> because azd resolves required Bicep parameters before the preprovision hook. After that, the hook reruns the same idempotent configuration on each provision.</p>
<p>Verify the deployed boundary:</p>
<pre class="language-bash" contenteditable="false" tabindex="0"><code>./scripts/verify-deployment.sh
</code></pre>
<p>The script checks that protected resource metadata is available, an anonymous MCP request is rejected, Azure CLI can obtain the delegated API token, and the same MCP request succeeds with that token.</p>
<p>During deployment validation, I invoked <code>whoami</code> against the deployed app. App Service returned the expected Azure CLI client and the delegated scope:</p>
<pre class="language-json" contenteditable="false" tabindex="0"><code>{
  "authentication_type": "aad",
  "client_id": "04b07795-8ddb-461a-bbee-02f9e1bf7b46",

<p>The response above is shortened for readability. The complete tool result also includes <code>name</code>, <code>subject</code>, <code>tenant_id</code>, and <code>roles</code>.</p>
<h2>Three details worth carrying into production</h2>
<p>The platform did the hard security work, but three integration details were easy to miss.</p>
<h3>1. Allow the audience Entra actually emits</h3>
<p>The client requests <code>api://&lt;application-id&gt;/user_impersonation</code>, but a v2 delegated access token can carry the bare application client ID in <code>aud</code>. The sample allows both the bare client ID and the <code>api://</code> form while still rejecting tokens for every other resource.</p>
<h3>2. Keep the SDK's DNS-rebinding protection</h3>
<p>The MCP Python SDK defaults to localhost when a server does not declare its deployment hostname. That is a safe local default, but a deployed request correctly fails with <code>421 Invalid Host header</code>.</p>
<p>The sample reads <code>WEBSITE_HOSTNAME</code> and allowlists only that exact App Service hostname and its optional port form. It does not disable the protection.</p>
<h3>3. Account for App Service claim mapping</h3>
<p>App Service maps some JWT claim names before it builds <code>X-MS-CLIENT-PRINCIPAL</code>. For example, the delegated <code>scp</code> value can arrive under the mapped scope claim URI.</p>
<p>The application accepts both representations, while continuing to trust only the principal header injected by App Service. A caller-supplied identity header never becomes proof of authentication because the platform strips and replaces these headers at the edge.</p>
<h2>The production checklist</h2>
<p>This sample gives you the authorization boundary, not every production control. Before using the pattern for a real tool surface:</p>
<ul>
<li>Apply Conditional Access deliberately, starting in report-only mode.</li>
<li>Add tool-level scope or role checks when different tools have different sensitivity.</li>
<li>Use managed identity or an explicit on-behalf-of flow for downstream APIs; never forward the MCP resource token.</li>
<li>Add private networking or an API gateway when the workload requires network isolation.</li>
<li>Keep access tokens and ID-JAGs short-lived.</li>
<li>Validate ID-JAG signatures with the enterprise IdP's published JWKS, discovered from its authorization server metadata. The lab's shared HMAC key exists only to keep the local flow self-contained.</li>
<li>Enforce single-use ID-JAG replay protection at the authorization server.</li>
<li>Log authorization decisions without logging bearer tokens or assertion contents.</li>
<li>Replace the SDK Git pin after the identity-assertion APIs reach a tested package release.</li>
</ul>
<h2>The takeaway</h2>
<p>EMA is bigger than eliminating another consent screen. It defines how an enterprise IdP becomes the authorization control plane for an MCP fleet, with a portable assertion that an MCP authorization server can validate.</p>
<p>Entra ID and App Service already give you many of the outcomes enterprises need: tenant policy, known-client governance, protected resource discovery, platform token validation, Conditional Access, and centralized telemetry.</p>
<p>Just name the boundary honestly.</p>
<p>Use App Service and Easy Auth when you want a deployable, Entra-governed MCP endpoint today. If your IdP already supports ID-JAG issuance, App Service can also host a custom EMA authorization implementation. Otherwise, use the local lab to understand and test the protocol while platform-native support develops.</p>
<p>That is the part I like most about the extension: enterprise authorization stops being an experience every MCP server invents and becomes a protocol the ecosystem can share.</p>
