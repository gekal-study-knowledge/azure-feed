<h2 id="where-reusable-pipelines-start-to-hurt">Where reusable pipelines start to hurt</h2>
<blockquote>
<p><strong>Who this is for:</strong> Platform and DevOps engineers who build shared Azure DevOps Pipeline Templates and want other teams to adopt them consistently.</p>
</blockquote>
<p>If you have ever built a set of shared Azure DevOps Pipeline Templates, you probably know how this goes. You write a whole library of clean, well-factored templates: provisioning infrastructure, deploying apps, scanning, promotion, and more. Each one is tidy on its own. Then the first team tries to actually use them together, and things get messy fast.</p>
<p>That is exactly what happened to us on a customer engagement, while building a DevOps framework for their engineering teams. The templates themselves were fine. The trouble was wiring them together. Every consumer pipeline had to know how to call each template it used: the right order, which values one template fed another, and the full parameter list for every one of them. As the library grew, those consumer pipelines grew with it, long and repetitive. That friction turned into a real adoption problem. Getting started meant wading through pages of parameters, so teams put it off, copied whatever the team next door had, or quietly built their own thing instead.</p>
<p>This post follows that story, from the tangle of parameters to the solution we landed on. Here is how it comes together.</p>
<h2 id="where-we-started-good-templates-hard-to-adopt">Where we started: Good templates, hard to adopt</h2>
<p>The DevOps framework we built had many templates. To keep this walkthrough concrete, we will follow just two of them: one that provisions infrastructure with Terragrunt (a wrapper around Terraform), and one that deploys an app to Kubernetes with Helm. Both are trimmed down to the essentials here so they are easy to follow.</p>
<p>The infrastructure template, <code>templates/infra/terragrunt-deploy.yml</code>:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>parameters:
  - name: stack
    type: string
  - name: workingDir
    type: string

steps:
  - script: |
      cd ${{ parameters.workingDir }}
      terragrunt plan -out=tfplan
      terragrunt apply -auto-approve tfplan
    displayName: "Deploy ${{ parameters.stack }}"</code></pre>
<p>The application template, <code>templates/app/helm-deploy.yml</code>:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>parameters:
  - name: releaseName
    type: string
  - name: chart
    type: string
  - name: namespace
    type: string
  - name: imageTag
    type: string

steps:
  - script: |
      helm upgrade --install ${{ parameters.releaseName }} ${{ parameters.chart }} \
        --namespace ${{ parameters.namespace }} \
        --set image.tag=${{ parameters.imageTag }}
    displayName: "Deploy ${{ parameters.releaseName }}"</code></pre>
<p>There is nothing wrong with either file. The pain showed up in the pipeline that had to use them, where a team had to stitch the templates together by hand, remember the order, and repeat that boilerplate for every environment. Do that across a dozen services and you get long, copy-pasted pipelines that teams struggle to adopt. And because the wiring is done by hand, it leaves loopholes: a team can skip a step or override a parameter and slip past the guardrails you thought were in place.</p>
<h2 id="challenge-1-wiring-the-templates-together">Challenge 1: Wiring the templates together</h2>
<p>The obvious move was to hide the wiring behind a single template that owned the order and the plumbing. We called it the orchestrator template: a consumer pipeline called that one template, and it wired up the rest.</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># templates/deployment-orchestrator.yml  (the single orchestrator)
parameters:
  - name: infraStack
    type: string
  - name: infraWorkingDir
    type: string
  - name: releaseName
    type: string
  - name: chart
    type: string
  - name: namespace
    type: string
  - name: imageTag
    type: string
  # ...and this list just kept growing

stages:
  - stage: Infra
    jobs:
      - job: infra
        steps:
          - template: infra/terragrunt-deploy.yml
            parameters:
              stack: ${{ parameters.infraStack }}
              workingDir: ${{ parameters.infraWorkingDir }}

  - stage: App
    dependsOn: Infra
    jobs:
      - job: app
        steps:
          - template: app/helm-deploy.yml
            parameters:
              releaseName: ${{ parameters.releaseName }}
              chart: ${{ parameters.chart }}
              namespace: ${{ parameters.namespace }}
              imageTag: ${{ parameters.imageTag }}</code></pre>
<p>A team used it by calling that one template and passing a value for every parameter it exposed:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># azure-pipelines.yml  (a team's pipeline)
parameters:
  - name: imageTag
    type: string

extends:
  template: templates/deployment-orchestrator.yml
  parameters:
    infraStack: network
    infraWorkingDir: infra/network
    releaseName: orders-api
    chart: charts/orders-api
    namespace: orders
    imageTag: ${{ parameters.imageTag }}
    # ...and a value for every other parameter, too</code></pre>
<p>This solved the ordering and the copy-paste, but it handed us a new headache. This one template now had to expose every parameter of every template underneath it, and the list grew each time we added a capability. Worse, a real service usually needed more than one infrastructure stack and more than one Helm release. A flat list of parameters cannot express “two infrastructure stacks and three Helm releases” without silly names like <code>infraStack1</code>, <code>infraStack2</code>, and so on. Nobody could learn the thing. We had solved the wiring, only to trade it for a parameter problem.</p>
<h2 id="challenge-2-the-orchestrators-parameter-list-explodes">Challenge 2: The orchestrator’s parameter list explodes</h2>
<p>So how do you shrink that list? Step back and ask what you are really describing: a set of things to deploy. So the input should describe that set, not a long flat list of loose values. That is where the deployment manifest came in: one small config that lists the infrastructure to create and the apps to deploy.</p>
<p>It reads about how you would expect:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>infrastructure:
  - stack: network
    workingDir: infra/network

applications:
  - releaseName: orders-api
    chart: charts/orders-api
    namespace: orders</code></pre>
<p>Now the orchestrator can take that single manifest and loop over it, instead of exposing dozens of separate parameters. Its parameter list collapses to one, and a <code>${{ each }}</code> loop turns each entry into a stage or job:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># templates/deployment-orchestrator.yml  (the orchestrator, now manifest-driven)
parameters:
  - name: manifest
    type: object
  - name: imageTag
    type: string

stages:
  - stage: Infra
    jobs:
      - ${{ each stack in parameters.manifest.infrastructure }}:
          - job: infra_${{ stack.stack }}
            steps:
              - template: infra/terragrunt-deploy.yml
                parameters:
                  stack: ${{ stack.stack }}
                  workingDir: ${{ stack.workingDir }}
  # ...an App stage loops over parameters.manifest.applications the same way</code></pre>
<p>And a consumer passes that manifest straight to the orchestrator:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># azure-pipelines.yml  (a team's pipeline)
parameters:
  - name: imageTag
    type: string

extends:
  template: templates/deployment-orchestrator.yml
  parameters:
    imageTag: ${{ parameters.imageTag }}
    manifest:
      infrastructure:
        - stack: network
          workingDir: infra/network
      applications:
        - releaseName: orders-api
          chart: charts/orders-api
          namespace: orders</code></pre>
<p>The parameter problem is solved. But hand-writing that whole manifest inside every pipeline is a lot to repeat, so the natural instinct is to pull it out into its own file. That is where things get tricky.</p>
<h2 id="challenge-3-the-manifest-is-read-too-late-to-shape-the-pipeline">Challenge 3: The manifest is read too late to shape the pipeline</h2>
<p>So we tried exactly that: we moved the manifest into a <code>deployment-manifest.yml</code> file and had the orchestrator read it back and expand it into stages and jobs. It sounded reasonable, but it did not work. To see why, you need to know how Azure DevOps builds a pipeline before it runs anything.</p>
<p>An Azure DevOps pipeline actually happens in two phases, and they are further apart than people expect.</p>
<p>First comes the build phase, before anything runs. Azure DevOps reads your YAML, pulls in every template, evaluates every <code>${{ }}</code> expression, and unrolls every <code>${{ each }}</code> loop. Out of this it produces one final, fully assembled pipeline. At this point no agent has started and no repo has been checked out. Only parameters and template expressions exist yet.</p>
<p>Then comes the run phase. The assembled pipeline runs. An agent starts, checks out your code, and only now can a script open a file on disk.</p>
<img />
<p>Here is the problem. Your <code>deployment-manifest.yml</code> does not exist as far as the pipeline is concerned until an agent checks out the repo, and that checkout happens during the run phase. So if the manifest is supposed to decide how many stages there are, or how many apps each get their own job, that decision has to be made earlier, while the pipeline is still being built.</p>
<blockquote>
<p><strong>Important:</strong> The shape of the pipeline, its stages, jobs, and loops, is locked in while the pipeline is being built. A file you read during the run comes too late to change any of it.</p>
</blockquote>
<p>That was the wall we hit. The manifest was the right idea, but reading it from a file happened too late for the orchestrator to turn it into stages and jobs. So the manifest could not come from a file read during the run phase. It had to already exist, as an object, before the pipeline was assembled.</p>
<h2 id="the-manifest-facade-pattern-build-the-config-while-the-pipeline-is-assembled">The Manifest Facade pattern: Build the config while the pipeline is assembled</h2>
<p>The solution is to stop thinking of the manifest as a file to read, and start thinking of it as an object you build while the pipeline is being assembled. Parameters are available then. Template expressions can build a whole object then. So we added a small template, kept in the team’s own repo, with one job: take a couple of simple inputs, build the full manifest from them, and pass it to the shared orchestrator.</p>
<p>We called it the builder, since assembling the manifest is its only job. It stays thin and lives next to the team’s pipeline, while the orchestrator stays in the shared platform repo.</p>
<p>This is not a brand-new invention so much as a few familiar ideas working together, applied at pipeline build time. The manifest is a Parameter Object (Martin Fowler’s refactoring for collapsing a long parameter list into one structured value). The orchestrator is a Facade (the Gang of Four pattern for putting one simple, unified interface over a subsystem, here the underlying leaf templates). And the small template in the team’s repo is the piece that assembles that Parameter Object from a couple of inputs. What makes it an Azure DevOps pattern is the timing: the manifest is built as an object while the pipeline is assembled, so it can drive template expansion instead of sitting in a file that only gets read during the run. That is the twist we did not see written down anywhere, so we gave it a name: the Manifest Facade pattern.</p>
<p>In practice it comes together in three small pieces: the consumer pipeline references the builder, the builder assembles the manifest and hands it to the shared orchestrator, and the orchestrator expands that manifest into stages and jobs. Here is how the files extend into one another:</p>
<img />
<p>Here is each piece in turn.</p>
<h3 id="step-1-the-consumer-references-the-builder">Step 1: The consumer references the builder</h3>
<p>The consumer pipeline extends the builder that lives in its own repo. It also declares the shared platform repo as a resource, so the orchestrator the builder calls is available while the pipeline is built.</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># azure-pipelines.yml  (the team's pipeline)
parameters:
  - name: imageTag
    displayName: Image tag
    type: string

resources:
  repositories:
    - repository: platform
      type: git
      name: platform/pipeline-templates
      ref: refs/tags/v1.0.0

trigger:
  - main

extends:
  template: config/deployment.yml@self
  parameters:
    environment: dev
    service: orders
    imageTag: ${{ parameters.imageTag }}</code></pre>
<p>Because the image tag is a runtime parameter, it is declared here in the consumer pipeline, which is what makes it appear in the Run pipeline panel for someone to fill in. Beyond that, the team passes only an environment and a service name, and the builder works out the rest.</p>
<h3 id="step-2-the-builder-assembles-the-manifest">Step 2: The builder assembles the manifest</h3>
<p>The builder takes those inputs and assembles the whole manifest from them, then hands it to the orchestrator. Every structural value here is a parameter or a template expression, so all of it is ready while the pipeline is being assembled.</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># config/deployment.yml  (builder, in the team's repo)
parameters:
  - name: environment
    type: string
  - name: service
    type: string
  - name: imageTag
    type: string

extends:
  template: deployment-orchestrator.yml@platform
  parameters:
    imageTag: ${{ parameters.imageTag }}
    manifest:
      schemaVersion: v1
      infrastructure:
        - stack: network
          workingDir: infra/${{ parameters.environment }}/network
      applications:
        - releaseName: ${{ parameters.service }}
          chart: charts/${{ parameters.service }}
          namespace: ${{ parameters.service }}</code></pre>
<p>The builder assembles the manifest inline from the environment and service, then passes it straight to the orchestrator. The image tag is different: it is a runtime parameter the user supplies at queue time, so it is passed through to the orchestrator template and never becomes part of the manifest. The team gets a tiny interface, and the orchestrator still gets the full structure it needs.</p>
<h3 id="step-3-the-orchestrator-turns-the-config-into-stages-and-jobs">Step 3: The orchestrator turns the config into stages and jobs</h3>
<p>The orchestrator takes a single object and loops over it with <code>${{ each }}</code>. Each stage and job gets generated while the pipeline is assembled.</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># deployment-orchestrator.yml  (shared platform repo)
parameters:
  - name: manifest
    type: object
  - name: imageTag
    type: string

stages:
  # a ValidateManifest stage runs first (covered in the next section)
  - stage: Infra
    jobs:
      - ${{ each stack in parameters.manifest.infrastructure }}:
          - job: infra_${{ stack.stack }}
            steps:
              - template: infra/terragrunt-deploy.yml
                parameters:
                  stack: ${{ stack.stack }}
                  workingDir: ${{ stack.workingDir }}

  - stage: App
    dependsOn: Infra
    jobs:
      - ${{ each app in parameters.manifest.applications }}:
          - job: app_${{ app.releaseName }}
            steps:
              - template: app/helm-deploy.yml
                parameters:
                  releaseName: ${{ app.releaseName }}
                  chart: ${{ app.chart }}
                  namespace: ${{ app.namespace }}
                  imageTag: ${{ parameters.imageTag }}</code></pre>
<p>Because the manifest is a real object by the time the loops run, <code>${{ each }}</code> unrolls it into actual jobs. List two stacks and you get two jobs. List two apps and you get two deploy jobs. And because the team only describes what to deploy, the sensitive wiring like service connections stays inside the platform templates, out of reach. The loophole is gone because the parameter is gone.</p>
<h2 id="why-the-order-of-things-matters">Why the order of things matters</h2>
<p>The whole pattern comes down to who does what, and when.</p>
<ul>
<li>The builder turns a simple intent (“deploy orders to dev”) into a full manifest, while the pipeline is being assembled.</li>
<li>The orchestrator turns that manifest into real stages and jobs, still while the pipeline is being assembled.</li>
<li>Only the leaf templates do the real deployment work during the run: checkout, <code>terragrunt apply</code>, <code>helm upgrade</code>.</li>
</ul>
<p>Nothing about the shape of the pipeline waits for the run, so nothing about it depends on a file that only shows up after checkout. That is the whole trick.</p>
<p>If you do have values you genuinely cannot know until the run, like a secret fetched from a vault or an artifact version an earlier stage writes to a variable, those still belong in runtime variables and variable groups. The manifest is for the structure and config you already know when you queue the build, which is almost always the part that was causing the pain.</p>
<h2 id="validating-the-manifest-against-a-schema">Validating the manifest against a schema</h2>
<p>Once the manifest became the one interface every team fills in, it needed a contract. We wrote that contract as a JSON Schema and kept it in the shared platform repo under <code>schema/v1/</code>. The folder name is the version: backward-compatible additions go straight into <code>v1</code>, and the day we need a breaking change we add a <code>schema/v2/</code> alongside it, so existing consumers keep working while the schema evolves. Each manifest carries a <code>schemaVersion</code> so the orchestrator knows which contract to hold it to.</p>
<p>On top of that, we validate in three layers, each catching a different class of mistake.</p>
<img />
<p>Layer 1 is build time, for free. Because the orchestrator’s parameters are typed, with <code>manifest</code> declared as an <code>object</code>, Azure DevOps catches a range of structural problems while it expands the templates, before anything runs. For example, if a manifest left out <code>infrastructure</code> or misspelled it, the orchestrator’s <code>${{ each stack in parameters.manifest.infrastructure }}</code> loop would have nothing valid to iterate over, and the failure would surface during template expansion rather than halfway through a deployment.</p>
<p>Layer 2 is a version check that runs at build time. Both the <code>${{ if }}</code> and <code>parameters.manifest.schemaVersion</code> are resolved while the pipeline is being assembled, so the orchestrator decides right then whether it understands the manifest’s version. If it does not, the only thing it generates is a single failing stage, and the real deployment stages are never built, so nothing runs against a contract the orchestrator does not know:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code># deployment-orchestrator.yml  (shared platform repo)
parameters:
  - name: manifest
    type: object

stages:
  # Layer 2: reject schema versions this orchestrator does not understand
  - ${{ if not(containsValue(split('v1', ','), parameters.manifest.schemaVersion)) }}:
      - stage: UnsupportedSchemaVersion
        jobs:
          - job: fail
            steps:
              - script: |
                  echo "##vso[task.logissue type=error]Unsupported manifest schemaVersion '${{ parameters.manifest.schemaVersion }}'"
                  exit 1
  # the ValidateManifest, Infra, and App stages below are generated only when the version is supported</code></pre>
<p>Layer 3 is a run-time check against the full schema. The first stage the orchestrator generates is <code>ValidateManifest</code>. Because the schema lives in the platform repo, the job checks that repo out first. Then it serializes the manifest object to JSON with the <code>convertToJson</code> expression, writes that JSON out to a file, and runs a JSON Schema checker to compare the file against the schema. If the manifest breaks the contract, the pipeline stops here, before any infrastructure or app stage runs:</p>
<pre class="lia-code-sample language-yaml" contenteditable="false" tabindex="0"><code>  # Layer 3: validate the real manifest object against the JSON Schema
  - stage: ValidateManifest
    jobs:
      - job: validate
        steps:
          # the schema lives in the platform repo, so check it out first
          - checkout: platform
          - script: |
              echo '${{ convertToJson(parameters.manifest) }}' &gt; manifest.json
              pip install check-jsonschema
              check-jsonschema --schemafile schema/${{ parameters.manifest.schemaVersion }}/deployment.schema.json manifest.json
            displayName: "Validate manifest against schema"</code></pre>
<p>Layer 1 is automatic, Layer 2 rejects an unknown contract at build time so the deployment stages are never generated, and Layer 3 confirms the actual values match the schema before any real work begins. Together they turn “the manifest looked right” into “the manifest is provably valid.”</p>
<h2 id="a-few-trade-offs-to-keep-in-mind">A few trade-offs to keep in mind</h2>
<p>No pattern comes without trade-offs. A few things worth weighing:</p>
<ul>
<li>The manifest has to be something template expressions can build. You can compose objects, loop, and branch with <code>${{ if }}</code>, but there is no running arbitrary code while the pipeline is assembled. Anything fancier may need a prep step or a file generated upstream.</li>
<li>Every team carries a small builder template. We think that is a fair trade, since it keeps their intent local and readable, but it is one more file per repo. Keep it thin and let the orchestrator hold the real logic.</li>
<li>Treat the schema as living documentation. Because the manifest’s JSON Schema spells out every field and what it means, teams can read it to build their own manifest with confidence, instead of reverse-engineering the orchestrator.</li>
<li>Pin the shared repo to a tag, like the <code>v1.0.0</code> above, so a change to the orchestrator does not silently change everyone’s pipeline on the next run.</li>
<li>Debugging takes a small shift in habit. When something looks off, use the pipeline’s preview to see the fully assembled YAML before it runs. It shows you exactly what the loops produced.</li>
</ul>
<blockquote>
<p><strong>Tip:</strong> Use the Azure DevOps pipeline preview to see the fully assembled YAML without running anything. It is the fastest way to confirm your manifest unrolled into the stages and jobs you expected.</p>
</blockquote>
<h2 id="wrapping-up">Wrapping up</h2>
<p>It is a journey a lot of platform teams will recognize. Clean templates, messy wiring, one orchestrator that fixes the order but drowns in parameters, a config file that brings back sanity, and then the surprise that reading it at the wrong moment means it can never shape the pipeline. The solution is small and it sticks. Put a thin builder template next to each team, let it assemble the manifest from a couple of simple inputs, and let a shared orchestrator turn that manifest into stages and jobs.</p>
<p>Teams get an interface they can easily understand and adopt. The platform team keeps the wiring and the guardrails in one place. And the timing gap that trips up so many “just read the config file” attempts stops being a problem, because you are working with it instead of against it.</p>
<h2 id="key-takeaways">Key takeaways</h2>
<ul>
<li>Shared Pipeline Templates stall on adoption when every team has to wire them together by hand.</li>
<li>A single orchestrator template fixes the ordering, but a flat parameter list does not scale to real adoption.</li>
<li>A config file read during the pipeline run cannot shape the pipeline, because stages and jobs are decided earlier, while the pipeline is assembled.</li>
<li>The Manifest Facade pattern builds the config as an object at assembly time, so one small input drives many templates, consistently and with the guardrails baked in.</li>
<li>Give the manifest a versioned JSON Schema and validate it in layers, so a broken contract fails fast instead of halfway through a deployment.</li>
</ul>
<p>How are you handling template sprawl in your own pipelines? We would love to hear what has worked for your teams in the comments.</p>

<h3><span><span>The Challenge: Synthesizing fragmented feedback signals, to improve Azure's experience quality at scale</span></span><span>&nbsp;</span></h3>
<p><span>Customers experience products and services end to end, but product&nbsp;experiences&nbsp;are often structured around individual service.&nbsp;One&nbsp;team may&nbsp;only&nbsp;know its top issues, while&nbsp;another may see only its own slice of&nbsp;experience.&nbsp;&nbsp;That structure&nbsp;makes&nbsp;it difficult to&nbsp;identify&nbsp;cross-cutting friction across the broader&nbsp;product&nbsp;experience.</span><span>&nbsp;</span></p>
<p><span>The&nbsp;feedback&nbsp;signals themselves&nbsp;are&nbsp;also fragmented. Customers share feedback through in-product surveys, support cases, field conversations, and social channels. Most product teams&nbsp;can&nbsp;see only part of that picture, making it hard to distinguish&nbsp;isolated&nbsp;comments&nbsp;from meaningful trends,&nbsp;understand which issues were having the greatest impact, and&nbsp;avoid missing&nbsp;critical feedback.</span><span>&nbsp;</span></p>
<p><span>For the Azure&nbsp;team,&nbsp;the challenges of&nbsp;fragmentation&nbsp;were amplified&nbsp;by scale.&nbsp;The&nbsp;team processed&nbsp;roughly 10,000&nbsp;to 15,000 customer feedback reports each&nbsp;month, and&nbsp;synthesizing that feedback required&nbsp;80 to&nbsp;100 hours&nbsp;of expert analysis.&nbsp;&nbsp;Additional&nbsp;effort was needed&nbsp;to translate findings into consistent engineering&nbsp;work&nbsp;items.&nbsp;As feedback&nbsp;volume&nbsp;grew,&nbsp;manual analysis&nbsp;became increasingly&nbsp;unsustainable&nbsp;creating&nbsp;delays in identifying and addressing customer priorities.</span><span>&nbsp;</span></p>
<p><span>Compounding&nbsp;the challenge was the absence of an&nbsp;effective&nbsp;feedback loop&nbsp;to measure the impact of&nbsp;quality improvements.&nbsp;Teams struggled to&nbsp;justify&nbsp;investments in quality over&nbsp;new features&nbsp;because the return on those investments was difficult to quantify.&nbsp;The absence of a closed-loop measurement system made it difficult to consistently assess the&nbsp;customer&nbsp;impact of quality improvements.&nbsp;</span><span>&nbsp;</span></p>
<p><span>The team needed a system that could&nbsp;operate&nbsp;across organizational boundaries and across the product development lifecycle:</span><span>&nbsp;</span></p>
<ul>
<li><span>Identify&nbsp;the&nbsp;most&nbsp;critical&nbsp;customer issues across&nbsp;fragmented&nbsp;feedback channels and product areas.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Convert&nbsp;those insights into&nbsp;actionable&nbsp;engineering work,&nbsp;help teams&nbsp;address&nbsp;issues&nbsp;effectively, and&nbsp;measure outcomes&nbsp;to close the loop.</span><span>&nbsp;</span></li>
</ul>
<p><span>The&nbsp;solution&nbsp;needed&nbsp;to preserve team-specific context,&nbsp;maintain&nbsp;auditability,&nbsp;continuously&nbsp;improve through feedback, and keep human experts in control of decisions that require judgment.&nbsp;To address these challenges, Microsoft launched the Great Experiences Matter (GEM)&nbsp;initiative.&nbsp;GEM is designed to analyze feedback signals in aggregate,&nbsp;with access controls and privacy safeguards designed to limit exposure&nbsp;of&nbsp;customer-identifiable information while helping teams&nbsp;identify&nbsp;patterns across channels.</span><span>&nbsp;</span></p>
<h3><span><span>The Solution: an agentic feedback-to-fix loop with humans in control</span></span><span>&nbsp;</span></h3>
<p><span>GEM created an AI-enabled&nbsp;feedback-to-fix&nbsp;workflow that connects customer listening, engineering action, and&nbsp;impact measurement across the product development lifecycle. The workflow uses&nbsp;Microsoft&nbsp;Foundry,&nbsp;Azure Data Explorer, Microsoft&nbsp;Fabric, Azure DevOps, and a set of custom agents to transform large volumes of qualitative feedback into prioritized insights and actionable&nbsp;engineering&nbsp;work.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<img />
<pre><span>Fig 1. GEM AI-enabled automation workflow</span><span>&nbsp;</span></pre>
<p>&nbsp;</p>
<p><span>The&nbsp;system closes&nbsp;the loop through&nbsp;two&nbsp;connected motions.</span><span>&nbsp;</span></p>
<p><span><strong>Find</strong>.</span><span>&nbsp;Agentic workflows remove noise and duplicate&nbsp;reports, assess relevance and actionability,&nbsp;classify&nbsp;feedback against known issues from UX research,&nbsp;cluster related&nbsp;issues, and&nbsp;surface&nbsp;likely&nbsp;root&nbsp;causes.&nbsp;GEM&nbsp;builds on&nbsp;years of deep end-to-end UX research that has&nbsp;identified&nbsp;systemic friction across customer journeys and product boundaries. By continuously triangulating GEM signals with ongoing research, we combine broad, scalable listening with deep human insight to inform a more cohesive Azure experience.</span><span>&nbsp;</span></p>
<p><span>The results&nbsp;are surfaced&nbsp;through global&nbsp;scorecards&nbsp;for cross-cutting Azure issues and vertical scorecards tailored to individual product teams.</span><span>&nbsp;</span></p>
<p>&nbsp;</p>
<img />
<pre><span>Fig 2.&nbsp;GEM Global scorecard of top issues&nbsp;with Azure, data has been fictionalized to protect intellectual property</span><span>&nbsp;</span></pre>
<p>&nbsp;</p>
<p><span><strong>Fix</strong>.</span><span>&nbsp;The workflow creates Azure DevOps work items with the customer&nbsp;context,&nbsp;likely reproduction&nbsp;steps, recommended next actions, and an auditable&nbsp;trace of the&nbsp;supporting&nbsp;analysis.&nbsp;To date,&nbsp;42% of the&nbsp;identified&nbsp;issues have been addressed&nbsp;through engineering action.&nbsp;The team is also extending&nbsp;an AI-assisted&nbsp;engineering&nbsp;workflow,&nbsp;using GitHub Copilot&nbsp;cloud agent,&nbsp;that can generate proposed fixes&nbsp;for&nbsp;straightforward issues. Engineers&nbsp;remain&nbsp;responsible for reviewing, refining, approving, and&nbsp;shipping any changes.</span><span>&nbsp;</span></p>
<p><span>The architecture is designed for inspection rather than blind automation.&nbsp;The recommendations&nbsp;include an&nbsp;auditable evidence trail&nbsp;allowing&nbsp;reviewers&nbsp;to&nbsp;inspect the&nbsp;source&nbsp;feedback, classifications, supporting references, confidence indicators, and recommendation&nbsp;actions.</span><span>&nbsp;</span></p>
<p><span>Human&nbsp;expertise&nbsp;enters the system at several points. Researchers shape the&nbsp;issue&nbsp;taxonomies and qualitative grounding. Product teams define&nbsp;ownership boundaries,&nbsp;business priorities,&nbsp;domain-specific&nbsp;vocabulary, and&nbsp;trusted&nbsp;sources&nbsp;that guide agent analysis. Engineers review and act on resulting work items, while leaders use scorecards to&nbsp;inform&nbsp;investment decisions.</span><span>&nbsp;</span></p>
<p><span>This context is captured in configuration files that&nbsp;evolve alongside&nbsp;the&nbsp;products&nbsp;they support.&nbsp;Teams&nbsp;can add new issue categories, refine keywords, clarify ownership boundaries, or&nbsp;identify&nbsp;trusted research&nbsp;sources. The next analysis&nbsp;cycle&nbsp;automatically&nbsp;incorporates&nbsp;&nbsp;the&nbsp;updated context without requiring&nbsp;changes to the underlying agents.</span><span>&nbsp;</span></p>
<p><span>That design creates a "feedback&nbsp;loop&nbsp;for&nbsp;the feedback&nbsp;loop".&nbsp;Teams review the root-cause analyses and work-item quality,&nbsp;identify&nbsp;gaps, and refine their configurations.&nbsp;This&nbsp;enables&nbsp;teams to continuously&nbsp;embed domain&nbsp;expertise&nbsp;into the workflow, improving how&nbsp;feedback&nbsp;is&nbsp;interpreted and prioritized&nbsp;without requiring changes to the underlying infrastructure.&nbsp;Their input improves&nbsp;subsequent&nbsp;runs, helping the system become more precise while preserving local product knowledge.</span>&nbsp;<br />&nbsp;<br /><span>The agent also&nbsp;maintains&nbsp;access to reports from&nbsp;previous&nbsp;runs and uses tools such as Web IQ and MCP servers to assess whether previously&nbsp;identified&nbsp;issues are improving, still require attention, or can be confidently closed.</span><span>&nbsp;</span></p>

The workflow generated an engineering work item&nbsp;describing the issue,&nbsp;customer impact,&nbsp;likely&nbsp;reproduction&nbsp;path, and recommended&nbsp;actions. The networking team reproduced the issue,&nbsp;validated&nbsp;the finding, and added it to its backlog.</span><span>&nbsp;</span></p>
<p><span>The goal is not to remove people from the process. Agents&nbsp;assume much of&nbsp;the cognitive load&nbsp;associated with&nbsp;sorting, clustering, tracing, and&nbsp;drafting,&nbsp;allowing experts&nbsp;to&nbsp;focus on judgment, prioritization, and implementation.&nbsp;Teams remain accountable for what is fixed, what is funded, and what is allowed to ship.</span><span>&nbsp;</span></p>
<h3><span><span>The Impact: measurable experience gains at Microsoft production scale</span></span><span>&nbsp;</span></h3>
<p><span>GEM began with manual interventions and is now scaling through AI-enabled workflows. The combined approach has produced measurable results across the Azure Portal and individual product experiences:</span><span>&nbsp;</span></p>
<ul>
<li><span>The workflow&nbsp;aggregates and&nbsp;analyzes&nbsp;approximately 10,000&nbsp;to 15,000 feedback reports each month across in-product, support, and social channels.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Automated analysis&nbsp;reduced manual synthesis time by&nbsp;over&nbsp;95&nbsp;percent, turning a process that required&nbsp;110&nbsp;to&nbsp;160&nbsp;hours each month into a workflow that runs in under&nbsp;60 minutes.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Between October 2025 and April 2026, Azure Portal feedback rates declined by 30%.&nbsp;During that same period, GEM helped teams&nbsp;identify&nbsp;and prioritize&nbsp;experience improvements, creating a clearer link between customer feedback, engineering action, and outcome measurement.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>Service-level outcomes&nbsp;also&nbsp;demonstrate&nbsp;how better signals can&nbsp;drive&nbsp;business impact.&nbsp;For example, improvements to VM Connect experiences&nbsp;reduced&nbsp;overall&nbsp;Core Compute support volume by&nbsp;1-2%&nbsp;per month, resulting in proportionate cost savings.&nbsp;The Azure Growth team increased subscription conversion by 9.1 percent after prioritizing issues highlighted through GEM.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span>The value goes beyond speed.&nbsp;Leaders gain a more consistent basis for prioritization, and engineering teams receive work that is already connected to customer evidence&nbsp;and impact signals.</span><span>&nbsp;</span></li>
</ul>
<p><span>Most importantly, every completed cycle creates new&nbsp;learning.&nbsp;Teams&nbsp;can measure&nbsp;changes in customer&nbsp;feedback and support volumes&nbsp;following improvements,&nbsp;incorporate&nbsp;partner input&nbsp;into future&nbsp;analyses, and&nbsp;continuously refine both the system and&nbsp;the products it helps improve.&nbsp;</span><span>&nbsp;</span></p>
<h3><span><span>Key learnings and transferable practices</span></span><span>&nbsp;</span></h3>
<p><span>The GEM experience offers several lessons for teams building agentic systems around complex, qualitative business processes:</span><span>&nbsp;</span></p>
<ol>
<li><strong><span>Start with&nbsp;real&nbsp;problems, not AI</span></strong><span> - </span>Value comes from understanding the genuine business needs and applying AI where it is demonstrably better than existing approaches.&nbsp;&nbsp;Applying AI without a clearly defined problem often adds complexity without delivering meaningful value.&nbsp;<span style="color: rgb(30, 30, 30);"> </span></li>
<li><strong>Design for the end-to-end workflow</strong><span style="color: rgb(30, 30, 30);"> -</span><span style="color: rgb(30, 30, 30);">&nbsp;Value comes from connecting&nbsp;insights to the broader business process,&nbsp;including grounding&nbsp;in prior knowledge,&nbsp;prioritization, engineering action, post-fix&nbsp;measurement&nbsp;and reporting.&nbsp;Standalone&nbsp;AI output creates limited value, while an integrated workflow drives outcomes.</span><span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
<li><strong><span>Design for human judgment and accountability</span></strong><span> - </span>Agents can reduce toil and cognitive load, but researchers, product managers, engineers, and leaders&nbsp;remain&nbsp;responsible for&nbsp;validating&nbsp;insights and determining&nbsp;appropriate actions.<span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
<li><strong><span>Ground agents in the knowledge of the teams they serve</span></strong><span> - </span>Shared models&nbsp;require&nbsp;local context. Editable configuration files allow teams to define ownership,&nbsp;business&nbsp;priorities,&nbsp;releases,&nbsp;examples, and trusted sources without&nbsp;modifying&nbsp;underlying agents.<span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
<li><strong><span>Build observability and feedback mechanisms into the agentic system itself</span></strong><span> - </span>Making analysis inspectable through&nbsp;reasoning traces, source context, and recommendations enables experts to&nbsp;identify&nbsp;gaps, improve outputs, and build trust over time.&nbsp;Build feedback mechanisms directly into the flow of work, making it effortless for users to provide input on the system.<span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
<li><strong><span>Tailor outputs to the people making decisions</span></strong><span> - </span>Executives need trends and investment signals. Researchers need evidence and themes. Engineers need reproducible, actionable work.&nbsp;Effective systems deliver the right information to the right audience.<span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
<li><strong><span>Start small and iterate quickly</span></strong><span> - </span>The AI&nbsp;landscape continues to evolve rapidly. Begin with a well-defined problem, measure outcomes, learn from feedback, and iterate as capabilities mature.<span style="color: rgb(30, 30, 30);">&nbsp;</span></li>
</ol>
