<p><strong>Business Scenario</strong></p>
<p>A retail organization runs <strong>multiple promotional sales events</strong> across its store network in different cities, featuring various product categories.</p>
<p>Data is captured from:</p>
<ul>
<li>Third-party systems (products, stores, sales events)</li>
<li>ERP system i.e. Finance and Operations (customer data)</li>
</ul>
<p>Customers are linked to stores <strong>based on city in the ERP system</strong>, and each store hosts specific sales events.</p>
<p>However, while significant investments are made in <strong>marketing campaigns, inventory allocation, and event planning</strong>, the organization needs to identify</p>
<ul>
<li>Which <strong>stores generate the highest revenue during events</strong></li>
<li>Which <strong>locations are having majority of customer footprint</strong></li>
</ul>
<p><strong>Solution</strong>:</p>
<p>Rather than creating custom reports on raw data, an <strong>agent</strong> can leverage the data in <strong>Onelake</strong> and use <strong>Fabric semantic models and Fabric IQ</strong> to provide conversational analytics. The agent can intelligently normalize user inputs and return accurate results even when values such as city names are entered with spelling errors or variations.</p>
<p>&nbsp;</p>
<p><strong>Advantage</strong>:</p>
<p>Because the data comes from two disconnected worlds (third-party systems for products/stores/events, ERP for customers), the "join" between them — customer → city → store → event → product — is business logic, not a database key. Fabric Ontology captures exactly that: entity types, relationships, rules and source mappings, so agents don't have to rediscover it from raw tables each time.</p>
<p>&nbsp;</p>

</ul>
<p><strong>How the data is connected:</strong></p>

<li>Customers are linked to stores based on <strong>city alignment</strong> (customer city = store location).</li>
<li>Sales events are associated with:</li>
<ul>
<li>The <strong>products being sold</strong>, and</li>

<h3><span><span>Introduction</span></span><span>&nbsp;</span></h3>
<p><span>Maintaining enterprise virtual machine images manually can lead to configuration drift, inconsistent builds, slow remediation and limited release traceability. A stronger pattern is to treat each image as a versioned build artefact: create it from a controlled source, configure it deterministically, validate the published image and promote only an explicitly identified version.</span><span>&nbsp;</span></p>
<p><span>This article presents a generic implementation using HashiCorp Packer and Azure DevOps. The examples intentionally use non-production placeholders and avoid customer-specific names, subscriptions, networks, credentials, repositories, gallery names, certificate material, package sources and internal promotion topology.</span><span>&nbsp;</span></p>
<h3><span><span>What this article demonstrates</span></span><span>&nbsp;</span></h3>

<li><span><span>Consolidate</span><span> a layered image process into a </span><span>parameterised</span><span> Packer build.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Preserve image metadata and Azure Marketplace lineage through publication.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Validate the published image version rather than only the temporary build VM.</span></span><span>&nbsp;</span></li>
</ul>
<ul>
<li><span><span>Publish validation evidence and make promotion decisions traceable.</span></span><span>&nbsp;</span></li>

<h3><span><span>Designing the image build</span></span><span>&nbsp;</span></h3>
<h6><strong><span><span>Why use a single reproducible build?</span></span><span>&nbsp;</span></strong></h6>
<p><span>Layered pipelines can be useful, but multiple sequential image builds create intermediate artefacts and dependencies that complicate remediation. Where the complete configuration can be reproduced from source, use one ordered flow: select the source image, configure the operating system, apply the chosen hardening profile, install the runtime, configure trust, run smoke checks, clean up and capture the result.</span><span>&nbsp;</span></p>
<h6><strong><span><span>Parameterise</span><span> the pipeline</span></span><span>&nbsp;</span></strong></h6>
<p><span>Keep environment-specific values outside the reusable image logic. Typical queue-time parameters include runtime version, image flavour, build region, optional security scanning and the image version to validate.</span><span>&nbsp;</span></p>
<h6><strong><span><span>Queue-time pipeline parameters (YAML)</span><span>&nbsp;</span></span></strong></h6>
parameters: 
- name: runtimeVersion 
  type: string 
  default: '17' 
  values: ['8', '11', '17', '21'] 
- name: imageFlavor 
  type: string 
  default: standard 
  values: [standard, cis] 
- name: enableSecurityScan 
  type: boolean 
  default: false 
- name: location 
  type: string 
  default: eastus 
<h3><span><span>Define the Packer builder and provisioning order</span></span><span>&nbsp;</span></h3>
<p><span>Use a single template with an explicit provisioning sequence. Fail the build for conditions that make the image unusable; keep advisory checks separate when the release process intentionally treats them as non-blocking</span></p>

report_dir="${REPORT_DIR:-validation-results}" 
mkdir -p "$report_dir" 
 
check() { 
  local name="$1"; shift 
  if "$@"; then 
    printf '%s\tPASS\n' "$name" | tee -a "$report_dir/result.txt" 
  else 
    printf '%s\tFAIL\n' "$name" | tee -a "$report_dir/result.txt" 
    return 1 
  fi 
}

<h6><strong><span><span>Consumer rollout</span></span><span>&nbsp;</span></strong></h6>
<p><span>The image pipeline ends at a versioned, validated gallery artefact. Consumers such as Virtual Machine Scale Sets should reference an explicit version during controlled rollout, validate health after deployment and move new deployments to a previous known-good version when rollback is required.</span><span>&nbsp;</span></p>
<h3><span><span>Conclusion</span></span><span>&nbsp;</span></h3>
<p><span>Image baking becomes easier to operate when it is treated as a software-delivery problem: source-controlled configuration, deterministic builds, explicit metadata, versioned outputs, independent validation, published evidence and controlled promotion. Packer supplies the repeatable image build, Azure DevOps supplies orchestration and governance, and Azure Compute Gallery supplies the distribution boundary.</span><span>&nbsp;</span></p>
<p><span>The most important addition is validating the image after publication so release decisions are based on the same artefact that downstream workloads will consume.</span><span>&nbsp;</span></p>
<p><span><strong>Adapt before use</strong>&nbsp; </span><span>The examples are intentionally generic. Replace placeholder names and policy thresholds for the target environment; keep secrets in protected variables or an approved secret store.</span><span>&nbsp;</span></p>
