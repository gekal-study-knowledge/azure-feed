<p><strong>Introduction</strong></p>
<p>One of the most common questions during Azure networking troubleshooting is:</p>
<p>“Did anything change before the issue started?”</p>
<p>Whether we are investigating VPN/, connectivity problems, Azure Firewall behavior changes, VM outages, routing issues, or application failures, identifying recent configuration changes is often the fastest way to determine the root cause.</p>
<p>Change Analysis is a powerful capability built on Azure Resource Graph that allows engineers and administrators to quickly see:</p>
<ul>
<li>What changed</li>
<li>When the change occurred</li>
<li>Who made the change</li>
<li>Which client or tool performed the change</li>
<li>The exact configuration differences before and after the change</li>
</ul>
<p>&nbsp;</p>
<p>&nbsp;</p>
<p><strong>What is Change Analysis?</strong></p>
<p>Azure resources are constantly being modified through:</p>
<ul>
<li>Azure portal</li>
<li>Azure CLI</li>
<li>PowerShell</li>
<li>ARM/Bicep deployments</li>
<li>Terraform</li>
<li>Azure Policy remediation</li>
<li>Automation runbooks</li>
<li>CI/CD pipelines</li>
</ul>
<p>In many organizations, multiple administrators and engineers have access to the same Azure tenant and subscriptions. Because teams often work across different regions and time zones, it can be difficult to determine who made a change and to quickly contact the responsible person when an issue occurs. While most changes are intentional and necessary for daily operations, some modifications can unintentionally introduce outages, connectivity issues, or performance problems. Azure Change Analysis provides a centralized view of resource changes and helps organizations quickly answer critical troubleshooting questions such as: Who changed a setting? Was a route table updated before traffic stopped flowing? Did someone modify an NSG rule? Was the Azure Firewall configuration changed? When was a virtual machine resized? By showing what changed, when it changed, and who made the change, Change Analysis significantly reduces troubleshooting time and helps accelerate root cause analysis.</p>

### Connect Azure Functions to more services with managed connectors

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/connect-azure-functions-to-more-services-with-managed-connectors/ba-p/4558711](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/connect-azure-functions-to-more-services-with-managed-connectors/ba-p/4558711)
- **Published**: 2026-09-23 04:51:43
- **Fetched**: 2026-09-23 11:02:24

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Azure Functions can already connect to many Azure services through triggers and bindings. With managed connectors, your functions can access about 1,700 connectors across services such as Microsoft 365, Microsoft Teams, <span>Dataverse, </span>SharePoint, OneDrive<span>,</span> and third-party systems.&nbsp;</p>
<p>Connector triggers deliver events from these services to your function, while typed connector clients let your code take actions against them. You get this broader integration surface without writing the webhook registration code or managing the OAuth tokens required to connect to each service. Focus on your function's business logic and let Azure Connector Namespace handles the connection.</p>
<p>Azure Functions integration with Connector Namespace is currently in <em>public preview</em>. It supports .NET isolated, Python, and Node.js. Review the <a href="https://learn.microsoft.com/azure/azure-functions/functions-connectors-overview" rel="noopener" target="_blank">managed connectors overview</a> for current language, hosting plan, and regional availability.</p>
<p>To demonstrate how connector triggers and actions work together, this article follows a .NET sample that automates RFP intake across SharePoint, Azure Content Understanding, and Teams.</p>
<h2>From an uploaded RFP to Teams notification</h2>
<p>Consider an organization that receives requests for proposals (RFPs) in a shared SharePoint document library. Someone must read each document, identify the requested capabilities, determine which subject-matter experts should respond, and notify the right team.</p>
<p>The <a href="https://github.com/Azure-Samples/functions-connectors-net-rfp-intake-sharepoint-teams" rel="noopener" target="_blank">automated RFP intake sample</a> turns that process into an event-driven workflow:</p>
<ol>
<li>A customer uploads an RFP to a SharePoint document library.</li>
<li>A SharePoint connector trigger invokes an Azure Function when the file is created.</li>
<li>The function uses a typed SharePoint connector client to retrieve the file contents.</li>
<li>Azure Content Understanding extracts the document’s text and layout.</li>
<li>The function applies deterministic rules to identify the customer, required capabilities, and recommended subject-matter experts.</li>
<li>The function uses a typed Teams connector client to post the results as an Adaptive Card in a channel.</li>
</ol>
<p>Connector Namespace manages the SharePoint and Teams connections. The function controls file processing, document analysis, routing rules, error handling, and notification content</p>
<h2>How the sample works</h2>
<p>The .NET sample demonstrates both parts of the connector programming model: a connector trigger receives an event from SharePoint, and typed connector clients provided by the Connector SDKs to perform actions against SharePoint and Teams.</p>
<p>The function starts when the SharePoint <strong>When a file is created</strong> trigger detects a new RFP. It declares the trigger using the ConnectorTrigger attribute and receives a typed payload containing the file’s properties:</p>
[Function("OnNewFile")]
public async Task OnNewFile(
    [ConnectorTrigger]
    SharePointOnlineOnNewFileItemsTriggerPayload payload,
    CancellationToken cancellationToken)
{
    // Process the newly uploaded file.
}
<p>&nbsp;</p>
<p>Because the trigger provides file properties rather than its contents, the function uses a typed SharePoint client to retrieve the document:</p>
byte[] response = await _sharePoint.GetFileContentAsync(
    Uri.EscapeDataString(siteAddress),
    fileIdentifier,
    cancellationToken: cancellationToken);

byte[] document = SharePointFileContent.Decode(response);
<p>&nbsp;</p>
<p>The SharePoint and Teams clients are registered through dependency injection. Each client uses the runtime URL of its Connector Namespace connection and authenticates with DefaultAzureCredential:</p>
services.AddSingleton(
    new SharePointOnlineClient(
        new Uri(sharePointRuntimeUrl),
        credential));

services.AddSingleton(
    new TeamsClient(
        new Uri(teamsRuntimeUrl),
        credential));
<p>&nbsp;</p>
<p>The function sends the document to Content Understanding’s prebuilt-layout analyzer, which extracts its text and structure. It then applies deterministic C# rules to identify the customer and required capabilities and map those capabilities to predefined subject-matter expert roles.</p>
<p>Finally, the function creates an Adaptive Card containing the results and posts it to the configured Teams channel with the typed Teams client:</p>
await _teams.PostCardToConversationAsync(
    postAs,
    postIn,
    request,
    cancellationToken);
<p>&nbsp;</p>
<p>Connector Namespace handles the SharePoint and Teams connections, while the function controls the document analysis, routing logic, error handling, and notification content.</p>
<h3>Try the sample</h3>
<p>The <a href="https://github.com/Azure-Samples/functions-connectors-net-rfp-intake-sharepoint-teams" rel="noopener" target="_blank">RFP intake sample</a> includes the function code, Bicep infrastructure, Azure Developer CLI configuration, and supporting scripts. Its README explains how to test the workflow locally and deploy it to Azure.</p>
<h2><span style="color: rgb(30, 30, 30);">Common connector patterns</span></h2>
<p>Managed connectors are useful when a function must react to events or perform operations in external systems. Common patterns include:</p>
<ul>
<li><strong>Event to action:</strong> React to an event in one service and take an action in another.</li>
<li><strong>Event to enrich to action:</strong> Retrieve additional information related to an event before acting.</li>
<li><strong>Event to document analysis to action:</strong> Extract text and structure from a document, apply application rules, and send the result through another connector.</li>
<li><strong>Event to AI to action:</strong> Analyze event data with an AI service and write the result back through a connector.</li>
<li><strong>Extend an existing function app:</strong> Add connector-based integrations alongside HTTP, timer, queue, Service Bus, Event Grid, or Durable Functions workloads.</li>
</ul>
<p>The RFP sample combines several of these patterns. A SharePoint event starts the workflow, a SharePoint action retrieves the document, Content Understanding extracts its contents, application code enriches the result, and a Teams action sends the notification.</p>
<h2>Closing thoughts</h2>
<p>Managed connectors extend the external systems that can trigger your functions and the services your function code can act on. This brings services such as SharePoint, Teams, Microsoft 365, and many third-party systems into the Azure Functions programming model without requiring you to build the underlying webhook and OAuth infrastructure.</p>
<p>Choose Azure Functions with managed connectors when you want this broader integration surface in a code-first application and need custom branching, application libraries and SDKs, other Functions bindings, document or AI processing, or application-specific logic between the trigger and action.</p>
<p>If the workload primarily orchestrates connector operations, involves little custom code, and would benefit from a visual designer, Azure Logic Apps is usually the simpler choice.</p>

### Run and scale AI applications on AKS – the latest product innovations

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/run-and-scale-ai-applications-on-aks-the-latest-product/ba-p/4559103](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/run-and-scale-ai-applications-on-aks-the-latest-product/ba-p/4559103)

<p>AI changed what teams ask of Kubernetes. Workloads today are more than a stateless web tier, they are an inference service with an expensive GPU behind it, an agent that behaves unpredictably, and a data path that shifts from dataset throughput to checkpoint durability to serving latency as the application matures. Today at the <a class="lia-external-url" href="https://aka.ms/BCNA/b" target="_blank">Reactor event</a>, we are showing demos and announcing new capabilities to support your AI workloads. &nbsp;</p>
<p>This wave of AKS releases answers three of those pressures directly: isolating AI workloads, assembling the componentry that agentic applications need, and making capacity work harder than it did last quarter.</p>
<p><strong>Workload and AI isolation</strong></p>
<p>Agents are unpredictable by design. Consider an agent installing packages, making unexpected network calls, or attempting to escape its pod into the node — with a shared kernel, one compromise becomes a node-wide problem. The AKS answer is layered: secure by default, verify the workload, then raise the boundary when the data demands it.</p>
<ul>
<li><strong>GA: Pod sandboxing support in node auto-provisioning (NAP).</strong> Every pod runs inside its own lightweight VM with an isolated guest kernel, built on the open-source Kata Containers project, so a compromise of one kernel instance is contained to one workload. With NAP support, that isolated compute is provisioned efficiently instead of hand-sized.</li>
<li><strong>GA: Confidential GPU support. </strong>AMD SEV-SNP confidential VMs with NVIDIA H100 Tensor Core GPUs, linking CPU and GPU trusted execution environments. Memory stays hardware-encrypted, which helps prevent data access by cloud providers, administrators, and privileged users — the control that makes sovereign, regulated, and privacy-sensitive AI workloads viable.</li>
<li><strong>GA: Trusted Launch support in NAP.</strong> Secure boot, virtual TPM, and boot integrity monitoring on Generation 2 VMs, applied automatically whenever NAP selects a Gen 2 SKU. No touch, no configuration, hardened nodes.</li>
<li><strong>GA: Identity Bindings. </strong>Removes the 20 federated identity credential ceiling on a user-assigned managed identity. Multiple clusters now share one managed identity through a single credential, with access governed by granular Kubernetes RBAC and AKS-managed token exchange — the difference between a platform that stops at 20 clusters and one that doesn't.</li>
<li><strong>GA: NFS encryption in transit and workload identity for Azure Files CSI.</strong> Protects traffic on the shared-file path and lets pods authenticate with identity instead of storage account keys, for the models, artifacts, and configuration many replicas read at once.</li>
<li><strong>GA: Argo CD extension for AKS.</strong> Automate application deployment and continuous reconciliation from Git with trusted access and security controls built in: see application health, sync state, and the deployed revision at a glance, get improved security through automatic updates of the Argo CD components, sign in to the Argo CD UI with Azure identities, and authenticate to ACR and Azure DevOps with workload identity.&nbsp;</li>
</ul>
<p><strong>Agent componentry</strong></p>
<p>Agentic applications need a path from code to a verified deployment, a runtime that absorbs bursts, and enough observability to find out why a GPU ran out of memory at 2am.</p>
<ul>
<li><strong>GA: Argo CD extension for AKS.</strong> Managed GitOps with application health, sync state, and deployed revision visible in one place, automatic updates for Argo CD components, single sign-on with Azure identities, and workload identity authentication to ACR and Azure DevOps. The Flux extension for AKS remains available for Flux-based workflows.</li>
<li><strong>Public Preview: Virtual Nodes v2 as a cluster extension.</strong> Burst into Azure Container Instances in seconds without waiting for node provisioning, pay only while pods run, and get Hyper-V isolated microVMs with confidential container support. Inference spikes and agent fan-out stop requiring permanently overprovisioned nodes.</li>
<li><strong>Public Preview: GPU memory profiling. </strong>See which functions allocate GPU memory, with no app code changes and no sidecar, and go from "memory is under pressure" to the exact call path as a flame graph. Profile, fix, re-profile.</li>
</ul>
<ul>
<li><strong>GA: NFS encryption in transit and workload identity for Azure Files CSI.</strong> Secures the shared-file path that many replicas read at once, protecting traffic on the wire and letting pods authenticate with identity instead of storage account keys. Best fit for models, artifacts, configuration, and shared application data reached through a Kubernetes-native interface.</li>
<li><strong>GA: Azure Container Storage v2.2.1. </strong>Improves local NVMe provisioning and expansion, reduces resource consumption at scale, and adds Elastic SAN support on tainted nodes, strengthening the production foundation for databases, data pipelines, and model-serving workloads that need container-native volume orchestration.</li>
<li><strong>GA: Azure CSI driver security hardening (AKS release v20260904). </strong>Stronger input and mount validation, credential isolation and refresh, protection against resource-exhaustion paths, and better diagnostics. The storage integration is part of the workload trust boundary, and this release treats it that way.</li>
</ul>
<p>Around these, the developer surfaces stay where teams already work: the AKS extension for VS Code, AKS Skills in GitHub Copilot and your preferred CLI, AKS desktop, and Azure Kubernetes Fleet Manager resource placement for declaring one release intent across many clusters and regions.</p>
<p><strong>Efficiency</strong></p>
<p>Getting the most out of expensive compute is key, and we want to ensure your training, inference, fine-tuning and batch jobs spend with purpose and scale with demand. We’re introducing the following capabilities to help support.</p>
<ul>

<h2>Agents Act. You Set the Limits.</h2>
<p>Your platform needs to run untrusted code. Agents choose actions at runtime, from installing packages to calling APIs. In a multi-tenant service, you have to support both without letting one customer's code reach another customer's data. That requires an execution environment you control for each tenant, session, or task.</p>
<p><strong><a class="lia-external-url" href="https://sandboxes.azure.com/" rel="noopener" target="_blank">Azure Container Apps Sandboxes</a> is that execution environment, as a service</strong><strong>.</strong> Each sandbox is a hardware-isolated microVM with its own Linux kernel. It starts in under a second, and you decide per sandbox what it can reach, how large it is, and how long it lives.</p>
<p>&nbsp;</p>
<img />
<p>&nbsp;</p>
<p>For each user, controlling which <strong>credentials </strong>their agent can use and what it can reach is key. Untrusted code must stay&nbsp;<strong>isolated </strong>from other workloads and the host kernel. Preserving a <strong>session state</strong> without giving up scale to zero or instant startup is important, as is <strong>visibility </strong>into what each agent did. Let's unpack these one at a time.</p>
<h2>Control What Your Agents Can Reach</h2>
<p>The first question about an agent is not what it can do, but what it can reach. <strong>Per-sandbox egress policies</strong> answer that: an external proxy evaluates every outbound request against rules you set - by host, domain pattern, or CIDR.&nbsp;<strong>You can start with a default 'Deny' action</strong>&nbsp;and allow only the endpoints the task needs, so a prompt injection or a compromised dependency has nowhere to go. Network Audit shows you what was allowed and what was denied.</p>
<p>Approved endpoints usually need credentials, and handing an API key to an agent means the key can be logged, echoed into a response, or carried off somewhere you did not intend.&nbsp;<strong>Transform rules can inject authentication headers at the proxy</strong> from sandbox-group secrets instead. The agent sends a request with no secret in it, the proxy adds the credential outside the sandbox, and the call goes through. The agent gets access to the service without ever getting the API key.</p>
<p>When a static allowlist cannot express the rule you need,&nbsp;<strong>an egress webhook hands each request to your own service</strong> before it leaves. You can build a service that reviews all outbound calls, approves some and rejects others.</p>
<p>Good results depend on the agent reaching the right data, and the data that matters usually sits on your private network. Outbound,&nbsp;<strong>VNet integration</strong>&nbsp;places the sandbox group on a dedicated subnet, so agents can reach internal APIs, databases, and services behind private endpoints. Egress rules are still enforced: routing is chosen per rule, so a call to an internal database is filtered, transformed, and recorded in Network Audit exactly like a call to the open internet. Inbound,&nbsp;<strong>a Private Endpoint brings the sandbox service into your VNet</strong>, so your own applications reach into your sandboxes without crossing the public internet.</p>
<h2>Run Untrusted Code Without Sharing a Kernel</h2>
<p>Each sandbox runs in a&nbsp;<strong>hardware-isolated microVM with its own Linux kernel</strong>&nbsp;and virtual hardware, with memory separation enforced through CPU virtualization. In contrast, typical container runtimes isolate processes while sharing the host kernel. In a sandbox, code calls into its own guest kernel, so the blast radius of a kernel exploit is one sandbox. You get that boundary with ACA Sandboxes.</p>
<p>Inside that boundary, the filesystem is yours to choose. The quickest way to start is by creating a sandbox based on a&nbsp;<strong>platform-provided disk image:</strong></p>

<p>You can also start from a sandbox you already have running.&nbsp;<strong>A disk snapshot captures the filesystem as a new disk image</strong>, while&nbsp;<strong>a memory snapshot captures disk and memory together</strong>, so a sandbox created from it resumes where the original left off. Installed dependencies, or a cloned repo, are set up once, and every sandbox created from the snapshot starts with them.</p>
<h2>Give Every Task Its Own Sandbox</h2>
<p>A sandbox starts in&nbsp;<strong>under a second</strong>, and that is why it is practical to give every task its own machine. When a machine takes minutes to come up, everything ends up sharing that same space. When it starts instantly, each task, user, or tool call runs in isolation, and gets deleted when the work is done. Thousands at a time.</p>
<p>Sandboxes are sized when created by selecting a&nbsp;<strong>resource tier</strong>. These range from&nbsp;<strong>0.25 vCPU with 0.5 GB of memory and a 5 GB disk</strong>, enough for a short script or a quick evaluation, to&nbsp;<strong>4 vCPU with 8 GB of memory and an 80 GB disk</strong> for compilation and heavier analysis, with multiple steps in between. Programmatically you can go up to&nbsp;<strong>16 vCPU with 32 GB of memory and a 320 GB disk</strong>&nbsp;for the most demanding work.</p>
<p>Sandboxes do not have to be discarded by hand.&nbsp;<strong>Lifecycle policies stop a sandbox once it goes idle</strong>, capturing the disk and optionally the memory. It can <strong>resume</strong> on a start command or automatically on arriving network traffic. A policy can also&nbsp;<strong>auto-delete</strong>&nbsp;a sandbox that has been stopped long enough, so abandoned work does not linger.</p>
<h2>Keep State and Bring Your Data</h2>
<p>Most agent tasks are short - run a script, or return a result. That is not the limit. A long-running agent needs state that outlives single runs, and&nbsp;<strong>volumes attach persistent storage to a sandbox at a path you choose</strong>. Code reads and writes to it through ordinary filesystem calls, and the data stays after the sandbox is deleted. There are three kinds:</p>
<ul>
<li>A&nbsp;<strong>Data Disk</strong>&nbsp;mounts to one sandbox at a time and gives it a fast, fully POSIX-compatible filesystem on local disk, which suits a working database, a build cache, or an agent's accumulated memory.</li>
<li>An&nbsp;<strong>Azure Blob volume</strong>&nbsp;mounts to many sandboxes at once, for sharing a large read-heavy dataset rather than supporting concurrent writers.</li>
</ul>
<ul>
<li><strong>Azure Blob BYO</strong> <strong>volume </strong>(bring your own) does the same for blob storage you already own, referenced by resource ID.</li>
</ul>
