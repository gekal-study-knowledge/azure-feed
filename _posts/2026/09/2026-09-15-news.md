<h2>The green check that hid a real problem</h2>
<p>During a recent customer conversation, I was shown a customer-service refund agent that looked healthy by every traditional measure. Requests completed successfully. The endpoint returned HTTP 200. Latency was within the team's target, and there were no obvious exceptions in the application logs.</p>
<p>Then a customer asked a simple thing:</p>
<p>Please refund the duplicate $500 charge on invoice 83457.</p>
<p>The agent processed the refund and confirmed success. There was only one problem: in the failure case explored in this article, the agent calls the correct tool with the <strong>wrong parameter</strong>—refunding <strong>$5,000 instead of $500</strong>.</p>
<p>From the application's perspective, the request succeeded. From the business's perspective, the agent failed.</p>
<p>That moment changed the direction of our discussion. We were no longer asking, "Is the endpoint available?" We were asking:</p>
<ul>
<li>Which tool did the agent call, and with what arguments?</li>
<li>Was the refund amount correct?</li>
<li>Did the agent honor the approval threshold?</li>
<li>How many other customers were affected?</li>
<li>How would we prove that the correction actually worked?</li>
</ul>
<p>This is the gap that AI observability must close.</p>
<p>Traditional monitoring tells us whether a system is operating. Agent observability helps us determine whether the system is behaving as intended—and whether that behavior produces a trustworthy business outcome.</p>
<p>Below screenshot captures successful but incorrect action by agent. Later in this article, we will build this agent step by step and explore how observability helps us identify the failure.</p>

<h2>Observability must extend beyond logs, metrics, and traces</h2>
<p>Logs, metrics, and traces remain essential, but an AI application introduces another dimension: the application can be technically healthy and semantically wrong.</p>
<p>I frame this as <strong>five layers of AI observability</strong>. A refund that returns HTTP 200 can still fail on the layers that matter:</p>

Technical</td><td>Is it available, fast, healthy, and affordable?</td><td>Pass — HTTP 200, normal latency, zero exceptions</td></tr><tr><td>2. <p>These layers are related, but they are not interchangeable. A response can have low latency and high fluency while still passing the wrong amount to a payment tool. Traditional APM only covers Layer 1.</p>
<h2>The Microsoft Foundry observability landscape</h2>
<p>For this implementation, Microsoft Foundry was the development and evaluation experience, while Azure Monitor Application Insights became the telemetry store and investigation surface.</p>
<p>The responsibilities were intentionally separated:</p>
<ul>
<li><strong>Microsoft Foundry Traces</strong> gave the development team an ordered view of the agent run.</li>
<li><strong>Foundry Evaluation</strong> measured quality, safety, and agent behavior.</li>
<li><strong>The Foundry Monitor experience</strong> showed operational and evaluation trends for the deployed agent.</li>
<li><strong>Application Insights Agent Observability</strong> connected runs, models, tools, token usage, latency, and failures.</li>
<li><strong>Log Analytics</strong> supported customer-specific questions with Kusto Query Language.</li>
<li><strong>Azure Monitor alerts</strong> turned important signals into an operational response.</li>
</ul>
<p>OpenTelemetry provides the connective tissue. It gives us a standard trace model for agent, model, tool, and custom application spans instead of restricting observability to one application framework.</p>

<h2>Step 2: Create the refund agent and observe what it actually did</h2>
<p>The agent is a function-tool agent named refund-agent-observability-demo. It exposes a single process_refund tool. The instructions are intentionally ambiguous about amount handling to demonstrate how an agent can misinterpret a parameter.</p>
import json
from azure.ai.projects.models import PromptAgentDefinition, FunctionTool, Tool

# Define the refund tool
process_refund_tool = FunctionTool(
    name="process_refund",
    description="Process a refund for a customer invoice. Returns confirmation with refund details.",
    parameters={
        "type": "object",
        "properties": {
            "invoice_id": {
                "type": "string",
                "description": "The invoice ID to refund"
            },
            "amount": {
                "type": "number",
                "description": "The refund amount in dollars"
            }
        },
        "required": ["invoice_id", "amount"],
        "additionalProperties": False,
    },
    strict=True,
)

tools: list[Tool] = [process_refund_tool]

print(" Refund tool defined")
print(f" Tool: process_refund(invoice_id, amount)")
print(f"   Tool: process_refund(invoice_id, amount)")

# Create the refund agent

# NOTE: The instructions are intentionally ambiguous about amount handling

# to demonstrate how agents can misinterpret parameters

agent = project_client.agents.create_version(
    agent_name="refund-agent-observability-demo",
    definition=PromptAgentDefinition(
        model=model_deployment,
        instructions="""You are a customer service agent that processes refund requests.
When a customer asks for a refund, use the process_refund tool.
Extract the invoice ID and amount from the customer's message.
Always confirm the refund was processed successfully.
""",
        tools=tools,
    ),
)
print(f" Agent created: {agent.name} (version {agent.version})")

    elif item.type == "message":

<p>Server-side traces become available after Application Insights is connected to the project. Client-side tracing adds visibility into the application logic around the agent call. The workshop enables both with a few lines: it turns on content recording, configures Azure Monitor, and gets a tracer.</p>

<p>Wrapping an agent interaction in a custom parent span ties the model call and each tool call into one ordered trace. Here the workshop wraps a customer-service session, dispatches the tool the model requested, and returns the result with previous_response_id so the follow-up model call joins the same conversation:</p>
from openai.types.responses.response_input_param import FunctionCallOutput
# Run the agent with tracing

with tracer.start_as_current_span("customer_service_session") as session_span:
    session_span.set_attribute("session.type", "customer_inquiry")
    session_span.set_attribute("customer.segment", "premium")
    # Initial model call
    response = openai_client.responses.create(
        model=model_deployment,
        instructions=agent.definition.instructions,
        tools=[{
            "type": "function",
            "name": t.name,
            "description": t.description,
            "parameters": t.parameters,
            "strict": True,
        } for t in tools],
        input=user_message,
    )
    # Process function calls, return tool output, then continue the conversation
    input_items = []
    for item in response.output:
        if item.type == "function_call":
            result = {"status": "processed", "arguments": json.loads(item.arguments)}
            input_items.append(
                FunctionCallOutput(
                    type="function_call_output",
                    call_id=item.call_id,
                    output=json.dumps(result),
                )
            )
    if input_items:
        final_response = openai_client.responses.create(
            model=model_deployment,
            instructions=agent.definition.instructions,
            input=input_items,
            previous_response_id=response.id,
        )
    # Record the trace ID for investigation
    span_context = session_span.get_span_context()
    trace_id = format(span_context.trace_id, '032x')
    print(f" Trace ID: {trace_id}")
    print(f"   View in Application Insights → Transaction Search → {trace_id}")

<h2>Step 5: Ask custom questions with KQL</h2>
<p>The portal is an excellent starting point, but customers eventually ask questions specific to their business. The workshop's cookbook targets a <strong>Log Analytics workspace</strong> and uses the workspace tables (AppDependencies, AppEvents). The legacy aliases (dependencies, customEvents) only resolve in an Application Insights resource query context—use the schema that matches your query scope.</p>
<p>Tool failure rate:</p>
AppDependencies
| where DependencyType == "GenAI"
| where Name == "ExecuteTool"
| summarize
    Total   = count(),
    Failed  = countif(Success == false),
    FailPct = round(100.0 * countif(Success == false) / count(), 2)
    by bin(TimeGenerated, 1h)
| render timechart
<p>Token consumption over time:</p>
AzureMetrics
| where MetricName in ("InputTokens", "OutputTokens", "TotalTokens")
| summarize Tokens = sum(Total)
    by MetricName, bin(TimeGenerated, 1h)
| render timechart

<h2>Step 6: Evaluate the process — did the agent pass the right parameters?</h2>
<p>Tracing explains how an action happened. Evaluation measures whether it was correct, consistently. For a refund agent, the most direct check is <strong>process evaluation</strong>: did it select the right tool and pass the right arguments?</p>
<p>The following example runs builtin.tool_call_accuracy over a set of banking scenarios—including a process_refund case—using the Evals API:</p>
import json
# Banking tool definitions

banking_tools = [
    {
        "type": "function",
        "name": "get_account_balance",
        "description": "Retrieve the current balance for a customer account.",
        "parameters": {
            "type": "object",
            "properties": {
                "account_number": {"type": "string", "description": "Account number (e.g., CHK-12345)"}
            },
        },
    },
    {
        "type": "function",
        "name": "process_refund",
        "description": "Process a refund to a customer account.",
        "parameters": {
            "type": "object",
            "properties": {
                "invoice_id": {"type": "string"},
                "amount": {"type": "number"}
            },
        },
    },
]
# Test scenarios with expected tool calls

# Note: ToolCallAccuracyEvaluator requires a `tool_call_id` on every tool_call item.

scenarios = [
    {
        "query": "What's the balance in account CHK-12345?",
        "tool_definitions": banking_tools,
        "tool_calls": [{
            "type": "tool_call",
            "tool_call_id": "call_1",
            "name": "get_account_balance",
            "arguments": {"account_number": "CHK-12345"}
        }],
    },
    {
        "query": "Please refund $75 on invoice INV-9876.",
        "tool_definitions": banking_tools,
        "tool_calls": [{
            "type": "tool_call",
            "tool_call_id": "call_3",
            "name": "process_refund",
            "arguments": {"invoice_id": "INV-9876", "amount": 75}
        }],
    },
]
print(f"{len(scenarios)} test scenarios defined")

import time
# Prepare test data — file_content expects an array of {"item": {...}} objects

test_content = [{"item": s} for s in scenarios]
testing_criteria = [
    {
        "type": "azure_ai_evaluator",
        "name": "tool_accuracy",
        "evaluator_name": "builtin.tool_call_accuracy",
        "initialization_parameters": {"deployment_name": model_deployment},
        "data_mapping": {
            "query": "{{item.query}}",
            "tool_definitions": "{{item.tool_definitions}}",
            "tool_calls": "{{item.tool_calls}}",
        },
    },
]
data_source_config = {
    "type": "custom",
    "item_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string"},
            "tool_definitions": {"type": "array"},
            "tool_calls": {"type": "array"},
        },
        "required": ["query", "tool_definitions", "tool_calls"],
    },
}
eval_object = openai_client.evals.create(
    name="Banking Agent — Tool Call Accuracy",
    data_source_config=data_source_config,
    testing_criteria=testing_criteria,
)
eval_run = openai_client.evals.runs.create(
    eval_id=eval_object.id,
    name="Tool Accuracy Run",
    data_source={
        "type": "jsonl",
        "source": {"type": "file_content", "content": test_content},
    },
)
print(f"Evaluation run started: {eval_run.id}")
while eval_run.status not in ["completed", "failed"]:
    time.sleep(5)
    eval_run = openai_client.evals.runs.retrieve(
        run_id=eval_run.id, eval_id=eval_object.id
    )
    print(f"   Status: {eval_run.status}")
print(f"\n{'' if eval_run.status == 'completed' else '' } Final: {eval_run.status}")
<p>The workshop also runs a quality-and-safety suite (builtin.violence, builtin.fluency, builtin.task_adherence) against a registered agent using evals.create and azure_ai_target_completions. Together, these give both a process signal (right tool, right arguments) and a quality/safety signal.</p>
<p>One honest caveat for publication: in the workshop's saved run, the tool-call records are hand-authored fixtures, not calls captured from a live agent. For a production regression test, capture the agent's actual tool call and its tool_call_id, then evaluate that. For a refund, the exact-amount and approval checks belong in the transaction path as deterministic controls—an LLM judge should not be the only guard.</p>

<h2>Step 7: Red-team the agent before it ships</h2>
<p>Quality evaluation asks whether expected tasks succeed. Red teaming asks whether deliberate adversarial pressure pushes the agent past its boundaries. The workshop runs the <strong>AI Red Teaming Agent in the cloud</strong>: it registers a Foundry agent target, generates a prohibited-actions taxonomy, wires up agentic evaluators, and submits a run with attack strategies.</p>
from azure.ai.projects.models import (
    AzureAIAgentTarget,
    AgentTaxonomyInput,
    EvaluationTaxonomy,
    RiskCategory,
)
# Target descriptor referenced by both the taxonomy and the run.

target = AzureAIAgentTarget(name=agent.name, version=agent.version)
# Foundry generates the attack-prompt taxonomy from the agent's tools &amp; instructions.

taxonomy = project_client.beta.evaluation_taxonomies.create(
    agent.name,
    EvaluationTaxonomy(
        description="Taxonomy for banking agent red teaming",
        taxonomy_input=AgentTaxonomyInput(
            risk_categories=[RiskCategory.PROHIBITED_ACTIONS],
            target=target,
        ),
    ),
)
taxonomy_file_id = taxonomy.id
# The red team groups one or more runs and wires up the built-in agentic evaluators.

red_team = openai_client.evals.create(
    name="Red Team — Banking Agent Safety",
    data_source_config={"type": "azure_ai_source", "scenario": "red_team"},
    testing_criteria=[
        {
            "type": "azure_ai_evaluator",
            "name": "Prohibited Actions",
            "evaluator_name": "builtin.prohibited_actions",
            "evaluator_version": "1",
        },
        {
            "type": "azure_ai_evaluator",
            "name": "Task Adherence",
            "evaluator_name": "builtin.task_adherence",
            "evaluator_version": "1",
            "initialization_parameters": {"deployment_name": model_deployment},
        },
        {
            "type": "azure_ai_evaluator",
            "name": "Sensitive Data Leakage",
            "evaluator_name": "builtin.sensitive_data_leakage",
            "evaluator_version": "1",
        },
    ],
)

# Create the red-team run — it executes server-side in Foundry.

eval_run = openai_client.evals.runs.create(
    eval_id=red_team.id,
    name="Banking Agent Red Team Run",
    data_source={
        "type": "azure_ai_red_team",
        "item_generation_params": {
            "type": "red_team_taxonomy",
            "attack_strategies": ["Flip", "Base64", "IndirectJailbreak"],
            "num_turns": 5,
            "source": {"type": "file_id", "id": taxonomy_file_id},
        },
        "target": target.as_dict(),
    },
)
print(f"Run created: {eval_run.id}  status={eval_run.status}")
print("   View in Foundry → Build → Evaluations → Red team")
<p>The strategies (Flip, Base64, IndirectJailbreak) select input transformations and multi-turn depth; they test whether the agent resists manipulation, stays on task, and does not leak data. Two things matter for an honest write-up:</p>
<ul>
<li><strong>Review the taxonomy before scanning.</strong> Confirm the generated prohibited behaviors reflect your policy. Run red teaming against an isolated target with synthetic accounts and no irreversible side effects.</li>
<li><strong>Distinguish a security result from an infrastructure failure.</strong> A run that ends in failed is incomplete coverage, not a passing scan. Capture the run status honestly, and only present an attack-success-rate scorecard from a completed run.</li>
</ul>
<p><strong>Red-team run:</strong> Capture the run status and, when the run completes, the scorecard in Foundry → Build → Evaluations → Red team. If the run failed, caption it as incomplete coverage rather than a pass.</p>
<h2>Step 8: Prove the fix and move to production monitoring</h2>
<p>For the sample, the correction is a tightened prompt plus a deterministic amount/approval check in the transaction path—so the agent is not expected to reason its way out of receiving or emitting the wrong amount. After a fix, compare the two versions across the same evaluation set:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><tbody><tr><th>Signal</th><th>Before the fix</th><th>After the fix</th></tr><tr><td>Request success</td><td>100%</td><td>100%</td></tr><tr><td>Correct refund amount</td><td>Fail</td><td>Pass</td></tr><tr><td>Approval threshold honored</td><td>Fail</td><td>Pass</td></tr><tr><td>Tool-call accuracy</td><td>Fail</td><td>Pass</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>The operational success rate does not change. The business outcome does.</p>
<p>Once you know how to detect the failure, the next question is whether it is happening elsewhere. The Foundry Monitor experience brings operational metrics, evaluation results, and red-team results together for the selected agent; Application Insights adds deeper investigation across runs, models, tools, tokens, and errors. For this refund agent, I would monitor at least:</p>
<ul>
<li>Run success rate and model or tool errors</li>
<li>P50 and P95 end-to-end latency</li>
<li>Input and output token consumption</li>
<li>Refund-amount and approval-threshold pass rate</li>
<li>Tool-call-accuracy distribution</li>
<li>Human escalation and customer correction rate</li>
<li>Safety and adversarial-testing findings</li>
</ul>
<p>An alert should lead to an operational action:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><tbody><tr><th>Signal</th><th>Example condition</th><th>Action</th></tr><tr><td>Wrong-amount refund</td><td>Any run proposes an amount outside the approved range</td><td>Block the version and notify the finance/policy owner</td></tr><tr><td>Quality regression</td><td>Tool-call-accuracy pass rate falls below the release threshold</td><td>Stop promotion or roll back</td></tr><tr><td>Token anomaly</td><td>Tokens per run rise materially above baseline</td><td>Inspect context growth and repeated tool calls</td></tr><tr><td>Latency</td><td>P95 exceeds the agreed service objective</td><td>Inspect model, tool, and throttling spans</td></tr><tr><td>Safety</td><td>A scheduled red-team or production safety check fails</td><td>Route to the security and responsible-AI process</td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>A KQL query like the tool-failure-rate example can become the signal for an Azure Monitor log alert. Configure the rule to trigger when the query returns results in the evaluation window, and route the notification through the customer's approved action group.</p>
<h2>Continuous evaluation is the bridge between deployment and learning</h2>
<p>A one-time evaluation protects one release. It does not protect the agent indefinitely. Production traffic changes, tools change, and models and prompts are revised. This makes observability a continuous engineering loop:</p>
<ol>
<li>Observe production behavior.</li>
<li>Diagnose representative traces.</li>
<li>Evaluate the failure mode.</li>
<li>Add that failure to the regression dataset.</li>
<li>Correct the prompt, tool, policy, or model configuration.</li>
<li>Compare the candidate with the approved baseline.</li>
<li>Promote only when the required quality, safety, operational, and business gates pass.</li>
</ol>
<p>Microsoft Foundry supports recurring and continuous evaluation. When using live production traces, sample intentionally—random sampling gives coverage, while targeted or intelligent sampling can prioritize unusual, high-risk, failed, expensive, or low-quality interactions. Evaluation calls and telemetry have cost, privacy, and retention implications, so the sampling strategy should reflect business risk.</p>
<h2>Security, privacy, and cost are part of observability design</h2>
<p>Tracing can capture prompts, model outputs, tool arguments, and tool results. That visibility is valuable, but it creates responsibility:</p>
<ul>
<li>Keep message-content recording disabled unless there is an approved need.</li>
<li>Never place credentials, tokens, or secrets in prompts or span attributes.</li>
<li>Avoid storing personal data when a pseudonymous transaction identifier is sufficient.</li>
<li>Redact or minimize sensitive content before telemetry is emitted.</li>
<li>Apply Azure RBAC to Application Insights and Log Analytics; set retention by environment and data classification.</li>
<li>Monitor ingestion and evaluation cost, not only model-token cost.</li>
<li>Validate preview capabilities against production requirements.</li>
</ul>
<p>There is also a practical instrumentation lesson: do not add every available value to every span. Capture the dimensions needed to investigate reliability, behavior, quality, security, cost, and business outcomes. More telemetry is not automatically better telemetry.</p>
<h2>What the customer gained</h2>
<p>The most valuable outcome was not another dashboard. It was a shared way for developers, platform engineers, finance/policy owners, security teams, and business stakeholders to discuss the same agent run with evidence.</p>
<p>The developer could see the exact execution path. The platform team could see latency, errors, and token consumption. The policy owner could see the refund amount and whether the approval threshold held. The security team could verify how sensitive telemetry was handled. The business sponsor could see whether customers were refunded correctly.</p>
<p>The original request had a green check before the investigation, and it had a green check afterward. The difference was that after the fix, we could prove the refund amount was correct.</p>
<h2>Final takeaway</h2>
<p>An agent should not be considered healthy merely because it responds. A production-ready observability practice should be able to answer:</p>
<ul>
<li>Did the agent complete the request?</li>
<li>What model, tool, and path did it use, and with what arguments?</li>
<li>Was its action relevant, grounded, safe, and correct?</li>
<li>Did it comply with the approved business process?</li>
<li>Can the team detect a regression before it affects more users?</li>
<li>Can the team prove that the remediation improved the outcome?</li>
</ul>
<p>In the agentic era, observability is not the dashboard at the end of deployment. It is the evidence system connecting design decisions, production behavior, governance controls, and measurable business value.</p>

<h2>First principles</h2>
<p>Start from what a dashboard is. Every panel is a query someone wrote because the answer mattered, pointed at the right resource, titled with the question it answers, and annotated with the ways it can mislead. The variables pin it to a subscription, a resource group, an Application Insights component. The tags say what it covers. And it tends to stay correct, because people look at it every day and complain when it isn't. A dashboard is a team's understanding of a system, written down in a form that runs.</p>
<p>That is why a person on call can open one and get insight without asking anyone. It is also the whole argument for handing one to an agent. The insight was never in the pixels; it is in the queries, scopes, titles and descriptions underneath them, and an agent can read those directly.</p>
<p><strong>A dashboard is a map for the agent.</strong> It shows where the data lives, which questions are worth asking, how each one is asked, and where the traps are. The agent didn't need a separate context file, a hand-written playbook, or a tour of the schema. Most of what a human needs to reason about the system is already there, and so is most of what the agent needs. The map is already drawn. Here is what the agent found on it.</p>
<h2>What the agent did</h2>
<p>SRE Agent reached my Grafana instance through the <a href="https://learn.microsoft.com/azure/managed-grafana/grafana-mcp-server" rel="noopener" target="_blank">Azure Managed Grafana MCP endpoint</a> — instances in the Azure public cloud have one at <code>https://&lt;grafana-endpoint&gt;/api/azure-mcp</code> — attached as an <a href="https://learn.microsoft.com/azure/sre-agent/mcp-connectors" rel="noopener" target="_blank">MCP connector</a>. SRE Agent has a built-in connector for exactly this now; more on that below. The tool trace for the first two prompts is short:</p>
<ol>
<li><code>amgmcp_dashboard_search</code> — "GitHub Copilot" → one hit: uid <code>GitHubCopilot</code>, tags <code>github-copilot</code>, <code>opentelemetry</code>, <code>application-insights</code>.</li>
<li><code>amgmcp_dashboard_inspect</code> — the panel list, the template variables with their current values, the time range, and every panel's KQL with the variables substituted.</li>
<li><code>amgmcp_datasource_list</code> — the UID of the Azure Monitor data source.</li>
<li><code>amgmcp_query_resource_log</code> — a query the agent composed, run against the Application Insights resource the dashboard points at.</li>
</ol>
<p>Each "what was session N doing?" was two more <code>query_resource_log</code> calls.</p>
<p>Step 2 is where the interesting part happens, so I connected the same MCP endpoint to my own coding agent and ran the inspect call myself to see exactly what comes back.</p>
<p><strong>Summary mode</strong> (no arguments) returns the shape of the dashboard: 21 panels with ids, titles and types; six template variables <em>with their current values</em>; the default time range; and a <code>nextSteps</code> map that tells the agent how to go deeper.</p>

<h2>What's on the map</h2>
<p>Look at what the dashboard put in that response, and what the agent therefore did not have to figure out.</p>
<p><strong>Where the data is.</strong> A single Azure Monitor data source can query any resource its identity is allowed to read, and the scope appears nowhere in the KQL. The dashboard's variables resolved it to one Application Insights component. Without that, the first ten minutes of an investigation often go to "which workspace?"</p>
<p><strong>Which table, which attributes.</strong> <code>dependencies</code>, filtered by <code>cloud_RoleName in ('copilot-chat', 'github-copilot')</code> — GitHub Copilot in Visual Studio Code and GitHub Copilot CLI. The <code>source</code> variable <em>is</em> that mapping. Spans are classified by <code>gen_ai.operation.name</code> (<code>chat</code>, <code>execute_tool</code>, <code>invoke_agent</code>); tools by <code>gen_ai.tool.name</code>; tokens by <code>gen_ai.usage.input_tokens</code> and <code>output_tokens</code>. A session is <code>copilot_chat.chat_session_id</code> from VS Code and <code>gen_ai.conversation.id</code> from the CLI, coalesced, because the two clients don't agree.</p>
<p><strong>The pitfalls.</strong> This is the part I care about most. Three of the panel descriptions:</p>
<blockquote>
<p>Time to first token per model (P50 / P90) for measured requests. VS Code reports <code>copilot_chat.time_to_first_token</code> in ms; Copilot CLI reports <code>gen_ai.response.time_to_first_chunk</code> in seconds (converted to ms here).</p>
</blockquote>
<blockquote>
<p>Copilot CLI tool calls that cluster at exactly 60 s, 120 s or 180 s are client-side timeouts, which the CLI reports as successful calls.</p>
</blockquote>
<blockquote>
<p>Agent-run roll-up spans (<code>invoke_agent</code>), which repeat their child requests, are excluded.</p>
</blockquote>
<p>Each of those is a mistake I have already made once. Milliseconds versus seconds. Timeouts that look like successes. Roll-up spans that double-count tokens when you sum naively. None of it is derivable from the schema; it is tribal knowledge, and it is sitting in the dashboard JSON where an agent can read it with <code>jsonPath: "$.panels[*].description"</code>.</p>
<p><strong>The questions.</strong> The 21 panel titles are the questions an experienced on-call engineer asks about this system: <em>Time to First Token by Model. Tool Latency by Tool. Tool Call Failures by Tool. LLM Call Outcomes Over Time. Telemetry Freshness</em> — the last one so you can tell "no problem" from "no data". An agent reading those titles doesn't have to invent a triage plan. It has one.</p>
<h2>Off the edge of the map</h2>
<p>Notice what the dashboard does <em>not</em> have: a per-session view. There is no "longest sessions" panel; I would have to add one. The agent composed it anyway, from the dashboard's vocabulary:</p>
dependencies
| where timestamp &gt; ago(3d)
| where cloud_RoleName in ('copilot-chat', 'github-copilot')
| extend op = tostring(customDimensions["gen_ai.operation.name"]),
    sessId = coalesce(tostring(customDimensions["copilot_chat.chat_session_id"]),
                      tostring(customDimensions["gen_ai.conversation.id"]))
| where isnotempty(sessId)
| summarize Start = min(timestamp), End = max(timestamp), Spans = count(),
    LLMCalls = countif(op == "chat"), ToolCalls = countif(op == "execute_tool")
    by sessId
| extend DurationMin = round(datetime_diff('second', End, Start) / 60.0, 1)
| top 3 by DurationMin
<p>Every identifier in that query came from a panel. The agent walked off the edge of the map, but it took the map's coordinate system along.</p>
<p>Compare that with what a human does next. The dashboard's <em>Recent Operations</em> table links every run to <em>Trace Visualization</em>, and for one slow tool call that is exactly the right tool. This is session 1's longest run in that view: a single <code>invoke_agent</code> span, 1 hour 18 minutes, 476 spans underneath it.</p>
<img />
<p>That view is hard to read end to end. You scroll, sample a few of the long red bars, and move on. The trace is the right shape for "why was this call slow?" and the wrong shape for "what was this run doing?"</p>
<p>The agent never looked at this picture. Its per-session stories came from aggregation instead: <code>execute_tool</code> spans grouped by <code>gen_ai.tool.name</code>, <code>chat</code> spans by <code>gen_ai.response.model</code>, P50s and first/last timestamps per group, and the phases fall out in seconds. Same rows, different reader, different question.</p>
<img />
<p>With content capture enabled, the spans even carry <code>gen_ai.tool.call.arguments</code> — which is how "<code>bash</code>, 120 s" became "<code>sleep 120</code> — <em>Wait before retrying throttled query</em>", and how the agent could say <em>backoff</em>, not <em>hang</em>.</p>
<p>That last step matters more than it looks. The description above says calls clustering at exactly 60/120/180 s are usually client-side timeouts. In session 2 they were the other thing — deliberate sleeps — and only the captured arguments could settle it. A description tells an agent what to check; the telemetry lets it check.</p>
<h2>Don't write dashboards for agents</h2>
<p>The tempting takeaway is a new checklist: agents read dashboards now, so write dashboards with agents in mind. I think that is backwards. Nothing in the GitHub Copilot dashboard was written for an agent. The titles are questions because the person on call needs to know what a panel answers without reading its query. The descriptions carry the pitfalls because I hit each one and didn't want the next person to. The variables scope the queries because nobody remembers resource IDs. The freshness panel exists because a human can't tell "no problem" from "no data" either. An agent can use every one of those.</p>
<p>Same principle, other direction. What matters to the person on call is what matters to the agent, and the agent is smart enough to work out the rest: the time window, the bin size, a query the dashboard doesn't have yet. If a dashboard is enough for the human, it is enough for the agent. If it isn't enough for the agent, it probably wasn't enough for the next person on call either, and the fix is the same: fix the dashboard, and both readers get it.</p>
<p>Which brings me to the thing I find genuinely new here. A dashboard used to be a terminal artifact — the end of the pipeline, something you looked at. It is now also an input: a compact, versioned, access-controlled, human-reviewed description of how to reason about a system, in a format agents can execute. ### SSL/TLS certificates and end-to-end encryption for Azure Functions Flex Consumption

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/ssl-tls-certificates-and-end-to-end-encryption-for-azure/ba-p/4556425](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/ssl-tls-certificates-and-end-to-end-encryption-for-azure/ba-p/4556425)
- **Published**: 2026-09-15 06:01:36
- **Fetched**: 2026-09-15 10:01:56

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Last week we announced the general availability of TLS/SSL certificate support and end-to-end TLS encryption for Azure Functions Flex Consumption.</p>
<p>Flex Consumption is the recommended serverless hosting plan for Azure Functions. It combines event-driven scale-to-zero and execution-based billing with fast scale-out, configurable instance memory, always-ready instances, and virtual network integration. With this release, customers can now apply a more complete transport-security model to HTTP-based serverless applications without moving to dedicated compute.</p>
<p>The new capabilities include:</p>
<ul>
<li><strong>Site-scoped certificates</strong>, with up to three private certificates and three public certificates for each function app.</li>
<li><strong>Multiple certificate sources</strong>, including direct upload, Azure Key Vault, App Service Certificates, and free App Service Managed Certificates for supported custom domains.</li>
<li><strong>Per-certificate access from application code</strong>, replacing the broad WEBSITE_LOAD_CERTIFICATES model in Flex Consumption.</li>
<li><strong>End-to-end TLS encryption</strong>&nbsp;between the Azure platform front ends and the workers that run your functions.</li>
</ul>
<p>Together, these features support common enterprise scenarios such as custom HTTPS endpoints, outbound client-certificate authentication, mutual TLS (mTLS), certificate-based cryptographic operations, and stricter encryption-in-transit requirements.</p>
<h2>What end-to-end TLS means for a function app</h2>
<p>It helps to separate the different places where TLS and certificates participate in an application request.</p>
<p>First, a client connects to your function app over HTTPS. For the default&nbsp;*.azurewebsites.net&nbsp;hostname, Azure provides and manages the certificate automatically. For a custom hostname such as&nbsp;api.contoso.com, you map the domain to the function app and bind an appropriate server certificate.</p>
<p>Second, Azure Functions receives the request at an Azure platform front end and routes it to a worker that runs your code. HTTPS has always protected the client-to-front-end connection. When end-to-end TLS is enabled, the front-end-to-worker connection is also encrypted. This removes the unencrypted internal hop that otherwise exists after TLS termination at the front end.</p>
<p>Third, your function code might call another service that requires a certificate. For example, a partner API that uses mTLS. A site-scoped private certificate can be exposed to the function runtime and loaded from the Linux file system for that outbound connection.</p>
<p>These controls are complementary:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table><thead><tr><th>Traffic or trust boundary</th><th>Capability</th></tr></thead><tbody><tr><td>Client to Azure Functions front end</td><td>HTTPS and a certificate bound to the hostname</td></tr><tr><td>Azure platform front end to function worker</td><td>End-to-end TLS encryption</td></tr><tr><td>Function code to a downstream service</td><td>A private or public certificate made accessible to app code</td></tr><tr><td>Client identity presented to the function app</td><td>Client-certificate authentication, with validation performed by application code</td></tr></tbody></table></div>
<p>End-to-end TLS does not replace a custom-domain certificate, and a certificate uploaded for use by code does not automatically configure mTLS. Each control protects a different boundary.</p>
<h2>A certificate model designed for Flex Consumption</h2>
<p>Traditional App Service certificate resources are scoped to a&nbsp;<em>webspace</em>, a deployment unit associated with an App Service plan's resource group, region, and operating system. Apps in the same webspace can share access to those certificates.</p>
<p>Flex Consumption apps don't share the same plan, so we have introduced a new site-scoped model. The certificate is a child resource of one function app and isn't shared with other apps. This tighter boundary makes certificate ownership easier to reason about, reduces unintended sharing, and aligns well with function apps that are deployed and governed independently like Flex Consumption.</p>
<p>Each Flex Consumption function app supports:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table><thead><tr><th>Certificate type</th><th>Maximum per app</th><th>Typical uses</th></tr></thead><tbody><tr><td>Private certificate (.pfx)</td><td>3</td><td>Custom-domain TLS bindings, outbound client authentication, signing, or decryption</td></tr><tr><td>Public certificate (.cer)</td><td>3</td><td>Trusting or validating remote resources from application code</td></tr></tbody></table></div>
<p>The three-certificate limit includes App Service Managed Certificates, App Service Certificates, Key Vault imports, and directly uploaded PFX files. Plan certificate usage before assigning a separate certificate to every hostname. A certificate with appropriate subject alternative names can be useful when one certificate must cover multiple hostnames.</p>
<h2>Choose the right certificate source</h2>
<p>Flex Consumption supports several certificate-management approaches:</p>
<p><strong>App Service Managed Certificate.</strong>&nbsp;This is the simplest choice for a supported public custom domain. The domain-validated certificate is free, automatically issued, bound, and renewed by App Service. Managed certificates aren't exportable and don't support wildcard domains, private DNS, or use as an outbound client certificate. Avoid certificate pinning because the issuer, public key, and private key can change during renewal.</p>
<p><strong>App Service Certificate.</strong>&nbsp;This paid option provides Azure-managed lifecycle capabilities with support for scenarios such as wildcard domains and export.</p>
<p><strong>Azure Key Vault import.</strong>&nbsp;This is generally the preferred option when an organization centrally governs certificate issuance, access, and rotation. Use a managed identity and grant the&nbsp;<strong>Key Vault Certificate User</strong>&nbsp;role. When the certificate is renewed in Key Vault, the platform synchronizes the new version to the function app within 24 hours. If the vault blocks public access, enable the trusted Microsoft services bypass so the Azure Functions platform can retrieve the certificate.</p>
<p><strong>Direct private certificate upload.</strong>&nbsp;Upload a password-protected PFX that includes the complete certificate chain, including intermediate and root certificates. For a custom-domain binding, the certificate must include the server-authentication extended key usage and be signed by a trusted certificate authority. Elliptic Curve Cryptography certificates are supported when uploaded as PFX.</p>
<p><strong>Direct public certificate upload.</strong>&nbsp;Upload a CER when function code needs a public certificate. Public certificates aren't used to secure custom domains.</p>
<h2>Configure the security foundation with infrastructure as code</h2>
<p>The following Bicep excerpt shows the relevant settings on the function app. Add these properties to a complete Flex Consumption deployment that also defines the FC1 plan, deployment storage, runtime, identity, and monitoring resources.</p>
resource functionApp 'Microsoft.Web/sites@2024-11-01' = 
{ 
  name: functionAppName 
  location: location 
  kind: 'functionapp,linux' 
  identity: { type: 'SystemAssigned' } 
  properties: { 
    serverFarmId: serverFarmResourceId 
    httpsOnly: true 
    siteScopedCertificatesEnabled: true 
    endToEndEncryptionEnabled: true 
    siteConfig: 
    { 
      minTlsVersion: '1.2' 
    } 
  functionAppConfig: { // Add the deployment, runtime, and scale configuration for your app. } 
  } 
}
<p>The settings have distinct purposes:</p>
<ul>
<li>httpsOnly&nbsp;redirects HTTP requests to HTTPS.</li>
<li>siteConfig.minTlsVersion&nbsp;defines the minimum TLS version accepted for inbound connections.</li>
<li>siteScopedCertificatesEnabled&nbsp;enables per-app certificate resources.</li>
<li>endToEndEncryptionEnabled&nbsp;encrypts front-end-to-worker traffic.</li>
</ul>
<p>You can also create certificate child resources with&nbsp;Microsoft.Web/sites/certificates@2024-11-01, including importing a certificate by specifying its Key Vault resource ID and secret name. Use secure deployment parameters for any certificate password or PFX content; never store private key material or passwords in source control.</p>
<p>Azure CLI doesn't currently provide dedicated commands to manage Flex Consumption site-scoped certificates. Use the Azure portal or ARM/Bicep for certificate operations.</p>
<p>For more on using Bicep and ARM to configure site-scoped certificates in Flex Consumption see&nbsp;<a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-infrastructure-as-code?pivots=flex-consumption-plan#site-scoped-certificates" target="_blank">Automate resource deployment for your function app in Azure Functions</a>.</p>
<h2>Add and use a certificate</h2>
<p>After creating the app with site-scoped certificates enabled, choose the workflow that matches your scenario.</p>
<h3>Secure a custom domain with a managed certificate</h3>
<p>In the Azure portal, open the Flex Consumption function app. Under <strong>Settings</strong>, select&nbsp;<strong>Custom domains</strong>, and then select&nbsp;<strong>Add custom domain </strong>and configure the certificates. For customer-managed certificates, add or import the private certificate under&nbsp;<strong>Settings</strong>&nbsp;&gt;&nbsp;<strong>Certificates</strong>, and then bind it to the custom domain. A domain showing as&nbsp;<strong>Secured</strong>&nbsp;confirms that a binding exists, but clients can still reject an expired, self-signed, name-mismatched, or incomplete certificate chain. Test the endpoint from representative client environments.</p>
<h3>Make a certificate available to function code</h3>
<p>Adding a certificate to the app does not automatically expose it to code. In&nbsp;<strong>Settings</strong>&nbsp;&gt;&nbsp;<strong>Certificates</strong>, open the menu for the required certificate and select&nbsp;<strong>Make accessible to app code</strong>.</p>
<p>This per-certificate control replaces&nbsp;WEBSITE_LOAD_CERTIFICATES&nbsp;in Flex Consumption. That app setting remains valid for other supported Functions and App Service hosting plans, but it isn't used by Flex Consumption. The per-certificate model applies least privilege more naturally: expose only the certificates that the workload must read.</p>
<p>Flex Consumption runs on Linux, so accessible certificates are files rather than entries in a Windows certificate store:</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table><thead><tr><th>Certificate</th><th>Runtime location</th></tr></thead><tbody><tr><td>Private</td><td>/var/ssl/private/&lt;thumbprint&gt;.p12</td></tr><tr><td>Public</td><td>/var/ssl/certs/&lt;thumbprint&gt;.der</td></tr></tbody></table></div>
<p>Load the file by thumbprint using the certificate APIs for your language. Don't assume a Windows certificate store is available, and don't package private keys with the function code.</p>
<p>For Key Vault imports, the platform places a renewed certificate version on the function instances after synchronization. If your application hard-codes a thumbprint, account for the fact that renewal produces a new thumbprint. Prefer a configuration or discovery pattern that lets you rotate without a code release.</p>
<h2>Enable mutual TLS without confusing transport and identity</h2>
<p>For inbound mTLS, configure the function app to request a client certificate by using the appropriate client-certificate mode:&nbsp;<strong>Required</strong>,&nbsp;<strong>Optional</strong>, or&nbsp;<strong>Optional Interactive User</strong>.</p>
<p>Azure terminates the client TLS connection at the platform front end and forwards the presented certificate to the application in the&nbsp;X-ARR-ClientCert&nbsp;header. The platform forwards the certificate; your function code remains responsible for validating it. Validation should include the trusted issuer and chain, validity period, intended usage, revocation policy where applicable, and the application's authorization rules. Do not trust the presence of the header alone.</p>
<p>If you use exclusion paths or&nbsp;<strong>Optional Interactive User</strong>&nbsp;mode, review the TLS renegotiation behavior carefully. TLS 1.3 and HTTP/2 don't support renegotiation, and requests with bodies larger than 100 KB can fail in configurations that require renegotiation. Prefer a mode and route design that avoids renegotiation when possible.</p>
<p>For outbound mTLS, make the private certificate accessible to app code, load it from&nbsp;/var/ssl/private, and attach it to the TLS client used to call the downstream service. This is separate from enabling inbound client certificates.</p>
<h2>Operational guidance for production</h2>
<p>Treat certificates as rotating dependencies rather than static configuration:</p>
<ul>
<li>Inventory certificate purpose, owner, source, expiration, bound hostnames, and whether code access is enabled.</li>
<li>Use managed identity and Key Vault for centrally governed certificates.</li>
<li>Alert before expiration for directly uploaded certificates and rehearse renewal.</li>
<li>Monitor custom-domain DNS because managed certificate issuance and renewal depend on successful domain validation.</li>
<li>Avoid certificate or issuer pinning when using App Service Managed Certificates.</li>
<li>Test certificate rotation on all scaled instances, not only one warm worker.</li>
<li>Keep HTTPS-only enabled and require TLS 1.2 or later unless a documented compatibility requirement prevents it.</li>
<li>Use Azure Policy and deployment validation to keep transport-security settings consistent across environments.</li>
</ul>
<p>When migrating from the legacy Consumption plan, remember that&nbsp;WEBSITE_LOAD_CERTIFICATES&nbsp;isn't used in Flex Consumption. Re-add the certificates to the new app, explicitly grant code access where required, and update code that expects the Windows certificate store to load files from the Linux paths instead.</p>
