## Azure Networking Blog

### Azure Firewall explicit proxy is now generally available

- **Link**: [https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-firewall-explicit-proxy-is-now-generally-available/ba-p/4552450](https://techcommunity.microsoft.com/t5/azure-networking-blog/azure-firewall-explicit-proxy-is-now-generally-available/ba-p/4552450)
- **Published**: 2026-09-03 00:40:04
- **Fetched**: 2026-09-03 03:11:05

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><span>We are excited to announce the general availability of&nbsp;explicit proxy&nbsp;in Azure Firewall. This capability brings the familiar explicit proxy configuration model natively to Azure Firewall, enabling applications and browsers to send outbound HTTP and HTTPS traffic directly to the&nbsp;firewall&nbsp;through standard proxy settings. Customers can now gain centralized policy enforcement and visibility while reducing their dependence on self-managed forward proxy appliances.</span><span>&nbsp;</span></p>
<h3><span><span>Proxy the traffic you choose—not the entire subnet</span></span><span>&nbsp;</span></h3>
<p><span>Traditional route-based steering can require all traffic from a subnet to traverse&nbsp;a firewall.&nbsp;Explicit proxy&nbsp;offers a more targeted model: configure selected applications or browsers to use the Azure Firewall private IP and proxy port, while other traffic&nbsp;continues on&nbsp;its existing route. This application-level control can simplify migrations, reduce unnecessary routing changes, and help teams apply inspection where it matters most.</span><span>&nbsp;</span></p>
<h3><span><span>What’s</span><span>&nbsp;new for general availability</span></span><span>&nbsp;</span></h3>
<ul>
<li><strong><span>A simpler single-port experience:</span></strong><span><strong>&nbsp;</strong>Serve both HTTP and HTTPS destinations through one HTTP explicit proxy endpoint port, reducing client configuration complexity.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><strong><span>More secure PAC file access:</span></strong><span>&nbsp;Retrieve customer-owned proxy auto-configuration files from Azure Blob Storage using a managed identity. PAC files can be up to 256 KB.</span><span>&nbsp;</span></li>
</ul>
<ul>
<li><strong><span>A streamlined portal workflow:</span></strong><span>&nbsp;Enable&nbsp;Explicit proxy&nbsp;when creating a Firewall Policy, with added guidance and validation to help prevent common configuration errors.</span><span>&nbsp;</span></li>
</ul>
<h3><span><span>Built for real-world modernization</span></span><span>&nbsp;</span></h3>
<p><strong><span>Modernize legacy proxy infrastructure.</span></strong><span>&nbsp;Use Azure Firewall as the forward proxy endpoint while&nbsp;retaining&nbsp;the explicit proxy model already configured in applications and browsers. This can help organizations&nbsp;consolidate&nbsp;infrastructure and reduce operational overhead associated with self-hosted proxy appliances.</span><span>&nbsp;</span></p>
<p><strong><span>Apply selective application-level steering.</span></strong><span><strong>&nbsp;</strong>Direct only the workloads that require centralized inspection through Azure Firewall, without forcing every flow on a subnet through the same path.</span><span>&nbsp;</span></p>
<p><span><strong>Secure Azure Arc connectivity in hybrid environments</strong>.</span><span>&nbsp;Organizations using ExpressRoute or VPN can configure Azure Firewall as a forward proxy for Azure Arc-enabled servers, providing an inspected, policy-controlled outbound path to required Azure services without opening direct internet access from corporate networks.</span><span>&nbsp;</span></p>
<h3><span><span>How it works</span></span><span>&nbsp;</span></h3>
<ol>
<li><span>Enable explicit proxy in the Azure Firewall Policy and choose the HTTP proxy port used for both HTTP and HTTPS destinations.<br /><br /></span></li>
<li><span>Configure applications manually with the firewall’s private IP and proxy port or enable proxy auto-configuration.</span><span>&nbsp;<br /><br /></span></li>
<li><span>If you use a PAC file, store it in Azure Blob Storage and configure the required managed identity and access permissions.</span><span>&nbsp;<br /><br /></span></li>
<li><span>Create an application rule in the Firewall Policy to&nbsp;allow&nbsp;the intended outbound destinations.</span><span>&nbsp;<br /></span></li>
</ol>
<h3><span>Get started today</span></h3>
<p><span>Ready to simplify outbound web traffic steering? Explore the&nbsp;</span><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/firewall/explicit-proxy?tabs=portal" rel="noopener" target="_blank">Azure Firewall&nbsp;explicit proxy&nbsp;documentation</a><span>&nbsp;for prerequisites, portal and API configuration steps, PAC file guidance, and supported scenarios.</span><span>&nbsp;</span></p>
<p><span>With&nbsp;explicit proxy&nbsp;now generally available, Azure Firewall gives organizations another flexible path to modernize secure egress—combining a familiar proxy model with the simplicity, scale, and centralized management of a cloud-native service.</span><span>&nbsp;</span></p>
</details>

### Build Advanced ServiceNow Response Plans in Azure SRE Agent

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/build-advanced-servicenow-response-plans-in-azure-sre-agent/ba-p/4553059](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/build-advanced-servicenow-response-plans-in-azure-sre-agent/ba-p/4553059)
- **Published**: 2026-09-03 23:07:15
- **Fetched**: 2026-09-04 15:37:21

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>A ServiceNow connection tells Azure SRE Agent which incidents it can see. Advanced filtering narrows that further, so each response plan handles only the incidents it should.</p>
<p>Advanced filters let a plan express the rule your on-call team already follows:</p>
<blockquote>
<p>Send High-priority production network incidents owned by the Network group to our network specialist, and require approval for its proposed actions.</p>
</blockquote>
<p>The response plan defines the incident criteria, response subagent, and autonomy level. The selected subagent uses the connectors, source code, telemetry, and Azure access already configured on the agent. If you are still building that foundation, see <a href="https://techcommunity.microsoft.com/blog/appsonazureblog/what-it-takes-to-give-sre-agent-a-useful-starting-point/4500343" rel="noopener" target="_blank">What It Takes to Give SRE Agent a Useful Starting Point</a>.</p>
<h2 id="match-the-incidents-your-team-owns">Match the incidents your team owns</h2>
<p>A plan can specify one or more assignment groups. Search by display name or <code>sys_id</code>, then choose the group from the list. The plan keeps the group's stable identity, so renaming it in ServiceNow does not break the scope.</p>
<p>If you leave the plan's assignment group empty, it inherits the group selected under <a href="https://sre.azure.com/docs/tutorials/incident-platforms/setup-servicenow-indexing" rel="noopener" target="_blank"><strong>Generate insights</strong></a> when ServiceNow was connected. If no group was selected there, priority, title, and the plan's other filters define the match.</p>
<img />
<p>You can narrow the match on fields your team already uses: priority, configuration item, category and subcategory, caller/requestor, location, state, impact, urgency, and severity. Title contains and title does not contain catch patterns those fields miss.</p>
<img />
<p>For fields specific to your ServiceNow instance, add up to 20 custom incident fields whose technical names start with <code>u_</code>. Custom fields use exact equality against the stored value. Reference fields normally use the record's <code>sys_id</code>.</p>
<p>If the integration account can read ServiceNow field metadata, the form suggests friendly labels and technical names. Manual entry remains available when discovery is unavailable.</p>
<img />
<p>All populated filters use AND matching. Within a multi-select field, an incident can match any selected value. A plan for the Network group, High priority, category <code>network</code>, and <code>u_environment = production</code> runs only when all four conditions match.</p>
<h2 id="configure-the-responder">Configure the responder</h2>
<p>Each plan can use the Meta Agent, when its ServiceNow skill is enabled, or a custom agent with focused instructions, skills, tools, and hooks. Custom agents share the parent SRE Agent's identity, Azure resource scope, and RBAC permissions.</p>
<p>The built-in ServiceNow skill covers common incident actions. For more control, create a skill with your team's procedure and add search, retrieval, or other tools when the workflow needs them.</p>
<p>Then set how far the responder can go on its own:</p>
<ul>
<li><strong>Autonomous</strong> is the default. The agent investigates and acts within its configured permissions.</li>
<li><strong>Review</strong> lets the agent investigate and propose actions for approval before it changes resources.</li>
</ul>
<img />
<h2 id="preview-and-tune-the-match">Preview and tune the match</h2>
<p>Before saving or enabling a plan, preview recent ServiceNow incidents against the filter. Adjust the criteria or time range until the results reflect the incidents you intend to route.</p>
<img />
<p>&nbsp;</p>
<p><em>This example intentionally uses a filter with no recent matches.</em></p>
<p>Start a new plan in Review mode. Move to Autonomous once the team has seen the filter select the right incidents and agrees with the actions the agent proposes.</p>
<h2 id="get-started">Get started</h2>
<p><a href="https://sre.azure.com" rel="noopener" target="_blank"><strong>Create or open your Azure SRE Agent</strong></a>.</p>
<p>Open <strong>Incidents</strong>, select <strong>Triggers &amp; response plans</strong>, and turn on <strong>Advanced filters</strong>. You can then use the preview in new or existing response plans.</p>
