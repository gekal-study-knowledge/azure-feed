### Automating Private Endpoint DNS Across Azure Tenants with Azure Policy and Azure Lighthouse

- **Link**: [https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/automating-private-endpoint-dns-across-azure-tenants-with-azure/ba-p/4557495](https://techcommunity.microsoft.com/t5/azure-infrastructure-blog/automating-private-endpoint-dns-across-azure-tenants-with-azure/ba-p/4557495)
- **Published**: 2026-09-17 23:49:01
- **Fetched**: 2026-09-18 15:46:40

<details class="entry-summary">
<summary>詳細を表示</summary>
<h2>Problem statement</h2>
<p>Azure Private Endpoints let applications connect to Azure platform services through private IP addresses. They reduce public exposure, keep traffic on private networks, and support a Zero Trust architecture.</p>
<p>In a single Microsoft Entra tenant, Azure Policy can automatically associate a Private Endpoint with a centrally managed Private DNS zone. The problem becomes more complex when an organization uses several tenants:</p>
<ul>
<li>A <strong>central management tenant</strong> owns the shared Private DNS zones.</li>
<li>Separate <strong>application tenants</strong> host workloads and Private Endpoints.</li>
<li>Application teams cannot modify resources in the central networking subscription.</li>
<li>DNS records must be created and removed automatically as Private Endpoints are created and deleted.</li>
<li>Cross-tenant access must be limited, auditable, and free from long-lived shared credentials.</li>
</ul>
<p>When an application creates a Private Endpoint, Azure must create a <code>privateDnsZoneGroup</code> and register an A record in the appropriate Private DNS zone. However, the Azure Policy identity in the application tenant cannot update a DNS zone in the central tenant unless it receives explicitly delegated access.</p>
<pre><code>Application tenant                         Central management tenant
------------------                         -------------------------
Application workload
        |
Private Endpoint
        |
Azure Policy
        |
Policy managed identity
        |          Cross-tenant delegation
        +------------------------------------&gt; Central Private DNS zone
                                                  |
                                                  +-- Private A record</code></pre>
<h2>Why not use a custom synchronization service?</h2>
<p>A central pipeline or Azure Function could copy DNS records between tenants. That approach can work, but it introduces more credentials, custom code, retry and reconciliation logic, monitoring, hosting costs, and record-cleanup responsibilities.</p>
<p>An Azure-native alternative is to combine <strong>Azure Policy</strong> with a carefully scoped <strong>Azure Lighthouse</strong> delegation. Azure Policy controls the Private Endpoint DNS lifecycle, while Azure Lighthouse gives its managed identity only the access required to work with the dedicated central DNS resource group.</p>
<blockquote>
<p><strong>Note:</strong> This article describes a proposed design assembled from publicly documented Azure capabilities; it is not an official Microsoft reference architecture or a claim of production implementation. Validate it through security review, threat modeling, and a non-production proof of concept before use.</p>
</blockquote>
<h2>Azure resources used in the solution</h2>
<h3>Azure Private Endpoint</h3>
<p>A Private Endpoint is a network interface with a private IP address from a virtual network. It provides private connectivity to an Azure service such as Storage, Key Vault, or Azure SQL.</p>
<h3>Azure Private DNS Zone</h3>
<p>A Private DNS zone resolves an Azure service name to the private IP address of its Private Endpoint. Hosting these zones centrally gives the platform team consistent ownership and allows cloud and on-premises networks to use a common DNS resolution path.</p>
<h3>Private DNS zone group</h3>
<p>A <code>privateDnsZoneGroup</code> is a child resource of a Private Endpoint. It associates the endpoint with one or more Private DNS zones. Azure then creates and removes the relevant DNS records as part of the endpoint lifecycle.</p>
<h3>Azure Policy</h3>
<p>A <code>DeployIfNotExists</code> policy detects a supported Private Endpoint and deploys the required DNS zone group when it is missing. Policy parameters identify the correct central zone for each Azure service and private-link group ID.</p>
<h3>User-assigned managed identity</h3>
<p>A dedicated identity in each application tenant performs policy remediation. Unlike a stored service-principal secret, a managed identity has no credential that operators need to rotate or distribute. A user-assigned identity also has a stable principal ID and an independent lifecycle.</p>
<h3>Azure Lighthouse</h3>
<p>Azure Lighthouse provides delegated resource management across Entra tenants. In this design, an application-tenant identity receives narrowly scoped access to DNS resources in the central tenant. In Azure Lighthouse terminology, the application tenant is the managing tenant for this specific delegation, while the central tenant owns the delegated resource group.</p>
<h3>Terraform and GitHub Actions</h3>
<p>Terraform creates the Lighthouse registration definition and assignment consistently for every tenant. GitHub Actions runs validation, planning, approval, and deployment. OpenID Connect workload identity federation should be used instead of a long-lived client secret.</p>
<h2>Proposed solution</h2>
<p>The solution gives each application tenant a dedicated policy identity and delegates that identity the <strong>Private DNS Zone Contributor</strong> role over only the required central DNS scope.</p>
<pre><code>+---------------- Application tenant ----------------+
|                                                     |
|  Workload --&gt; Private Endpoint                      |
|                    |                                |
|            DeployIfNotExists Policy                 |
|                    |                                |
|          User-assigned managed identity             |
+--------------------|--------------------------------+
                     | Azure Lighthouse delegation
                     | Private DNS Zone Contributor
+--------------------v--------------------------------+
|              Central management tenant              |
|                                                     |
|  Central Private DNS zones -- DNS resolution path   |
+-----------------------------------------------------+</code></pre>
<p>The identity does not receive general access to the central networking platform. Its delegation is limited to the dedicated resource group containing the centrally managed Private DNS zones.</p>
<h2>How the solution works</h2>
<ol>
<li>An application deploys an Azure service and a Private Endpoint in its tenant.</li>
<li>Azure Policy evaluates the new Private Endpoint.</li>
<li>The policy identifies the service using properties such as <code>groupId</code> and <code>privateLinkServiceId</code>.</li>
<li>The policy uses its managed identity to deploy a Private DNS zone group.</li>
<li>The zone group references the appropriate Private DNS zone in the central tenant.</li>
<li>Azure registers the endpoint's private IP address in the central zone.</li>
<li>Cloud or on-premises clients resolve the service name through the central DNS path.</li>
<li>When the Private Endpoint is deleted, Azure removes the associated DNS record through the zone-group lifecycle.</li>
</ol>
<h2>Deployment sequence</h2>
<p>Deploying this pattern is best approached as a sequence of platform onboarding phases rather than a single infrastructure deployment. Each phase establishes a dependency required by the next.</p>
<h3>Begin with the central DNS foundation</h3>
<p>Start in the central management tenant. Create the required Private DNS zones and connect them to the approved resolution path. Depending on the wider network design, this may include virtual network links, Azure DNS Private Resolver, forwarding rules, and integration with on-premises DNS. Completing this foundation first ensures that application tenants have a valid destination for their Private Endpoint records.</p>
<h3>Prepare the application tenant identity</h3>
<p>Next, create a dedicated user-assigned managed identity in the application tenant. Record its tenant ID and principal ID because these values identify who will receive delegated access. Keeping this identity dedicated to DNS policy remediation makes its purpose, permissions, and audit trail easier to understand.</p>
<h3>Establish the Lighthouse delegation</h3>
<p>Create the Azure Lighthouse registration definition and assignment in the central tenant. Delegate only the dedicated DNS resource group using the Private DNS Zone Contributor role. Before continuing, confirm that the managing tenant, principal, role, and scope are all correct. This step must finish before Azure Policy attempts remediation; otherwise, the identity will not be able to work with the central zones.</p>
<h3>Introduce the policy automation</h3>
<p>With delegation active, deploy the relevant DNS policy definitions or initiative in the application tenant. Assign the policy to the managed identity and provide the central Private DNS zone resource IDs as parameters. For Private Endpoints that already exist, start a remediation task so that they receive the same configuration as newly created endpoints.</p>
<h3>Prove the complete lifecycle</h3>
<p>Finally, deploy a test Private Endpoint. Confirm that Azure Policy creates the Private DNS zone group, that the correct A record appears in the central zone, and that an approved workload resolves the service name to its private IP address. Delete the endpoint and verify that Azure also removes the DNS record. This final cleanup test is important: automation is only complete when it handles both creation and deletion.</p>
<h2>How to validate the solution</h2>
<p>A successful deployment does not prove that name resolution and application connectivity work. Validation should cover three layers.</p>
<h3>1. Control-plane validation</h3>
<ul>
<li>The Lighthouse registration definition exists.</li>
<li>The registration assignment references the correct definition.</li>
<li>The managing tenant, principal ID, role, and scope are correct.</li>
<li>The policy assignment uses the intended managed identity.</li>
<li>The policy parameters contain the correct central zone resource IDs.</li>
</ul>
<h3>2. Resource validation</h3>
<ul>
<li>The test Private Endpoint exists.</li>
<li>The policy reports compliance or completes remediation successfully.</li>
<li>A Private DNS zone group exists below the endpoint.</li>
<li>The zone group references the intended central zone.</li>
<li>The expected A record exists and matches the endpoint's private IP address.</li>
</ul>
<h3>3. Resolution and lifecycle validation</h3>
<p>From an approved application network, resolve the service name and confirm that it returns a private IP address:</p>
<pre><code>Resolve-DnsName myservice.blob.core.windows.net</code></pre>
<p>Test application connectivity over the private path. Then delete the test Private Endpoint and confirm that the corresponding record is removed from the central zone.</p>
<h2>Security considerations</h2>
<ul>
<li>Use a dedicated identity for DNS policy remediation.</li>
<li>Scope the Lighthouse delegation to only the dedicated DNS resource group.</li>
<li>Separate deployment identities from runtime identities.</li>
<li>Use workload identity federation instead of stored secrets.</li>
<li>Require approval before applying delegation changes.</li>
<li>Protect tenant configuration and Terraform state.</li>
<li>Monitor Lighthouse registration assignments, policy remediation, and DNS changes.</li>
<li>Test both DNS record creation and deletion.</li>
<li>Review every new Private Link service before enabling its policy.</li>
</ul>
<h2>Benefits and trade-offs</h2>
<p>This pattern can provide central DNS governance, automatic registration and cleanup, repeatable tenant onboarding, reduced custom code, and narrowly scoped cross-tenant access. Azure Lighthouse itself does not add a service charge.</p>
<p>The design also has trade-offs. Each application tenant requires an explicit delegation, and the central platform must govern identities originating in multiple tenants. Azure Lighthouse primarily delegates Azure control-plane access; it does not solve every data-plane authorization requirement. Policy definitions must also be maintained as new Private Link services are introduced.</p>
<h2>When to use this pattern</h2>
<p>Consider this architecture when workloads span multiple Entra tenants, Private DNS zones must remain centrally owned, application teams should not receive broad central-network access, and the organization prefers an Azure-native lifecycle over custom synchronization code.</p>
<p>A simpler design may be more suitable when all resources are in one tenant, only a few endpoints exist, or organizational policy does not permit cross-tenant delegated identities.</p>
<h2>Conclusion</h2>
<p>Cross-tenant Private Endpoint DNS is more than a DNS challenge. It combines networking, identity, governance, automation, and resource lifecycle management.</p>
<p>Azure Policy and Azure Lighthouse provide a promising Azure-native pattern: policy manages the endpoint-to-zone association, Azure manages the DNS record lifecycle, and Lighthouse supplies only the cross-tenant permission required for the operation.</p>
<blockquote>
<p>Grant the smallest required DNS scope, automate the complete lifecycle, and validate the result from policy evaluation through application connectivity.</p>
</blockquote>

### Enable Dynamic Workflows in Azure Functions hosted skills

- **Link**: [https://techcommunity.microsoft.com/t5/apps-on-azure-blog/enable-dynamic-workflows-in-azure-functions-hosted-skills/ba-p/4551993](https://techcommunity.microsoft.com/t5/apps-on-azure-blog/enable-dynamic-workflows-in-azure-functions-hosted-skills/ba-p/4551993)
- **Published**: 2026-09-17 21:00:00
- **Fetched**: 2026-09-18 10:48:16

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Azure Functions already gives you a familiar way to build event-driven apps. A queue message, HTTP request, timer, or event triggers the code that handles the work.</p>
<p><a class="lia-external-url" href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-hosted-skills" rel="noopener" target="_blank">Azure Functions hosted skills</a> (formerly Serverless Agents) add AI reasoning to that model. A hosted skill can read a request, use the regular tools you give it to inspect context, and choose the next step, while your triggers, tools, and business logic stay in place.</p>
<h1>When the work needs to keep going</h1>
<p>Consider an insurance policy servicing request. A hosted skill can use its regular tools to understand the requested change, look up the policy, and inspect the submitted documents. If the information is ready and the request can finish now, the normal tool loop, where the model calls a tool, reads the result, and decides the next step, is a good fit.</p>
<p>That changes when the work must continue after the initial request. An insurance policy servicing request may need to inspect several documents in parallel, wait for a configured delay before checking again for missing information, and build a review packet after the checks it depends on complete. In a normal tool loop, each result returns to the model before the skill can decide what happens next. The application must keep the job alive, save its progress, and deliver the final result.</p>
<p>At that point, the work needs to keep running independently of the original interaction instead of relying on the model and application to coordinate every step. For a queue or other non-HTTP trigger, the final result also needs to be written or sent somewhere useful because there is no response channel.</p>
<p><span style="color: rgb(30, 30, 30); font-size: 34px;">Introducing Dynamic Workflows</span></p>
<p><a href="https://learn.microsoft.com/en-us/azure/azure-functions/functions-hosted-skills-dynamic-workflows" rel="noopener" target="_blank">Dynamic Workflows</a> is a Durable Functions-backed way to run a hosted skill's multi-step plan outside the original request. It separates planning from execution. At run time, the AI model generates a structured plan from the workflow-safe tools and subagents you explicitly allow. The hosted skill calls start_workflow with that plan. The runtime validates it, starts a Durable Functions orchestration, and runs each task when its dependencies are ready.</p>
<p>That separation addresses the limits of the normal tool loop: the workflow store keeps state and intermediate results out of the model's context, independent checks can run in parallel, and durable timers resume waits without holding a worker open. Because a Durable Functions orchestration handles execution, the work can continue after the original request or a Functions worker restart.</p>
<p>To test the difference, we ran the same structured multi-step task with the regular tool loop and with Dynamic Workflows, using a Foundry gpt-5.4-mini deployment. We ran it with inputs for one service and then ten services. In the Dynamic Workflows version, the model made the plan once, while the runtime kept intermediate tool results in the workflow store instead of sending them back to the model after every tool call. Dynamic Workflows used 56% fewer total model tokens for the one-service run and 93% fewer for the ten-service run, while producing the same final reports. Results will vary by workload and model, and small jobs can have planning overhead. The savings are largest when intermediate tool results would otherwise return to the model after every tool call.</p>
<h1>How it works</h1>
<p>Enable workflows in the hosted skill's Markdown front matter. The runtime then adds the management tools: <em>start_workflow,</em> <em>get_workflow_status</em>, <em>list_workflows</em>, <em>cancel_workflow,</em> and <em>terminate_workflow.</em> You do not implement those tools. You choose the workflow-safe tools and subagents that a plan can use.</p>
<p>At run time, the AI model uses the hosted skill's instructions to generate a structured plan, limited to the workflow-safe tools and subagents you explicitly allow. The hosted skill calls start_workflow with that plan; the runtime validates it, starts a Durable Functions orchestration, and returns a workflow ID right away.</p>
---
name: Add Driver Review
description: Prepares an add-driver document review for an insurance representative.
workflows:
  enabled: true
trigger:
  type: queue_trigger
  args:
    queue_name: policy-service-requests
    connection: AzureWebJobsStorage
---
<p>Put workflow-safe handlers under tools/ and decorate them for use in a workflow. Each handler must run synchronously, accept one dict argument, return JSON-serializable data, and be idempotent. A worker failure can cause a handler to run more than once, which is why that last point matters. Ordinary tools retain their existing behavior unless you explicitly make them available to a workflow.</p>
<a class="lia-mention lia-mention-user" href="">workflow</a>_tool(
    description=(
        "Inspect one document from an add-driver request. Args: "
        "{document: &lt;document&gt;, position: int}. Returns the document and evidence state."
    )
)
def inspect_driver_document(args: dict[str, Any]) -&gt; dict[str, Any]:
    document = args["document"]
    evidence_state = {
        "received": "present",
        "missing": "missing",
        "expired": "needs_current_copy",
    }[document["status"]]

    return {
        "position": args["position"],
        "document_id": document["document_id"],
        "type": document["type"],
        "file_name": document["file_name"],
        "evidence_state": evidence_state,
    }
<p>Dynamic Workflows runs on Durable Functions. You can configure Durable Task Scheduler in host.json and use its dashboard to see per-instance task state, retry history, and controls for work that is still running. Durable timers let a workflow wait without keeping a worker busy, then resume the steps that are ready. The workflow stays visible and durable instead of depending on an open request or a best-effort background task.</p>
