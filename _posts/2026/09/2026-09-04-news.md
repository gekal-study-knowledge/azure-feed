### Your Private Endpoint Does Not Cover Agent Egress: Locking Down Azure AI Foundry in Both Directions

- **Link**: [https://techcommunity.microsoft.com/t5/azure-architecture-blog/your-private-endpoint-does-not-cover-agent-egress-locking-down/ba-p/4547864](https://techcommunity.microsoft.com/t5/azure-architecture-blog/your-private-endpoint-does-not-cover-agent-egress-locking-down/ba-p/4547864)
- **Published**: 2026-09-04 23:59:04
- **Fetched**: 2026-09-05 00:15:41

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>I got asked a question a few weeks ago that sounded simple. Lock down Azure AI Foundry with Private Link, and let the agents call an MCP server hosted on a VM in a different virtual network. Everything private, nothing over the public internet, and proof rather than a diagram.</p>
<p>I said yes, that is straightforward. I was wrong about the second half.</p>
<p>What follows is what I actually built, what broke along the way, and the one thing that cost me most of an afternoon. Everything here was deployed and verified on a live subscription. The scripts and the raw logs are on GitHub if you want to reproduce it:</p>

<h2>The mistake almost everyone makes</h2>
<p>Here is the thing I want you to take away, even if you read nothing else.</p>
<p>A private endpoint on your Foundry resource secures traffic going <strong>into</strong> Foundry. It does absolutely nothing about the traffic your agents send <strong>out</strong>.</p>
<p>Those are two different features, configured in two completely different ways, with two completely different sets of failure modes. If you configure the private endpoint, disable public network access, see your test call succeed from inside the VNet, and call it done, you have secured exactly half of the problem. Your agent can still be reaching out to a tool endpoint from a Microsoft owned public IP address, and nothing in the portal will tell you that.</p>
<div class="styles_lia-table-wrapper__h6Xo9 styles_table-responsive__MW0lN"><table border="1" style="border-width: 1px;"><thead><tr><th>&nbsp;</th><th>Direction</th><th>Mechanism</th></tr></thead><tbody><tr><td>Inbound</td><td>client to Foundry</td><td>Private <strong>endpoint</strong></td></tr><tr><td>Outbound</td><td>Foundry agent to your API</td><td>Network <strong>injection</strong></td></tr></tbody><colgroup><col style="width: 33.33%;" /><col style="width: 33.33%;" /><col style="width: 33.33%;" /></colgroup></table></div>
<p>I built and proved both. Let me take them in order.</p>
<div class="placeholder"><img />Inbound vs Outbound traffic via Private Link.</div>
<h2>Part one: the inbound half</h2>
<p>This part is well documented and mostly behaves. The shape of it:</p>
<ul>
<li>A VNet with a subnet for private endpoints, with <code>private-endpoint-network-policies</code> disabled, which is mandatory and easy to forget</li>
<li>A Foundry account created with a <strong>custom domain</strong>, which is required for Private Link to work at all</li>
<li>Private DNS zones, and here is the first trap</li>
<li>A private endpoint with a DNS zone group</li>
<li><code>publicNetworkAccess</code> set to <code>Disabled</code></li>
</ul>
<p>The DNS trap is that you need <strong>three</strong> zones, not one:</p>
<pre><code>privatelink.openai.azure.com
privatelink.services.ai.azure.com
privatelink.cognitiveservices.azure.com</code></pre>
<p>The Foundry endpoint answers on several FQDNs, and if you only create the zone matching the hostname you happen to be testing with, the others silently resolve to the public IP. Traffic still works, which is exactly what makes it dangerous. It looks fine.</p>
<p>All three zones have to be linked to the VNet, and the DNS zone group on the private endpoint is what actually writes the A records. Miss the zone group and you get zones with nothing in them.</p>
<h3>Proving it, properly</h3>
<p>This is where I want to push back on how these setups usually get validated. People run one test, from inside the VNet, see a 200, and declare victory.</p>
<p>That proves nothing on its own.</p>
<p>A 200 from inside the VNet is perfectly compatible with a resource whose public endpoint is also wide open. You need both halves:</p>
<pre><code>from inside the VNet   -&gt;  DNS resolves to 10.0.1.5, call returns HTTP 200
from my laptop         -&gt;  HTTP 403, "Public access is disabled"</code></pre>
<p>Only when both are true have you proven anything. I wrote a small script that runs both and prints a single verdict, because I know that if it is two commands, one of them eventually gets skipped.</p>
<div class="placeholder"><img />iTerm TEST proving the inbound and outbound traffic.</div>
<p>A couple of things bit me here that are worth knowing.</p>
<p>The tenant had key based authentication disabled by policy. Every <code>api-key</code> call returned <code>403 AuthenticationTypeDisabled</code>, and attempts to set <code>disableLocalAuth</code> back to false silently reverted. Not a problem, Entra ID tokens are the better practice anyway, but if you are following an older tutorial with <code>api-key</code> headers you will lose time wondering why your key is rejected. Inside the VM I used the managed identity via IMDS, so there were no secrets to copy around at all.</p>
<p>The subscription also blocked public IP creation, which meant Azure Bastion could not be deployed. That turned out not to matter. <code>az vm run-command invoke</code> runs scripts inside a VM over the Azure control plane, no SSH, no public IP, no Bastion required. I now prefer it for this kind of testing.</p>
<h2>Part two: the outbound half, where it got interesting</h2>
<p>Now the actual request. The agent needs to call an MCP server on a VM in a separate VNet, and I need to prove the call arrives from a private address.</p>
<p>The mechanism is <strong>network injection</strong>, officially "Standard Setup with Bring Your Own Virtual Network". You give Foundry a delegated subnet in your VNet, and the agent runtime gets network interfaces in it, so its outbound calls originate from your address space.</p>
<p>Three requirements caught me out before I wrote a single line.</p>
<p><strong>The delegation is <code>Microsoft.App/environments</code>.</strong> Not <code>Microsoft.CognitiveServices</code>, which is what I assumed. Agent compute runs on Azure Container Apps under the hood, which is why the delegation belongs to the <code>Microsoft.App</code> namespace. You also have to register both <code>Microsoft.App</code> and <code>Microsoft.ContainerService</code> as resource providers. Skip that and ARM happily accepts your account, then puts it in <code>provisioningState: Failed</code> several minutes later.</p>
<p><strong>Network injection is creation time only.</strong> You cannot add it to an existing Foundry account. I had a perfectly good account from part one and it was useless for this. Plan for a rebuild, or better, make the decision before you deploy anything.</p>
<p><strong>Private networking forces Standard Setup</strong>, which means bring your own Storage, Cosmos DB and AI Search. These are not optional extras you can add later for convenience. The capability host will not provision without all three. That is real money, AI Search Basic alone is around 75 dollars a month, so budget for it and remember to tear it down.</p>
<p>For the proof I wrote a deliberately dumb mock MCP server. About sixty lines of Node.js, JSON-RPC on port 8080, no authentication, running as a systemd unit. Its only real job is forensic: log <code>req.socket.remoteAddress</code> for every single caller to a file.</p>
<pre><code>const ip = (req.socket.remoteAddress || '').replace(/^::ffff:/, '');
log(`CALLER=${ip}  ${req.method} ${req.url}  ua="${req.headers['user-agent']}"`);</code></pre>
<p>That log file is the entire experiment. Everything else is scaffolding.</p>

<h2>The thing that cost me the afternoon</h2>
<p>I built everything. Subnet delegated correctly, verified. Providers registered, verified. Account created with <code>networkInjections.scenario = "agent"</code>, and I could read the property straight back off the resource to confirm it. Peering connected in both directions. The MCP server responding happily to curl from a VM in the other VNet, logging the caller as <code>10.0.2.4</code>, so cross-VNet private routing was definitely working.</p>
<p>Then I ran the agent and got this:</p>
<pre><code>BadRequestError: Error code: 400 - {'error': {'message': 'Server returned 424: None',
'type': 'external_connector_error', 'param': 'tools', 'code': 'http_error'}}</code></pre>
<p>And the MCP server log showed nothing at all. Not a failed connection, not a rejected handshake. Zero packets.</p>
<p>That "424" tells you almost nothing. My first instinct was networking, because that is what the error smells like, and because I had just spent an hour on networking. I checked the NSG. I went back over the peering. I confirmed the delegation again. All fine.</p>
<p>The actual answer is that <strong>there are two capability hosts</strong>, and I had only one.</p>
<p>The <strong>account level</strong> capability host is created implicitly for you when you set <code>networkInjections</code>. You will see it exist, it will say <code>Succeeded</code>, and it looks like the job is done.</p>
<p>The <strong>project level</strong> capability host has to be created explicitly, along with connections to your three BYO resources. Until that exists, the agent runtime has nowhere to run. Every tool call fails with that opaque 424, and because the runtime never starts, your tool endpoint never sees a packet, which sends you looking at the network instead of at the thing that is actually missing.</p>
<p>I also had to grant the project's managed identity data plane roles on Storage, Cosmos and Search, or the capability host provisioning itself fails.</p>
<p>Worth noting: the documentation says to expect 30 to 35 minutes for this on a network injected account. Mine completed in about four. Do not cancel it either way, but do not block your afternoon on the higher number.</p>
<div class="placeholder"><img />Account vs Project level - Microsoft Foundry capabilities host.</div>
<h2>The proof</h2>
<p>With the project capability host in place, I ran it again. The agent's response:</p>
<blockquote>The MCP server reports that your request arrived from source IP <strong>10.0.4.119</strong>.</blockquote>
<p>And from the MCP server's own access log:</p>
<pre><code>2026-08-17T15:07:02.378Z  CALLER=10.0.4.119  POST /  ua="AzureAIFoundryAgentRuntime/231188750"
   {"method":"initialize","params":{"protocolVersion":"2025-11-25",...}}
2026-08-17T15:07:02.508Z  CALLER=10.0.4.119  POST /  ua="AzureAIFoundryAgentRuntime/231188750"
   {"method":"tools/list","params":{},"id":2,"jsonrpc":"2.0"}
2026-08-17T15:07:03.829Z  CALLER=10.0.4.119  POST /  ua="AzureAIFoundryAgentRuntime/231188750"
   {"method":"tools/call","params":{"name":"whoami","arguments":{}},"id":2,"jsonrpc":"2.0"}</code></pre>
<p><code>10.0.4.119</code> is an address from the delegated agent subnet, <code>10.0.4.0/24</code>. The user agent is the Foundry agent runtime identifying itself. The full MCP handshake is there, initialize, then tools/list, then tools/call.</p>
<p>That is the whole point of the exercise, in one line of a log file. The agent reached a server in a different virtual network, over peering, from a private IP address, and I can show you the packet arriving rather than asking you to trust an architecture diagram.</p>

<h2>Smaller things that wasted my time</h2>
<p>In case you hit the same walls:</p>
<ul>
<li><code>az vm create</code> would not resolve my subnet. By name it tried to create a new one at <code>10.0.0.0/24</code>, which was not what I asked for at all, and by full resource ID it insisted the subnet did not exist. I gave up and created the NIC explicitly with <code>az network nic create</code>, then attached it with <code>--nics</code>. Worked immediately.</li>
<li><code>az cosmosdb create</code> has no <code>-l/--location</code>. It wants <code>--locations regionName=... failoverPriority=0</code>.</li>
<li><code>az vm run-command</code> executes under <code>/bin/sh</code>, not bash. My script started with <code>set -euo pipefail</code> and died on line one with "Illegal option -o pipefail".</li>
<li><code>azure-ai-projects</code> 2.x changed shape. <code>list_agents</code> is gone. I used <code>client.get_openai_client()</code> and the Responses API with a native <code>mcp</code> tool type instead, which worked cleanly. It also needs <code>httpx</code> installed and does not pull it in.</li>
<li>Role names differ per tenant. "Azure AI User" did not exist in mine. "Azure AI Developer" and "Azure AI Administrator" did.</li>
<li>And an early self inflicted one, I put <code>set -euo pipefail</code> in a variables file that was meant to be <strong>sourced</strong>. That applies the flags to your interactive shell, so the first command returning non-zero closes your terminal window. If a file is designed to be sourced, leave strict mode out of it.</li>
</ul>
<h2>If your DNS lives on premises</h2>
<p>This came up straight after, so it is worth including.</p>
<p>Azure Private DNS zones are not reachable from on premises. <code>168.63.129.16</code> is a VNet internal address and is not routable over VPN or ExpressRoute, so your own DNS server cannot query the zone directly.</p>
<p>Deploy an <strong>Azure DNS Private Resolver</strong> with an inbound endpoint in the VNet, then conditional forward from the on premises resolver to that private IP. Forward <strong>only</strong> the <code>privatelink.*</code> zones. Do not forward <code>openai.azure.com</code> wholesale, because the public lookup returns the CNAME that the whole chain depends on, and taking that over breaks other Azure endpoints.</p>
<h2>What I would tell the next person</h2>
<ul>
<li>Test both directions, and test the negative case. A 200 from inside proves nothing on its own.</li>
<li>Decide on network injection before you create the account, because you cannot add it later.</li>
<li>If you get a <code>424 external_connector_error</code> and your endpoint logs are empty, stop looking at the network. Check whether the project level capability host exists.</li>
<li>Budget for Cosmos and AI Search from the start, they are mandatory, not optional.</li>
<li>Prove it with a log from the destination. A source IP in an access log is evidence. A diagram is a claim.</li>
</ul>
